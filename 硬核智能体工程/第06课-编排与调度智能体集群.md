## 2. 课程全景回顾（Greg 快速串起 Session 1–5 → 6）

Greg 用一张「我们走了多远」的图把六课串起来（也帮迟到的同学对齐）：

1. **Session 1**：模型 loop 会**非确定性地停**（当推理引擎决定不再调工具）。于是加**前置编译的 check**，让一个**确定性进程**去评估，逼 loop 继续跑（而不是「Ralph Wiggum 式」的「就跑 20 次」）。此外，「goal」≠「spec」——goal 绑定到 harness 的**执行状态**，是持久的。
2. **Session 2**：管理多个模型时要**捕获规范化（normalized）的日志流**，才能处理失败模式与需要你介入的场景（Claude Code 和 Codex 存日志的方式不同）。
3. **Session 3**：失败总会发生——最简短的一节讲了 **containment**；怎么**从日志状态 resume**；引入 **tool catalog + policies**；以及**交互模式**（幂等：别自动 resume 又把付款打一遍）。
4. **Session 4**：全讲 **check**——什么是好 check、什么是坏 check；**mutation testing**（让 check 先失败）。
5. **Session 5（上周）**：**从 traces 里复合与改进**——把 session 证据反馈回 harness 源码、修改它，防止失败/边缘情况咬你；对比了 DeepSeek/Prime 等新 harness 怎么「用不同方式吸收 trace 数据」。
6. **Session 6（今晚）**：**并行/编排**——所有 seam 在哪。

## 5. 关键洞察：Codex 的 app server

- OpenAI Codex **暴露了一个 app server**，让你能**通过其它客户端与 Codex 交互**；这个 app server **内嵌在 Codex CLI 代码里**。
- 这是一个很好的**关注点分离（separation of concerns）**——**Claude Code 没有做这个**。
- 当然你可以用 `-p` 之类的 flag（非交互模式）驱动 Claude Code/Codex，但 app server 让你能把「**底层进程的两个状态**」分开。
- 这为什么重要：**实时 steering**。在 Dead Reckon 里，如果 spawn `codex exec -p`，你**在它完成之前无法与它交互**；只有 app server 这种方式能让你跟**真正底层的进程**交互，从而**在 run 中途实时纠偏**，而不是等 job 完成。
- 结论：这是 Greg 倾向用模型实验室 harness 的又一原因——它们在能力上**领先半步**。

## 6. 本课核心：并行/编排的动机与成本

### 6.1 现实类比：管理一群人
- 假设你在管理多人：**用一个非常聪明的人串行做** vs **扇出给很多没那么聪明的人并行做**——后者可能得到**次优结果**，还有**协调成本**（进程间通信的额外开销）。
- 这个类比对应的就是「更强的推理模型」vs「一堆更弱的模型」。

### 6.2 触发 Greg 做 Dead Reckon 的原始痛点
- 他**总是用同一个模型实现（比如 Claude Code），再用 Codex 从 commit 快照做一次检查**。
- 结果：**「我得照看这个 Claude Code 会话、等它干完；我知道它总会偷懒——stub 掉东西、加注释说『我回头再弄』其实没弄。」** 他不想每次都这么 babysit。
- 于是想：**harness 能不能自己管理多个子进程**——甚至跑 **DAG（directed acyclic graph，有向无环图）** 式的工作流，混搭不同模型。

### 6.3 何时 handoff 才有意义？
- 单个 worker run 被前置 check 管住，就能跑很久而不需要过早结束——所以**并行/交接只在特定场景才值得**。

## 7. 三种（四种）组合规则

Greg 给出编排工作的四种「composition rule」（他说其实是三种 + 合并冲突）：

### 7.1 Synthesis（合成 / 扇出汇总）
- 你平时就在做：研究一个代码库 + 研究公开网络，**扇出一堆子 agent（各有角色）→ 汇总成一个结论**。
- **在代码里的问题**：并行性——一个 job worker 可能先于另一个返回；它可能**改了另一个 worker 依赖的代码**，于是你要处理**合并冲突**（代码 ≠ 原始信息）。

### 7.2 Union（联合 / 跨子系统并行）
- 在一个**定义良好、你充分理解**的代码库上，把工作**按有边界的子系统并行**（如 API / UI / tests），再**几乎机械地合并**。
- 这就像团队里「前端/后端并行做、再找小的 seam」，但**不是同时改所有文件**。

### 7.3 Ordered integration（顺序执行 / 排序）
- 把工作分解成步骤（像老 Microsoft Project 的 **work breakdown structure**），定义**执行顺序与依赖**。
- 需要**前置规划能力**（Dead Reckon 里叫 **job planner**）。
- 缺点：**串行 = 等得更久**。（但你可以让某个子节点内部做 synthesis 扇出——Greg 自己没走那条路，因为更复杂。）

### 7.4 Merge conflicts（合并冲突）
- 当你走开、遇到合并冲突怎么办？
  - **semantic repair（语义修复）**：让 harness 理解意图、执行顺序、留出余地，用模型自己修；
  - **refuse to repair（拒绝修复）**：超级保守，让人介入。
- 无论哪种，都意味着**又一个进程要设计**。

> Greg 的总结：**「在 agentic CLI 之上再加 harness 做并行，复杂度陡增。若要延伸本课，ordered execution 是迄今为止最容易推理的——但它仍有挑战：步骤间需要连续性，且你可能没在 job graph 里预先规划正确，就得考虑 retries。」**

## 8. 外部证据 1：Nature 论文（顺序 vs 并行）

- 一篇 Nature 论文在问的正是：**对一个任务序列，顺序执行还是并行执行？** 什么任务该并行，收益/损失在哪？
- 发现：
  1. **不必要的分解（unnecessary decomposition）** 会为「没有很多执行步骤的任务」产生**大量协调消息（coordination messages）**，白白烧 token。
  2. 但**只要有一个好的分解方式**，结果就**大幅提升**——评估任务的均分从 **0.349（单 agent）→ 0.631**，约 **+80%**。
  3. 反过来，**当任务不需要额外推理、还叠加了协调税（coordination tax）**，多 agent 执行会**显著降级**。
- 结论：**「除非有很好的理由，否则并行化的成本往往超过收益。」** 要的是 **fit for purpose（为目而配）**。
- Greg 的共鸣：「连我本人也总想『把这个并行掉』、想走开，但这个数据证明了——你得有理由，通常不值那些 token。」

## 9. 外部证据 2：work trees（探索解空间）

- 另一项很新的研究，**大量镜像了 Dead Reckon 已有的做法**：造一个 eval set + 示例代码，**扇出多个 work tree（工作树）去探索解空间，但不一定 join 结果**。
- 适用场景：**你不知道某个 API/设计的最优形态**——不是让多个 worker 做同一个结果，而是**评估很多个不同的候选，挑最好的合并进 main**。
- 异步并行执行跑在**隔离容器**里，形成 work tree。
- Greg 的实战案例（**OLCP，Online Context Processing**）：
  - 背景：想把 Spec Story 的历史痕迹存成结构化 DB，解决「怎么在正确时间注入正确上下文」这个**检索问题（precision/recall）**。
  - 做法：造一个 **golden dataset**，benchmark 各种算法（有些连他都不确定），**扇出一堆 work tree（每个只改算法的一个地方）**，然后**把真正提升 recall/precision 的候选 promote 给他**。
  - 要点：**你得有一个 metric-driven 的结果可以验证**；否则（比如设计一堆前端 mock、想看不同视觉设计）很难复用。

## 10. 模型路由（Model Routing）

- 新闻：**Stripe 以 $80 亿收购了 OpenRouter**。
- 最基础的路由（约一年前出现）：**ChatGPT 的 auto mode**——一个小 classifier 决定「发到哪个版本的 ChatGPT、用多少 thinking effort」。它当时被骂「帮 OpenAI 省 token」，但其实**对很多消费者是好事**（问个基础问题干嘛等很久）。
- **Cursor** 的 auto mode 同理，但按量计费（订阅会被耗尽）。
- **OpenRouter**：一个统一 API endpoint，把 token 都路由过去；好处是**某个 API 挂了有规则路由到备选**，服务不完全降级。
- 研究前沿：**传统 LM router** = 一个 classifier 决定「这个任务用便宜/弱的还是强的 LLM」。新研究更进一步：**先用便宜模型做一点 search/discovery「预启动」任务，再回头决定是否该用更聪明的模型**。
- 意义：上游那个「很小的二分类」如果错了，就会影响用户体验——所以「先探后定」很有意思。

## 11. Codex subagents 与 Claude Code workflows

### 11.1 Codex 的 subagents（开源，能看到它怎么想并行）
- 有 root thread（主对话）+ 一堆 child threads（subagents）。
- 它把 child threads **注入回主线程做 synthesis 再继续**——**不改工作树的不同部分**，subagent 只返回合成结果给主编排器。
- 好处：**消除了大量复杂度**；代价：**不能选不同模型、几乎没有任何 determinism**（很难精确告诉 Codex 你想让 subagent 干什么）。

### 11.2 Claude Code workflows（Greg 的最爱）
- 这是本课反复强调的「**给非确定性系统加确定性**」最落地的载体。
- Greg 现在**每个 job execution 都流经一个有明确形状的确定性 workflow**，他能确保它永远发生。
- 效果：过去 12 天里，不仅能看所有代码，还能看**每个 workflow 的阶段步骤映射回一个巨大 backlog**，精确理解发生了什么，并**把它当模板复用**。

## 12. 现场：Torty 的确定性工作流 + 循环工程（Himanshu 提问）

Himanshu 问「怎么构造那种确定性、保证每次结果形状一致」。Greg 掏出 Torty 这个真实项目讲透了他的「小软件工厂」。

### 12.1 动机（10 天前开始）
- 烦两件事：① VS Code/Cursor 里管理一堆 shell 太累；② **关掉 Cursor 会杀掉所有 session**（因为终端由它管）。
- 于是想建一个 **durable sessions 一等公民** 的编辑器 → **Torty**。

### 12.2 技术选型
- **Electron**（稳健生态、本质是 web app）→ 能被 **Chrome DevTools** 驱动，做自动化测试。
- **tmux**：所有 session 其实跑在 tmux 里（视图与后端数据分离），关掉窗口也不丢；你**不需要懂 tmux**。
- **SSH**：管理远程机器（他的 Mac Pro）。
- 对比 **Zed**（Ram 提）：Zed 也有 ACP + terminal 双线程、重开即恢复；Greg 也认识 Zed 团队，但 Torty 把 session 放进 tmux、不是靠窗口管理器，还内置了更多保证。

### 12.3 「循环工程（loop engineering）」
- **Claude Code + Ultra Code Mode + workflows**：Ultra Code Mode **强制 Claude 优先用 workflow**（不用每次说 `/workflow`）。
- **/loop = cron job**：武装 loop → backlog 里排队 → 它会**按项目约定**生成一个新 phase 的 workflow（spec → build → test → 更新 backlog → 下一个）。
- **单文件 backlog**（immutable log）：只往末尾 append；新 phase **tail 读末尾**看哪些没完成；整个产品的开发史都在一个文件里。**为什么不拆多文件？** ① 省心；② 模型好读——「一个 ground truth 文件」优于管理 Linear/GitHub issues 一堆对象。
- **phase 命名**：`phase 100`、`phase 101`…每个 commit 对应一个 phase，容易追踪。
- **workflow 缓存**：杀掉 workflow 后能 `continue` 从缓存接着跑（比如 phase 3/4 继续）。
- **commit 不停**：loop 整夜跑，每小时都在 commit。
- **grooming**：只把「真的想 ship 的东西」排进队列；research 和 implementation 用不同措辞；可以**重排 phase**（把需要人在场的远程任务推到后面）。

### 12.4 确定性的来源（三件套）
1. **项目专属 CLAUDE.md**：每个 phase 必须遵守的**不变量（invariants）** + 每种 workflow 的**验证方法**（取决于它碰了项目的哪部分）。
2. **外部 harness 驱动 app**：用 Chrome DevTools 真的去**修改、点击、测试** UI。
3. **分阶段 workflow 的确定性形状**：spec → implement → verify →（needs work 则自 kick 一个 loop 回来）。

## 13. 现场：Dead Reckon 的 job graph 演示 + Julian 的前置条件之问

### 13.1 演示（半翻车但讲清了）
- 想让 Dead Reckon 做一次**full orchestration**（上次 Twitter clone 只做了 single run，没看到 job graph）。

### 13.2 Julian 的问题：构造依赖图时会设前置条件吗？
- Greg 解释「形状判定」的机制（**类似第 10 节的路由器**）：
  - 写 goal 时，有个步骤会用**额外的 LLM 做一点 search/discovery**，再决定「该是什么形状」——这实际上**开始构建 job graph 的开头**。
  - 你选 **orchestrate / review mode / single run**，会给 plan 加额外东西；plan mode 被映射到 Dead Reckon 支持的执行形状。
  - 形状只有三种：**single run / 全编排（顺序或并行）/ review mode（一个模型实现 + 另一个模型 review + retry）**。
- Greg 的诚实：**他并不总信任 classifier 会选对，有时会否决它**。

### 13.3 Greg 对并行的「白鲸」坦白
- 他自己**大多只用 single run 或 phased execution**。
- 因为**「每当我在做并行，它就以各种非确定性方式坏掉」**——这违背了「想走开」的初衷。
- 解决并行合并，仍是他的 **white whale**。
- 结构上：他给 Dead Reckon 加了一个 **job supervisor 进程**，专门追踪并行/多节点 run 的 scope、state、retry attempts、final evidence——**单 run 不需要，但并行必须有**。

## 14. Dead Reckon 与 Spec Story 的关系（Julian 问）

- 起源：完成一次**七个月**的产品发布后，Greg 开始认真做 Dead Reckon。
- 动机：**受够了 babysit 一堆 agent session**——尤其 Opus 5 这种「用你听不懂的新语言说话」的模型，读几亿行输出极其痛苦。
- 过程：用 **Spec Story** 翻出那次构建的 **1300–1400 个 session log**，汇编成 **《25 Patterns in Agentic Engineering》** 这本书——把「我潜意识/隐性在做的事」固化成证据。
- 两个典型 pattern：
  1. **一个 worker 攒一堆 phase commit → 换 Codex 做 code review 再 push**；
  2. **「docs / API between turns」**（在 turn 之间用文档跟踪状态，且文档会老化）。
- Dead Reckon 里没细讲但很重要的一点：**run 结束后它会「叙述（narrate）」自己做了什么，还生成一张 mini 架构图**——这正是 Greg 以前手动给自己做的。
- **provider 日志规范化** 的能力，是从「研究各家异构 provider 的日志」继承来的；Dead Reckon 也复用了 Spec Story 的部分源码，避免从零重造。

## 15. 学员项目：Jack 的 scope lab

- Jack 用 prove-it harness 做了一个 **scope lab**：一个「**最终权威内核（final authority kernel）**」——**不管用什么模型/harness，都要控制「哪些文档能被更新、用于什么目的」**。
- 目标：扇出多个 agent 去**自主推进想法**（出最简原型、mock UI），他再判断值不值得深入。
- 已验证的能力：**「这个没改那个文件、这个改了那个文件、不允许」**——越界就被踢出、标记为 failure。
- 遇到的坑：想让某个改动发生时（比如把 **Calvin & Hobbes** 作为「哲学/记忆碎片」注入），**模型把自己搞混了，没正确执行**（他还在查日志）。
- 反馈：**这个课程「极其验证」了他的方向**（有界执行、沙盒、证明它做了什么）。

## 16. 反思：模型实验室为什么不做「确定性 check」？

- Greg 的困惑：**为什么模型实验室还没把「确定性 check 进程」做进 harness？**
- 现状：`goal` 功能很好（也是他入坑的起点），但 goal 的「definition of done」**只是文本，模型去 classify，不是编译后的 check**。他早年用 Codex goals 建 Dead Reckon，**goal run 跑几小时甚至几天，仍然漏掉一堆东西**，还得再跑一个。
- 例外：**Anthropic 是唯一一个在做类似事情（确定性）的模型实验室**（Claude Code 的 workflows），而且**不依赖另一个模型去 classify**。
- 为什么别人不做：**复杂度 + containment**——如果某个东西能改你的前置编译 check，你就得做结构性隔离，跨 OS 更麻烦；「如果能伪造收据，整个 setup 就失效了」。
- 但 Greg 认为**理解这套机制本身极有价值**——像一门「**逻辑物理学（logical physics）**」。

## 17. 收尾：Zen of Torty（产品原则）+ 防 burnout + concise mode

### 17.1 产品原则：Zen of Torty
- 呼应 Jack 的「Calvin & Hobbes 精神」——Greg 给 Torty 写了一套 **「Zen of Torty」**（价值观/产品原则），写进项目 CLAUDE.md，作为**分阶段 workflow 的非确定性兜底**：
  - 当某个 phase 的 spec 没完全定死、worker 自己发挥时，若它「本该问我却没问」，**fallback 就是：这符不符合 Zen of Torty？**
  - 例子：**不能妥协「session 线程的持久性」**（这是产品核心承诺）；UI **别让信息淹没屏幕**（「hide the machinery」）。
- 好处：① 让 LLM 真正**守住承诺**、防止 feature creep；② 帮 Greg **对自己诚实**；③ 研究阶段可做 **adversarial critique**——「我反对这个，因为它违背 Zen」→ 若想推翻，就**给 Zen 加一条新原则**。
- Jack 的共鸣：他给每个想法都建一个「**grounding document（锚定文档）**」，跑偏了能拉回来。

### 17.2 两条「不用 babysit」的好方法
1. **确定性 workflow + 循环**（Greg 现在的首选，推特已开源）。
2. **前置定义清楚**（缺点：要求你事先知道更多）。

### 17.3 防 burnout 与「眼睛不再是 gate」
- 目标：**别让「我们的眼睛」成为一切事的 gate**——这会带来 **executive function fatigue（执行功能疲劳）**。
- Julian 的共鸣：厌倦了「盯 agent 4 小时、回来发现它跑偏了」，尤其 Claude「超级主动，但不是最好的那种主动」「自己做太多假设」。
- 顺带吐槽：Claude Code 的 **hooks**「超级基础」——能写「每次 commit 跑个 check」，但那是在**模型已停止执行之后**，不是同一个前提。
- **今日更新**：Claude Code 出了 **concise mode**（`config output style concise`）——Greg 推荐打开，能帮我们「不用眼睛」。（Julian 提到 Anthropic 还加了**文本水印**，Greg/Julian 都觉得「那不是好事」。）
- 最终建议：**「别照抄课程里的一切，把它适配到你的场景，把有用的碎片抽出来。」**
