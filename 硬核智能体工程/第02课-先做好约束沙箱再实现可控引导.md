# 硬核智能体工程（Hardcore Agentic Engineering）第 2 课：先做好约束沙箱，再实现可控引导

> 课程定位：**Hardcore Agentic Engineering — for builders who ship**（面向真正交付产品的构建者）。
> 本课（Session 2 / p03）是 6 讲系列的第 2 课。第 1 课讲了 **Define Done Before You Run（在运行前定义完成）**；本课在其基础上**新增两个概念**：
> 1. **Goal（目标）** —— 把「完成契约」升级为「附着在运行时上的、可被召回/恢复/重启的持久化组件」。
> 2. **Durability（持久性）** —— 通过**保存并规范化事件日志（event log）**，让元 harness 能在进程中断后「忠实恢复」，从而支撑「可控引导（steering）」。
> 题目「先做好约束沙箱，再实现可控引导」点出本课的方法论顺序：**先把 loop 与 gate 沙箱隔离、把状态持久化，然后才谈得上「走开、中断、纠偏、恢复」这套可控引导能力。**
> 讲师：**Greg**（Spec Story 联合创始人，前 Pluralsight CPO）；学员：**Julian、Raj、Jack、Sean、Don、Ram** 等。

## 0. 本课一页速览

| 维度 | 内容 |
|---|---|
| 新增概念一 | **Goal（目标）** —— 附着到运行时的、带 run ID 的、可恢复/重启的持久化任务定义 |
| 新增概念二 | **Durability（持久性）** —— 保存 + 规范化事件日志，使 run 可忠实恢复 |
| 核心对比 | **spec（设计权威，不入运行时）vs goal（融合进 harness、控制其状态）** |
| 核心差异 | 原生 `/goal` 用「小模型判定停止」**无确定性**；自建 harness 用**确定性门** |
| 核心金句 | **「The log is the agent（日志本身就是智能体）」** |
| 现场演示 | 两个 Claude 进程同时被中断：**右边（有持久日志）恢复续跑，左边（无日志）从头重来** |
| 引导（steering） | 纠偏的「成本光谱」：补事实 → 给参考 → 要 mini-plan → 取消重跑 → 重写契约 |
| 下讲预告 | 循环内的 **mini policy engine（策略引擎）**：恢复时该做什么 |

## 1. 开场热身：并行 worker、work tree 与认知负荷

正课开始前，Greg 与 Julian 有一段关于「并行运行多个 worker」的真实讨论，本身就是本课主题（可控引导 / 认知负荷）的铺垫。

### 1.1 Julian 的困境
- Julian 连续工作了 16 小时以上；他发现自己有一个坏习惯：**「正在跑一个任务时，又冒出一个新想法，于是开始并行跑多个 worker」**。
- 有时需要「spin work tree（开工作树）」，但**有时工作是相关的**，并行后反而难收拾。
- 他最近在跑 GPT-5.6，给它**一长串小任务清单**，结果它跑得**太快、太并行**，导致「几乎不可能跟上它在干什么」——不是因为它并行，而是因为它太快，快到没法读文本。
- Julian 自嘲：**「我知道该避免，但忍不住诱惑，就是想把一长串小任务甩给模型看它怎么办。」**

### 1.2 Greg 对 work tree 的演变观察（重要）
- **历史建议**：同一 repo 上并行干活、有潜在冲突编辑时，老建议是「check out 多个 work tree」。但这样有「join 问题」——把多个 work tree 合回来，会有「一个文件被共同编辑的不同状态」。
- 如果 repo 很大，「开 work tree」等于「复制一个大 repo 好几份」。
- 如果不勤清理 work tree，会失控。
- **Greg 现在实际发现的更优做法（两点）**：
  1. **批量 + 排队（batch + queue）**：排队系统已经变好很多。构建一个 goal 时，它内部会有一个 **run ID** + 一个内部 plan（就是那些「小任务打勾清单」）。Greg 在「有活跃进程在跑时仍主动发送新消息」这件事上**相当激进地排队**，并让模型**延迟到「完成当前 goal 的这个 phase 之后」再去处理新消息**——但要说得非常具体（「在你完成这一阶段之后再添加这个」），并且因为没有保证，事后要去检查它是否真的开了一个新 phase。
  2. **停止用 work tree**：因为太乱。Greg 发现即使两个 Codex 进程同时跑，它们现在**凭上下文窗口大小，能相当好地知道自己在对话里改了什么**；即使有轻微重叠编辑，也**不太可能落到「行级真正冲突」**，它们很擅长跟踪「同时的读写」。甚至可以明确告诉其中一个：「现在有另一个 session 在跑」，它会自己去找那个进程 ID 并保持同步更新。
- Julian 也观察到：代理会「等另一个人改完这个文件我再继续」，并让代理**自己决定要不要开新的 work tree**；现在 work tree 也做了优化（用 symlink 代替复制文件来避免重复）。
- **并非绝对停用 work tree**：对「超级长、我不想中断」的 run，以及 Greg 用自建工具在跑的某些任务，work tree 仍可能有用；他停用的是「默认靠 work tree 解决一切并行」那条旧最佳实践。
- **Subagent 不完全由你决定**：即便你倾向独立终端并行，底层模型/工具仍可能自行利用 subagent；除非彻底关掉，否则有时控不住——独立终端命名主要是降低「你跟不上」的认知负荷。
- **阅读负荷的时间压缩感**：有人描述「认真盯一小时流式输出，体感像干了一整天」——这正是后面要造机器接管「盯屏苦活」的生理动机。

### 1.3 关于 subagent 与并发（衔接第 1 课）
- Julian 重提 Greg 上一课「尽量少用 subagent，好盯着 agent 在干什么」的观点，但他仍难抵抗「尽可能并行以最大化并发」的诱惑，尤其在资源富余时。
- Greg 的策略：
  - 周二的问题本质是「**什么时候明确让 subagent 在主 session 里干一堆活**」。他的例子是：**收集大量证据（读很多东西、再合并回主编排）**，或**确定性移植（port）**。
  - 他倾向于**把并行任务交给「独立的 session/终端」**，而不是在一个 session 里全部 spawn 出来；并**给每个终端命名（描述它在做什么）**，这样能快速「记起该回到哪」。
  - 关键变量完全因人而异：**「你能在前额叶皮层里同时装下多少东西？你能实际读多少？」**

### 1.4 决策疲劳（decision fatigue）——本课反复出现的动机
- Julian 读 Reddit 帖子：人们抱怨用智能体后**要做更多「微观决策」（评估模型输出、工具调用等）**，比手写代码还累，甚至导致一些人「停止在生活里做决策」（选个吃饭的地方都要爆炸）。
- Greg 自己也「正中这一条」：一整天的 agent 输出之后，连「去哪吃饭」都决定不了。
- 反例幽默：Greg 说「我相反，上帝总夸我品味好，所以现在我想拥有每一个决策，因为我是史上最好的决策者」——调侃模型「拍马屁」会让你误以为自己无所不能。
- **这条线索贯穿全课：为什么要造机器来接管「盯着屏幕读流式输出」这种苦活？就是为了对抗执行功能疲劳。**

## 2. 清晰度检查（Clarity Check）：第 1 课概念回顾

Greg 开场先花约 10 分钟做「术语/框架」回顾，并补充了新的示意图（用 Cali Draw 画的），原因是：很多人没读完 Session 0 的阅读就「冷启动」进来了，术语容易混。

### 2.1 五个核心术语（务必分清，否则「agent / harness」会混在一起）
- **worker（工人）**：就是你在用的原生 agent —— Claude Code、Codex、Cursor CLI、Pi…… 在 prove it harness 里，它只是「被驱动的那个」。之所以叫「worker」，是为了和「harness」区分开。
- **check（检查）**：done contract（完成契约）里的一个**条款**。
- **gate（门）**：那个「评估循环是否结束」的东西；是**确定性进程**。
- **loop（循环）**：每当你用 prove it 或自己的元 harness 时，一直在跑的那个循环。
- **receipt（收据）**：从另一端出来、记录「做了什么、通过了哪些检查」的产物。

### 2.2 第 1 课回顾：从 vanilla 到「加一层」
- **vanilla 起点**：prompt（可能带 spec / skill）→ 催化一个 run/session → 发生多轮 exchange → 模型调完工具、发出 done → **你用眼睛 review 所有 diff** → 结束。（可能有 hooks、额外 process，但核心就是「用眼睛做门」。）
- **第 1 课加的额外机制**：给这个熟悉的 loop 套上
  1. **done contract**：你可以往 outcome checks 里塞**任意东西**。
  2. demo 里：两个 Claude 进程，其中一个带着一个「它不知道」的检查（跑一个基础单元测试，评估 slugify 实现对不对）；如果它因为不知道这个检查而做错，就被「踢回去重跑」，直到通过才被允许结束。
  3. **gate 函数**：每当模型 emits done，就按「definition of done contract + outcome checks」决定**允许结束 or 继续循环**。
- Greg 强调这不是纯 TDD，契约「可以是任何东西」（见第 7 节）。

### 2.3 为什么要「接管手动工作」放进软件
- 如果你**没有**元 harness，那么**你自己就是那个 harness**：你的眼睛必须盯着目标、做所有「困难的阅读和摄取」——注意漂移、决定何时打断、何时继续。
- prove it（玩具）和 Dead Reckon（成熟版）**没有发明任何新工作**，它们要做的是**接管这些手动工作，并把它们放进「耐用的软件」里**。
- 目标：**把「你必须手动做的那些事」尽量程序化，从而停止执行功能疲劳。**

### 2.4 「done contract」是当前 harness 里没有的新东西
- 想封装现有 agent harness 并「让它按你的意愿停下」，最好的方式之一就是**事先定义 done contract**——今天**没有任何厂商 harness 给你这个**，这是本课要带走的主要 novelty。
- harness 在子进程里跑另一个 agent 时，要能「记住那份带 checks 的 agreement（协议）」。
- loop 必须能：
  1. **重新实例化 loop（若需要）**；
  2. **检查某样东西**（这个确定性 gate 过程：看 done contract，确定性地评估「是否允许 break loop」）。
- **receipt（收据）**：今天你用任何模型都**拿不到一张「它做了这些事、并通过了检查」的收据**。今天的现实只是「一堆 tool call + 模型输出 + 你满意后提交的 diff」，没有任何记录证明「你以为发生的事真的发生了」。收据可以附到 PR 上、用于溯源。

### 2.5 不必造 Dead Reckon
- Greg 强调：Dead Reckon 是「理想形态」，是他在过去 18 个月～2 年里「越过边缘看到的手动工作都可以被构建成更好的软件」的候选集合。**你不需要照搬它**，只需要抓住「done contract + gate + receipt」这个最小内核。

### 2.6 何时写 Done、何种任务适合长跑

- **产品/工程目标还不清楚时怎么办？** 完成契约不必等于「会话循环关闭时你想要的一切」。若目标是真正走开，先从**更容易预先定义**的任务类型开始练「先写 Done」——不要等「完全想清楚产品」才动手。
- **长跑任务的交换条件**（回应 Jack「什么适合长时间自主代理」）：你要先为「想交给长跑 agent 的事」设好参数与好标准（可以是可优化的 **metric**，或其它可约束的边界）。这与许多人习惯的「开场就对要完成的事有极紧凑想法」的 prompting / spec 开发不同——你是在用**更多代理推理 + 更长轮次**，去交换「不一定更少的前期精度，但更好的边界与约束」。
- **三条运行光谱（向 goal 过渡）**：
  1. **交互式配对**（人眼当 harness）；
  2. **非常受限的短跑**；
  3. **完整的完成循环（done loop）**。  
  本课的 goal / durability，是把第 3 档做得可离开、可恢复。
- **自主时长刻度**：当你不想为「读完每一轮结束时吐出的一切」痛苦时，时长可以是 **10 分钟 / 30 分钟 / 2 小时 / 2 天**——done contract 就是为这种跨度准备的前期工作。

## 3. 决策疲劳与「证据（evidence）」——本课的主线动机

### 3.1 我们处于「混乱的中间地带」
- 我们都已采用这些工具，工具也被「打磨到契合我们当前实践」，但**我们还没造出「真正接受这些结果所需的流程」**。
- 结果：每个人都开始**决策疲劳**。Greg 自己：全天候运转到某个点，尽管有多巴胺刺激，也会开始「写更乱的 prompt」「开始 YOLO 它」。

### 3.2 「检查的质量」才是关键
- 我们确实能拿到「连贯写出的代码」，但如果懒了、退化了，就会**盲目接受**。
- 所有机器都依赖**「你的 checks 的质量」**——无论你用 definition of done 范式、还是在原生 harness 里用 goal，这一点都变得极其重要。
- 「什么是一个好 check」很难教，因为它**高度依赖情境**；但「写它们、看见它们」的练习本身就是第 1 课项目要理解的东西：**你无法完全停止做所有决策，但「把脑力花在哪」才是关键。**

### 3.3 「契约不只是单元测试」的再强调（回应 Ram 的问题）
- Ram 问过「这（契约）能包含什么」，Greg 强调：**前期控制模型循环的契约，可以是任何东西**。
- 例子（绿地游戏）：
  - 游戏需要网络功能 + 特定外观才允许极长自主 run 停止。
  - 这类「网络配置是否真的可用」「下载示例图并用 OCR 比对」很难写进纯单元测试（TDD 那套），但可以写成一个**进程**：在 loop 被允许结束前，**跑网络配置监视器评估是否有真实网络调用功能；下载示例图、用 OCR 比对是否匹配**（不会完美匹配，但这就是「解锁」）。
- 核心：**你可以让 loop 想跑多久就跑多久，并用「开箱即无」的一定程度的确定性去约束它。**


### 3.4 Jack 问答：谁还在看输出？收据、问责与「眼睛在哪里」

我们正站在悬崖边：**代码编写已大量外包**；团队仍口头强调 review，但细粒度理解正在下降——很多人更多是扫一眼。若你很熟项目、或在改 **schema / 持久化** 等高风险面，人们还会看；若用的是不超级熟的语言、但能验证「系统在工作」，审查更容易退化成只看系统状态。

- **问题不止评估**：还需要把 run **叙述成压缩、人类可读的故事**，好让你知道该下钻哪里。这与收据相关——收据可以不止「通过了哪些 SHA/检查」，还可以包含：
  - 对文档的更新；
  - **完整运行叙述**（不必回去狂滚终端）；
  - 终端代理场景下，输出甚至可能被遮蔽——更应在结束时**提前交付**可读摘要，而不是事后再问一堆问题。
- **金句**：**「我们有这些强大的长跑代理工具，但我们的眼睛在哪里？我们用这些眼睛做什么？如何信任从另一端出来的东西？」**
- **问责制**：小 PR、工程师该审——归根结底是**你负责**。可以不看就合，但生产事故的后果在你。要把问责以更强方式建进系统（人会犯错）。
- **案例（本课现场复述）**：AWS 发布规范驱动 IDE **Kiro** 时，曾有生产事故可追溯到工程师**用自家系统却未实际审查代码**。若 AWS 会发生，别处也会——不是工程师「不够好」，而是外星级系统让我们为杠杆**委托注意力**。问题变成：如何尽量不踩自己的脚？若不能更可信地定义想要什么、发送边界、消化出口物，就拿不到 agentic engineering 的承诺。
- **捷径原则**：代码仍是运行时真理来源，必须有评估它的方法。我们在找捷径，但要以**提高信任水平、而非降低信任**的方式找。动力工具实验室给我们超能力工具，我们仍是动力工具用户——**别因为没开安全就锯断自己的腿**。工具 alone 不够，文化与团队规范也要一起解。

## 4. 本课新增的两个概念

Greg 用「绿色 = 新增」的示意图，点明今天只加两样东西：
1. **Goal（目标）** —— demo 里会「翻页看一个 goal」；demo 里的 goal 极简单（几乎就是一个 prompt），但重点是理解「当我们围绕自己的子进程造好机器后，要让这种 run **durable** 需要做什么」。
2. **Durability（持久性）** —— 各厂商 resume 功能都依赖一个「不同格式的事件日志」；如果我们要有自己的元 harness 包裹这些子进程，**必须存储这些事件**，因为它们才是让「harness 内的 loop 无论怎么起停都能忠实恢复」的东西。

## 5. Goal（目标）详解

### 5.1 goal 不是 spec 的反面
- Greg 的心智模型：
  - **spec 的角色 = 你希望 agent 做什么的「设计权威（design authority）」**。实现前你会花大量时间想清楚条件、写下来。spec 对「用这些工具」极有用（可以提前做决策、确保给模型正确上下文），但**它不会被保留在模型的运行时里**——你把它当 context 喂给模型，**和 harness 本身毫无关系**。
  - **goal 的区别**：它**把一个 outcome 附着到一个活跃任务上**，模型随后可以 **recall / resume / restart** 它。它是**持久的、harness 的一个组件**。
- 一句话：**spec 是磁盘上的 markdown（或 plan mode 保存的任务计划），与 loop 运行时无关；goal 是「融合进 harness、控制其状态」的东西。** 两者写起来可能很像，但运行时行为根本不同。

- **Spec 的现场范例结构**（多人视频会议产品里的 Theo 入职实时 agent，浓缩版）：purpose / 目标与**非目标（non-goals）** / 当前实现状态与数据流 / 性能与如何观测。写 spec 无标准答案，它仍只是仓库里的 markdown——利于思考与规划，**不会把运行时绑到任何持久物上**，本质是「更大的提示 + 设计权威」。
- **Spec 的现实张力**：要不要长期保留？要不要版本控制？Greg 版本控制了大量 spec，对「事情如何产生」有溯源价值；但不断写新 spec，它们会与代码当前状态**漂移**。Spec 很有用，也自带「养文档」的问题——这更凸显 goal「附着运行时」的差异。
- **Goal 从 outcome 起笔**：折叠版 goal 往往不是「嘿，这是我在设计的东西」，而是**从一个结果开始**；再挂上上下文引用、姿态/不变项、phases、verification、stop condition。

### 5.2 goal 的历史与「writer」
- goal 是**大约在 5 月才引入**的，很多人不熟；最初被限制为**只有 4000 字符**。
- 因此课程里有个术语 **writer**：**额外上下文，可以装任何东西，往往就是你可能写在 spec 里的那些内容**。因为 goal 有字符限制，所以把「spec 类内容」塞进 writer，作为「可被 goal 引用的额外上下文」。

### 5.3 `/goal` 命令的实际行为
- 输入 `/goal` 并粘贴文本（文本可存文件、可版本化），**会改变实际的模型运行时，并给它分配一个 run ID**。
- 如果你中途退出模型/harness，它会**自动问你「要不要 resume 你的 goal？」**
- 澄清（Raj 问「这是 skill 吗 / 是命令吗」）：**`/goal` 不是 skill，是一个内建命令（command）**。它和 Claude 里的一样，有「停止前检查 goal 条件」的同一套概念机器。
- 注意：**Cursor 没有原生 goal**（没有 `/goal`）。Cursor CLI 可以在你自己的元 harness 里引入它，但原生不支持。OpenAI / Claude Code 有；OpenClaw（见下）也有；Cursor 需要扩展。

- **可以「几乎空着」也开 goal**：支持该功能的工具里，生成/设置 goal 时未必先塞满验证步骤；前提仍是「让模型能跑很久」。但停止判定在原生实现里仍外包给小模型分类器——这与自建确定性 gate 的差距不变。
- **Labs 互相跟随**：Cursor 暂无原生 `/goal`；Greg 假设某一刻其它工具也可能跟上（文档当时还没有）。

### 5.4 各厂商的 goal 实现对比（关键差异：确定性）
- **OpenAI / Claude Code 的 goal 机制**：不用 `/goal` 时，你产生一个「ask」，模型跑完一轮就等你下一步；用了 `/goal`，它有一个**内部循环，被「目标结果」约束**（可以是一个机械实现，也可以是保持循环的 metric），你可以在一个**验证步骤**里枚举约束。
- **关键差异**：这些原生实现**都没有内建任何确定性**。例如 Claude Code 的 goal：**每轮结束后，一个小而快的模型（大概 Haiku）去检查「停止条件是否成立」**——你把停止条件写在 goal prompt 里，但仍然把大量判断外包给了「处于其 turn loop 中的模型」。
- **Greg 的方法更保守（也稍贵）**：如果要「真的能走开」，就要对停止条件有更多控制。所以概念全部照搬，但**多加一步**：用**确定性的外部进程**来验证，从而能在 loop 里使用**任意模型（无论它本身有没有内建 goal 机制）**。

### 5.5 goal 与 done contract 的相似与差异（Raj 问「它们不是差不多吗」）
- **相似**：goal 也有 gate、也会一直检查直到 loop 结束，和 done contract 概念上同源。
- **差异**：
  - goal 里你**用文本写停止条件**，是在「播种（seeding）控制权」，但那个「检查」只是**另一个小模型分类器**说「满足 / 不满足」。
  - 自建 harness 里，你有一个**确定性进程，总是会跑**，从而让你**验证「这一组 turn 是对的（至少符合我的规范）」**。
- 相关背景：**OpenClaw** 是 Pete Steinberger（在 OpenAI，几乎只用 Codex）相关的**元 harness（包裹其他 agent 的 harness）**，有类似 goal 的概念；Pi 用户也可通过扩展获得「持久的长目标」。但这些**也都不是开箱即有的确定性**。

### 5.5b 为什么元 harness 要 goal-driven，而不是再造一个聊天框

- 新模型几乎每隔一天就发布；全世界的供应商与开源已经把**各种配置的交互式提示**做烂了（IDE 内外皆是）。
- **缺口不是「另一个更会交互式提示的工具」**，而是**更多自主性**：goal 驱动、附着 run 状态，让你在需要时才退回现有交互式工具。
- 因此元 harness 里会有额外代码：这是一条**被持久记录的 run**——我知道**什么启动了它**（可以是 goal，也可以不是；goal 格式是 Greg 的写法偏好）。无论自建还是原生，你都需要这份 **run state**。

### 5.6 Greg 的 goal 结构（他自己的写法习惯）
Greg 用一个 skill 把 prompt 重新裁成他喜欢的结构化格式。他写 goal 的一般结构：
1. **Outcome / objective（前置目标/结果）**：通常是**单一目标**（不强制，但他发现单一目标从「心态上」更好理解「这个文档是干嘛的」）。一个 goal run 可能产生很多 commit / 很多分阶段工作，但「知道它当初是为了什么跑」很有用。
2. **Context（该去看的上下文）**：可以是 simlinks 或引用，**不是把全部上下文前置塞进 goal**。
3. **Posture / 不变项（这次 run 的姿态、不想改变的东西）**。
4. **Phases（阶段数量）**：他希望把工作**切块**到「有 commit shot 可以回看」的粒度；**一般设 10～20 个 phase**，取决于工作量估计。这样「模型跑两天，你实际想回看几个 commit？」——用 phase 数来**约束「你要 review 多少次 commit」**。
5. **Verification（如何验证工作完成）**。
6. **Stop condition（何时告诉模型真正停止）**——这正是「内建 goal 机器」替你做的事：看那一行、跑它的小模型、问「这事发生了吗」。

### 5.7 为什么不信任「模型自证完成」
- 如果只用 vanilla 实现，停止与否**受制于「模型说它做完了」**，你无法从任何日志里**轻易**确认真实完成（可能埋在某条极长 trace 里）。
- **解决之道：把「验证是否该停」拆出来，变成独立进程（gate），不让「正在干活的那个模型」来验证自己完成。**
- 呼应第 1 课 Ram 的经历：模型**多次篡改测试容忍度（tolerance）来让循环完成**。所以验证必须是分离的、确定性的。
- 即便不造元 harness，**开始理解并利用 goal** 也很有效：你还没到「完全自主」，但已经能「事先指定一个更难的任务、让模型 run 更久」。

### 5.8 让模型帮你写 goal
- 支持 goal 的模型**很擅长帮你写 goal**（`/goal` 生成）。结构无对错，各人偏好不同；模型自己写自己的 goal 尤其好。
- Greg 愿意**在 GitHub 开一个「goal / spec 文档库」**，从各类项目里收集真实例子，方便大家看「具体差异」（学员表示「越能钉到具体例子越有用」）。

## 6. Durability（持久性）与「日志就是智能体」

### 6.1 事件日志（event log）是恢复能力的地基
- 任何用过 resume 功能的人都知道：**每个厂商都会写一个事件日志，但格式各不相同、信息也不同**。
- 如果我们要有自己的元 harness 包裹这些子进程，**必须存储这些事件**，因为它们才是「让 harness 内 loop 无论怎么起停都能忠实恢复」的东西。
- **核心金句（出自一篇 X 文章）：「The log is the agent（日志本身就是智能体）。」** —— 即「发生了什么」的那份日志，就是智能体本身。

### 6.2 Claude 的例子：不可变日志流
- Claude 的「救命稻草」：它**存储一份不可变（immutable）的、记录一切发生的日志流**（API 挂了它也不会丢）。
- 但问题在于：**你的元 harness 不知道这个格式、也无法访问它**，除非你**自己存储它、并赋予 harness「利用它、并把它绑定回你实例化时用的 run ID / goal」的能力**。
- 这为什么重要：即使现在只有一个 Claude，**课程会逐步加复杂度**，你可能想用两个不同 CLI 模型干两件事，就需要**把日志规范化（normalize）到一个通用格式**，让元 harness 能读、能交互。

- **动机句**：一旦日志持久化做成功，**run 的持久性就是「你离开时不必一直担心」的那件事**。
- **异构编排想象**：元 harness 里可能同时跑「实现者」与「批评/审查者」等不同 CLI worker——于是「把各家日志规范化到通用格式」从可选项变成刚需。
- **「日志就是智能体」的游戏存档类比**（X 文章）：标准化各 provider 的日志流后，你可以从任意点加载正确上下文、**换模型启动/恢复**——重要的是启动时把正确上下文装进另一个 agent，而不是死守原来的工具身份。

### 6.3 各厂商日志格式现状（现场实探）
- **Claude Code / Codex / Gemini CLI**：在项目目录下，每个 session 一个 **JSONL 文件**（Greg 现场展示 `~/.claude` 下海量 JSONL，且「每家长得都不一样」）。这已变成「大多数人写 agent harness 都采用/借用/偷用的一种模式」（虽不叫标准）。
- **Cursor**：**不一样**。磁盘上看到的是一堆项目目录，里面是**类似 SQLite 的数据库**，其「代表 agent 历史的 schema」已演化无数次，很乱；是一种「演化出来而非设计出来」的世界。里面是「少数几张表 + 大 JSON blob 作为行」（更像文档数据库而非关系型）。
  - Greg 自己的 Cursor 数据库 **1.7 GB**。
  - Cursor 早期是「先锋」，很多人抄它；但后来 Claude Code 等**决定不写进这种数据库**（因为 Cursor 起飞时那个数据库老是损坏、用户丢聊天记录）。所以 JSONL 是更明智的后来选择。
- **schema 会不会乱变？**（Julian 问）
  - Greg：从 Spec Story 维护 provider model 的经验看，**它们其实不常变**。因为很多项目依赖它；Claude 曾在约 6~7 个月前改过一次格式（摆弄 resume 时）引发众怒。
  - 大多数情况下**向后兼容**地演化：一旦 harness 成熟到有 resume 功能，就自带「向后兼容问题」（你可能恢复三个月前的 session），乱改格式要么弄坏自己的 resume、要么得维护并行代码。
  - 成熟 harness（Claude / Codex / Cursor）现在**缓慢生长**：加个新 tool call、加 subagent 时，schema 就「长出新附肢」，但**一般不会推倒重来**（那只会发生在全新 harness 的前 6 个月）。

- **Claude 一次格式改动的实质**（约 6～7 个月前、折腾 resume 时）：不止「字段变了」，还包括**如何把子代理会话附着到主会话**的模型调整；社区有过反弹。Spec Story 一侧曾用 **DAG** 等方式把子会话拼回主会话。成熟 harness 的 schema 更像「长出新附肢」（新 tool call、subagent），而不是推倒重来——推倒重来多见于全新 harness 的前约 6 个月。

### 6.4 「读日志」是解锁很多能力的关键
- 现场演示：在某个 session 里让 Claude 写 Fibonacci，停下后拿到 UUID，去对应 JSONL 里找 session log（UUID 能对上）。
- 所有 resume 功能原理都一样：**把完整日志读回上下文（终端窗口）**，你就回到了原处。
- 日志里基本固定包含：**system prompt、user prompt、agent、工具响应**——因为「它现在就是一个 loop」。
- 从 Spec Story 的角度：**开始读懂日志，是很多事情的「解锁」**，因为它带来巨大的可扩展性。

### 6.5 Spec Story 的「跨 agent 恢复」（Raj 问 + Greg 演示）
- Raj 问：能不能用 Cursor 当元 harness、用 Claude 干活？
  - Greg：Cursor 有 **SDK**（不是你在用的那个 vanilla IDE / Cursor CLI），可以拿它处理部分模型循环、在其上构建；但「让 vanilla Cursor 当控制器」不行（没法扩展、没源码可 fork）。Cursor SDK 可能是更好的起点。
- Spec Story 的能力演示：它能**跨所有项目/所有 agent 看到一个统一视图**（把会话同步成 markdown），而且支持**从「原来那个 harness」恢复到「另一个不同的 harness/模型」**——底层做的事就是**把那个 session 重写成「能让另一个 harness 接受」的格式**。
  - 恢复不需要完美（演示里也有点小 issue），因为「你要做的只是把上下文塞进另一个 harness」，它反正只是把文本读成一个 collapse block，**不需要知道上一个模型用过什么工具，只要能从格式恢复**。
- **给自建者的建议（Jack 问「是不是直接用 Spec Story 就行」）**：
  - Spec Story 的 `sync` 做的是「去项目里所有 provider 下找日志、写成通用 markdown」的**特定工作**，没 baked 进你自己的元 harness。
  - 你该从 Spec Story 源码里学的是**「provider model + 日志规范化标准」**：哪家 provider 把日志存哪、如何把它们规范化成一个标准格式（**既有 JSON 格式，也有 markdown 格式**）。
  - **别重复造轮子**：自建元 harness 时，直接用这套标准、从 Spec Story 的 provider 源码里挑你要支持的那 1~2 家，**让 Claude/Codex 帮你 port 过来**即可（Greg 当年给 Dead Reckon 建 provider 时就是这么干的）。
  - Spec Story 支持的候选 provider 格式大约有 **~8 种**量级；`sync` 会扫项目下各 provider 日志、写成通用 markdown（也可再同步到云等）。你自建时通常只需 port **你常用的 1～2 家**，不必求全。

## 7. 现场演示：Durable run 的对比（两个 Claude 同时被中断）

### 7.1 演示设置
- 像第 1 课一样，**在 prove it harness 里跑两个 Claude（sonnet）进程**，两边拿同样的 brief：**「实现 slugify 函数，让它健壮、处理真实 CMS 会抛给它的一切」**。
- 两边都有**契约 + 检查**。
- 唯一区别：**右边有持久日志流，左边没有**。
- 然后制造一个「惊喜」：**两边进程都被中断（kill）**（模拟网络断开 / 无法到达 API）。

### 7.2 恢复时的判断（这就是「steering」）
- 中断后该做什么？「steering（引导）」在这里的含义极其简单：**「恢复它并按下 continue」**。
- 判断依据：**除了被未知错误打断、进程死了，其实什么都没变**——我们要的结果没变，所以**不需要新契约**，只需「continue」，让东西**从断点继续控制子进程，而不必重新 brief**。

### 7.2b Toy 成功 vs 生产风险（本课口头警告）

- Demo 任务极简（读文件、写文件、过检查），两边最终都能「做对」——**答案本身不重要**。
- **警告**：若是难实现、很多轮次、或中断并非「几秒内就停」的场景，裸「continue」**可能已经进入糟糕状态**。本课故意用玩具例子只证明「有持久日志就能从断点捡起」；生产里「恢复时该做什么」要等下讲的 mini policy engine。
- ProveIt 练习里的工程提醒：**你没给上下文的地方，往往就是真正的答案/缺口**——brief 留白不是中立，而是把判断甩回模型或甩回你事后的眼睛。

### 7.3 两边结果
- **右边（有持久日志）**：从日志流**拾起续跑**，没有启动新进程；日志明显更长。它「救了我们的屁股」。
- **左边（无持久日志）**：harness 只能**重新给一遍 brief**，于是 spawn 一个新的 Claude 进程、turn 1 从头开始。
- 在这个 toy 例子里，因为任务太简单（读文件、写文件、通过检查），两边最终都能做对，**答案本身不重要**；重要的是前提：**如果你有 durable run events，遇到更复杂的 goal/writer 时就不必从头开始。**

### 7.4 日志时间线查看器（log timeline viewer）
- Greg 写了一个小工具，把「引擎盖下的原始事件日志」变成好读的时间线（因为原始 JSON 太难读）。
- 从时间线上能看清：左边「stop → resume → 重新给 brief → turn 1 重来」；右边「stop → 从断点 resume → 日志更长」。

### 7.5 小结
- 关键就是：**保存你的日志、让它们 durable**。当你通过元 harness 用 goal/writer/任何东西催化子进程时，**记录 run ID、记录所有不可变状态**，全部存下来。

## 8. Steering（可控引导）与纠偏的成本光谱

### 8.1 引导是一门需要大量「rep」的技艺
- 什么时候打断、怎么打断，需要很多次练习。目标是：**能走开；即使不走开，也能 pivot 到别的事**；不想浪费时间/token 在「本可更早纠正」的运行上。
- **错误会复合**：如果你在开场 prompt/goal 里给了错误上下文，错误会随 session 运行而**复合**；若在 prove it harness 里进程死了、又没有 durable log，纠正就「消失」了。这也是**把上下文放进「goal + writer」这种持久东西**的理由——重启时，要么没纠正、要么直接编辑那个文件。

### 8.1b 纠偏会沉淀成模式（现场例子）

- Greg 从真实会话日志抽出一例（元 harness 之前）：盯着构建步骤时，模型想**重新启动 build**；他打断：「不需要，我们已经构建过了。」——这类引导有效，而且模型的回声后来会变成可识别的**模式**（正是后续「从前馈 / skill / 日志分析」里要吃的料）。
- 结合 Stoa 的 614/1300 打断数据：我们**一直**在做这件事；有效，但太耗时，且放任错误复合会毒化上下文、逼你交互在场或换提示重跑。

### 8.2 纠偏的「成本光谱」（从便宜到昂贵）
1. **补充一个缺失的事实（supply a missing fact）**——最便宜。你盯着屏幕，模型没动得那么快，你说「不，你需要的事实是这个」，希望下一轮接住。
2. **给一个好的参考示例（reference example）**——给一段能跑的代码 / 一个含特定组件的仓库 / 一个 API。但前提是**你得知道那个参考是什么**。
3. **让模型在 run 内给一个 mini-plan**——成本略高：常见小交互对话框弹出时，你要付出额外认知努力（「Claude/Codex 这条建议真的值吗？要不要再和模型聊一轮？」）。也可以纯打断、escape 逃到下一步，但仍要自己决定下一步做什么。
4. **取消 run、重新开一个 session**——成本更高（可能留下 dirty working state）。
5. **拒绝一切、回到干净工作状态、重写开场 brief / contract**——**最贵**。

- 核心：**你今天能手动做的所有这些「引导」动作，都是你构建元 harness 时要「enable（使能）」的东西。**

### 8.3 Raj 的实操问题：如何早期捕获错误？
- Raj 场景：写 Java 代码，让 agent「build → run test → deploy → health check」；结果它在 `pom.xml` 里写错了一个依赖，于是**不断循环、检查一个根本不存在的 artifact**。
- 问：怎么「用 gate 那套东西去 trap 这些错误」？因为这种错需要你改指令重跑，所以怎么在 agent 运行时**中断并快速得到反馈**？
- Greg 的回答：
  - 依赖一堆外部系统时，「有时它就会发生」，这不是万能药。
  - 如果这种行为**不止一次出现**，那就值得**在前期 checks 里把它「编码成一定程度的确定性」**——就像你把反复出现的 prompting 模式沉淀成一个 skill 一样。
  - 现阶段（还没到第 5 课），如果只是「模型有 poison context / 因为你没充分指定而没遵循指令」，能做的只有：**steer 纠正它，或 cancel 重跑并给更新后的上下文**。
  - 但要先**手动**（写个脚本去读这些日志、理解这些错误）看清「这些 log 事件随时间发生了什么」，它们会成为**「前馈指令（feed-forward instruction）」的候选素材**——可以是「让模型执行的 skill」或「加载进 agent.md / CLAUDE.md 的上下文」。**最终你希望 harness 自动帮你做这种模式分析。**
  - **递归自我改进**：目前几乎没有任何 harness 做「递归自我改进」（session 发生 → 观察结果 → 把模式/错误/结果变成对运行时的修改）。

### 8.4 Prime Intellect Harness（刚发布，最前沿）
- Greg 提到一家公司 **Prime Intellect**，「昨天刚发布」了 **Prime Intellect Harness**，构建在 Pi 之上，实现了两篇论文的两个概念：
  1. **递归语言模型（recursive language models）**；
  2. **持续 harness（continual harness）**：里面有一个 **`reflect` 命令**，会看你的 traces，**帮你（但不改 harness 源码）创建 skills / supplemental prompt / subagent specs**（基于你的 runs）。
- Greg 的观察：它缺的一点是**它不改 harness 源码**——这有道理（你也不想让非确定性过程改你的源码），但有些**确实想加的东西**可能就该从那些 traces 里长出来，形成「持续日志检查 → 更好的反馈循环」。

### 8.5 数据点：我们有多常「steer」
- Greg 查了自己 **Stoa 项目**的 **1300 份 transcript**，发现 **「request interrupted by user（被用户打断）」出现了 614 次**（每份 transcript 可能含数百次 prompt/exchange）。
- 结论：**我们一直都在打断、纠正**，所以要想出更好的办法构建元 harness，让自己不必这么做（尽管它有效，但太耗时；而且放任错误复合会「毒化上下文窗口」）。

## 9. 下讲预告（周二）：循环内的 Mini Policy Engine

- 本周「裸恢复（nakedly resume）」时没有任何潜在 run effect / 灾难风险，因为任务极简单（两个小 Claude + 烂 brief）。
- 但在生产里，如果要控制一堆 agent 去动一个你在意的系统，**恢复时「该做什么」就不只是「continue」**——因为可能已经发生了某个事件。
- 所以 ProveIt 里有一个 **mini policy engine（策略引擎）**，给工具授予能力。
- 下周会深入：**不只记录日志流，还要记录「在某个模型动作之前的『实际预期效果（intended effect）』是什么」**；这样当 harness 需要恢复（不是手动恢复，而是 harness 自己理解该干嘛）时，能**在其中注入更多智能**。

## 10. 课程项目（作业）

- 项目**非常简单**：基本就是「**用或不用 harness，描述你的流程，并开始记录它**」。
- 具体：**在 markdown 文件里写一些文字，记录你今天观察到的、你在做的事**（就像你在实践「定义完成」那样）。
- 目的：两天里灌进这么多概念机器，太多了；项目只是**强化概念**，别为它焦虑。有精力的人可以在 ProveIt repo 里开个分支、提个 PR，做点「超出」的东西，但不强求。

## 11. 本课核心金句（可直接引用/记忆）

1. **「The log is the agent.」**（日志本身就是智能体。）
2. **「你不能让『正在干活的模型』来验证它自己是否完成。」**
3. **「spec 是设计权威，不入运行时；goal 融合进 harness、控制其状态。」**
4. **「原生 `/goal` 用一个小模型判定停止，没有确定性；自建 harness 用确定性门。」**
5. **「把『验证是否该停』拆成独立进程，别让干活的那个模型自证完成。」**
6. **「错误会复合、会毒化你的上下文窗口。」**
7. **「你今天能手动做的所有引导动作，都是你构建元 harness 时要 enable 的东西。」**
8. **「合同写在文本里不可执行；这个契约层介于文本与测试之间。」**（承接第 1 课）
9. **「别重复造轮子：日志规范化直接抄 Spec Story 的 provider 标准。」**
10. **「检查的质量，才是这套机器真正的关键。」**
11. **「我们有强大的长跑代理，但我们的眼睛在哪里？」**
12. **「以增加信任、而非降低信任的方式找捷径。」**
13. **「不必再造交互式提示器；缺口是更多自主性。」**
14. **「日志像游戏存档：标准化后就能换模型加载继续玩。」**
