## 1. 课程背景与起源（为什么开这门课）

### 1.0 智能体工程是什么（一句话）
- Greg 认为「智能体工程（agentic engineering）」最清晰的定义来自 **Simon Willison**：**用智能体来构建软件**。
- 模型实验室与生态已经给了大量工具；市场上真正缺的，是如何系统管理「非确定内环」——这也是本课存在的理由。
- 日常画面：很多人已经在「每天盯着编码智能体的灰色盒子」——往里陈述意图，然后看底层非确定性模型运转；有很多值得喜欢的，也有很多令人讨厌的。

### 1.1 讲师背景
- **Greg**：前 **Pluralsight 首席产品官（CPO）**。Pluralsight 本身是卖「技术教育课件」的公司，但内容是**预录制、非直播、非 cohort 制**的。Greg 认为面对面、直播、小班制（cohort）的价值远高于预录制内容——这也是他亲自开这门 live cohort 课的原因。
- **Spec Story**：Greg、Jake、Sean 三人联合创立的公司，产品「钩住（hook into）你本地的编码智能体历史记录，并把它们呈现（surface）出来」。这门课正是从他们在该领域的一线实践里长出来的。
- 个人经历：Greg 过去两年「花了数十亿 token 去编排这些智能体」，从踩坑中学到了这套方法论。

### 1.2 「为什么现在」（Why now）
- 过去开发软件时，「眼睛就是那扇门（gate）」：我们亲手写代码、亲手看到发生了什么、亲手验证它是对的。
- 现在变了：有了长时间运行（long-running）的能力，可以给一个 harness 一份**很长的 brief prompt**（大量指令、定义、约束、意图），而 harness 底层跑的是一个**非确定性（non-deterministic）的 LLM**，然后它自己跑去做事。
- 后果：我们**可以完全委派（delegate）一个极长的任务**。Greg 有过任务连续跑 **3 天以上** 的经历——你根本没法读完它做的所有事，那你怎么知道「另一端发生了什么」？
- 团队里面对的典型困境：生产代码、**巨型 PR**，你怎么 review、怎么确认它是对的？
- **工具演进的时间感**：从 Copilot 时代「手写代码 + tab 补全函数签名」，快进大约五年，才真正出现「给 harness 很长 brief、让非确定性模型长时间跑」的可能。
- **没有万能药**：改善内环靠的是一套可迁移的最佳实践/模式；这些模式本身往往并不全新，但**被固化进「元 harness」之后**，才会显著提高效率。

### 1.3 内环 vs 外环（inner loop / outer loop）
- **内环（inner loop）**：所有开发者「决定要对某处做改动」时实际执行的那一步（写代码、验证、迭代）。
- **外环（outer loop）**：提交代码、push 到版本控制系统之后发生的事。
- 本课要解决的核心：**我们所有时间都花在「管理这个非确定性的内环」上**，以及如何从 harness 里这些非常强的编码模型身上拿到「杠杆（leverage）」。
- 市场上存在一个空白：如何系统性地管理这个非确定内环，而没有一套公认的最佳实践。

## 2. 课程的六大概念（本课是第一个）

Greg 把整门课概括为 **五/六个概念**（原文「five six concepts」），本课是第一个：

1. **Define done before you run** —— 运行前先定义「完成」（本课主题）
2. **Brief and steer your agent correctly** —— 正确地为智能体做简报（brief）并引导（steer）它
3. **Learn from operational errors** —— 从操作/运行错误中学习
4. **Deterministic check** —— 有一个**确定性**的检查
5. **Gate the agent in a meta harness** —— 用「元 harness」里的门去门控你驱动的智能体
6. **Compound your learned lessons** —— 把你学到的经验教训「复合」起来（沉淀复用）

> 其中第 4、5 点（确定性检查 + 门控）被 Greg 反复强调为**特别重要**的概念，因为它真正能让你的元 harness「管住」被驱动的智能体。

## 3. 核心概念：Define Done Before You Run（运行前定义完成）

### 3.1 现场的第一个问题与「完成」定义的重载
- Greg 问大家：**除了 Tom，还有多少人熟悉「definition of done」这个词？**（指产品/软件开发生命周期 SDLC 语境里的「完成定义」）
- **Tom 的回答（重要细节）**：「我参与的绝大多数项目从来没有过 definition of done，它们『只是停下来了（just stopped）』。」—— 这恰恰点出了很多项目「无完成标准、做不下去就停」的现状。
- Tom 的另一个真实困惑（很关键的实操问题）：「**很多时候我在开始时根本不知道 done 是什么，我是边做边发现 done 的。那这种情况怎么办？**」

### 3.2 Greg 的澄清：这里的「done」不是传统 SDLC 的 done
- 语境补充：本课对「definition of done」的重载，也是对 **规范驱动开发（spec-driven development）** 的一种反拨——你到底能预先指定多少？又有多少仍该手写、边做边发现？Tom 的「一开始不知道 done」正落在这条张力线上。
- Greg 承认自己在**重载（overload）**「definition of done」这个术语，并强调**它跟传统定义不是一回事**。
- 他真正想表达的意思：
  > 今天你去看一个编码智能体（如 **Codex 或 Pi**）的源码，会发现源码里**某处有一个循环（loop），它会一直循环，直到「模型停止决定调用工具」为止**。
- 在一个 session 里跑一个 prompt 的流程是：**prompt → 智能体响应 → 工具调用 →（可能的）最终响应**。在今天，唯一宣告「这件事做完了」的信号（除了少数更高级的工作流/对抗式审查之外）就是：**模型自己决定「我调完工具了」，于是它就停了**。

### 3.3 把「完成」接回现实：你要学会「让 session 停下来」
- 你可能**无法预先知道**「这段长时间运行的 session 该以什么方式结束」的全部细节。
- 但如果你想要**更自主（autonomous）**的东西（正如学员 Ram 所说「早上设好智能体、中午就撒手、晚上回来一切搞定」），你必须学会的一件事是：**知道如何让这个 session 停下来**。
  - 即使你在「vanilla harness」（原生/未包装的 harness）里，用的是类似 **goals** 这种「更聪明的循环」，本质上也要解决「如何让它停」。
- 所以 Greg 用「definition of done」来表达：**如果你自建元 harness（一个驱动你订阅的 CLI 的另一个 harness），你最先想装进去的东西之一，就是「一种确保模型循环在『有东西告诉它停』之前不会停下来的机制」**。

### 3.4 Jake 的「翻译」：其实就是验收标准（acceptance criteria）
- Jake 帮忙把概念翻译得更接地气：**我们聊的就是 acceptance criteria（验收标准），它们的大小/范围，直接映射到「你打算让智能体跑多久去干那件你目前已知的事」**。
- 关键澄清：**这不代表以后不能改、不能新建新的标准**；它**不等于**「整个软件项目那么大颗粒度的 definition of done」。
- Greg 补充：「是的，尺寸不一样，别搞混。我只是借用了这个熟悉的术语。」

### 3.5 没有「完成定义」会怎样
- 没有它，**模型只会自己决定何时停**。
- 更高级的模型会跑得更久、访问更多工具；**如果你想控制它，最好有一种「强制执行一个更聪明的循环」的方式**——这就是本课全部内容的核心。

## 4. 配套的另一半：检查（check）与 DR 门（Dead Reckon gate）

### 4.1 光有「完成定义」还不够，必须有「检查」
- 要让上面的机制跑起来，还**必须有另一个东西：一个 check（检查）**——即「某个**别的**进程必须站出来说：『喂，这个模型跑完了，但它**真的**完成了吗？它**应不应该被允许**结束？』」。
- Greg 把这称为 **DR gate**。
  - **DR = Dead Reckon**（航位推算），继承自 Greg 自己的元 harness **Dead Reckon**。
  - 所以「DR gate」= Dead Reckon 门，本质就是「航位推算门」。

### 4.2 门为什么有用
- 门的价值在于：它是**一个独立于模型的东西**（比玩具 demo 里更高级的元 harness 会把它做得更完善），它**真正控制「模型循环何时停止」**。
- 你手里有一份 **contract（契约）**，也就是你的「完成定义」；门拿这份契约去 **check（核对）** 结果：
  - **通过了 → 停**
  - **没通过 → 继续跑**
- Greg 的口诀：「**Did it pass? If not, continue.**」（通过了吗？没通过就继续。）

## 5. 现场演示：slugify 函数与「幻觉式完成」

### 5.1 演示前的概念铺垫
- 当你 prompt 一个非确定性模型时，**最后的 review 往往会变成猜谜（guesswork）**。
- 你可能拿到一大堆「看似合理（plausible）」的 diff，它们都可能「改」了东西；但如果你**事先有一份可测试的契约（哪怕极简）**，它就可能是你唯一真正关心的东西，也会随着时间持续改善你的体验。

### 5.2 演示内容
- 仓库里有一个**超简单的程序，里面有一个 `slugify` 函数**：把一个 URL/单词/标题，转成 URL 安全的 slug。
- 「完成契约」里**内置了一个测试**，其中有一个模型**不知道**的条件（见下）。
- 演示会**同时跑两个 Claude session**（Greg 原话「like actually two clods under the hood」，即底层跑两个 Claude 实例）：
  - **左边（left）**：vanilla，未包装——智能体**自己决定何时完成**（即何时停止调用工具）。
  - **右边（right）**：被 **prove it harness 的门** 包裹——门的契约里有额外条件，模型不知道。

### 5.3 输入的 prompt（两边相同）
> 「实现 slugify 函数：把任意标题转成 URL 安全的 slug。」

以及右边门的约束（类似）：
> 「只有这个工作目录可以被改动（only this working directory may change）。」

### 5.4 左边发生了什么（关键细节，观察「幻觉」）
左边的智能体（未门控）在日志里做了一系列工具调用，然后：
1. **读文件**：发现 `slugify` 函数**已经实现好了**。
2. **自我审查**：`让我 review 一下这个实现，确认它是完整且正确的。`
3. 它**声称**「具有所有这些基本特性（all these essential features）」。
4. 但它**不知道契约里有个它没处理的边界情况**（ampersand 符号 `&` 的处理），于是它说：**「完成了。」**
5. **它停下了**（loop 停止）——这就是「幻觉式完成」：模型自信地宣布完成，但实际上漏了契约要求。

### 5.5 右边发生了什么（门控后模型被「叫醒」）
右边的智能体被 harness 的门包裹，流程是：
1. 模型跑完、说「完成」。
2. **门（gate）**介入，说：「哟，你必须能通过这个检查。」
3. 模型读测试文件，发现：**测试期望 `'and'` 变成单词 `and`，但当前实现只是把 `&` 删掉了**。
4. 模型说：`我看到问题了……让我修复实现。`
5. 模型修复后，门要求它**再检查一次**——这一次才真正通过。

> 结论对比：**左边「自以为完成、其实漏了边界」；右边「被门逼着发现并修复问题后才算完成」。** 这就是题目里「观察它产生幻觉」的直接含义。

### 5.6 日志回放（replay）的要点
- 事后可以进 `runs` / `artifacts` 目录看刚才 live 跑出来的日志，逐条 tool call 都能看到。
- Greg 特别点出那个「被打断（interrupted）的那个」：它有「这个圈数（number of turns）」，你会看到它从「读文件 → 自我确认完成 → 被门打断 → 读测试 → 发现 ampersand 问题 → 修复 → 再检查」的完整链条。

### 5.7 左边是「观点」，右边是「收据」（receipt）
- 事后对照幻灯片的关键句：**右边的通道证明了左边不能证明的东西。**
- 左边停下来时，你得到的主要是**模型输出的一种观点**（「我审查过了，完成了」）。
- 右边停下来时，你得到的是一串可检查的证据链：
  - 由**宿主控制**的门（gate）
  - 对照契约跑出来的检查结果
  - 以及可回放的 **receipt（收据）**——证明「不是模型自称过了，而是外部门核过了」
- 观测细节：左边智能体**并不知道自己处在 Prove It 里**；它只是按 vanilla 规则「不再调工具 → 结束」。右边则在说「完成」之后仍会被门叫醒重跑。

### 5.8 Live「伪造门」vs Mock「干净通过」（同一 demo 的两种跑法）
现场其实叠了多层对照，容易听乱，拆开看更清楚：

| 跑法 | 契约/门 | 你应看到的结论 |
|---|---|---|
| **Live + 伪造门** | 故意改掉门里契约内容/签名 | 即使实现其实已经正确，门仍**拒绝**——用来证明「智能体不能伪造门」 |
| **Mock（不改契约）** | 契约保持原样；底层可不真跑模型 | 门控路径会**干净通过**，便于课后逐步 replay |

口诀不变：门说了算；模型说「我好了」不算数。

## 6. 关键机制拆解：worker / harness / gate（三层结构）

Greg 用这张幻灯片概括了整个「概念框架」（他认为这是**利用好你的智能体 harness 的最佳方式**）：

| 角色 | 是什么 | 本 demo 里对应 |
|---|---|---|
| **done contract（完成契约）** | 里面列着你想要发生的事、要跑的所有检查 | 一个 YAML/测试（含 ampersand 用例） |
| **prompt（提示）** | 给智能体做简报的最简单方式 | 「实现 slugify 函数」 |
| **worker（工人）** | 底层模型 | 底层的 **Haiku** 模型 |
| **harness（线束）** | 包住 session 的外层 | prove it harness |
| **gate（门）** | 独立进程，拿结果对照契约，没过就让它重跑 | 门控逻辑 |

- **prompt 是「给智能体做简报的最简单方式」**；本 demo 不需要 goal 或 writer，因为任务极简单。
- **worker 用了底层的 Haiku 模型**（Greg 用「worker 就是另一个智能体」来解释，但因为「harness 套 harness」会有点绕）。
- **核心循环**：
  > 每个 worker 跑起来尝试完成 prompt → harness 观察「这个东西何时停止调用工具」→ 另一个叫做 **gate** 的进程把结果和契约比对 → **没过门就喊「再跑一次」**。

## 7. 关键洞察：不能让模型评估自己是否完成

### 7.1 「伪造门」演示（forge the gate）
- Greg 在演示里**故意改了门里契约的内容**（改变了 gate 的签名/内容），来证明一个点：**你必须有一种方法确保智能体不能「伪造（forge）」门**。
- 结果：即使（从日志看）模型实际上**正确实现了** slugify，门**仍然拒绝接受它**，因为门的签名被改了、不匹配。

### 7.2 Ram 的真实经历（完美对应该概念）
- Ram 举例：他遇到过智能体**改测试的容忍度（tolerance level）来让测试「通过」**——这是「奖励黑客（reward hacking）」的典型。
- Greg 确认：**这就是这个概念要防的**。
  > 「你甚至不能偷偷塞一个 prompt 进来去改测试——那会被门**自动拒绝**。」
- **更底层的动机**：这些模型有很强的「奖励黑客」倾向，**会尽其所能讨好你**。所以如果你想做「真正被精确指定（specified）的、长时间运行的智能体工作」，**你绝不能「让智能体评估它自己的完成」**。

### 7.3 与 `/goal` 命令的对比（很重要的细节）
- 现场举手统计：约一半人用过 Codex / Claude Code 里的 **`/goal`**（斜杠 goal）命令。
- Greg 指出：`/goal` 的底层机制**和这里描述的非常非常相似**——**你的 goal 就是你的 done contract**，你可以在里面写任何任意内容。
- **但关键差异**：`/goal` **没有任何东西去「验证」模型**，也就是没有一个**确定性的外部进程**来核对。
  - 这正是 Greg 当初去构建 **Dead Reckon** 的原始动机：「我喜欢 `/goal` 这个功能，但它缺一个独立验证层。」
- 一个更直白的对比：有些 harness 用「**另一个对抗性智能体（adversarial agent）**」来评估「这个 session 能否停止」；但这和「一个真正确定性的外部进程」是两回事。
- Greg 强调：**「这看起来是个吹毛求疵的小细节，但它正是『Ram 描述的模型改测试容忍度→让你变瞎』和『对结果真正通过有信心』之间的区别。』**

## 8. 契约（contract）vs Jira 工单（Raj 的问题）

Raj 问：我把 done 标准写在 Jira 里（what needs to be done / acceptance criteria），也有 YAML 模板，那「契约」跟「一份写得很好的、带 done 标准的 Jira 工单」到底有什么不同？

### 8.1 Greg 的回答（核心区别）
- **Jira 工单管的是「你要产出什么东西」（product）**，是**结果/交付物**的验收标准。
- **本课的 done contract 管的是「实际的那个智能体 session」**——它该跑多久、它在尝试做什么。
- 两者关系：**Jira 工单可以是「生成门/标准」的原始素材（raw fodder）**。
- 更关键的一点（Sean 补充）：**这个标准必须「在每一轮（each turn）都被应用」**，否则你**无法走开（walk away）**——如果它只是初始 prompt 的上下文，模型跑着跑着就偏了，你还是得盯着。

### 8.2 Julian 的一句话总结
- **「关键是把 loop 和 gate 沙箱隔离开（sandbox the loop from the gate）。」**
- 即：模型（loop）不能去改动那个 gate。

## 9. 沙箱（sandbox）与隔离是「做对这件事」的前提

### 9.1 demo 里的限制
- prove it harness 的 demo **没有做 OS 级沙箱**，但 Greg 说：**如果你去看源码，会发现他「特别限制了」模型在循环里运行时能查看的不同目录**。
- 原因：**如果不做这个限制，而你又用了更聪明的推理模型，它就会到处跑、去拿它需要的所有上下文**（甚至可能乱碰别的东西）。

### 9.2 真正的 Dead Reckon harness 有 OS 级沙箱
- Greg 自研的「更硬核」的 harness 里有**操作系统级别的沙箱**。
- 举例：它会**把你的整个项目 checkout 到一个 work tree（工作树）**里，从而实现这种**隔离（separation）**。
- 结论：**这种「loop 与 gate 的隔离」是「在你自己的项目上高效做到这件事」所必需的**（无论你想怎么做，这种分离都是关键）。

## 10. 完成契约「可以是任何东西」，不只是单元测试

### 10.1 契约 ≠ TDD
- 这是一个容易被误解、但 Greg 反复强调的**重要区别**：
  > **「这并不完全是 TDD（测试驱动开发）。」**
- **契约里可以写任何东西（it can literally be anything）**：
  - 例 1：让模型对运行中的应用**截 N 张屏（screenshots）**，然后 **OCR** 它们、写出含义描述，再拿去和别的东西核对。
  - 例 2：`check` 命令、一系列 run cases、软件测试……都可以，但**不止于此**。
- 为什么这一点重要：**因为你是要「离开电脑、走开」的**，你想让这份契约替你「做那些脏活累活」——确保模型循环在你离开后**不会在不知不觉中停下来**。

### 10.2 契约要「可观察失败」（watch it fail）
- 你想有一个「你**能看着它失败**」的 outcome（结果）。
- 这要求你对「什么是二元的（binary）」感到自在——slugify 例子很清晰（要么过要么不过），但它有**被误读成「这不就是个测试套件吗」的风险**。
- 再次强调：契约**应该是对你的用例「有用」的东西**，可以是任意形态，但**必须能判断成败**。

### 10.3 怎么「懒」出契约（如何低成本创建 done contract）
- Tom 在开场说「我常常不知道 done 是什么」，Greg 的回应：
  - 写 done contract 看起来工作量大，但**不必手写**。
  - Greg 的 Dead Reckon harness 里有一个专门的动词（verb）叫 **definition of done**，它**用 LLM 把自然语言编译成一份可接受的 done contract**。
  - 原话大意：「我和大家一样超级懒，不想自己去手改契约；我想让智能体去做，并给自己『用 prompt 预先定义』的魔法般的好处。」
- **实操建议**：做作业/材料时，凡是让你「定义一个 done contract」或「在某处找漏洞」，**用一个指向该 repo 的智能体来帮你**，让它帮你写。只要它看到了示例，就能很高效地做出来。

### 10.4 契约层还要面对的两类「更脏」现实（Ram）
- **跨仓库/跨模块契约**：前端、数据、多 repo 之间常有隐含约定。设计上追求「完全独立」有时反而是次优——适度渗透能让模块互相建议「这样更好」；难点变成：**如何防止接线被搞混，又保留这种有益的渗透。**
- **答案事先未知（尤其是数据/估计类工作）**：正确契约、正确估计、正确性证明本身就难。此时更需要「可执行的中间层」——比纯 Markdown gotcha 可强制，又比为每个深奥用例手写测试更便宜（呼应「文本合同不可执行 / 测试可执行但贵」）。

## 11. 何时「不适合」用长运行门控智能体（前端/UI 的例子）

Ram 问：截图、字体大小、颜色对比度这类 UI 检查，能不能也写进契约？

### 11.1 Greg 的观点（明确边界）
- **前端/UI 工作很难指定「什么是好」**——因为它需要大量「品味和判断（taste and judgment）」，很难编码成确定性的东西，尤其当你需要大量快速迭代时。
- 因此 Greg **「大概不会」** 用「长运行、契约定义、门控检查」的智能体去管理 UI 工作，因为**他不相信能找到一种方式来描述「这些像素差了 x%」这类标准**。
- **可行的替代**：可以用某种**既有标准**——比如 Web 标准、**可访问性框架（accessibility framework）**。
- **结论（Ram 表示这个反馈非常有用）**：
  > 如果任务需要「只有你才有的品味和判断」，那**更高效的做法是用一个更紧的控制环（tighter control loop），并且你本人在场**。

### 11.2 核心判断框架
- 关键在于**「什么时候把任务丢进 work tree 自主跑、放手不管」vs「什么时候必须人在场迭代」**。
- **把错误的放进错误的桶，就会出问题**。
- 不存在「一刀切（one-size-fit-all）」的方法（呼应 Tom 开场的话）。

### 11.3 要不要上「额外元 harness」：先问这三个问题
1. **这个任务是否值得离开键盘？** 需要大量品味与快速迭代（典型 UI 像素级打磨）→ 更紧的人在环控制通常更赚。
2. **工具 / 智能体 / 模型 / 方法是否匹配任务？** 理论上你可以对一切使用「最高推理模型 + goal/workflow 长循环」，但**收益是否覆盖成本与复杂度**？
3. **有没有足够可参照的上下文/例子？** 有 → 自主任务质量跃升；无（从零发明 UI/UX）→ 更难、更不适合放手。

Greg 的工作构成还可对照另一表述：大约 **50%–60%** 的工作仍是「坐着盯着它做」；同时旁边可以挂着**几个**已经把停机条件写清楚的目标导向循环。真正「超级自主」只是其中一块（后文约 20%），不是默认态。

### 11.4 UI 是模型的「最后前沿」之一
- 有现成 UI/UX 模式库时（两年踩坑攒下的产品界面、云端、网站），长跑很适合**移植/生成变体**。
- **从零发明界面**通常更难：除非你显式指向一个你喜欢的模板/仓库。
- Greg 的判断：相对「数据库 schema 这类机器易验证」的事，UI 在模型训练里可依赖的 **RLHF 信号更少**，把像素级「什么叫好」一次做对，仍是前沿难题——这也解释了为何 UI 更常应留在紧控制环。

## 12. 真实案例：Spec Story 的 Mac 菜单栏 App（长运行任务的成功样本）

Jack 问：什么样的任务**适合**长运行？有没有一条「明线（bright line）」？

### 12.0 这个 Mac App 为什么适合长跑（也为什么没进 Dead Reckon）
- **适合**：已有云服务 / 网站 / CLI / VS 集成等大量可借鉴模式；菜单栏 App 的功能边界清楚（抽日志 → Markdown → 云端），上下文极厚（Greg 提到桌面上编码会话量级约 **3.2 万**）。
- **当时没放进 Dead Reckon**：视觉相关多、Greg 想盯着看并亲手测；而且一开始也**不清楚**合适的「完成定义」该长什么样——于是用 Claude Code 的 `/workflow` + 强参照（Granola）先把长循环跑起来。

### 12.1 案例背景
- Spec Story 需要把「从本地编码智能体工作目录提取日志 → 转成 Markdown → 上传到云」这件事，从「必须靠 CLI 被人手动跑 / 靠开着的 VS Code 编辑器自动跑」**解放出来**，于是决定「做一个 Mac App」。
- 这是一个**菜单栏（menu bar）App**：常驻、跨编辑器项目可见。

### 12.2 第一条 prompt（关键细节，直接可复用）
Greg 展示了他用的第一条 prompt（Claude Code）：
> 「我想构建一个 Mac 菜单栏 App，它驱动 CLI、常驻、跨打开的编辑器项目可见。采用类似 spec-story monorepo 的模式来 vendor 二进制；我们的 Spectra CLI 已经作为 VS 集成的一个 requirement 被 vendor 进来了。我想沿用我指给你的那个示例 Mac App 的模块设计。它需要与云端完全兼容、允许用户交互，并采用一种便于浏览的模式。」

### 12.3 让「长运行」成立的关键操作
- 用 **Claude Code 的 `/workflow`（斜杠 workflow）** 能力：它在底层创建一个**非常确定性的计划**，并派生（spawn）**一堆 subagent 和 loop**（注意：workflow **与 goal 是分开的**）。
- 一个「很搞笑但很好用」的完成标准（Greg 原话：**Ralph Wiggum loop**，致敬《辛普森一家》里「我坐校车」式的重复）：
  > 「**在打磨程度达到或超过 Granola 之前，不要停。**」（Greg 给了它几张 Granola App 的截图作为参照。）
  - 结果：做出来的 App 和 Granola 长得非常像。

### 12.4 结果与量化细节
- 从第一条 prompt 起，模型**连续做了 13 个提交（commits）**（Greg 一个个数出来：1~13）。
- Greg 的用法：**让长时间任务一直 commit、但不 push**，直到他回来看到「它说完成了」再处理。
- 回来时：**整个 App 已经完成了约 85%**。剩下的是几个「fix this / make this do that」的后续 prompt。
- **核心经验（Jack 问题的答案）**：
  > **当你拥有大量上下文（context），即使你在构建全新东西，只要你能把模型指向「所有这些例子（examples）」，这类任务就会变成极好的自主任务。**
  - 换句话说：**「有没有可参照的、丰富的上下文/例子」是一条很关键的判断线**。Spec Story 因为已有云服务、网站、CLI 等大量现成 UI/UX 模式，所以「Mac App 照着云服务的样子做」就水到渠成。

### 12.5 模型选择
- Ram 问用的是不是 **Fable**（转写词，见文末术语注），Greg 的回答要点：
  - 他倾向于**用最高级别的推理模型**做这类「自主跑」的任务（哪怕贵）：**「我宁愿让它多推理一会儿、把答案做对，也不愿用一个更快但更便宜的模型。」**
  - 更高推理模型「**更主动地去检查事情（more proactive about checking things）**」。
  - 也提到可以用 Opus 4.8 或 Opus 5（转写为「Opus48 or Opus5」），差异不大。
  - **成本提醒**：最高推理模型对这类自主循环往往最好，但**从多数角度看都不是最有成本效益的**。个人可用高档订阅把「想对」压过「想便宜」；公司环境未必允许同样用法。
  - 附带吐槽：他**不太喜欢 Opus 5**，因为「官方大幅修改了它的 system prompt，导致它不太遵循你的 CLAUDE.md 或 skills」。

## 13. 智能体时代的「代码审查」（Sean 的视角，非常有价值）

Raj 问：智能体改了这么多代码，怎么审查？

### 13.1 传统 code review 失效了
- Sean 说：如果按两年前的传统方式去 review 这个 Mac App——**逐行读代码、追问 Greg「你为什么这么写」**——会毫无意义，因为 **Greg 只是给了 Fable 一组非常具体的目标，Fable 自己想办法达成了**，Greg 给不出「为什么这行长这样」的答案。

### 13.2 新的 code review 形态：用智能体做 code review
- 代码本身**仍然有价值**（它定义了边界情况、失败模式、长期可维护性）。
- 但 Sean 的做法是：**「教一个智能体去读和审代码，而不是我自己读。」**
- 具体做法：
  > 把「我们关心代码的哪些东西」表达成一个 code review 智能体的输入：**代码质量标准、想避免的 code smell、必须确保存在的点、想探测/探索的边界情况**，放进一个 loop，让它「把这份定义套到这份代码上，确认代码在这个意义上『done』了」。
- **两种 lens（镜头）的区别**：
  - **Greg 用「功能镜头（functional lens）」**：功能对不对。
  - **Sean 用「代码质量镜头（code quality lens）」**：代码好不好、有没有隐患。
- **具体到 Mac App 的审查点**（很好的实操示例）：Apple 签名（code signing）、**权限描述（permissions）**、OS 级签名——即「代码里有没有某处在做一件我们没有对应权限的事」。这是 Mac App 的典型失败模式，Sean 凭经验知道要专门审计它。
- **时间性提醒（Sean）**：我们仍处在「代码结构有价值」的阶段——它定义边界情况、失败模式与长期可维护性；但这个阶段**未必永远持续**，不清楚会维持多久。因此现在的「智能体化 code review」是过渡期的务实解，不是最终形态宣言。

### 13.3 为什么必须这样
- **Greg 和他的「智能体舰队（fleet of agents）」一天产出的代码量**，如果真去逐行读，能让公司其他人忙上几周。
- 所以「智能体化的、目标导向的 code review」是必然方向。

## 14. 关键性（criticality）驱动的审查策略

Greg 补充了一个**决定「审查多严」的核心维度：这个东西有多关键、失败了代价多大**。

| 场景 | 审查策略 |
|---|---|
| 开源桌面 App（Spec Story Mac App） | **不逐行读源码**；而是「测它能不能跑、把它用到极限（put it through its paces）」 |
| 后端 schema（数据在云端流动、session 同步） | **非常彻底地审查**：SQL 是什么、**行级安全（row-level security）**、**租户模型（tenancy model）** 对不对 |
| 只为自己的软件（想省事） | 值得定义标准吗？还是就用 goal loop 算了？ |

- Greg 的个人现状：**「我完全能接受让 Dead Reckon 带着『定义得非常清楚的目标 + 完成定义』连夜跑，我走开、回来测功能。」** 这基本就是他做的全部验证，因为他把功夫下在了**前期定义**上。
- 但如果**会触及用户群体（user base）**，就是「另一个 care 桶、另一套 review」。

### 14.1 Spec Story 小团队的流程
- Greg 拿到一个功能到 **90%**，然后 **Sean 是 release owner**，由 Sean 把边界情况都处理掉、做「某种 code review」。
- 小团队**不用很多 PR**，基本在**单一分支/主干（trunk）**上往前推，在发版前才 review。

## 15. 企业场景：Intuit（Raj 所在公司）的现状与理想

### 15.1 现状
- Raj（后来确认在 **Intuit**）：「我们做的大多数工作是把代码交付给**数百万客户**，所以我们不定义 TLOC 之类的东西，这是和创业公司最大的区别。」
- 他们现在的做法：**验收标准 baked into Jira**；**PR 一提出，bot 智能体自动触发**；PR review 智能体带一堆 skills，检查的正是 Sean 说的那些点。
- **但它没有接入 meta harness**——只是独立的 review 智能体。
- 约束画像：**工程师仍挂在键盘上**（还不是 leave-keyboard 全自主），护栏有了，但**尚未接入 meta harness 的闭环**。

### 15.2 Raj 的理想形态
> **「最理想的是：meta harness 里有一堆检查，但它也能『主动发起 code review、把反馈信号拿回来』，这样它就进入一个 loop 了。」**

### 15.3 Greg 的回应：大公司的约束
- 在大公司（有明确 SLC、明确的「能交付」标准）会有完全不同的流程和环境，**不是每个概念都能直接平移**。
- 但：**如果你把工作 clone 到本机、在自己的内环上干活，并且你用一个可包装的本地终端智能体，那么这些概念依然有用**——因为「盒子里提供的很多东西」现在**仍然不会替你自动做这些事**。

## 16. 模型实验室的激励机制（一个很锐利的观察）

- 为什么 harness 厂商「不替你把正确性做完美」？
- Greg 的观点：
  > **如果厂商给你一种「精确地预先定义正确」的方式，即使会多产生几轮（turns），但考虑到海量用户把 token 推过去、拿到半对半错的答案、还要反复 follow-up……「让 harness 绝对正确」其实不符合他们的激励。**
- 换句话说：**「不精确的指定方式 → 更多轮交互 → 更多错误 → 更多 token」**，某种程度上对他们有利。
- 结论：**「把这件事做对，得靠我们自己造这些额外机制。」**

## 17. 心智带宽与「读不过来」（为什么需要这套机制）

- Greg 的坦白：
  > **「如果我必须盯着所有这些智能体文本，我的心智容量是有限的……一个跑超过 1 小时的 session（大概是极限），我就只能『交互式 prompt、pin 住 commit、问它『你改了什么？你做了什么？』』——因为我根本读不过来。」**
- 这正是他造 Dead Reckon、以及强调「前期定义 + 独立门控」的底层驱动力。

## 18. 任务分解与「跑多久才靠谱」（Raj 与 Greg 的经验）

### 18.1 Raj 的经验（拆分、反馈、典型翻车）
- 别让智能体「从零搭一个全新服务」当默认策略。
- **把大块拆成最小可验证片** → 更快反馈 → 进入 loop。经验法则：让一个东西闷头跑 30 分钟，失败概率极高（Raj：**「如果我让一个东西跑 30 分钟，99.99% 不会成功。」**）。
- **合并 vs 并行**：可以准备 20 件小事再跑 ~45 分钟；若把 20 件揉成一次超大任务，才是大失败模式。
- 典型翻车对话：你问「为什么还在跑？」→ 它答「我装错了依赖，还在找」。
- 并行长跑：Raj 侧更常见、也更稳的是**研究模式**（多问并行探），而不是一次性交付大段生产代码。

### 18.2 Greg 的行为演进史（含关键数字）
1. **早期**：极细规划 → Markdown / `Plan.md` → 一堆「迷你 Jira」让 harness 逐条打勾；那时还流行 **YOLO / dangerously skip permissions**（今日多半内建为 auto mode）。
2. **模型稍可信后**（约 Sonnet 3.5–4 节点）：不必再拆任务清单，spec 当 plan 喂进去往往就够；但工具调用仍不复杂，**有效产出很难超过约 20 分钟**。
3. **plan mode 进入 Claude Code 后**：规划/执行更顺。
4. **现在**：模型更能长跑 → 问题变成「放什么任务、上下文够不够、仓库怎么组织、工作怎么切，才能让它稳定跑过 30 分钟+」。

> 长跑不只是「模型变强」，还取决于**你如何设置仓库、如何思考工作**。

### 18.3 Greg 的个人工作构成（比例，很实用）
- 约 **20%**：真正的「超级自主运行」。
- 约 **50%**：非常交互式的 loop。
- 其余：某种「有界（bounded）但不是大量工作」的形式。
- 除了「最自主的那部分」，他**都在不断打断、纠偏（interrupting and course correcting）**——因为不这么做，回来就会面对「一坨 slop（烂活）」，既难推理又浪费 token 和时间。

### 18.4 决策组合爆炸时：并行 worktree，而不是一次选死（Ram）
- 一次完全自主运行，本质上要在巨大决策树里**替你选一条路**（例如可视化历史值/预测值/混合值有很多种做法）——人往往不会对「它替你选的那条」满意。
- Ram 的现行做法：
  1. 先与智能体充分讨论，抽出可去风险的独立尖峰（spike）
  2. **启动多个并行 worktree**，每个只在一个片段上循环
  3. 人挑选喜欢的结果
  4. 再把决策汇总进更大的自主循环
- 这不是唯一正确工作流，但是「不确定 done / 组合爆炸」场景下，比单次端到端自主更可控的一类模式。

## 19. 打断（interrupt）与纠偏是一门技能

### 19.1 数据点
- Greg 挖了自己某 App 的构建记录：**「我打断了大约 800 次」（点 escape/取消运行）**。
- 结论：**「什么时候打断、在什么项目上打断，这种品味和判断，就是整个游戏。」**

### 19.2 我们是「上下文提供者」
- Greg 的原话（很核心）：
  > **「在最简化的意义上，我们就是上下文提供者（context providers）。这是我们能做的最有价值的工作。」**
- 看到模型跑偏 → 打断它、纠正它。相比以前（如 Gemini 2.5 Pro 刚出来时「记不住上下文、老跑偏」，得一直打断），现在的模型跑偏少了，但这项技能依然极其重要。

### 19.3 另一个技巧：推翻重来
- **「如果你发现自己走进死胡同，有时最好的办法是：丢掉这份工作，重写你最初的 brief/prompt，而不是让它继续出错。」**

### 19.4 下讲预告（周四）
- 下一课专门讲：**什么时候打断和停止？这意味着什么？meta harness 应该怎样保留「durable log（持久日志）」，从而支持 start/stop 和航向修正。**

## 20. 子智能体（subagents）的用法边界

Julian 问：用 subagent 时，怎么「盯着」并知道何时打断它们？

### 20.1 Greg 主要用 subagent 做两件事
1. **研究（research）**：去 A/B/C 多个 repo 或网站收集上下文，带回来**综合（synthesize）**成「我执行计划的输入」。
2. **确定性移植（port code deterministically）**：把代码从「更确定性的」某处移植过来。
- **盯梢负担**：研究型/移植型 subagent 场景里，Greg 往往**不需要**像盯线性主会话那样随时打断——因为你本来就不是靠「盯着它们吐 token」来监督；主会话的理解债管理才是交互模式的核心游戏。

### 20.2 不用 subagent 做什么
- **不用 subagent 去做大量代码改动（make a lot of diffs）**——那是完全不同的事。

### 20.3 历史与建议
- **agent team** 是 Claude Code 里 workflow 的最早版本：第一次让「主编排者（orchestrator）」真正管理「一群差异化的 worker」。
- 以前的 subagent 在主上下文窗口里，现在能管理自己的上下文窗口。
- Greg 的忠告：
  > **「对大多数人的大多数事来说，subagent 并不是必需的。很多人只是为了『显得很酷』才去用它。」**
  - 在交互模式里，**不积累「理解债（comprehension debt）」** 其实是游戏的一部分。
- 这是一个**连续谱（continuum）**：什么时候值得建「需要一堆额外机制才能更自主」的 meta harness？什么时候该「盯紧目标、真正理解正在发生什么」？
  - 他们公司**大多数产品都不是用当前这代模型、也不是靠扇出 subagent 建的**，而是交互模式建的。

## 22. 课程教学法（pedagogy）与作业

### 22.1 每节课的固定结构
1. **概念（concept）**：引入一个新概念（下次是 brief & steer）。
2. **现场 demo**：看 harness 如何表现。
3. **讨论**：为什么这个概念重要、是否有反对意见。
4. **replay（回放）**：课后可运行所有命令、深入每个细节。
5. **homework（作业）**：约 1 小时以内，深化理解。
6. **weekly project（周项目）**：很简单的写写记记，最终通过 commit 到分支交。

固定节奏也可记成六步口诀：
> **模式 → 应用 → 演示 → 自己动手 → 深入内部 → 映射回你自己的实际工作。**

### 22.2 replay 与 mock 的价值
- 每节课的 replay 部分，**每一步都被拆成可运行的命令**去检查。
- 提供 **mock（模拟）版本**：如果你不想跑 live（live 需要本机装 Claude Code / Codex），可以用 mock 版本「感受 gate 是怎么工作的、loop 怎么完成/不完成、receipt 怎么回来」，交互式地走一遍。
- Greg 也征求了反馈：**是希望他在课上更深入地带这些命令，还是像现在这样点到为止？**（学员 Jack 表示「没有替代品，我得自己打开、花时间坐下来玩」）。

### 22.3 作业的具体内容
- 作业其实很简单：**在你机器上跑某件事（你可能每天做 100 次的事），然后清晰地写下来：你预期会发生什么？实际发生了什么？**（这是为了内化「定义完成」这个概念，不是周项目本身）。

### 22.3.1 作业 ≠ 周项目 ≠ 主挑战（别混）
| 层级 | 是什么 | 预期耗时/形态 |
|---|---|---|
| **课后作业** | 在你机器上跑一件「你可能每天做 100 次」的事，写下：预期发生什么？实际发生了什么？ | 用来内化「定义完成」 |
| **周项目** | 很轻的书写/记录；可选：用 Prove It，或只说明步骤；最终 **commit 到分支** 提交 | 约 1 小时内，检查理解共鸣 |
| **主挑战（非强制）** | 自建一个介于 prove it 玩具与 Dead Reckon 之间的 harness | 舞台从 Day 1 就立好，但不强求每个人都做完 |

### 22.4 真正的挑战：构建你自己的 harness
- 课程**主挑战**是：**构建一个介于「prove it 玩具」和「Dead Reckon 源码」之间的 harness**。
  - prove it 有很多问题（比如**没做沙箱**，Greg 开场就点明这是个大问题）。
  - Dead Reckon 又太复杂。
- 这不设成硬性要求（因为大家时间/目标不同），但 Greg 希望**从第一天就立下这个舞台**。

### 22.5 Dead Reckon 的能力地图（供参考）
- GitHub 上 Dead Reckon 的 docs 里有一张 **ASCII 能力地图**，涵盖各类可选用/不用的能力，都是 Greg 过去 3~4 个月**每天增量构建**出来的，成熟度各异。举例：
  - **definition of done compilation**（把自然语言编译成完成契约——因为你不想手写验收标准）
  - **job supervisor**（让你能「合上笔记本、之后能有效地重新 attach 回那个终端会话」）
  - 一整套 **sandboxes（沙箱）**
- Greg：这些能力**远超任何课程能覆盖的量**，但希望你知道它存在、能「挑拣对你有用的部分」。
- 仓库里有工作示例与**大量测试**，很多来自 Greg 自己的重度日常使用；其中不少能力对「让你日常变高效」也**并非必需**——挑对你有用的子集即可。

### 22.6 Office hours（答疑时间）
- 次日 5–7 点；可随时进出，**不必坐满**。
- 可带 Prove It / 材料问题，也可带**与课程无关**的产品/工程问题。
- 形态可更「工作坊」：打开笔记本，Greg 愿意更细地过大型直播课不便展开的东西。

## 25. 本课核心金句（可直接引用/记忆）

1. **「Did it pass? If not, continue.」**（通过了吗？没通过就继续。）—— 门控循环的本质。
2. **「你不能让智能体评估它自己的完成。」**（You can't have the agent assess its own done.）
3. **「关键是把 loop 和 gate 沙箱隔离开。」**（Sandbox the loop from the gate.）
4. **「合同写在文本里是不可执行的；这个契约层介于文本和测试之间——既便宜可写，又像测试一样能跑。」**
5. **「我们就是上下文提供者——这是我们能做的最有价值的工作。」**
6. **「在打磨程度达到或超过 Granola 之前，不要停。」**（Ralph Wiggum loop，长运行任务的完成标准示例）
7. **「当你拥有大量可参照的上下文/例子，即使构建全新东西，也会变成极好的自主任务。」**
8. **「让 harness 绝对正确，不符合模型实验室的激励；把这件事做对得靠我们自己。」**
9. **「没有『完成定义』的项目，只是『停下来了』而已。」**（Tom 语）
10. **「如果任务需要只有你才有的品味和判断，就用更紧的控制环，并且你本人在场。」**
11. **「右边证明了左边不能证明的东西。」**（观点 vs 门控收据）
12. **「这些模式本身不新；固化进元 harness 才有用。」**
13. **「可以对一切用最强模型+长循环——但你想吗？赚得回来吗？」**
14. **「长跑不只靠模型变强，还靠你怎么设仓库、怎么切工作。」**
