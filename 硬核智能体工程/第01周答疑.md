## 2. Raj 的核心问题：done contract 里到底放什么？

### 2.1 Raj 的背景与困扰
- Raj（Intuit）用 **Spring Boot Java 服务**做例子，写了 user story 喂给 agent，也照 Greg 的例子写了 contract。
- 他的两个痛点：
  1. **测试质量**：agent 写了测试，但**没有断言（assertions）**。
  2. **护栏/steering**：想限制 agent「能跑多疯」，让它只写该写的东西，别到处乱写。
- 关键困惑（**术语重载导致的**）：story 里已经有一个「definition of done」（如 API 要 200 for GET、201 for POST、要断言），那**「agent 侧的 definition of done」**到底是什么？contract 里应该放什么「done-ness criteria」？

### 2.2 Greg 的回答：contract = 一组由 gate 求值的 check 条款
- **prove it harness** 本质：跑一个 loop，控制一个 agent。
- 为什么这样建模：Greg 当初用 Claude Code / Codex 时，把「偷走我时间」的各种 pattern 提炼出来，**固化（durable form）成软件**。
- Dead Reckon 的最初设计需求：**想复用不同 agent 订阅**（Claude Code、Codex 都有订阅），所以**不是从零造一个新 harness（像 Pi 那样），而是「包一层（wrap）」现有的 agent CLI**。
- 概念再澄清一遍：
  > 有一个 loop 驱动一个编码 agent；有一份 **done contract**（本质上是一组 check），**这组 check 就是「控制那个 loop」的东西**；每当给 meta harness 一个 prompt，控制「Claude 或 Codex 或它们一对」跑到 N 层复杂度的东西，就是 **gate**。
- **为什么用「worker」这个词而不是「agent」**：因为它就是一个**子进程（subprocess）**，非交互地运行；Dead Reckon 里调用 provider 的方式就是「当子进程调用」。它**可以是任何东西**。
- 所以 done contract 里的 check：
  > **「你的 check，就是 done contract 里的一个 clause（条款），由 gate 来求值。」** 在 prove it 例子里它恰好是 slugify 的一个单元测试，但它可以是任何东西。
- 结论：**done contract 里放什么「条款」没有对错**，而且它**不同于你的 Jira 验收标准**。

### 2.3 Sean 的洞察：真正的解锁 = 自动化「部分集成测试」
- Raj 在 Jira 里写的是「API 端点、POST/GET、响应码」这类验收标准。
- Sean 提出一个**新视角**：你肯定有单元测试（做响应码检查等），但**现在能做、以前做不到**的是——**自动化「部分集成测试」**。
- 举例（API PUT 端点）：一个 PUT 可能**既写数据、又在别处有副作用**——可能调一个 Lambda、可能分支做三四件事、全都有副作用。**以前我们从不为这些写单元测试，因为太贵、太脆（brittle）。**
- **现在的解锁**：你可以写一个**确定性（deterministic）的集成测试**，去查**数据库**、查 **Lambda 调用日志**、查「被这个 Lambda 调用的另一个运行系统的日志」。
- 一句话总结：
  > **这就是「传统单元测试 + Jira 验收」和「你能用自动化 harness 做的事」之间的区别。**

## 3. 前馈/反馈环（Intuit 的现状）

### 3.1 现状描述
- Raj 所在组织约 **10,000 名工程师**（他个人团队 ~100）。
- 他们给 agent 的是 **markdown story**；**repo 本身就是 context**；story 里有全部验收标准。
- 流程：代码写完 → 让 agent **跑单元测试、跑集成测试** → 因为 **Jenkins pipeline 反馈太慢**（要触发 + 回来才给反馈），工程师就**在本地先跑**，这样「pipeline 跑的时候我有信心拿到同样的确定性」。
- 多级反馈：**单元测试**（失败了 agent 知道代码不对、回去改）、**集成测试**（保证 90% 对）、**bot agent review 代码**、**PR skill review 代码**，最后回到工程师。
- 关键：**大部分还不是自动化**，Raj 仍「在键盘上」（能做别的事，但离不开键盘）。

### 3.2 Raj 的真正目标
> 「我知道反馈信号是什么，但**怎么把它们串起来、放回 loop 里、让 agent 被引导到正确方向**——这就是我们想做的自动化。」

### 3.3 Greg 的对应 pattern：把「文档类琐事」变成 done contract 的条款
- Greg 在 Dead Reckon 里固化的一个 pattern：**每次和 goal 关联的本地提交，都有一组以前手动做的「文档类」动作**。
- 例子（**直接可抄进 done contract**）：
  1. **change log**：自动更新 changelog 文件，精确记录改了什么。
  2. **as-built architecture（建成架构）**：维护一份「整体子系统概览」文档，把它作为**不想再花 token 重读的上下文**，让 agent 去更新它。
- **为什么需要确定性（determinism）而不是「给个 skill 就行」**：
  > 你大概看过一些论文——**60% 的时间里，即使某个 skill「本该被推断式调用」，它其实并没有被调用**。所以光在 CLAUDE.md / AGENTS.md 里放上下文常常不够，**确定性（强制跑）的价值就在这里**。

## 4. 从 Cursor 到确定性循环的第一步（blocking & tackling）

### 4.1 Raj 团队用什么
- Raj 团队**大多数用 Cursor**（因为 IDE 体验比 Claude Code 好得多）；公司「没有 Codex，但其他工具都有」。

- 结论：想脚本化，就必须用 **Code CLI 或 Cursor CLI**。

## 5. CI 流程集成：GitHub CLI 是「大解锁」

### 5.1 Raj 的痛点
- 合同写好了、脚本也跑通了，但**怎么把 CI 的反馈接回来**？
- 现状：工程师**手动把 CI 日志复制粘贴回 agent**，让 agent 去修。

### 5.2 Greg 的现场演示 + 技巧
- 前提：**装 GitHub CLI（`gh`）并鉴权**（它以「你」的身份登录，继承你的权限）。
- 用法（Greg 正 live 演示）：
  - 一个 **Codex 终端正在尝试发版 0.82**，它**循环检查 GitHub Actions 的 job run**，评估发生了什么，失败就做渐进式修改。
  - 技巧：告诉 agent「我们要发版，这是打 tag / 监控的步骤」→ 用 `gh` 监控 Actions 端点 → 设置一个 **watch / 延迟循环** → agent 拿到**确切的 Actions 结果**做反馈 → 修正 → 再触发。
- 为什么值得：Greg 有些 build **要跑 40+ 分钟（因为 matrixed）**，「如果整天坐那儿盯这个，我会疯掉」。
- 现场细节：他确实有 **1000 个测试**，失败常常是 **flaky（偶发）**，不是真问题——所以让 agent 盯着、失败自愈特别划算。

### 5.3 Sean 的补充：把「check 状态」写进 done contract
- `gh` CLI 既能「读并总结最近的 PR」，也能「**给出所有 checks 的状态**」。
- **你的 definition of done 可以直接包含「checks 的状态」**，把它作为反馈喂回 agent。
- 直击痛点：
  > 如果你现在有个手动动作——「review checks → 复制 Jenkins 日志 → 喂给 agent」——那就**把它变成 loop 的第二次自动运行**。

## 6. 非编码迁移：Jack 的 Gadfly（苏格拉底答辩 agent）

### 6.1 项目是什么
- **Gadfly（牛虻）**：一个**苏格拉底式面试（Socratic interview）agent**。
- 工作方式：接收一篇论文，基于**讲师生成的 brief**，和学生进行对话。
- 核心概念：**「lethal assumption（致命假设）」**——如果 brief 里这个假设错了，整篇论证就崩塌。
- 想验证的问题：
  > **学生是否真正「拥有（own）」他们论文里的判断（judgment）？他们能否有效为之辩护？**
- 痛点来源：老师常拿到「**流利但可能是 AI 写的**」论文，有漂亮论点，但**不知道是谁写的**。

### 6.2 Jack 想解决的最棘手问题（provenance）
- 能控制 agent 和学生互动，但难的是：
  > **学生是否「继承了 agent 提供的东西」然后拿去辩护？出处（provenance）应该属于学生。**
- 三个层级的好坏：
  1. **学生自己提出想法 → 好**
  2. **agent 提出想法 → 坏**
  3. **学生接住 agent 的想法再扩展 → 更坏**（因为那本来就不是他的想法）
- 有没有办法围绕「你是否真的从论文和 brief 出发」「你是否引入了本不该有的新东西」做检查？

### 6.3 定位：这是「自动化论文答辩」
- Jack 澄清：Gadfly 既是「帮你理解/探索论点的对练 agent」，又是「分辨这是你原创、还是 AI 帮你搭的」。
- 本质：**一场自动化的 thesis defense（论文答辩）**。

### 6.4 落地场景：National War College
- 在 **National War College（国家战争学院）** 做战略研讨会（strategy seminars）。
- 学员是「有前途、要在职业上升级」的**作战人员（operators）**，他们产出的 brief 本质上要能**站在国家安全委员会面前当面汇报**。
- 现场张力（Jack 原话）：
  - **保守派**：「我们不想让任何这类工具进入教学环境。」
  - **作战环境**却在飞速前进：「你根本不知道这些系统在做什么，你只能去**验证**它。」
- 核心问题被尖锐化：**判断（judgment）坐在哪里？如何验证这个判断存在？**

## 7. Greg 对 Gadfly 的迁移建议：预处理 + 动态 gate

### 7.1 起点：每个 agent 都是 loop
- 每个 agent 都是「某种 memory 持久化 + LLM 调用」的 loop。所以**可以在你的 loop 里触发确定性**（不一定为了本课程的目的，但为了 Gadfly 自己的问题）。
- 例：Gadfly 现在有一套「多少轮、问多少次、如何深化论点、引用文献、具体化、别抽象」的规则。

### 7.2 当前 Gadfly 的做法（Jack 描述）
- **学生版**：把整篇论文「**塞进（jam）**」上下文窗口，给几条规则，就开聊。
- **教师版**：有更多结构（教师有「该探索什么、为什么、学生该学什么」的想法）。
- 「defend my thesis」版 = 「这是你的论文 + 规则，请便」。

### 7.3 Greg 的建议（数据视角，可迁移）
1. **先预处理**：不要只是 jam 进去，先从论文里**抽取结构化数据**（主题 themes、论点 arguments、新颖/突出观点 salient points），可能还要**实体抽取（entity extraction）**。
   - 原因：底层 LLM 有 **attention 问题**（他举了「上传一篇讲《奥德赛》的论文」的例子）。
2. **动态 gate**：从预处理结果里，**为每篇论文动态生成一组「paper 专属规则」**——例如「至少要覆盖 3 个预先抽取的主题」。
   - 类比 prove it：**不要让整个 loop 完全由交互中的模型驱动**，而是有一个 gate 能看这些 criteria、控制轮数。
3. **用分类器 LLM 做匹配**：学生的回答动态、无法预知，所以用**另一个 classifier LLM** 把回答和你抽取的实体/主题做匹配，按**概率置信度**打分，满足就 **increment 一个 counter**（= 某条 check clause 被满足）。
   - 这样就不必死板地「跑 12 轮」，而是「**直到覆盖了该覆盖的主题才停**」。
4. **schema 要「宽但别太窄」**：用**通用占位符**（参数数量、论证实质、被发现的主题），保持足够灵活，避免过早收窄。

### 7.4 Greg 的同款实践：董事会「证据卡」App
- Greg 在一家公司当董事，把董事会材料（board deck、厚厚的手册等）做成手机 App，后端 schema **能接任意文档**，预处理后抽取**实体和事实**，生成「证据卡（evidence cards）」。
- 论文里未必有「事实」，但有**陈述/断言**，可以有一遍 pass 判断「它们是否连贯（coherent）」。

### 7.5 Greg 的隐藏背景（对 Jack 很关键）
- **Greg 曾是 GitHub 的机器学习与数据科学负责人，并且亲自发布了第一版 GitHub Copilot**——所以他「整天都在做数据分析」。
- 这对 Jack 是极强的信号：Greg 愿意单独约时间一起深入（「这就是我爱的活」）。

## 8. 学术/战略论文的「结构模式」与 Pluralsight 案例

### 8.1 论文有可锚定的结构
- 任何学术论文都有近似模式：**摘要 → 开篇 → 研究问题 → 带引用的文献综述 → 实验设计 → 分析的数据**……
- 战略文件也有可锚定的结构：**应包含的属性、塑造方式、lines of effort（努力方向）**——军事场景有大量已发表的范例可锚定。

### 8.2 Pluralsight 的类比（Greg 亲身案例）
- 离开 Pluralsight 前，他们在做「**给整个课程库建 taxonomy（分类法）**」（课程内容 + 定向学习路径 + 动手实验 + **Skill IQ**（计时测验））。
- 目标：根据用户偏好/历史行为/Skill IQ 分数，给**定制学习路径**。
- 难点：**你没法把所有这些数据塞进一次 LLM 调用的上下文窗口**——必须**先结构化**。
- 他们当时也没有 gate/独立 loop，但**用「结构化机制」往 UX 里注入确定性**，让用户「真的会点某个东西」，而不是「对着 LLM 祈求好运」。
- 判断标准很简单：**「这比搜索更好吗？」**（人会不会点推荐、点了会不会完成？）

## 10. 明天（Session 2）的预告与教学反馈征集

### 10.1 明天主题：durable log（持久日志）
- 前提：如果你要建 meta harness 管理**多个 CLI 子进程**，一旦有**中断（interruption）**，从连续性角度你需要一份 **durable log**。
- 今天「resume」这个能力是**免费的**（原生 agent 会从 chat log 恢复），但**一旦你包了一层、子进程是短暂的（ephemeral）**，你的 wrapper 就得**自己当那个 durable log 的主人**。
- 难点：想包**异构（heterogeneous）的一组 agent** 时，**各家原生日志格式都不同**，你得建模 + 规范化（normalize）。

### 10.2 Greg 征求「怎么讲才最好懂」
- 他原计划：直接开讲，但意识到「不是每个人都理解了 loop/gate/监督子进程」这套。
- 他设想的引入方式：**从一次 vanilla Claude/Codex session 开始**——prompt 一下、让它跑、cancel/escape，然后把「你会 resume 的那份日志（带 UUID）」调出来，解释它怎么工作；再讲「如果你要包它，你就得成为 durable log owner」。
- 他向 Jake、Raj 征集反馈。

### 10.3 Raj 的反馈（很有价值的教学建议）
> 「**除非有人知道一个 vanilla harness 需要哪些能力（capabilities），否则他不会知道该为 meta harness 构建什么。**」
- 建议：先给「今天 packaged harness 长什么样」的 overview，再讲「定义 meta harness 时你要 engineering 哪些能力」。
- Greg 采纳，并补充：**还要多花时间拆解「一个好的 goal 长什么样」**（因为很多人不写 goal）。

## 11. Goal Engineering（目标工程）

### 11.1 Raj 的疑问：「我们从不写 goal，goal 到底是什么？」
- Raj 团队现状：**一切都在 user story 里**；有 repo 时 repo 就是 context，没 repo 就一个 markdown 说明要做什么；**没人用过 goal**。

### 11.2 Greg 的 Goal 文件结构（他有「goal engineering」长文 + Dead Reckon 里有几百个 goal）
- **vanilla harness 对 goal 文件大小有硬上限：约 4,000 字符**。
- 所以 Greg 的 goal 结构是（关键细节）：
  1. **Opening / read first**：先「读一个文件」——用来装**塞不进 goal 的上下文**（通常是一个 **writer 文档**，可以有无限多的上下文/例子）。
  2. **Goal statement（in context）**：目标陈述。
  3. **Constraints**：关于「这里别做什么」的约束（有点平行于 done contract 的概念，但它**没被监督**，只是在 Codex 里裸跑）。
  4. **Progressive commits（渐进式提交）**：明确要求「**每 10 轮左右提交一次**」——否则模型跑完给你一个**巨型 commit**，你就没有任何「渐进快照」可以回去定位问题。
  5. **Verification & stop when（验证与停止条件）**：很像 bake 进 meta harness 的那套。

### 11.3 什么是 rider（骑手）
- **rider = 附加上下文**，可能是 spec 或任何东西，**没有规定格式**，就「挂在 goal 后面」。
- 例：一个 goal 文件会配一个 rider，Dead Reckon 开源 repo 里每个 goal 都有 rider。

### 11.4 一个真实 goal 示例
- 一个「实验性」goal：
  > 「评估 Dead Reckon 的整个『面』上哪里有摩擦，然后落地一个**最高杠杆的易用性改进**。」
- 附带：as-built architecture 作为上下文、要改的 crate、posture 想法（关注什么、复用什么）、以及「**分阶段落地 + 渐进提交 + 别 push + 跑 make verify 脚本 + 跑特定测试才能 break loop**」。
- **关键区别**：这和「写一份 implementation spec」不同——**不要预定义模型该做的一切**，否则就失去了用 goal 的意义（要留一点 **serendipity（意外发现）**，让结果「惊喜」你）。
- 「**我大部分产品都是靠写 goal 建出来的。**」（Raj 问「你就是靠写这些 goal 建产品的吗」→ Greg 肯定）

### 11.5 Goal 是怎么来的（方法论）
- 来源：**初始 unmet needs（未满足需求）** → 从实践中提取 pattern 写进 **25 模式书** → 大量 research。
- 原话拆解：「今天有哪些事你做不到、但让别的东西来做会很好？」「我把时间都花在哪了？」「raw-dogging（裸用）Claude Code 时，什么最痛苦？」
- 早期 GitHub 历史里有一份「**巨大的需求清单**（Claude Code / Codex 没解决的事）」，他逐条 build 过去。

### 11.6 Goal 的「作者」是一套 skill
- 写多了之后，他把「写 goal」做成一个 **skill**：
  > 「这里是我本来可能写成 spec 的 prompt；你有 100 个『goal-rider pair』的例子；把它转成那种格式。」
- 这个 skill 会：按格式写（文档结构是 **YYYYMMDD 日期**）、带不同 subheader、**永远做一次字符数检查**（因为 goal 有 4000 字符硬上限）。
- 现场测试：他粘了 **358,000 字符**进 Codex，看它会不会「barf」（吐出来拒绝）。

## 12. 元 harness 的适用性 & Greg 的真实产品（回应 Raj 的疑虑）

### 12.1 Raj 的疑虑
- 「我理解你做了什么，但**这能多大程度用在我的日常**（现有代码库、平台公司、一堆后端/服务）上？」

### 12.2 Greg 的回应（打消「这人是 vibe coding」的误解）
- 「我干的和你们一样：**20 万用户**。」「我大概 build 了这产品 **80%**。」
- 澄清一个可能的误解：
  > 「你可能以为：这人编了门课、造了个 prove it 玩具，然后还有一个 vibe-coded 的 harness。**不是的**——我们建的是**非常严肃的基础设施**，几千用户、非常复杂的多服务后端。」
- 他 **30,000 个 session** 跨多家 provider，agentic 方式建过多类产品：**extensions、CLI 工具、全分布式系统（用 CRDT、ephemeral containers）、production pipeline、多环境**。

### 12.3 课程真正的交付
- 核心是 **inner loop（内环）**：我们的工作现在是「**验证 agent 的工作**」，但远不止一句「我想验证 agent 的工作」那么简单。
- 希望你能带走：
  - 一些「**以前没想过的事**」；
  - 在你**独特处境**里如何真正改善 inner loop；
  - 「**怎么选对的模型/harness**」「怎么判断该对话式 prompt 还是放手跑」「怎么知道另一端吐出的答案对不对」。
- 坦诚：**这个领域进化太快，没人有正确答案**。但 Spec Story 有「过去两年和大量用户交互」积累的**失败案例语料**，这是课程的另一半底气。
- Raj 的表态（很关键）：「**我希望结束时，我能把一大块工作拆好、喂进 pipeline，让 meta harness 一个接一个可靠地编码、满足所有验收标准，而我不用 AFK。**」

### 12.4 「从粘贴 ticket 到拥有确定性」的转变
- Greg 画的「before/after」：
  - **Before**：把 ticket 粘进 agent → 按回车 → 看滚动 → 20 分钟后一个 diff → 读一半 → 跑点测试 → merge → 开 PR → 有人问「这是啥？」
  - **After**（学完概念后）：即使你还没建好整套机制，你也会**知道**：「如果我想走开、又没能力读完所有 diff，我该有一个带确定性 check 的 done contract、由一个 gate 管理；给 agent 更具体的 goal/rider 标准；有办法 break loop、更新证据。」
- 提到一个还没深讲但重要的概念：**gate 产生的「receipt（收据）」**。

## 13. 收据（receipt）与出处（provenance）

### 13.1 理想形态（Greg）
- 作为 operator，理想是：
  > 给 meta harness 一个 prompt → 走完所有步骤 → 产出代码 → 通过 done contract 和 gate → **我拿到一张 receipt**。
- 这张 receipt **能附在 PR 上**，链接到**出处（provenance）**：发生了什么、我用什么 steer 的。

### 13.2 Raj 的共鸣
- 「agent 在你机器上跑，但**我是 reviewer，我根本不知道 agent 到底做了什么**」——所以 receipt 极有价值。

### 13.3 Spec Story 的现状与局限
- Spec Story 只有 4 个人、整天交流、彼此信任，所以**不总是**这么做。
- 但**把巨型 transcript 存进 git 本身不友好**（不是 Git-friendly）。
- 不过他们有个例子：**Spec Story sync 是共享 repo**，`.specstory` 文件夹里的 transcript 会**随提交一起进 git log**（其中有些是 Jake 的）。所以你可以让 agent：
  > 「看这个 commit，告诉我 Eric/Jake 当时想干什么。」
- 结论：**对大多数公司这是巨大的空白**——如果你在本地裸跑 agent、不附加交互的 provenance，别人问「你为什么改这个组件？」，**你可能根本答不上来**（因为你当时在验证 app 运行、没盯整个项目树）。
- 所以：**「附加 provenance、在重要场合让它可见」**，是建 meta harness 时要考虑的（取决于你的 outer loop；不必每个 commit 都做）。

## 14. dev-to-main 自动摘要（Spec Story 的可借鉴实践）

- Spec Story 在 dev 和 main 之间，用**一个自动化 GitHub Action**：
  - 当 **dev 有新的 commit 且没有开向 main 的 PR** 时，**自动开一个 PR**。
  - 它去看那个 commit 的历史，**不断重写 PR 描述**，让你「一眼看到现在 dev 里到底进了哪些变更」。
- 它总结什么（Raj 追问）：**总结每个 commit + 与之关联的 agent trace**（不只是日志）。实现上会 **spawn 一个 Claude container** 来做总结。
- 价值：在**合并到 prod 之前**，理解「co-mingled（混在一起）的工作」。
- 备注：这不是课程目的，但既然可以随便问，就分享出来。

## 15. 前馈/反馈自动化：只能靠自建 meta harness 吗？

### 15.1 Raj 的问题
> 「自动化前馈/反馈，**只有自建 meta harness 这一条路吗？**」

### 15.2 Greg 的回答
- 市面上有 **ThoughtWorks 的文章**（约 4 月，作者转写为「Brigitte」）讲「feed-forward」的心智模型，但**偏概念**：讲 skills、repo 内容，**并没有真正改变 harness**，也没做「没人不知道」之外的有用事。
- Greg 真正想做的（**实验性**）：
  - Dead Reckon 记录**每一次 tool call、每段 prompt/narrative**（它把 agent 当子进程驱动并录音）。
  - 这些日志里偶有 **tool call 错误**（read/write/grep/glob 出错，比如断网）。
  - 他想把**错误处理 built into harness 本身**：跑完后，让 harness **看自己的 log stream，自动 propose 代码改动**（解释「为什么出这个错」）——错误可能来自**编排（orchestration）**，也可能来自**被驱动的模型**。
  - 一句话：
    > **「我控制不了 Claude Code，但我能控制我的 supervisor。」**
  - 目标不是「让 harness 更智能」（那得改模型权重），而是「**让它更 resilient（更抗造）**」——这是「只用厂商 harness、且没有 fork 它」的人拿不到的机会。
- 补充：**meta harness 该跑在哪？** 今天 demo 都在笔记本上跑，但**意图不是这样**——你真正想要的是一个「**听着 Jira、自动 spin up 一个 sandbox、在里面跑 story**」的 job（Raj 补充：喂 story → 自动起 sandbox → 代码在 sandbox 里写和执行）。

## 16. 廉价实验（Cheap Experimentation）与 OLCP 数据库

### 16.1 前提
> **如果你有正确的控制机制，「实验」会变得比以往任何时候都便宜得多。**

### 16.2 OLCP 数据库（Greg 的 side project）
- **OLCP = Online Context Processing（在线上下文处理）数据库**，为了解决「**brilliant amnesiac（聪明却失忆）**」问题——每次新起一个 coding agent 都毫无上下文。
- 做法：把**所有 agent trace 结构化**（而不是存全文——日志会涨到好几 MB），接到一个 **MCP server**，看能否对「repo 的 ground-truth 事实」有更高的 **recall/precision**，从而比「去 grep 一堆平文件」带来更好的 steering 能力。
- 现状：先建在 **SQLite** 上（因为重点是 recall 前提，不是性能）；接口是一个**单行 verb 的 CLI**（`recall` + 全文输入）。

### 16.3 关键方法：先立 metric benchmark，再放 agent 去刷
- Greg **一开始就带着「一组 metric 基准」去设计**。
- 拿到「一组事实的正确答案」的 benchmark 后，他做的事：
  > 「agent 1、2、3、4、5、6，去 **work tree** 里，把文献里所有办法都试一遍，**在 loop 里跑 metric benchmark，直到能/不能超过它**。」
- 结论（很深刻）：
  > **如果你能定义一个「有量化 benchmark」的问题（golden dataset），就能让模型自己跑、做你永远没时间做的实验。**
- 局限：不是每个问题都有现成 metric（搜索/检索恰好有一套众所周知的指标）；但**「做 golden dataset + 立 benchmark + 放模型跑」**是一条「更受限、但更工程化」的路，比「写个 goal 设约束就放手（vibe coded）」更靠谱。

## 18. 本场金句（可引用/记忆）

1. **「你的 check，就是 done contract 里的一个 clause，由 gate 来求值；它可以是任何东西。」**
2. **「真正的解锁，是自动化『部分集成测试』——去查数据库、Lambda 日志、下游系统日志。」**（Sean）
3. **「60% 的时间里，即使 skill 本该被推断调用，它其实并没有被调用——所以你需要确定性。」**（Greg）
4. **「GitHub CLI 一旦装好并鉴权，就能成为你 loop 的一部分——让它监控 Actions 结果、失败自愈。」**
5. **「学生自己提想法 = 好；agent 提想法 = 坏；学生接住 agent 的想法再扩展 = 更坏。」**（Jack，provenance 三档）
6. **「先预处理抽取结构化数据，再做『为每篇论文动态生成规则』的 gate，而不是死板地跑 N 轮。」**（Greg 对 Gadfly 的迁移）
7. **「goal 别写成 implementation spec——不要预定义一切，要留一点 serendipity，让结果惊喜你。」**
8. **「我控制不了 Claude Code，但我能控制我的 supervisor。」**（Greg 论 meta harness 的反馈）
9. **「如果你能定义一个『有量化 benchmark』的问题，就能让一群 agent 在 work tree 里自动刷指标——实验会变得极其便宜。」**
10. **「除非知道 vanilla harness 需要哪些能力，否则你不会知道该为 meta harness 构建什么。」**（Raj 的教学反馈）
