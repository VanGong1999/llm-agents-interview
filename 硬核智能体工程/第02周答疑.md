## 1. 开场：Jack 的 Docker 安全事故（一条活生生的教训）

- Jack 团队和第三方合作一个项目，对方早上要求「起个实例跑点东西」。
- 他们跑起来后，**对方的 Docker 端口是开放的（open on port），起来几分钟就被黑客攻破了，数据库没了**。
- Greg/Jack 共识：**「现在对所有东西都有端口狙击手（port snipers for everything）」，这是现代世界的常态。**
- 讽刺点：**Claude Code 早就提示过「端口大开，需要修」**——这是很基础的东西，但被忽略了。
- 这个开场正好印证了前几课反复讲的「**沙盒 / 权限 / 控制平面**」的重要性：真实世界的副作用（被删库）就这么快发生。

### 1.1 事故背后的组织角色（容易忽略）
- Jack 团队的真实位置：经慈善机构 / 对方 AI 团队授权「能用他们的 key」，更像被钦点的**跑任务中间人**，不是实际交付方——对方说「跑一下这个」，他们就起实例。
- 第一次合作时 Claude / 他们就看到过「**八百个端口全开**」；这次再起实例，几分钟内被扫穿、库没了。现代默认假设：**公网端口一开，就有 port sniper**。
- Claude Code 当时已提示「完全敞开，需要修」——基础安全告警被忽略，比「不会用工具」更糟。

### 1.2 Greg 对「课程落后 / 作业卡壳」的态度
- 不必逐行把 prove-it / 启动器跑到完美；小毛病不该挡住更大目标——**理解「构建自己的 harness」的概念框架**，并在脑子里有一条可实践路径。
- 反例（Ram，R 用户）：prove-it 并不要求你真在框架里跑通一切，只需部分指向工作目录；但循环会对目录做哈希并与「完成合同」门禁比对——**RStudio 一打开就改项目文件**（未必在 `.gitignore` 里），哈希漂移像「失败」，其实是**概念干扰**。Greg 关心的是「概念抓住没有」，不是作业对错本身。

## 2. 日志：价值、代价与「元技能挖矿」

### 2.1 Sean 的问题：那个看日志的小 UI 是什么？
- Sean 问：直播演示里「把日志放进一个可视化界面」是不是 Greg 主要的工作方式？他手动 inspect 日志简直是噩梦，而且发现**很多东西其实没被记录（hidden），得确保它们没被藏起来**。
- Greg 澄清两件事：
  1. **直播里的并排 UI 是他自己的「教学装置（teaching device）」**，故意只截一小片、把底层进程的 tool call 藏起来，避免分散注意力。
  2. 真正的通用答案是 **Spec Story Cloud**：Spec Story 的核心业务就是把**所有 agent 日志规范化成可读的 markdown**。

### 2.2 Sean 的痛点：日志文件变成「怪物」
- Sean 早年在 Isaac 的课上开始用 Spec Story，日志文件**巨大到 GB 级、开始吃光磁盘**，他只好 ignore 掉、甚至想「是不是该买更大的盘」。
- Greg 的回应：那些日志**本来就在你磁盘上**，Spec Story 只是给你一份「可复现/可检索」的版本；真正的价值是**项目依赖**的：
  - 独自工作时的主要好处：**在一个目录里积累「你的代码是怎么来的（provenance，来源）」**，方便 grep/搜索。
  - 这在「agent 还不会 compaction（压缩上下文）」的早期更有用——当时 compaction 算法很烂，交接给下一个 agent 质量很差。

### 2.2.1 磁盘卫生（Sean 的连带灾难）
- 日志 GB 级之外，Sean 还试过**本地模型**，再一次把磁盘吃满、机器卡死——教训是：对「本地存什么、为何存」要挑剔，否则机器变垃圾堆。
- Greg 补充：原始日志本来就在盘上；Spec Story 只是规范副本。若纠结要不要 Git 提交——**价值完全取决于项目与是否协作**。
- 独干活时，除了 provenance / grep，很多时候日志的真实效用只是**备份式的安心（backup peace of mind）**；「格式良好的原始 markdown」未必会被人重读。

### 2.3 Greg 真正觉得有价值的用法：元技能（meta skill）挖矿
- 关键洞察：**大多数人永远不会回去逐条读日志/提示**，它们更多是「分享用的资产」。
- Greg 真正觉得有价值的是他写的一个 **meta skill（元技能）**：**挖掘你所有的 transcript（会话记录），然后「提议」你可以安装或不安装的技能（skills）**。
- 前提：需要在**同一个项目里积累大量 session** 才能榨出价值。
- Sean 补充的历史记忆价值：从一件事转到下一件事时，「**我保留了什么 vs 我放弃了什么**」；「某个问题当初是怎么解决的、后来为什么换了解法」这种**跨项目的历史记忆**非常有用。他举例：做过 UI 后忘了在哪个项目、怎么把东西 pipe 进/出 stitch 很麻烦——这些都会被丢。

### 2.4 Spec Story Cloud 的现场演示
- Greg 共享屏幕展示 Cloud：Cloud Sync 开启后，每个项目（如 Dead Reckon）都有一堆规范化 transcript。
- 优势是「动态可视化」：可以**关掉 responses 只看所有 prompts**，快速重新定位；也能**清掉所有 tool call 的噪音**。
- 随着 coding agent 变强，这些东西变得**极其庞大**，所以「有没有办法清掉杂乱」很重要。
- 演示项目例：Dead Reckon 等；Cloud Sync 开后按项目聚合 transcript。
- 除产品 UI 外，也可以**自己写小脚本**做可视化；要点是动态过滤：只看 prompts、清掉 tool call / thinking 噪音——coding agent 越强，transcript 越大，**「清杂乱」本身就是能力**。

### 2.5 思考轨迹（thinking traces）加密的论文
- 聊到日志里是否暴露 thinking，提到当天的一篇论文：**「暴露隐藏的 AI reasoning」**。
- 背景：有些模型（如 **DeepSeek**）会直接展示 thinking；但 **OpenAI 早期就发现有人用 o1/ChatGPT 的思考轨迹来「蒸馏（distill）」模型是怎么工作的，于是开始把它们加密（encrypt）**。
- 这正是前几课提到「Anthropic 怕 Fable 被蒸馏」的同一主题。
- 当场刷到的论文方向大致是「暴露隐藏的 AI reasoning」（讨论里提到 Alexanders 相关传播）；DeepSeek 类模型会直接展示 thinking，而 **ChatGPT o1 早期** OpenAI 发现有人用思考轨迹**蒸馏**模型行为，于是加密——与「怕 Fable 被蒸馏」同一主题。

## 3. Tom 的真实项目：给 HealthStream 做文档搜索（本场核心）

Tom 是**非程序员**，用 **Claude Co-Work** 给客户做了一个产品。这是他带来的完整 case。

### 3.1 项目背景与问题
- 客户：**HealthStream**（医疗保健公司），卖几千种产品，营销材料**散落在 SharePoint 里**。
- 痛点：**200–300 名销售人员**在 SharePoint 里**找不到任何东西**，于是各自保留本地副本，而不是用最新材料。
- **成功标准（bar）**：让这个工具「**比保留本地副本更省事**」。
- 现状：销售人员是来**找营销材料/文档（files）**，未来可能演变成「**问问题、要答案（answers）**」。

### 3.1.1 交付约束（笔记易漏的「生产门槛」）
- Tom：**非程序员**，用 **Claude Co-Work** 给客户建网站 / 文档搜索；本场是来「认错没交作业」顺带求设计评审。
- 客户 HealthStream 是**微软店**，**AI 技术栈尚未敲定**；Claude 自称整套可做成「可迁移服务」。
- 试点 **13 → 30 人** 的硬门槛：先过**安全审计**；并确保最终能被开发者接手进真实环境。
- 数据性质：营销材料——「分享到哪都不会特别可怕」，但仍要过企业安全叙事。
- Tom 问工期，Claude 答 **约 3 个月** → Greg：**永远别问 Claude 时间表，它糟透了。**

### 3.2 解决方案架构
- **Golden Library（黄金库）**：让营销团队把最新材料放进 SharePoint 的一个指定区域，约 **700 份文档**。
- **Claude 的角色**：监控这个库 → 新文档进来时读取 → 分配标题、产品系列等元数据 → 填入 **Airtable 的元数据表** → 把新条目推给营销团队人工审批（「我做得对吗？」）。
- **前端**：托管在 **Netlify**，免费文本搜索 + **别名库（alias library）**（输缩写也能命中），用 Claude 在 Airtable 里做检索。
- **认证现状**：目前是**一个共享密码**；Tom 打算找 IT 要一组 **IP 白名单**（只有 VPN / 公司办公室能访问）。
- **部署现状**：Netlify 的「拖 zip 全量重部署」方式，**没有版本控制**。
- Tom 问 Claude「多久能被开发者接手做进真实环境」，Claude 说 **3 个月**——Tom 的反应是「WTF？为什么这么久？」（Greg 吐槽：**永远别问 Claude 时间**，它很烂）。

### 3.2.1 端到端链路（比「架构一句话」更细）
1. 营销把最新材料丢进 SharePoint **Golden Library**（~700 文档）。
2. Claude **监视**该区域 → 新文档进来则读取 → 写标题、产品家族等元数据进 **Airtable 元数据表** → **推给营销人工审批**（「我做得对吗？」）。
3. 前端（Netlify，活站点）：销售自由文本搜索；站点要「足够聪明预判想要什么」；**别名库**让缩写也能命中。
4. 检索时：Claude 接搜索 → 查 Airtable（元数据 + 别名 + 目前还把**文档全文反刍进字段**）→ 文档本体仍在 SharePoint。
5. 运行时现实：站点在 Netlify 上；Tom **不完全确定** Claude 是否「本地 Co-Work」——更像前端/服务里用了 **Anthropic 小模型 + 他的 key/许可证**。评审时要主动问清：**API 嵌在哪、密钥在哪、调用是否出网**。
6. 技术默认猜测（Greg）：几乎肯定是 **JS/TS**，Claude 常选 **Next.js**；托管也可是 Cloudflare / Vercel 等。

### 3.3 Sean / Greg 的设计评估
- **设计是否合理**：合理。关键区分——**Airtable 存的是「文档的元数据」，文档本体留在 SharePoint**。既然能简单，就别搞复杂。
- **当前做法的一个细节**：Tom 目前是「**把文档的整个上下文复制进 Airtable 作为字段**」——即「读取文档 → 把文本反刍进数据表」。这**现在够用**。
- **未来方向 = RAG**（Sean/Greg 反复点出的核心概念）：
  - Spec Story Cloud 本身做的就是这个：人们上传超大 chat transcript → **chunk（切块）** → **embedding（嵌入）** → 用 **retrieval augmented generation（检索增强生成，RAG）** 给出**带引用的答案（cited answers）**。
  - Tom 的用例现在是「找文档」，将来要变「问问题要答案」，那就是 RAG。
- **规模化/生产化**：不特别难，但要考虑：
  - **认证**：与其自己实现 OAuth，不如考虑现成的 **SSO / auth 提供商（如 Clerk、Zero 等）**；IP 白名单是「绕过 OAuth」的便宜方案，但企业大概率因安全想用 SSO。
  - **托管位置**：可以托管在客户自己的环境（**VPC / Azure**），避免数据经公网传到外部 Claude，减少「生产就绪」的担忧。
  - **成本**：文档摘要 + 存储 + 搜索 + 后续一个小 chatbot，**全都很便宜**；Greg 建议 Tom 检查自己的 API key 烧了多少（听起来很低）。

### 3.3.1 安全审计与「出网 vs 内网」未决题
- 便宜路径：共享密码 → **IP 白名单**（VPN / 办公室）≈ 绕过自建 OAuth。
- 企业大概率仍要 **SSO**；现成商用 auth（**Clerk、Auth0/AuthZero** 等）比自撸 OAuth 省事，但更贵、更绕。
- 若客户是微软店：尽早想清楚如何搭 **Active Directory / Entra（现名）** 的便车，而不是另起一套身份。
- Tom 已问到的关键分歧：**信息能不能发送到「网络某处托管的 Claude」**，还是必须在客户环境**百分之百严密**——客户对「怎么落地 AI」往往还没想那么远；这会决定架构是「调公有 API」还是「VPC / Azure 内推理」。
- SharePoint 经验建议：**越久越好的模式是「只约定一个投放桶，系统去取」**；一旦要在 SharePoint 里找、更新、回写，通常比你愿意处理的更乱。
- 成本体感：摘要 + 存元数据 + 搜索 + 将来一个小 chatbot，**全都很便宜**；先查自己的 API key 烧了多少。定性：这是**很好的原型**；过了试点，更多是客户侧商业/安全决策。

### 3.4 下一阶段：从「找文档」到「生成文档」
- HealthStream 在 **Frontify**（数字资产管理系统）里把企业声音/品牌定义得很好，且 **Frontify 有 MCP 连接 Claude**。
- 下一方向：**「用 HealthStream 的品牌和声音，基于现有营销材料，生成关于 X 的销售 deck」**——今天完全做得到。
- 但 Tom 不想吓到公司内部的设计师，得找对定位方式（「我不是来让你们失业的」）。
- Greg 的关键建议：**尽快成为那些文档的「source of truth（唯一真相来源）」**——别只是抓取/排序/存储现有材料（因为下一版又得重抓），而是**让内容直接在你这儿产生**，你就不用再去别处抓。
- 现实障碍是**组织/流程问题**：今天创意团队做完文档 → 打电话给产品经理 → 产品经理把文档随手丢进 SharePoint 的某个桶。要变成「丢进我们的桶」，是一个组织动力学问题。
- Tom 作为「局外人」为什么能推进：**组织里的人都太忙于「操作现有系统」，没时间去想「它可以变成什么样」**——这本质上就是「顾问为什么存在」。

### 3.4.1 「抢不抢设计师饭碗」的更准表述
- Greg 的尖锐版：某种程度上你**就是**在取消那类待完成工作（排版 / 拼销售 deck）；更健康的叙事是——**取消这份 job-to-be-done，同时给他们另一份更高杠杆的工作**，而不是假装「完全不影响」。
- Frontify 已有品牌 / 声音 / 系统定义 + **MCP 连 Claude** → 「按品牌声音、基于现有材料生成关于 X 的销售演示」今天就能做；卡点是**组织批准与定位**，不是模型能力。

### 3.4.2 为什么是外部顾问在推（组织动力学）
- 同样机会内部人也能看见，但产品 / 创意 / IT 往往**忙于运营今天的系统**：回邮件、应付高管杂务、优先级碎片化——**没专注力重新想象系统可以是什么样**。
- 顾问不背那些组织负担，所以能在更短时间做出可演示物。这几乎就是「为什么会有咨询」的现场版。
- Tom 的角色目标（自述）：成为 HealthStream 的 **AI 思想领袖**，把试点产品化，让组织看见「用 AI 前进的一条路」。

### 3.5 Tom 的构建过程（非程序员的 agent 工作流）
- 起点：**访谈 30 名销售**，录音存 Airtable，让 Claude 总结访谈、填满字段 → 这就是「定义问题」的基础。
- 然后：让 Claude 写「总结问题的报告」→ 把报告变成网站 → 问 Claude「怎么托管」。
- 节奏：访谈从 4 月开始，6 月起开发，**每周约 2 天**。
- 关键方法论（Tom 记住了 Greg 的话）：**「造一个不会撒谎的测试用例（test case that can't lie）」**——因为 agent 会告诉你「我做好了、一切 OK」，但你去试才发现不是。
- **Airtable 为什么对 Tom 特别有用**：他可以**肉眼看到字段到底有没有被真的填满、有没有缺数据、有没有它过去做过需要重做的事**——这就是「可见的验证」。
- Tom 的体感：**和 Claude 是真正的「合伙（partnership）」**，过程非常有机（organic），中间有 serendipity（他本来就是 Airtable 用户，Claude 也有 MCP data table）。

### 3.5.1 过程时间线与「可见验证」
- 访谈约从 **4 月**；**6 月**起开发；强度约 **每周 2 天**；访谈约 **30 名销售** → 录音进 Airtable → Claude 总结并填字段 = 问题定义底座。

- 方法论锚点：造 **「不会撒谎的测试用例」**——agent 会说「做好了」，你必须能证伪。
- Airtable 对非程序员的特殊价值：**字段有没有真填满、缺不缺数据、过去做过的要不要重做**——肉眼可见的验证面板。

### 3.6 版本控制（Git）为什么值得（Sean/Greg 回答 Tom）
- 现在 Tom 靠「拖 zip 全量重部署」，等于每次**重写一切**。
- 版本控制的两大好处：
  1. **灾难恢复**：备份到 GitHub 之类托管处；本地删了/硬盘坏了也不至于「screwed」。
  2. **可回滚**：你周四周五进入「zone」狂写，周五早上清醒过来觉得「其实昨天那版更好/有 bug」——**有 Git 就能一键回到快照**。
- 操作上：**每发一个会改源码的 prompt，就留一个 snapshot**；用 GitHub 集成 Netlify，push 即自动部署（CI/CD 概念，但 Tom 不用深究）。
- Greg/Sean 建议：**直接问 Claude「你更想用 Git / 让 Netlify 走 GitHub 部署吗？」，它会一步步带你配好**。
- 定性：原型/头脑风暴阶段不必第一天就有版本控制，但**人一多、依赖一上来，就是「基本卫生（good hygiene）」**。

### 3.6.1 给非程序员的 Git 话术
- 心智模型：每个会改源码的 prompt 之后，留一个 **snapshot**；满意一块工作就对 Claude 说「**我喜欢这个，放进版本控制**」。
- 与 GitHub 集成后，push → Netlify 自动部署（CI/CD 概念可先不深究）。
- Tom 以为「整站炸了两分钟就能让 Claude 重建」——**别信两分钟**；有远程备份才是真正的灾难恢复。
- 原型第一天不必有 Git；人一多、开始依赖它，就是**基本卫生**。直接问 Claude：「你更想用 Git、让 Netlify 走 GitHub 吗？」它会逐步带着配。

## 4. 什么是 harness？（Tom 的原始问题，全场的概念高潮）

### 4.1 定义（Greg 的系统讲解）
- **Harness 就是你一直在用的东西**：Claude Co-Work 本身就是一个 harness 的例子。
- 拆解心智模型：
  - **模型（model）最基础只做一件事**：对输入推理、预测下一个 token 序列。
  - 模型本质是**巨大的权重二进制文件**（在 **HuggingFace** 上开源权重模型就是这么放的；Sonnet / Fable / Opus 同理）。
  - 所以**需要一个 wrapper（包装层）**让人能跟它对话、拿回响应。
- **最早的 harness 很简单**：一个界面，追踪对话、存日志，让每次重新 prompt 时上下文窗口被保留。
- **约一年半前的重大进步**：引入了**能真正读写你文件系统、跑任意 bash 命令、执行程序的工具（tools）**——这**才是「agentic harness」的定义性特征**。
- 一句话：**「能读写文件 + 跑命令 + 一堆其它机制」包着模型，就是 harness。** 而 **模型 + harness = 人们说的「agent」**（agentic harness / agent harness 是同义）。
- 举例：Codex、Claude Code、Copilot、Cursor、Devin、Droid、**AMP**…… 都是**「harness 公司」**——用底层模型，靠「围绕它的机器」让它更强。

### 4.1.1 和本课的衔接（外层 harness）
- 日常交互是：提示 → 等回复 → 再提示；回复常有副作用（看桌面、收集上下文、写代码、落盘）。
- 若要**长时程目标完成**，思路是：**在现有 harness 外面再包一层 harness**（元框架）——接管人类操作员「盯着、推一把、给权限」的职责。
- Co-Work **只是品牌名**，背后是 **Claude Code 经 GUI 驱动**；你「不知不觉在用 Claude Code」。其它厂商大多是**不同系统提示 + 不同工具集**的同构物。
- 名单补全：Codex、Claude Code、Copilot、Cursor、Devin、Droid、**AMP**……本质都是 **harness 公司**。

### 4.2 两个比喻（Tom 与 Greg 的对话）
- **Tom 的比喻（马 + 缰绳）**：模型是马，有一堆力量、能乱跑；你得给它套上 **guardrails（护栏）**——护栏可简单可复杂。
- **Greg 的延伸（引擎 + 车）**：
  > 模型 = **引擎（engine）**，本身搁在煤渣块上什么也做不了，只能「产生动力」。**Harness = 那辆车**——油门、刹车、化油器、变速箱、车轴、车轮，把动力「控制并送达」到你想去的地方。
  > 前沿厂商在造「最强大最节能的 V8 引擎」，而 harness 厂商在竞争「**把最好的车包上去，把动力和控制交给驾驶员（你）**」。
  > **安全、动力输送、方向盘、控制**——这些全在 harness 里。你要赢比赛需要好引擎，也需要好车，否则会「开下桥 / 撞死自己」。

### 4.3 「我造了个 harness」还值得惊讶吗？
- Tom 问：别人说「我造了个 harness」，他不为所动——这个立场合理吗？
- Greg 的答案：**合理，甚至应该这样**。因为：
  - 18 个月前「让 LLM 在真实数字世界做事」还是先锋创新；
  - 现在这条路**越来越陈旧（well-worn）**，甚至有开源库可以抓来改改就自称「这是我的」——**dime a dozen（一打一打地不值钱）**。
  - 关键要问的是：**「他们是怎么做的？带来了多少自己的创新/想法，而不是 rinse and repeat（照搬重来）？」**
  - 这门课的目的之一就是**给 harness engineering 去魅（demystify）**——你学完就该知道对方到底做了什么、值不值得重视。
- Greg 推荐一个「闪电课」资源（时长约 1 小时的 YouTube + 幻灯片，John Barman 制作）：**把 Claude Code 拆到最核心**——API 怎么拿回响应、拿回来怎么用、怎么开始包一个 wrapper——特别适合 Tom 建立「LLM 在哪结束、harness 在哪开始」的直觉。

### 4.3.1 「我造了个 harness」为何不值钱（去魅）
- 18 个月前：让 LLM 在真实数字世界做事 = 先锋。
- 现在：路径被走烂；开源库改改就能贴牌；甚至有 **Maven 上的 harness 工程课**——你不必是顶尖工程师也能看懂概念与案例。
- 本课目的之一：**给 harness engineering 去魅**——结束时应能准确看出对方做了什么、有多少真创新、多少 rinse and repeat。
- 资源（适合 Tom）：**John Barriman** 约 1 小时 YouTube + 幻灯片，把 Claude Code **剥到最核心**——API 如何拿回响应、拿回来做什么、如何开始包 wrapper；建立「引擎在哪结束、车从哪开始」的直觉（刻意避免「太底层」吓人，其实是高层心智模型）。

## 5. Claude Co-Work vs Claude Code：给 Tom 的进阶建议

### 5.1 Co-Work 是什么
- **Claude Co-Work 只是品牌名，它背后就是 Claude Code 在通过 GUI 驱动**——你「不知不觉在用 Claude Code」。

### 5.2 为什么建议 Tom 试试 Claude Code
- **Co-Work 的限制**：斜杠命令很受限，只有文件选择器、看 usage 等；**没有 `/goal`**。
- **Claude Code 的优势**：有全部 skills 和内置 slash commands，尤其 **`/goal`（「keep working until condition is met」——持续工作直到条件满足）**，能写一个带「完成定义（definition of done）」的长运行目标。

- 定位金句：**「Co-Work 是带训练轮的 Claude Code（Co-Work is Claude Code with training wheels）。」** 如果 Tom 想成为 HealthStream 的「AI 思想领袖」，**迟早要为自己卸掉训练轮**。
- 别被「Code」吓到：Claude Code 只是「对软件工程有特定系统/问题」的 harness，但背后还是 Opus/Sonnet/Fable，**照样能做各种办公任务**。
- 实践建议：开一个会话，**用 `/goal` 给一个比平时更宏大、更少 babysit、更长时程的任务**（比如为咨询业务做研究），晚上启动、早上回来看它走了多远，与「人工 loop」对比——**像练 prompt 一样练 goal**。
- Greg 自己的偏好佐证：他早就不用 Co-Work 了，因为**「总得把它从各种沙盒/控制洞里拽出来，不值得」**。

### 5.2.1 可执行的切换清单
- Co-Work 改版后 `/` 菜单很瘦：文件选择器、看 usage……**几乎练不了课程里的 goal 循环**。
- Claude Code：完整 skills + 内置 slash（含 **`/goal` = keep working until condition is met**）；写带停止条件的长目标，把课上的 definition of done **内化进日常工具**。
- 别被「Code」吓到：它有偏软件工程的系统/问题设定，但背后仍是 Opus/Sonnet/Fable，**办公任务照做**。
- 练习设计（可并行）：
  1. 另开 Claude Code 会话；
  2. 选一个咨询侧「本来就要很多轮」的研究任务；
  3. 用 `/goal` 设**比平时更宏大、更少 babysit、更长时程**的目标；
  4. **晚间启动、早上看走了多远**，对比人机迭代体感；
  5. 先敲 `/` 浏览菜单，并直接问 Claude：「规划 / 执行 / 审查类 slash 分别何时用？」
- Greg 的离开理由补强：Co-Work 的沙盒/控制面经常把人困住——**「如果反正都要往外爬，为什么先把自己关进去？」** 金句仍成立：Co-Work = **带训练轮的 Claude Code**；想当组织 AI 思想领袖，迟早要卸轮。

### 5.3 为什么 Tom 过夜任务总是卡在「要权限」
- Tom 抱怨：过夜批处理（读文档、填摘要、存表）跑几分钟就**弹权限请求**，第二天早上发现它卡在「等你批准」。
- Greg 解释（第 2 课也讲过）：
  - 现在 Claude 和 OpenAI 模型里都内置了**工具分类器（tool classifier）**——**每次工具被调用，其实有另一个模型在背后对它分类**；对 Co-Work 用户完全隐藏。
  - 它可能把某个动作判成**「risky action」→ 触发审批流**，**即使你开了 dangerously skip permissions 也照样拦**。
  - 原因：**品牌伤害太大**——你在 Twitter 上骂「Co-Work 把我的机密文件发到公网 / 删了我的硬盘」，厂商承受不起，所以**它不在乎你设了什么**。
  - 更深层：这些 guardrail **已经「烙进」新模型本身**（从安全与对齐角度，写进 **Claude 的宪法（constitution）**，属于真实训练的一部分）。当旁边那个分类模型说「你得跑这个我不熟的 CLI」，它就被推回主线程说「我不能做」。

### 5.3.1 权限弹窗的操作级理解
- 场景：夜间批处理（读文档 → 摘要 → 反刍进 Airtable）跑约五分钟就弹权限；早上看见「在等你批准」。
- 机制：工具调用旁路跑 **tool classifier**（对 Co-Work 用户通常不可见）→ 判为 risky → 走审批；**dangerously skip permissions 也挡不住**品牌红线。
- 更深一层：护栏已进**模型训练 / Claude 宪法**；分类器把「不熟的 CLI / 本会话没见过的命令」推回主线程 → 模型说「我不能做，请你帮我跑」。
- 产品含义：Co-Work 优化的是偏 **~5 分钟反馈环**，不是「交给它过夜直到金标准」。

## 6. Virtual Tom：外层 harness 驱动 Co-Work（一个思想实验）

- Greg 想把「外层 harness」概念套到 Tom 的 GUI 场景上：
  - 思路：**用「可访问性控制（accessibility control）」**——为什么很多这种活用终端 harness 做，是因为 **Unix 一切皆管道**，CLI 能被程序控制；但理论上你也能写一个 app **从字面上控制 Co-Work 在做什么**（一个「**virtual Tom**」）。
  - 你可以给它定高层目标（几乎像集成测试），例如：**「用另一种语言重建我的 HealthStream 文档查找 app，加 RAG，部署到 Vercel 而不是 Netlify」**。
  - **完成定义（definition of done）不是单元测试**，而是：「**网站真的部署了、实际驱动过网站、拿到了 5 条带引用的答案作为证据**」。
  - 这样你就能「**去泳池边喝玛格丽塔**」，而不是坐那儿 babysit。
  - 现实可行性：现在有些模型**非常擅长用 Mac accessibility controls 驱动其它程序**（开箱即用），所以这个实验值得做。
  - 前提：你得有一个**能描述「done 长什么样」的目标**（例如来自 IT 的需求：「不要 Netlify，要进 Azure 环境」→ goal = 「把 Netlify 上能用的东西迁到 Azure，5 个查询得到相同响应」）。
  - 为什么需要外层 harness：**所有 harness 都会到达一个「停止点」等人类推一把**；外层 harness（virtual Tom）的职责就是**让它别放弃、一直干到满足目标标准**——可能跑 2 小时，也可能 2 天。
- 总结：**Co-Work 是 harness，外层驱动它的 virtual Tom 也是 harness——「任何让 LLM 用工具干活直到达成某目标的东西，都是 harness」，只是层级不同。** Co-Work 默认假设的是「5 分钟反馈循环」，不是为长任务设计的。

### 6.1 Tom 的意外观察：单会话超长运行不退化
- Tom 几个月来**一直待在同一个 chat 里**，东西越积越多；他试过换新 chat，结果一团糟又换回来。
- 他发现**性能没有退化**，还能「去读一个月前的 transcript 找东西」，完全没问题——这为「长会话」提供了一个反直觉的真实观察。

### 6.2 可行性边界与完成合同示例
- **难**：直接「围绕 Co-Work 再包一层」——GUI 不像 Unix 管道好控。
- **可**：用 **Mac accessibility** 字面驱动 Co-Work（现模型对此已相当强，开箱可用）；Greg 表示若有精力可给 Tom 做个示意原型——**正确性不如课用 CLI starter**，但足以强化概念。
- 外层名字随意：外循环 / **meta-framework** / virtual Tom——职责只有一句：**别让内层 harness 在停止点放弃，一直干到不可伪造的 done**。
- Done 示例（来自 IT 真实约束）：「把 Netlify 上能用的迁到 **Azure**；用同一提示跑 **5 个文档查询**，响应与 Netlify 金标准一致。」——验证的是**已部署站点被真实驱动**，不是单元测试绿了。
- 跑 2 小时或 2 天都无所谓；成功标准已定义时，肉身 Tom **没有增量贡献**，可以离席（泳池边玛格丽塔）。
- Tom 的补充观察：同一 chat 用几个月、上下文越堆越多，**未见性能退化**；试过换新 chat 反而一团糟又退回——且能让它去读一个月前的 transcript。这与「必须勤换会话」的直觉相反（仍不解决权限卡死）。

## 7. Torty（原 G Mux）：Greg 自建的 durable sessions GUI

Jack 问起 **BB**（另一个终端多路复用器），引出了 Greg 正在做的产品。

### 7.1 动机：durable sessions（持久会话）
- Greg 的主痛点：**想要「关闭窗口后，会话要么继续跑、要么能轻松恢复」**。
- 他对 Cursor 的不满：
  - 用它当「包着 Codex / Claude Code 的 wrapper」时，**标签窗口太多、难跟踪**；
  - **关窗口 = 终端死了**，而他有大量长运行任务；
  - 所有超级 App 都「**朝向左侧栏布局**」、长得一样（都基于 Conductor 设计，换个 logo 而已）；
  - **看不到 Git log、不能轻松浏览文件**，很烦。
- 结论：**干脆自己造一个 GUI 替代 Cursor**。

### 7.1.1 为什么连 BB 也没认真用
- 痛点组合：Cursor 当 Codex/Claude Code wrapper → 标签爆炸；**关窗/崩溃 = 终端死**；长任务丢上下文；还要在「原生终端 / 独立 Claude Code / Cursor / BB…」间找会话——**一只脚踩七个阵营**。
- 审美/产品抱怨：超级 App 都在变成左侧栏 **agent 管理窗**；看起来都一样，**基本基于 Conductor 设计换 logo**（Claude Code、Cursor Agents…）；Git log / 轻松逛文件体验差。
- 结论：自己造一个「看起来仍像 VS Code（Cursor 本就是 fork），但**围绕 durable sessions**」的 GUI。

### 7.2 Torty 是什么、核心特性
- 原名 **G Mux（Greg Multiplexer）**，改名 **Torty**（龟壳猫）。**Electron app**（同 VS Code / Cursor），周日开工、约 **109 commits**，几乎全在**一个巨型 session** 里完成。
- **核心设计：会话（session）是一等公民**：
  - 主视图是**终端窗口**（不是文件），可在会话间点击切换、无限回滚。
  - **Tmux 内置**：按 `Cmd+T` 打开任意 agent；会话**不在本窗口进程里跑，而是在一个私有的 tmux 服务器里跑**——所以**关掉 GUI 窗口，会话照样活着**，重开一切照旧。
  - **项目在顶部**（不是左侧），可拖拽多路复用（把 Muse / Claude / Codex / Cursor 等不同 harness 并排）。
  - **Git 集成**（Git Graph，Greg 离不开的杀手功能）、**文件树搜索**（VS Code 做不到）、`Cmd+P` 跨项目全局搜索、海量键盘快捷键（可把常用 agent 会话绑到快捷键）。
- **技术选型哲学（Zen of Torty）**：**只用「老而经过实战检验（old and battle-tested）」的库**，尽量不自己造轮子。只有两个较新的库，是熟人写的：
  - **Pierre 的 Diffs**（作者们是前 GitHuber，diff 渲染器比 VS Code 基于 Monica 的快得多）；
  - **Pierre 的 tree 库**（虚拟化树渲染，支持搜树）。
- **后续计划**：做一个**第一流的 skills / servers / hooks 侧边栏**（第四个菜单项），让你一眼看到装了什么技能、MCP server、hooks（Greg 也烦「我到底装了什么 skill」）；会开源。

### 7.2.1 Torty 更多「生活质量」细节（录音有、笔记偏浅）
- 命名：原 **G Mux（Greg Multiplexer）** → **Torty**（玳瑁壳猫）；Electron；周日开工，约 **109 commits**，几乎全在**一个巨型 session**。
- 会话一等公民：主视图是终端不是文件；`Cmd+T` 开任意 agent；进程跑在**私有 tmux 服务器**——关 GUI ≠ 杀会话；可杀窗再开，状态还在（dev 下甚至只是 `npm run dev`）。
- 项目在**顶部**（非左侧），数字键快速跳项目；会话可重命名；拖拽并排 **Muse / Claude / Codex / Cursor** 等多 harness，**不用学 tmux 键位**。
- Git Graph = Greg 的杀手功能；文件树可**搜树**（VS Code 常态做不到）；`Cmd+P` **跨同一窗口内所有项目**找文件；另有内容搜索（字符串命中太多，他个人很少用）。
- 设置向：登录自启、`Cmd+T` 默认终端、回滚深度（渲染器不托管 agent，**后台 tmux** 才托管）、扫描本机已装 coding CLI、海量快捷键（可把常用 agent 绑到如 `Cmd+Shift+A`）、**全局**「Claude Code 总是 dangerously skip permissions」。
- 计划：一等公民侧栏展示 **skills / MCP（HTTP）servers / hooks**（第四菜单）；集成 Spec Story；**开源**。动机：项目级 skill、Claude 的 symlink、agent「用了一个你忘了装过的 skill」——维护税太高。

### 7.2.2 技术选型与 Zen of Torty
- 本想 **原生 Swift**，但树管理 / git diff 等缺成熟库 → 改 **Electron**，避免从零造轮子。
- Zen：**只用老而 battle-tested 的库**；仅两个较新库且是熟人作品——**Pierre Diffs**（前 GitHub 人；堆叠/并排；比 VS Code/Monaco 历史方案快得多）、**Pierre tree**（虚拟化树 + 可搜索）。
- 产品边界刻意收窄：是「带一点 IDE 家具的**终端多路复用器**」，**不是编辑器**；不急着做扩展合同 / 远程云容器；先把一件事做好——**别丢会话 + 同窗组织所有项目**。

### 7.3 构建过程：backlog + loop + 自我验证（本场最能体现课程方法论的部分）
- Greg **没有用 definition of done**（因为几乎全是 UI），而是用了一个**「backlog + loop」**的近似方法：
  1. 维护一个 **backlog**；
  2. 一个 loop 持续从 backlog 拉任务、做 phase；
  3. **不断注入新 backlog 项**，loop 自动接住继续。
- 两个 markdown 文件描述了这套工作流；其中**每个 phase 都带「对抗性一致性（adversarial conformance）」部分**：
  - 因为它是 Electron app，**agent 会真的把这个 app 打开、spawn 多个实例、点击、拖拽 resize**，来**实际验证**「这个功能真的能用」。
- 效果：**「周日的一个想法 → 三天后一个完全 durable、rock-solid 的 dev build」**；测试过程**大部分自动化**（这就是昨天直播里「后台那个长跑进程」在干的事）。
- 金句：**「不断注入新任务让它循环、自我验证、继续跑——这就是梦想。」** Greg 强调他在动工前做了**海量 agent 驱动的库调研**（哪些 JS 库能解决问题），从而避免造轮子。

### 7.3.1 backlog + loop 的现场数字与姿势
- 几乎全是 UI（除 tmux 后端），故**没用经典 definition of done**，而用 **backlog + 持续 loop**：loop 拉 phase；人不断注入新 backlog 项；发现问题当场纠正后走开。
- 方法写成**两个 markdown**（工作流说明里每 phase 含 **adversarial conformance**）；Claude 以很高 effort（录音作 **effort ultra**）跑，并做大量**智能体驱动的库调研**（JS 生态里「已有库/组合能否解决问题」——避免自定义堆）。
- 对抗性验证例：多文件打开、resize 遮住会话、临时全屏读文件——agent **真的 spawn 多个 Electron 实例、点击、拖拽**，到「可打磨」的测试大部分自动化（直播后台长跑即此）。
- 体感：周日一个想法 → 约三天后 durable、rock-solid 的 dev build；该 loop **曾连跑约三天**才第一次关掉；「看着它构建自己，又不用担心构建过程中把自己搞坏」。
- 可复用配方（Greg 给 Jack）：把那两份 markdown 给 agent → 建 backlog → 建「从 backlog 取任务」的 loop → **给足够大块的工作**它就会持续做。

### 7.4 远程访问（Jack 的功能请求）
- Jack 想要：**能在钓鱼时（Starlink + 笔记本）「看一眼」机器上的会话**——只是「查看」，甚至要能「自我封锁（self-block）」防止自己过度使用。
- Greg 的立场：他**故意限制自己不装 Tailscale / Mac Teleport / 手机查看工具**，因为不想 24/7 被工作绑架。
- 折中：Greg 考虑做一个「小 web portal」用于查看（virtual terminal），但**先保持产品简单、只做好一件事**——**「别丢你的会话 + 在同一窗口组织所有项目」**；它**不是一个编辑器**，是「带点编辑功能的终端多路复用器」。

### 7.4.1 「只看一眼」vs「被工作绑架」
- Jack 需求：钓鱼时（Starlink + 笔记本）**只查看**会话；最好还能 **self-block** 防止自己过度使用。BB 对他有用的点正是「机器上虚拟跑着、控制面看一眼」。
- Greg 立场：故意不用 Tailscale / Mac 远程 / 手机看 Claude Code——早期全试过，发现生活被接管；**没有 goal loop、卡在等人批准**时远程确有用，但他优先保护边界。
- 折中可能：小 **web portal / 虚拟终端只读**；仍坚持先做简单基础版。云容器后端不是本场承诺。

## 附：本场核心概念速查（术语表）

| 术语 | 含义 |
|---|---|
| **Port sniper（端口狙击手）** | 自动扫描公网开放端口的攻击者，实例一上线就可能被打 |
| **Provenance（来源/出处）** | 你的代码「是怎么一步步来的」的完整记录，靠日志积累 |
| **Meta skill（元技能）** | 挖掘所有 transcript、再「提议」可安装技能的技能 |
| **Thinking traces（思考轨迹）** | 模型推理过程；DeepSeek 直接暴露，OpenAI 为防蒸馏而加密 |
| **Golden Library（黄金库）** | 指定区域的「最新最真」文档集合，作为唯一来源 |
| **RAG（检索增强生成）** | chunk + embedding + 检索 → 生成「带引用」的答案 |
| **Embedding（嵌入）** | 把文本块向量化以支持语义检索 |
| **Alias library（别名库）** | 缩写/别称到正式条目的映射（输缩写也能命中） |
| **Source of truth（唯一真相来源）** | 让内容直接在你系统产生，而非抓取散落副本 |
| **Harness** | 包住模型的「车」：工具、上下文管理、权限、沙盒等一切外围机制 |
| **Model（模型）** | 「引擎」：只会推理输入、预测 token；本质是权重二进制 |
| **Agent** | **模型 + harness** 的合体 |
| **Tool classifier（工具分类器）** | 每次工具调用时在背后判断「是否有风险」的独立模型 |
| **Guardrails（护栏）** | 烙进模型（如 Claude 宪法）的能做/不能做边界 |
| **/goal** | Claude Code 内置命令，写「完成定义」的长运行目标 |
| **Definition of done（完成定义）** | 目标的可验证停止条件（如「5 条带引用答案」） |
| **Durable session（持久会话）** | 关闭窗口后会话仍存活/可恢复 |
| **Tmux** | 终端多路复用器；Torty 在后台用私有 tmux 服务器保活会话 |
| **Backlog + loop** | 维护任务清单 + 一个循环持续拉任务并自我验证 |
| **Adversarial conformance（对抗性一致性）** | 让 agent 真的打开/操作 app 来验证功能，而非只声称完成 |
| **Prove-it 门禁哈希** | 对工作目录哈希比对「完成合同」；IDE（如 RStudio）暗改文件会导致假失败 |
| **Entra** | 微软现身份/SSO 品牌（原 AD 叙事的当代名字）；企业试点常要搭这便车 |
| **Meta-framework / 外层 harness** | 驱动另一个 harness（如 Co-Work）直到金标准完成的程序（如 virtual Tom） |
| **~5 分钟反馈环** | Co-Work 类产品默认假设的人机节奏，不适合过夜长任务 |
| **Zen of Torty** | 只用老而经实战检验的依赖；少造轮子；会话持久优先于编辑器野心 |
| **IDE 家具** | 终端多路复用器上附带的最少编辑/浏览能力，不是完整 IDE |
