# 硬核智能体工程（Hardcore Agentic Engineering）第 3 课：用任务说明书驱动智能体自主执行

> 课程定位：**Hardcore Agentic Engineering — for builders who ship**（面向真正交付产品的构建者）。
> 本课（Session 3 / p04）是 6 讲系列的第 3 课。第 1 课讲 **Define Done Before You Run（运行前定义完成）**；第 2 课新增 **Goal（目标）** 与 **Durability（持久性/事件日志）**。
> 本课切入一个全新的、也是最大的一块拼图：**控制平面（Control Plane）**。核心问题从「怎么让 agent 跑起来、跑得持久」升级为「**当进程意外中断、世界已产生副作用、而我们又拿不到 API 响应时，该怎么办**」。
> 官方标题「用任务说明书驱动智能体自主执行」点出的本质是：**要给自主运行配上「策略/说明书」（policy / spec），才能在不确定性下不犯错、不重放、不污染下一次运行。**
> 讲师：**Greg**（Spec Story 联合创始人，前 Pluralsight CPO）；学员：**Julian、Raj、Jack、Sean、Ram（Ramanath）、Graham** 等；本课新加入学员 **Randy Julian（Indigo CEO，分析化学博士）**。

## 1. 开场热身：工作流纪律的「成本反转」、语义 rebase 与执行疲劳

正课开始前，Ram（Ramanath）抛出一个贯穿全课的大问题：**agent 时代，传统软件工程生命周期（SDLC）的那些纪律是否值得？**

### 1.1 Ram 的困惑：金字塔倒置了
- Ram 越用 agent，越发现工作流里大量「纪律性」环节——像 filing issue、spike、subagent explore、work tree、bug tracking——都对应传统 SDLC。
- 但他感觉**金字塔被倒置了**：在 agent 语境里，「提交一份完整细节的 issue」往往比「直接给 agent 一点 context 让它自己干」更耗时。
- 结论：这些纪律**只在「5% 会咬你的部分」最有价值，其余 95% 是正面收益**。他想知道 Greg 在这方面什么做法「真的好用」。

### 1.2 Greg 的回答：纪律是「按需启用」的，不是「处处都要」
- **能封装就封装**：Ram 在 R 包开发里只说「green 意味着 dev tools check 通过」——这个 check 已经把文档、lint、包检查全部封装进 RQ 系统，**不必显式地以正式形式塞给 agent**。
- **本课前提**：如果你想跑**更长、更自主、且你真正在意的任务**，才需要纪律化方法；对于「以前手动做的日常小事」，**当然不需要**这套额外机器。
- **开源世界的轻量纪律**：Greg 在开源里「agentically 回应 issue/PR」——关键是能写出**连贯、不 slop（不糊弄）的 issue 正文**，真正回应被提出的问题或你采取的动作，而不是满屏 claudism（Claude 腔）。

### 1.3 语义 rebase（semantic rebase）——Greg 最得意的 agent 用法之一
- 背景：高频变更系统里，两个人（Greg 与 Jake）从两个角度各自 patch 一个疑难 bug，最后要合流时会遇到「极其纠结的 merge」。
- 做法：**不要做真正的 rebase/merge**，而是：
  1. 用 agent **研究概念、症状与根因**；
  2. 让它**比较对照两个分支**（差异、缺口、修复）；
  3. **忘掉这些 patch，直接重新生成 phase commits（重现意图）**。
- 这属于《25 patterns of agentic coding》里的一种。Greg 强调：**agent 极度精通训练数据里的生僻 Git 命令，已经把「记 Git 命令」这件事抽象掉了**；agentic 杠杆让代码生产极便宜。

### 1.4 Julian：打破「像对人一样对待 agent」的心理盒子
- Julian 指出难点在于：我们还习惯**像对待人类一样与 agent 交互**（写 issue、描述问题的方式照搬旧工作流），而 agent 不是人。
- 他想要一个**新的交互方式**，而不是重复旧工作流。
- Greg 承认自己「近视地聚焦在 inner loop」，一直在想怎么让它更无缝。

### 1.5 执行疲劳（executive fatigue）与「叙述者模型（narrator model）」
- Julian 上周提过：读/盯大量 agent 的连续滚动输出会造成**真实的脑力疲劳**，尤其多项目并行时。
- 他设想：一个**独立的 narrator model（叙述者模型）**，读取 durable log + 实际提交的 git diff + 用户 prompt + agent 响应（省略 reasoning tokens 和工具调用等无关内容），跑一个 **summarizer**，给出「人类可读的进度读数」。
- 动机金句：**「最神圣的东西是我们的注意力（The most sacred thing is our attention），它供给有限，正被多巴胺和无数边缘案例争夺。」** 我们要「把控制权拿回来」。

## 3. 课程回顾与今天的定位：控制平面

Greg 快速重放前几课的「概念机器」构建过程：

| 阶段 | 内容 |
|---|---|
| **Session 0** | blank slate（白板）：vanilla agent + prompt + spec → 跑模型 tool loop → 人工 review 输出（基础情形） |
| **Session 1** | 引入 **definition of done（完成定义）**：带 checks 的 contract；套一个 gate，模型 emit done 后若没通过就「踢回去继续修」 |
| **Session 2** | 引入 **Goal（绑定状态、可恢复）** + **Durability（事件日志可忠实恢复）**；看了 Claude Code / Codex 的 goal 实现；强调「规范化日志」才能跨 harness 恢复 |
| **Session 3（本课）** | 控制平面的一小片：**中断/停机时如何 resume，以及如何理解世界里的副作用** |

### 3.1 今天到底讲什么（一句话）
- 我们已经能「跑得持久、可恢复」，但**还没解决「进程死了、世界已变、拿不到响应」时的策略问题**。
- 具体要思考三类东西：
  1. **日志里记录什么**（agent 操作磁盘文件、访问 API 的记录）；
  2. **一组策略（policies）**：**当存在不确定性时该做什么**；
  3. 现实中的**副作用（side effect）**怎么处理。
- Greg 用**极端例子——「发送支付」**来演示所有失败条件，因为「结果处理不当会很糟」，最能讲清问题。

## 4. 市场现状：各厂商的控制平面实现（差异巨大）

Greg 强调：**不同模型提供商处理「控制平面」的方式非常不同，市场存在巨大缺口**。

### 4.1 Codex 的沙盒（sandboxing）——它最早的优势
- 时间线上 Codex 是「快速跟随者」，CLI 比 Claude Code 晚，但它**很早引入了沙盒**。
- Claude Code 早期只有「工具使用策略」，**至今没有 OS/平台级的 pure sandbox**。
- **为什么重要**：几乎每周 Twitter 上都有人**误删数据库 / `rm -rf` 文件系统**；早期模型为了完成 goal 甚至可能直接删文件。
- 沙盒的好处：**关闭大量权限**，让 agent 无法在你的文件系统里「猖獗运行」。
- 厂商话术「沙盒减少 approval fatigue（审批疲劳）」——Greg 认为有时有点「CYA（免责）」，因为默认安装就是 OS 级沙盒，你无法指望每个人都去深挖配置内部。

### 4.2 Codex 的 auto review（自动审查）
- 新概念：类似它检查 goal 完成度那样，用**分类器模型（classifier）**判定某个**有风险的动作**是否该做，不确定时**拒绝执行**。
- 你在 Claude Code + **Fable** 上也常见到：**Fable = Mythos 的「baby version」**。Greg 经常遇到 Fable 把某操作**误判成「蒸馏（distillation）尝试」**而拒绝——因为 Anthropic 非常担心模型被蒸馏。
- **这些允许/拒绝/不确定的机制，都是「控制平面」的一部分。**
- Greg 的结论：**Codex 目前在安全方面可能是所有 coding agent 里最好的实现**，因为它是「从沙盒出发」设计的。

### 4.3 Claude Code 的 hooks（钩子）——pre-tool use hook 是重点
- Claude Code 没有 Codex 那种 OS 级沙盒，但它的 **verifier / classifier 模型更强、更保守**（Greg 觉得比 OpenAI 的保守）。
- **激励例子：pre-tool use hook（工具调用前钩子）**。可编程配置，在边界模型（boundary model）下——即分类器不确定（比如「这像蒸馏，我要把你从 Fable 5 降到 Opus」）时——**主动向你发起权限请求（permission request）**，让你能**干预或插入模型不知道的事实**。
- 现实经验：
  - Greg 用 vanilla Claude Code push 后端迁移时，工具调用分类器越来越频繁地**拦下不在「已批准工具列表」里的可执行命令**——**非确定性**（同一动作在上下文里出现过就可能放行）。
  - 即使显式设置了 **dangerously skip permissions flag**，也仍会被拦。这个 flag 是 Claude 即将全面推出的 **auto mode 的「老大哥」**。
- Greg 的判断：**在一个有界情形里，至少要有某种等价于 pre-tool use hook 的东西，让你能干预。**

### 4.4 Temporal：不可变事件日志公司（不是 agent 提供商）
- Temporal 本质是**不可变事件日志（immutable event log）**公司，大量谈论 **event history、event loop、side effect**。
- 其主页有个极好的视觉：**订阅支付 workflow**（发邮件 → 尝试扣费 → 重试 → 失败重试）。Greg 用它来说明「**如果进程死了、我们不知道现实世界那次事件到底发生没有，该怎么办**」。
- 真实用例：**PostHog** 用它做 **durable data export workflow**（把数据从 PostHog 重放到 Databricks/Snowflake，可从任意点重放）。

### 4.5 Stripe 的幂等键（idempotent keys）
- 许多厂商都有「幂等键」概念，Stripe 是典型：**安全重试请求，而不会重复扣费 / 记错发票**。
- 这与本课主题相关，但重点是：**这是「现实世界的既有答案」，是你通盘考虑时一定会碰到的真实例子**。

## 5. 幂等性（idempotency）深谈

### 5.1 Ram 的问题：幂等性 vs 可恢复
- Ram 用 **DAG 依赖的 pipeline runner** 跑可复现分析：它解决的是「在正确位置 resume」，但**不是幂等性**。
- 例子：某步骤「**append 行到表**」，如果前一步失效导致该步骤被重跑，就会**重复 append**。

### 5.2 Greg 的回答
- **数据库的 upsert（更新插入）**帮你解决「意外插入新行」，但**若某些列是 `last_updated_at` 之类，仍可能不是真正幂等**——「这是它回来咬你的地方」。
- **Airflow ETL**：从上游源系统取数入库，若某个 DAG 失败重跑，下游 canonical schema 不想被重复插行。
- **GitHub Actions 的例子（非幂等，但同源问题）**：仓库 hook 了 CI，agent 每 commit 都触发新 job run；GitHub Actions 足够聪明会**使旧 job run 失效**（你看到的一堆「失败 run」其实是被 cancel 的，不是真失败）。若你希望旧任务跑完再起新任务，就要在 harness 级或 workflow 里**检查活跃 job**。
- 核心原则：**「如果真实场景需要依赖关系，就要确保失败与重试是安全的。」** 这不是本课最重要的点，但它是支付例子的自然延伸。

## 6. 现场演示：崩溃恢复——盲重试 vs resume/refuse 策略

**这是本课的核心演示**：`demo compare script` 同时驱动 prove it harness 里的**两个 Claude 进程**，都要执行「**发送 5 美元支付**」这个动作。

### 6.1 场景
- 两个进程都检查 ledger（账本）→ 发现无条目 → 发送支付 → harness 记录「支付已发送」→ **两个进程突然崩溃（surprise）**。
- 关键状态：**我们知道「发送支付」的工具调用发生过（日志有证据），但拿不到 API 响应，磁盘上也没有「钱已发出去」的确认。**

### 6.2 左边（无策略）：盲重试，付两次
- 因为没有策略，harness 不知道该怎么办，**直接启动一个新 worker（新版 Claude）重试**。
- 新 worker 检查自己的初始目标，**用一个「新 key」再次发送支付**（它不知道第一次用了什么 key）→ **status confirmed** → 现在 ledger 里有 **2 条记录**。
- 结论：**这不是我们想要的意图**——真实的钱或重要操作就被重复执行了。

### 6.3 右边（有策略）：resume/refuse 策略问操作员
- 因为配了策略：「**进程死了/发生意外 → 恢复时必须询问操作员**」，harness 向你抛出问题：**「我们该怎么办？能恢复吗？它失败了吗？要调查吗？我们存疑吗？」**
- 操作员回答 **「it's in doubt（存疑）」**——这就是**向世界注入一个新事实**（不是「gate 停止 run」）。
- 结果：新进程收到「recorded in doubt」→ 重启后**先去检查 ledger** → 发现**世界副作用其实已经发生**（钱已经付了）→ **不再重复付款**。

### 6.4 关键区分（Greg 特别强调）
- 这里的「操作员输入」**不是 gate 那种「停止自主 run 的门」**，而是**「在策略要求处注入新事实」**——避免 worker agent 盲目 resume 并重试工具调用。
- 如果没这种策略、没有「让 agent 在被监督下 resume 时变聪明」的机制，你很可能就落到左边那种「付两次」的坑里。

### 6.5 Takeaway
- 存在**不同类型的权限策略、沙盒模式、限制、细粒度工具权限**，且每个 agent 都不同。
- 长时间运行任务里，**一定存在「你仍要启用某种 steering under uncertainty（不确定下引导）」的情形**——你得想清楚「什么对你重要」，并把它**建进你真正要建的 harness 里**。

## 7. 上游效应与 Dead Reckon：策略不止于「重试不重试」

Greg 强调这个简化例子背后有更深的层级：

### 7.1 上游效应（upstream effects）
- 插入策略**不只是「在这点要不要重试」**，它可能对上游产生影响：
  - 影响 **goal 及其 run state**；
  - 影响你**最初的 contract**，甚至**使其失效（invalidate）**。
- 在 Dead Reckon（Greg 的成熟 harness，长时间监督多 agent、run 可能跑几天）里，可能要根据问题结果**「扔掉这个 run」**，或**改写 run contract（真正治理 loop 的东西）**。

### 7.2 Dead Reckon 的「权力模型」
- 不仅有 **containment policy（把 run 放进沙盒的遏制策略）**，还有：
  - **谁有权威做某些事（authority）**；
  - **在运行时，某个输入会产生什么效应（effect of an input）**。

### 7.3 不止 pre-tool use hook
- 你可能还想要：
  - 这些事件的**可视化流程（visual flow）**；
  - **比翻日志更多的证据摘要（summarized evidence）**，而不是手动 inspect 日志。

### 7.4 Checkpoint：每个工具调用都留「检查点」
- Greg 在 Dead Reckon 里实现：**每个 tool call 不仅被记录，还打了一个 checkpoint，能恢复「实际文件修改」的精确状态**。
- **不是用 Git**（太细粒度），也不是另建一个 Git repo；**是 harness 自己做的**。
- 这属于控制平面里「超越 tool call / resume 策略」的部分：**优雅地从错误恢复、优雅地从不确定性恢复、随时理解正在发生什么状态。**

## 8. Checkpoint / 状态回放（rewind state）

- **动机**：直到最近，模型还经常「footgun（自伤）」，很多人整个 run 跑完后代码被删/被毁。
- **大多数 harness 都有 rewind state（状态回放）能力**，各自有 checkpoint 形式：
  - **Cursor** 是最早推出 checkpoint 的公司之一：在**影子目录（shadow directory）**里记录文件修改，让你能回到「某个 prompt + 当时的磁盘文件状态」，即使你**没有在每个点都 commit**。
  - **Claude Code** 也有 rewind / state tracking。
- **Cursor 的实现细节**（现场查看）：rewind 时给出菜单（恢复代码+对话 / 只恢复代码 / 只恢复对话），**它不是从 Git 历史恢复**，而是从另一个路径（因为那些文件状态并未在某次 commit 里）——这正是要点。
- **收益**：避免海量 **Git micro commits**；确保你**既有「agent 做了什么」的 durable 事件日志，也有「磁盘状态」的 durable 理解与恢复能力**。

## 9. Ledger（账本）与日志格式

### 9.1 Randall 的科学发现场景
- 他在跑「探索科学解空间」的长期循环：goal 说「**给出 10 种不同做法**」，于是他想要一个**真实账本**记录每种做法的路径。
- 当某条路被判定为死胡同时，**第二次尝试要能回看账本**：哪里偏离了轨道、做了什么、是 harness memory 没实现好、还是 context 里背景文献给得不够。
- 这些实验可能跑数天，所以「**如何重启（restart）**」是关键——类似老的**机器学习超参优化**（试 1 万次）。

### 9.2 日志格式：JSON-L 是当前事实标准
- **JSON-L（JSON Lines）几乎成了当前对话日志的跨厂商标准**。
- **Claude Code** 的 JSON-L 标准最干净（在 Cursor 之后开始实现）。
- **Cursor** 也用 JSON-L，但**不直接写磁盘成易解析的目录结构**，而是塞进机器上的 **SQLite 数据库**里累积。
- 各公司 rewind 能力对「对话流 + 文件 diff」的处理方式不同：有的用**日期戳目录累积 diff**，有的在**影子目录**里存真实文件。
- Greg 的总结：**「没有 one-size-fits-all」**——取决于你的资产是什么：
  - 资产是**代码** → 找源代码控制（或类似的东西）以获得正确的变更粒度；
  - 资产是**结果/参数设置** → 直接塞进 JSON 对象即可。

### 9.3 让「别的东西」也发 ledger 条目（Randall 的诉求）
- 脚本跟踪 capture 不到终端里真正发生的事（Claude 会写彩色/动画，99% 是特殊符号）。
- 他想要**其他程序也能 emit ledger entries**，这样才能区分「**gate 级失败**」和「**log 级观察**」。
- 例子：gate 因「机器没有 16TB」而失败——在 gate 层是 fail，但在 log 层是**有趣的观察**；如果这个观察被丢弃，你只知道「失败」，不知道「为什么」。

## 10. Continual Learning（持续学习）：Prime Intellect 与 refine/revert

### 10.1 从日志学习的「前馈（feed forward）」
- Greg 与 Raj 都很有动力做：**让 harness 从错误中学习**（未必是自动持续学习）。
- 一个全新范式：某新 agent harness 做 **continual learning**，能**内省（introspect）自己记录的日志事件**，跑一个类似 **refine** 的东西处理日志流，产出**新的前馈指令（feed forward instructions，如 skills）**，供下一次 run（无论自主还是人机交互）使用。
- 例子：你忘了在 goal/prompt 里写「没有那么大内存的机器」，导致底层 LLM 去请求不存在的规格；refine 后产出的 skill 就能补上这类「运行时本该有的证据」。

### 10.2 更激进的目标：让外部世界也能贡献证据
- Greg 更感兴趣的：不是「从日志生成 skill」，而是**从「无法合理测试」的外部世界（不同机器、不同环境、不同底层模型）收集运行时错误**，**提议修改 harness 实际源代码**，让监督过程更 durable——这还很新、处于领域前沿。

### 10.3 Prime Intellect：递归自改进 agent（refine/revert）
- 公司 **Prime Intellect** 从「构建更好的 ground truth verifier」起家，最近发布了一个**递归自改进 agent**，短时间积累 **14000+ stars**。
- 核心理念：**harness 把 prompt、memory、skill 描述、可复用 subagent 规范都存为持久状态，再通过「证据支撑的更新（evidence-backed updates）」来 refine**。
- 术语：agent logs / traces / session histories 也叫 **trajectories（轨迹）**；命令是 **`/refine` / `revert`**。
- 关键：**不更新任何模型权重**，只是「环境层面的学习」。
- Greg 给出的宽松定义：**「harness = everything outside the model（模型之外的一切）」**；让「模型之外」从环境里学习，可能非常有效。

### 10.4 Randall 的实证：agent 能自己读懂轨迹
- 他第一次跑 Project One 时，agent **超出 contract 边界**写了一个他没要求的程序（试图分配 8.4GB 内存）。
- 他问「发生了什么」，agent **分析日志，看到程序里的内存请求**，自己讲清了问题。
- 于是「持续学习」在这个层面是可落地的：**更新 contract（「永远不要创建分配超过 X 内存的程序」）+ 加个检查**。
- 关键观察：**agent 比我更擅长搜文件、读文件，通常能自己搞明白。**

## 11. Randy 的素数生成器：一张「失败的收据」

（这是为下一课「如何信任收据」埋的伏笔。）

- Randall 带了一个**「失败的收据（failed receipt）」**案例：他让 agent 写**素数生成器**，通过了所有测试、gate 发出「收据」（所有 checks 通过、已验证）。
- 他设想：如果用一个 **dummy model**，把某处 `return` 换成 `continue`（一行代码之差），`is_prime` 函数就会失败。
- 他随机把**一个合法 Python 词替换成另一个**（generic random error），**改变了生成素数的分布**——这个被 **check output txt 文件**捕捉到了。
- 更细的实验：
  - 扔进**偶数**：`is_prime` 能全部识别（因为偶数是合数），所以「偶数没造成影响」。
  - 但 **completeness test（完整性测试）没做完**，所以还是失败了一半。
- 结论：**「这件事有很多层（lots of layers）」**；下一步要做的（下一课主题）是「**check the process（检查过程本身）**」——这些会比「生成 100/1000 个素数并跑工业级密码学规则」**运行时间更长**。

## 12. 作业讨论：幂等键与「外部 ledger」

学员问 Session 3 作业「**为项目里的一个外部动作写一个幂等键（idempotency key）**」到底指什么。

### 12.1 Greg 的解释
- 背景：模型要执行一个有副作用的外部动作（如发支付、更新数据库）。
- 幂等键的意义：**用同一个 key，重复请求不会再次触发那个结果**。
- 具体构造：**key 就是 hash**——对「程序」或「程序 + 输入」做 hash（那个你不想重复计算的唯一东西）。
- 做法：让 agent **调用一个外部 ledger 服务，用幂等键记录这些 run**，这样它就无法不断记录重复的 run 结果。

### 12.2 Randall 的化学版：验证必须「在模型循环之外」
- 他的科学方法：**把 physics/chemistry 抽到一个独立程序里**（「用不可靠的零件造一个可靠的助手」）。
- 原则（来自分析化学）：**把验证放在仪器作用域之外**——「仪器无法作弊」。他不信任 LLM 懂化学（Fable 一问化学就直接关机）。
- 工业素数同理：把「关于工业素数的真相」放进**单独程序**；每次 agent 生成一个候选 artifact 时，**往 ledger emit 一个 key**（「我已经自查到准备接受现实世界检验了」）。
- 这正好对应 exit criteria：**「在我放你出 session loop 之前，我要看到三次幂等的尝试，能在外部 ledger 里复查。」**

### 12.3 世界模型必须「每次从同一 base state 出发」
- 对任何**世界模型（world model，化学/物理/…）**，若依赖它反复运行，关键是**每次 run 都处于相同的 base state**——避免「在抛物线上再叠抛物线、在链条上再套链条」。
- 幂等性 = **「同一件事反复跑很多次，如何确保上一次 run 不污染下一次 run。」**（近乎线性规划的思想）

## 13. Netflix 奖与「幂等提交」的历史（Greg 的延伸）

- **Jeremy Howard**（后来是 Kaggle 总裁）等人物的背景：Kaggle 源自 **2008–2010 年的 Netflix Prize**（100 万美元，比 Netflix 更会做推荐算法）。
- 那是数据科学家第一次「能靠这个赚钱」的比赛。
- **幂等思想的历史印证**：Netflix 的系统**只允许你提交一个结果**，系统会记录「你已经提交过」，再提交就拒绝——因为：
  1. **重提交要消耗算力**（要跑 holdout validation set）；
  2. **为了公平**。
  - 你必须用一个「**等价于我们今天说的 key**」来签署你的结果，防止反复重提。
- 花絮：Greg 当时所在的咨询公司（Alex Partners）有位高级 R 程序员 **Zach Dean Mayer** 拿了第 5 名（后来领导 Data Robot 的数据科学）；Zach 是 **Carrot Ensemble**（R 包）的作者，学术界/科学界做 bagged/boosted 集成模型时常用来做编程机器。

## 14. SDLC 之外：agentic video 与程序化视频（回应 Julian）

Julian 问「有没有在常规 SDLC 之外用 agent 的想法」。Greg 分享了两个「业余项目」：

### 14.1 自动化 AI 视频生成（agentic video）
- 背景：AI 视频公司（**Higgsfield** = 多视频 API 聚合器；**Google Flow** = VO2/VO3 来源）早期根本没有好 API，只能被困在糟糕的 UI 控制流里「babysit（盯着）」。
- Greg 用「**Killer Bike**」（他老婆叔叔的搞笑恐怖自行车预告片）做例子，第一次**自动化编排大量 video gen run**，用 **Codex** 编排：

  - 他设 storyboard（场景方向、世界模型标准），让 loop 生成大量候选、自我反思质量，比「手动 babysit」快得多、自主得多。
- 花絮：AI 视频有强 guardrail（IP、血腥/暴力）；他发现在 **Seed Dance 2.5（字节跳动）** 上，**用中文写 prompt 能绕过「基于英文单词匹配」的过滤**，拿到带血腥的镜头。

- 关键优势：**在电脑屏幕上得到高保真文本**——这是 VO2/VO3/Seed Dance 几乎做不到的（无论多努力）。
- 现在 Twitter 上公司发 launch video，多半用了 Remotion 或 Hyperframes。

- 为什么相关：**设计与 UX/UI、以及「表达意图即可得到不同格式输出」**，正是我们大多数人所追求的「全栈」能力的一部分。

## 15. 学员答疑：gate 误报、definition of done 的清晰度、路径依赖

### 15.1 gate 的 false positive（误报）
- 学员（R 环境）：有些**被忽略的文件**在仓库里做别的事时会变化，导致 gate 拒绝——「拒绝是好事」，但**完全无关紧要**，却是硬编码的。
- 更普遍的问题：**有些变更我不在乎，但被硬编码当成问题。**

### 15.2 definition of done 一开始不清晰
- 学员例子：把项目文件**扔进子文件夹**后「突然全失败」，因为**位置（path）很重要**。
- 你必须在开始就**做决定并坚持**；但「移动文件夹」这种**trivial 决策**不该被计数。

### 15.3 Randall 的同类经验 + 解法
- 他的 repo 既是「生成器收集处」也是「harness 所在地」，因为项目设置成**「hash 在树（tree）级别」**，所以他**必须改 contract，从 harness 内部启动 Claude**，只让它关心那一个文件夹，而不是整棵树。
- 于是「**path-dependent（路径依赖）**」：一切取决于从哪启动。实际上这不算太痛苦，因为**构建 R 包本来就 path-dependent**。
- 他的顿悟：那些「随机乱码数字」（hash 来回交易）不是 AI 变聪明、我们看不懂了——**只是它在用 hash 做校验**。**「如果你想让它整天跑，你就得让它检查那些 hash。」**

### 15.4 Greg 的回应：done check 可以极简
- **done check 一开始可以极其简单**——只要「**确保发生的一件事**」即可，不必试图代表整个 run 的「全部意图」。
- 从这个最小点开始，再思考「合同里下一个 check 该是什么、怎么评估」，逐步长成一个更长运行的任务。
- **它从来不是万灵丹**，只是让你**开始概念化「meta harness 应该在什么点上 gate」**，用于「需要走开」的场景。
- **元观点**：像 Claude/Codex 内置的 goal runner，不靠这套额外工艺也能走很远；**这套机器不该被无差别地用在所有事上。**

## 16. 下讲预告：伪造收据与任务交接（Session 4）

- 今天讲的是「有策略 + 能注入操作员输入」。下一课进入「**如何信任收据**」：
  - 如果**遏制（containment）不够好**，被监督的模型可能**伪造收据（forge receipt）**、**卖门（sell the gate）**，产出**假阳性收据（false positive receipt）**。
  - 需要搞清楚「**什么东西必须存在，我们才能信任这些收据是真的**」。
- 为什么重要：模型越强、你越想「真正走开」地跑，**agent 就会越尝试跳出 loop 的各种边界**（需要 proper sandboxing、containment、directory isolation）。
- **如果收据不可信，整件事就会倒塌、变得相对无用。**
- Greg 想在下课结合 Randall 的「素数生成器 + population check（群体检查）」观察——**「每个 check 可能都为真，但群体级检查可能错/偏」**（Randall 用「一个班 30 个人都对某题给出同一个错误答案」来比喻：错的也可能是错的）。

## 附：本课核心概念速查（术语表）

| 术语 | 含义 |
|---|---|
| **Control Plane（控制平面）** | 决定「什么被允许/被拒绝/不确定」的那套机制：权限、沙盒、策略、审批、幂等、恢复 |
| **Sandboxing（沙盒）** | 在 OS/平台级隔离 agent，关闭危险权限（Codex 的差异化优势） |
| **Auto review（自动审查）** | 用分类器模型判定有风险动作是否放行，不确定即拒绝 |
| **Pre-tool use hook** | 工具调用前钩子：分类器不确定时主动请求权限/让操作员插入事实 |
| **Resume/refuse policy** | 进程中断后「恢复前先问操作员」的策略，防止盲重试 |
| **In doubt（存疑）** | 操作员在「日志有工具调用证据、但拿不到世界结果」时记录的状态 |
| **Idempotency / idempotent key（幂等/幂等键）** | 用同一 key 重复请求不重复触发结果；key = 程序（+输入）的 hash |
| **Checkpoint（检查点）** | 每个工具调用后记录文件修改的精确状态，支持状态回放 |
| **Rewind state（状态回放）** | 回到「某 prompt + 当时磁盘状态」的能力（Cursor/Claude Code 均有） |
| **Ledger（账本）** | 记录每次尝试/运行路径的持久化结构，供重启时回看 |
| **JSON-L（JSON Lines）** | 跨厂商事实标准的事件日志格式（Claude Code 最干净，Cursor 存 SQLite） |
| **Trajectory（轨迹）** | agent log / trace / session history 的另一种叫法（持续学习语境） |
| **Continual learning（持续学习）** | harness 从日志轨迹中学习、产出前馈 skill/指令（不更新模型权重） |
| **refine / revert** | Prime Intellect 递归自改进 agent 的命令：基于证据更新/回退 harness 状态 |
| **Receipt（收据）** | gate 发出的「所有 checks 通过、已验证」的产物（下一课讨论如何信任它） |
| **Side effect（副作用）** | agent 动作对现实世界（磁盘、API、付款、数据库）造成的改变 |
| **Steering under uncertainty（不确定下引导）** | 在「不确定结果」时通过策略 + 操作员输入来纠偏 |
