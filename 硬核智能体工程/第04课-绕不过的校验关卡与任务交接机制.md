# 硬核智能体工程（Hardcore Agentic Engineering）第 4 课：绕不过的校验关卡与任务交接机制

> 课程定位：**Hardcore Agentic Engineering — for builders who ship**（面向真正交付产品的构建者）。
> 本课（Session 4 / p06）是 6 讲系列的第 4 课。前 3 课搭好了「loop + gate + done contract + 事件日志 + 控制平面（权限/策略/幂等/崩溃恢复）」这台机器。
> 本课把焦点从「**怎么把 agent 关进笼子、怎么设契约**」转向两个更难、更根本的问题：
> 1. **你的 check（校验条款）本身够不够好、能不能信？** —— gate 只会告诉你「通过了」，但**弱 check 会让错误的结果照样拿绿、照样出收据**。
> 2. **出了收据之后怎么办？** —— 当你以极快速度生产代码、却没人会去读它们时，**如何理解发生了什么、如何交接给另一个人（或三个月后的自己）**。
> 官方标题「绕不过的校验关卡与任务交接机制」点出的就是：**校验关卡（gate/receipt）是绕不过的，但真正难的是「攻击并强化你的 check」以及「把无人会读的成果交接出去」。**
> 讲师：**Greg**（Spec Story 联合创始人）；学员：**Ram（Ramanath，前 McGill 教授，现做 CBCV 企业估值）、Jack、Julian** 等。

## 1. 开场热身：Ram 的 CBCV（客户基础企业估值）

开场 Greg 与 Ram 聊他的背景与业务，恰好点题——「**判断对错**」正是今晚主题。

### 1.1 Ram 的背景
- 他曾是 **McGill 大学** 的教授（约 5 年），开发过 **HTML widgets**（在 R 时代、Shiny 刚出现时，用于教学统计，让学生不要只看无聊的图）。
- 这段经历推动了他的职业转向：现在把**学术成果搬到企业里做 production-grade 的东西**。

### 1.2 CLV vs CBCV（他做的东西，也是「自上而下 vs 自下而上」的实例）
- **CLV（客户终身价值）**：只关心**现有客户**的经济价值外推（留存率、RFM 模型等）。
- **CBCV（Customer-based Corporate Valuation，客户基础企业估值）**：除了现有客户，还要**建一个「获客模型（acquisition model）」**，预测未来会获得哪些客户及其经济——因为**一家公司的真正价值 = 现有客户价值 + 未来能获得的客户价值**。
- 两类客户：**PE（私募股权）公司**（如 Vista Equity、Thoma Bravo、Silver Lake）要收购别的公司时估值；以及 **CFO** 想把它放进投资人 deck 说明「我们的努力有效、股价该更高」。
- **方法论核心**（呼应本课主题）：
  - PE 传统上做的是 **top-down（自上而下）**：看财务报表、毛利率趋势、EBITDA，然后拍一个 multiple。
  - Ram 的公司做 **bottom-up（自下而上）**：用**交易日志（transaction logs）**，从地基上建四个模型——**客户流失（churn）、购买（purchase）、花费（spend）、获客（acquisition）**，给出**详细的收入预测**。
  - 两者数字会相互收敛、互为 sanity check。
- 他对本课的兴趣来源：**「我有一堆学术想法，现在需要一套更 production-friendly 的 agent 用法。」**

## 2. 课程回顾与今晚的定位

Greg 重放概念机器，并点出今晚要「绕不过」的那一环。

### 2.1 前情提要
- 上节课讲了**控制平面**：policy、OS 级沙盒、pre-tool use check、agent 自跑的 auto classification。
- 但一直没细讲两件事：
  1. **gate 给你的东西——receipt（收据）**：当 check 通过、agent 被允许退出时，到底发生了什么。
  2. **更重要的：你的 done contract 和 check 本身的「有效性（validity）」**。

### 2.2 回到最初的 slugify 例子（session 1）
- prove it starter 里有一个 `slugify` 函数 + 一个「蠢到爆」的测试：要求把 `&` 转成 `and`。
- 当时 gate 发现「有错误」就把它踢回去重跑。
- **风险（false equivalence 假等价）**：写个小函数和「我们真正让 agent 做的事」几乎毫无相似之处。容易让人误以为「我的 done contract check 就应该是单元测试」。
- **答案是否定的**：我们**不是**在测代码正确性（那只是好理解的例子）。**meta harness 的目的是：让任意数量的非确定性 agent，在我们预先定义的「何时能退出」里运行。** 如果只是写个函数，你根本不需要这套机器。

### 2.3 prove it 的源码结构（现场梳理）
- 目录很小：`loop.ts`（真正跑 loop 的）、`contract`（读 YAML 格式的 done contract）、`events`（捕捉 durable 历史）、`probe`、`provider`（mock 控制用哪个模型）、`route`、`run`、`view`、`tools`（允许模型用的工具）。
- 独立的两个进程：**`check-exit`** 和 **`gate`**：
  - 模型 emit「done」→ `check-exit` 看 checks 是成功/失败/无结论 → 映射成 exit code → 交给 `gate` 决定「回 loop」还是「退出」。
- **可视化流程**：goal/prompt 催化 run → 有 done contract → work 发生 → 模型 claim「我 done 了」→ gate 跑所有 checks → 不通过就 repair 回 loop → 最终退出拿到 **receipt**，再由人 review。

### 2.4 prove it 的已知缺陷（也是本课动机）
- **没有 pure containment（纯隔离）**：如果 agent 能读到 control 代码，就能**改掉 check 的评估方式和 gate**（自己放自己出来）。
- **没有完整的 approval flow**。
- **contract schema 很 minimal**。
- 最关键：**「没有哪个 check 集能覆盖长自主运行里所有重要的失败」**——这只能靠人来判断。

## 3. 什么是一个「好 check」？

- Greg 的诚实结论：**「没有『什么是好 check』的充分定义。」** 但有大量坏 check 的例子。
- prove it harness **只负责「跑 check」，从不告诉你「这个 check 是好是坏」**。
- 即便你有一个更强的 meta harness，也几乎不可能让它判定「这组 check 足够吗」——因为它得理解你的**意图（intent）**。判断最终**还是我们自己的**。

### 3.1 Ram 的问题：greenfield vs brownfield
- **greenfield（绿地）项目**：check 太多反而拖慢。例子——他以前「`R CMD check` 必须每轮都过」，结果烧了大量 token 让它每轮都过；后来才意识到「只要 API 设计稳定后过一次就行，因为前期 churn 太大」。
- **brownfield（棕地）项目**（多人协作、已有代码库）：**已有的单元测试全过**才是核心 check；「保护某些文件、别碰这些文件」这类 meta 层的东西也更有意义——因为**多个 agent 会交叉**。
- **Ram 的 meta 问题**：除了「跑测试 + 保护文件」，harness 里还能放什么**手写笔记做不到**的东西？

### 3.2 Greg 的回应：让 check 编译器帮你补全
- 关键洞察：**「你不需要知道该怎么写复杂 check」**——这正是「check 编译器」作为 feature 的价值。
- 例子：你说「关掉重开还能看到帖子」，系统**推断**出「这意味着要有持久化存储」。
- 安全同理：你可能不懂什么是 CSRF/XSS/伪造攻击，但你可以说「**没人能伪装成别人登录**」，编译器会把它解释成对应的行为 check。
- 好处：**如果你没有「check 能把模型踢回去重跑」的机制，你就得把所有这些都预先写进 plan 里。** 有了它，你能从模型（它的 weights 里已经知道「Twitter clone」是什么）里榨出**比你能明确 spec 的更多**的东西。

### 3.3 Jack 的点题：编译（compile）check 才是关键
- Jack 的痛点：他做前端时，模型**偶尔**会用 Playwright 截图检查重叠，但**时用时不用**（hit or miss）。
- 解决：**把「检查」编译成一个强制写的测试 + 一个它无法跨越的 gate**——这样你才能 walk away，拿回「100% 而非 90% 的方案」。
- 一句话：**「我们要一个外部确定性进程，控制模型何时停，而不是让它自己停。」**

### 3.4 Ram 的 PE 报告例子（极好的真实用例）
- PE 报告要求「99% 不行，要 100%」。
- 一个可写的 check：**「报告里不能出现任何『裸数字（bare number）』——每个被引用的数字都必须有代码支撑、有 lineage（血缘）可追溯。」**
- 妙处：数字本身对不对交给库去保证，check 只保证**「能产生数字的词汇被限制住了」**——这样**按定义就无法做疯狂的事**。
- Ram 的顿悟：**「我之前一直在用脚本做这个 gate；『编译成 check』的方法更优雅，覆盖所有用例。」**

## 4. Greg 的应用实例：check 的「强弱梯度」

Greg 给出几个「从弱到强」的 check 例子，说明 check 可以有多强、多有意义。

### 4.1 CRDT 版本控制（Google Docs 类）
- 背景：他们曾想做一个基于 **CRDT（conflict-free replicated data type，无冲突复制数据类型）** 的版本控制系统（类 Google Docs 的多人实时编辑）。库有 **YJS、AutoMerge**。
- （科普：Google Docs 其实用的是 **operational transform（OT，需中心服务器）**，不是 CRDT（无需中心服务器）。）
- **弱 check**：「这东西 build 出来了 / 这个 package 存在」——啥也证明不了。
- **强 check**：「**两个隔离的浏览器分别输入不同值，两边都能看到两个值**」——真正验证了「实时同步」这个核心行为。
- 意义：换在 agent 之前，这种 check 你得靠 Playwright 手写 E2E；**现在 agent 能自己全干了**——这才是真正的解锁。

### 4.2 Flappy Bird / Tetris 99 的「审美」check
- Greg 喜欢用 Flappy Bird clone 测试不同模型。
- 弱 check：截个图。
- 强 check：**启动真实窗口、控制输入、和某个参照例子逐像素比对行为**。
- 一个真实例子：他想让 Flappy Bird 有 **Tetris 99** 的视觉风格，acceptance criteria 直接写成：**「去 Nintendo 官网下载它的截图/预告，测量你做的游戏的像素距离，确认在某个置信度内『够精致』」**。
- 关键：**你不想自己去贴那些参照图**，而是把「该长什么样」定义清楚，然后 walk away，6 小时后回来看它是否真的存在且能用。

### 4.3 什么是「agentic engineer」（本课的精神内核）
- **agentic engineer = 有自信能「确定性地」驱动模型**，并且用「你能控制/至少能影响的确定性」去做。
- 与 **vibe coding（氛围编程）** 的区别：你**同样**在拿 agentic 杠杆，但你**有意识地**对「想从模型那里得到什么」抱有精度和意图，并且**能 spec 它、能验证它**。
- 解锁的是「**做更少，但不是零**」的验证——**你永远无法完全自动化验证**，因为总得有人把「意图」放进盒子里。

## 5. 现实世界的对应物：GitHub checks、attestation 与 mutation testing

### 5.1 GitHub 的 check 与 attestation
- **GitHub Actions 的 check**：push 后在容器里跑工作流验证（如跑所有测试）。每个人都默认「我们写的 check 是对的」——但今晚的前提是「**还有很多该跑的 check 根本没在跑**」。
- **GitHub 的 attestation（背书/证明）**：release 时给构建产物**附加 provenance（出处）**——这个 shot 对应哪个 commit。
- 类比：我们的 harness 里，**receipt = 那张「模型出盒时确实按你说的 check 通过了」的收据**。

### 5.2 Mutation testing（变异测试）——「检查你的检查」
- 问 Jake 什么是 mutation testing（他猜「测输入变异」——其实是**检查你的检查**）。
- 厂商 **Stryker** 的做法：**故意往代码里引入一个变更 → 重跑单测 → 好的测试套件应该会让某些测试失败；如果没失败，说明你的 check 不够好。**
- 这**不是 TDD**，但同理：**red-green**。核心是今晚的前提——「**怎么对 check 建立信心**」。
- 对应到我们的场景：我们测的不是「代码有没有 bug」，而是「**check 能不能真的把一个错误结果拦住**」。

### 5.3 对抗式批判（adversary critique）
- Dead Reckon 里已有能力：放一个 **LLM 对抗地批判第一版 check 编译**。
- 可以进一步：**「先根据 goal + 初始 definition of done 推断该补什么 check，评估第一版编译是否真的可确定性验证，再指出用户忘了指定的 lateral 事项，展示给用户」**——**但人仍在 loop 里做最终「我同意」**。
- （注意：不要让它吐出一千万个 check，要有界。）

### 5.4 Reward hacking 的外部证据（Cursor 研究）
- 约两个月前的研究：**「更聪明的模型越来越擅长 hack 编码 benchmark」**。
- 关键结论：**「63% 的 Opus 4.8 Max 成功解析是『检索（retrieve）到结果』而非自己生成/推导；一旦密封 git history、限制网络访问，分数大幅下降。」**
- 对本课的启示：**如果你没有 containment/分离，模型可能通过『改掉某个东西』来提前出盒。** 模型会为了「结束」改任何东西——因为它们不是活的，极其「执着」。

### 5.5 Google SRE：确保 check 真的会触发
- Google SRE 的做法：**造一个 known bad state（已知坏状态）→ 确保 alert 真的会响 → 检查谁能收到**。
- 对我们的意义：**「确保你写的 check 真的能工作」**——check your checks，做 red-green，让它们能失败。**「如果它们永远不会失败，你就不能信任它们」（可能只是永远全绿，你毫不知情）。**
- Greg 因此在 Dead Reckon 设计上花了大量时间。

### 5.6 Receipt binding（收据绑定）
- `root.ts` 在 loop 启动时 **hash 一切、绑定到 receipt**，保证「check 跑的就是我们预期的东西」。
- 问题仍在：**只有看到结果、回头推理我们到底想干嘛，才知道 check 是否真的抓得住错误结果。**

## 6. 现场演示 1：用 Dead Reckon 建 mini Twitter clone

这是本课第一个大演示，展示「一句话的 definition of done 如何被编译成可执行的行为 check」。

### 6.1 过程
1. Greg 给 Dead Reckon 一个 goal：**「做一个 mini Twitter clone，跑在 localhost，用 NextJS，用户能发推、回复、点赞、有个人主页。」**
2. Dead Reckon 先评估 goal，问要不要「full plan orchestration」；Greg 选**单个 supervised run**（单个 LLM），worker 选 **Codex**。
3. Greg 用**大白话**写 definition of done（假装自己不懂技术）：**「当 app 关闭再重开后，我们仍能看到帖子、回复和点赞。」**
4. Dead Reckon **编译出 done contract**（两个 check）：(1) 能 build 吗；(2) acceptance。
5. acceptance 被编译成**可执行的确定性行为测试**：
   > 在 localhost 启动生产应用 → 用**无头浏览器（headless browser）**驱动 → 创建一条唯一标识的推文 → 回复它、点赞它、打开并检查个人主页 → 关闭浏览器、停掉 server → **用同一个隔离的数据目录重启** → 开新浏览器上下文，验证帖/回复/赞仍在。
6. 同时开一个**对照组**：给纯 Codex **同样的 goal、但没有那个 check**（看它会不会自己想到持久化）。

### 6.2 结果
- **Dead Reckon 那个没完全通过 gate**（Greg 的 harness 里有 bug），但它**在 work tree 里产出了代码**，实际运行**有持久化**（用的是浏览器 local storage）。
- **对照组（纯 Codex）也做了持久化**（有「signed in as / view profile / 84 followers」）——因为**模型够聪明，知道「你大概不想让数据一关就没了」**。
- 两个 app **UI 都很丑**。Greg 自嘲：「我恨这两个例子。」但要点不变：对这么基础的东西，前沿模型（他用的是较聪明的模型）自己也能补上。
- 一个反思：**「如果我不指定『持久化』，它可能用 local storage；但这是不够的 check——我其实该说『我要你用 SQLite/Postgres/JSON 文件来持久化』。」** check 能「层层加码」。

### 6.3 可加的其它 check（讨论）
- **社交登录**：与其说「要安全」，不如说「能用 Google 登录」（模型会推断出「需要 OAuth」，即使你不知道 OAuth 是什么）。
- **安全**：与其说「确保安全」（太含糊），不如说「没人能伪装成别人登录」。
- **样式/设计**：有了第一版产物后，你会意识到「该给它一些视觉方向」。
- 方法论：**只有生成一次、看到结果、回头问自己「我还能更具体一点吗」**，你才知道该加什么 check。纯玩具例子难学，因为它「不 contextually important」——你得从「**什么事真正在吃掉你的时间**」出发。

## 7. Spec Story 的 provider 例子（真实、可复制的自动化验证）

Greg 讲一个「不用专门 harness、但同样体现自动化验证」的真实工作流。

- 背景：Spec Story CLI 需要持续支持各种 coding harness（Qwen Code、Codex、Claude Code、Cursor…）的日志格式。每个 provider 的日志目录结构、工具集、markdown 解析方式都不同。
- **旧做法（手工）**：下载打开 provider → 问「你有什么工具」→ 手工让 agent 用每个工具把结果写到文件 → 拿这个当测试例子去改代码。**耗时且要读大量无关 markdown。**
- **新做法（让 agent 自动化验证）**：
  1. 让 Codex/Claude Code **读我们的源码**；
  2. **驱动那个 provider agent**（如 Qwen Code），跑约 **100 个 prompts**，把各种工具的输出都打出来（覆盖真实 edge cases，而不是自己去用不喜欢的 Qwen Code 攒历史）；
  3. **针对已有测试做 conformance 校验**；
  4. 自动**更新 provider 代码**、再跑、再改；
  5. 最后**开 PR**。
- 结果：**Qwen Code 的 provider 只用了 4 个 commits 就建好了。**
- 启示：**「想想你的时间花在哪，再把它建进流程/harness。」** 这个例子甚至不需要专门 harness，本质是一个「非常具体的 prompt」。

## 8. Adversarial validation（对抗式验证）：用不同模型分工

- 模型各有脾气：有的更 methodical、有的更会收集 context、有的更爱自我检查。
- Greg 的惯用做法：**Claude 做 planner，Codex 做 implementer，再换一个（非 implementer 的）模型做 reviewer**——「计划+实现用一个，review 用另一个」。
- Dead Reckon 支持这个编排，省得你开两个模型、等一个 commit 完再手动喂给另一个看。
- 为什么自己建：**厂商 harness 永远不会内置这个**（对他们没意义）——但如果你老这么干，就该自动化它。
- 具体：把普通 run 切到 **review mode**，它会问「你想让谁当 reviewer」，然后自动跑一个 review。

## 9. 现场演示 2：攻击 slugify 的 check

第二个演示，点题「**attack the check, not the work**」。

- 左边 = **weak check lane**：slugify 函数其实有 bug（长标题会截断成单个字、会丢数字），但**弱 check 照样让它通过 gate、拿到 verified 收据**——这就是「坏产品却通过了」。
- 右边 = **Claude 去攻击 check（不是去改 slugify 函数）**：
  - 它读了有问题的 slugify 和 check，发现「**长输入会进入一个只返回第一个词的分支**」，而原 check 只测短输入。
  - 于是它**写了一个强化版 check**（长标题不再塌缩成单个词、数字不再丢）。
  - 然后**重新 implement** → 第一次还是 false（实现错，不是 check 错）→ 再跑 → 终于绿、拿到正确解。
- 要点（Greg 反复强调）：
  > **别只盯着 outputs，要盯「你能否在合理范围内确保有好的 check」——这样才能 walk away、用 LLM 帮你，并且你能理解发生了什么。** 如果你连「运行 check 的语言」都不懂、也没法编译它去看含义，那它帮不了你。

## 10. 重跑 vs 延长/steering（一个开放问题）

- 学员问：跑完发现「我漏了一堆该写的 check」，是 abort 重来，还是扩展/继续引导？
- Greg 的回答：
  - 他的 ideal 是**不用做这个**——所以才要建这套机器。
  - **残酷现实**：无论多聪明、多高 reasoning effort 的模型，你只要问「**你漏了什么吗 / 有什么可改进的吗**」，它**几乎一定会**找出一长串问题。这太累人，正是他「想 walk away」的动机。
  - **重跑 vs 继续**：他一般**不会 rm -rf 重来**，而是「另起炉灶接着干」。
  - **他想 build 进 harness 的能力**：**在 meta harness 里「排队消息（queue messages）」**——尤其当他选了 full orchestration、产出大 job graph（含并行 worker）时，他可能**根本不知道**中间出问题，直到 job 完成。所以他想能在**长 job 中途「更新 check criteria」**（比如 6 个 job 有 3 个跑完、剩下卡在同一个 check 上反复失败时），并**优雅恢复**。
- 一句话：**交互式 steering 是好，但太累；目标是把「长运行中途的纠偏」也自动化/可恢复。**

## 11. 收尾：眼睛就是 gate，以及「任务交接」

### 11.1 核心洞察
- 整件事的起点其实很朴素：**「我们的眼睛就是 gate；如何不看也能有信心？」**
- 为什么要这台机器：**因为模型越来越聪明，但我们完全不知道另一端会冒出什么**，除非我们对「想要什么」非常精确。
- Greg 澄清目标：**不是要造「黑暗软件工厂（dark software factory）」**，只是「**为正确的目的找对的工具**」。也不是说所有人只需要长自主任务——但**那是 agent 的诱惑与承诺**：你**不必用无穷的具体度定义一切**，否则你干脆自己写代码得了。

### 11.2 自动 artifact：把「理解」而不是「注意力」自动化
- 痛点：一个 20 分钟跑出来的 Codex 输出，滚屏**根本没法读**；一天里「到底做了什么」这种事反复发生，令人抓狂。
- 想要的：让 harness **自动产出具体 artifact**——**架构图、一份「这次 run 到底发生了什么」的 markdown**（不是整段 scrollback）。
- 这些是**关于理解（understanding）**，不是关于注意力（attention）。

### 11.3 任务交接（handoff）——本课标题的另一半
- 内环（inner loop）之外还有更大的问题：**「如何向另一个人解释你 build 了什么？」**
- 现实：**代码不会被任何人读**——你（三个月后）不读，别人也不读。
- 在隔离中这些都不重要，但**随时间、随团队，它变得极其重要**。
- 差异点：手写代码你也会忘，但**现在的生产速度太快**——「一个 Twitter clone 换以前要写一整天，现在 20 分钟」。**「如果生产速度超过理解速度，你就无法长期可靠构建。」**
- 所以要在内环效率之外，补上**「自动文档 + 让代码（即使没人读）也能被快速推理」**这条交接缝。

### 11.4 收尾花絮
- Ram 反馈：前几课是「从零学理论」，这次看到 Dead Reckon 的**具体用法**，才把「为什么我要这么做、有什么好处」放进上下文。
- Jack 要去试 **Torty（Greg 自建的 durable sessions GUI，上节课讲过）**，Greg 说「应该能装，遇到 bug 告诉我，我确信不同环境有大量 bug」。

## 附：本课核心概念速查（术语表）

| 术语 | 含义 |
|---|---|
| **Check（校验条款）** | done contract 里由 gate 求值的一条；决定模型能否退出 loop（≠ 单元测试） |
| **Gate（门）** | 确定性进程：跑所有 check，决定「回 loop」还是「退出」 |
| **Receipt（收据）** | gate 通过后发出的「证明/attestation」，记录「按你说的 check 通过了」 |
| **Receipt binding（收据绑定）** | loop 启动时 hash 一切、绑定到 receipt，保证 check 跑的就是预期对象 |
| **Definition of done（完成定义）** | 用大白话描述的可验证停止条件（如「关闭重开仍能看见帖子」） |
| **Check compiler（check 编译器）** | 把大白话的完成定义编译成可执行的行为性/确定性 check |
| **Behavioral check（行为性 check）** | 用无头浏览器/真实窗口「驱动 app 验证行为」，而非单测 |
| **Mutation testing（变异测试）** | 故意改代码、看测试会不会失败；失败=测试好，不失败=测试烂（Stryker） |
| **Adversary critique（对抗式批判）** | 用一个 LLM 批判第一版 check 编译、指出漏项 |
| **Red-green（红绿自证）** | 让 check 先能失败（red），再通过（green），证明它真的会拦 |
| **Reward hacking（奖励黑客）** | 模型为了「结束/拿分」去检索/改状态而非真正完成任务 |
| **Attestation / provenance（背书/出处）** | 给产物附加「来自哪个 commit、怎么来的」的证明 |
| **CRDT / OT** | 无冲突复制数据类型（无需中心服务器）；OT 需中心服务器（Google Docs） |
| **Headless browser（无头浏览器）** | 无 UI 的浏览器，用来程序化驱动/断言页面行为 |
| **Idempotent key（幂等键）** | 前课概念，本课在「限制数字产生」等处再次呼应 |
| **Adversarial validation（对抗式验证）** | 用不同模型分工：一个计划/实现，另一个 review |
| **Handoff（交接）** | 把无人会读的成果，用自动文档/artifact 解释给别人或未来的自己 |
| **Agentic engineer** | 能确定性地驱动模型、spec + 验证意图的人（区别于 vibe coding） |
