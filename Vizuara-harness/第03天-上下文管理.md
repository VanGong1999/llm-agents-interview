## 二、上下文的关键组成（9 个组件）

沿用比喻：LLM=引擎，工具=轮子，**上下文=燃料**。燃料有**预算限制**（宝贵资源，不能随便加内容）。

循环接受两个参数：**messages（消息）** 和 **max_turns（最大轮次）**（可能还有 tools）。消息数组持续增长。

### 2.1 进入消息数组的 9 个组件（分 NC / C 两类）
| # | 组件 | 是否被压缩 |
|---|---|---|
| 1 | 系统提示（system prompt） | **NC（永不压缩）** |
| 2 | 工具（tools，带完整 name/label/description） | **NC** |
| 3 | 技能文件（skills，只加载 name + 简短描述） | **NC** |
| 4 | 记忆文件（agents.md / claude.md 等） | **NC** |
| 5 | 当前工作目录（CWD） | **NC** |
| 6 | 日期（date） | **NC** |
| 7 | 用户消息（user） | **C（会压缩）** |
| 8 | 助手消息（assistant） | **C** |
| 9 | 工具调用（tool call） | **C** |

- **只有"用户/助手/工具调用"这部分（消息的来回）会被压缩**，其余永不压缩。
- **日期注入**很重要：模型必须知道"今天"是哪天（否则"明天安排邮件""下周发邮件"无法理解）。系统必须把当前日期放进提示。
- 工具只带 name/label/description 三个要素；技能文件只带 name + 简短描述（**整个技能文件不在上下文里**，选中才加载）。

### 2.2 系统提示 vs 用户消息
- **系统提示**：固定的全局指导（如"你是专业编码助手，可通过读文件、执行命令、编辑代码来帮助用户"，含可用工具清单、指导原则）。任何人都可用，开启新会话即原样加载。
- **用户消息**：用户在特定会话里的具体提问。
- 例：Py 把"工具列表 + 系统提示"合并在一起作为基础模板。
- **助手消息** = LLM 的思考/回应（思考 token 或回复）；**工具调用** = 选工具并执行（选工具时必须工具调用，然后工具被执行）。
- **具体区分例子**：用户说"把数据库迁移到 Rust"（如讲者的 Vizuara 代码库正全面迁移到 Rust）——这是**用户消息**（本次会话问的）；而系统提示（"你是 PI 内的编码助手…"）无论用户问什么都保持原样加载，因为它是 PI 本身的高级指导方针。
- **问：能否让系统对专家用户和非专家说不同的话？系统提示就只有一个吗？**（这是好问题，引出下面对 PI 组装方式的讲解——如何"应用上下文"）。

## 三、Py 如何组装上下文（5 个部分）

Py 把上下文分解成 5 个部分（讲者称"组装系统提示"）：
1. **基础模板（base template）**：即"系统提示"——"你是专家级编码助手 + 可用工具列表"。
2. **项目上下文（project context）** = 白板上的**记忆（memory）部分**。

### 3.1 项目上下文（祖先系统 ancestor system）
- 人们通常有 `CLAUDE.md` / `agents.md` 文件，里面是"如何完成这个特定项目"的指导。
- 文件层次结构：项目里可能有 `claude.md`，更高层级可能有另一个 `agents.md`/`claude.md`。
- Py 的做法：从**当前工作目录开始向上查找，一直到文件系统根目录**，收集所有 `agents.md`/`claude.md`（候选定义为 Agent 和 CloudMD），**去重**，把所有这些 Markdown 文件纳入项目上下文。
  - 两个来源：① 智能体目录中的**全局文件**（跨项目执行指令）；② 从 CWD 向上遍历的本地文件。
- **覆盖规则**：最接近本地仓库的文件优先（子目录文件覆盖根级文件）。
- **为什么每次都要遍历**：因为会话中可能编辑 `claude.md`/`agents.md`，下次重建（组装系统提示）时必须捕捉到最新内容。
- 注意：本地项目不该有太多 markdown 文件（会累积、造成混淆）。
- Py 在内存处理上有局限：**没有独立的内存机制**，只有 agents.md/claude.md，依赖用户自己更新。

### 3.2 项目上下文相关问答
- **markdown 文件之间有矛盾怎么解决？** Py 优先采用**最接近本地仓库的文件**（你的 claude.md）。理想情况下本地项目不该有太多 markdown 文件（会累积、造成混淆）。
- **DAR 文件的数量有限制吗？会考虑上下文吗？** **没有限制**。Py 的代码定义了从两个来源取文件（全局文件 + 从 CWD 向上遍历），去重后全部纳入。
- **上下文的定义和记忆管理在不同系统不同吗？** 是的，这就是为什么叫**工程控制（engineering control）**——没有单一方法定义一个 harness，要按需求设计。设计 Hermes 的人希望智能体自我提升，所以默认需要比 Py 好得多的内存系统。
- **针对编码任务的 harness 能用于其他目标导向吗？** 可以。一旦搞懂 Py/Hermes 的工作方式，就能为具体任务创建任何 harness——只需了解 harness 的基本要素。

## 四、技能文件（Skills）与渐进式披露

### 4.1 什么是技能文件
- 一个 **Markdown 文件**，有 name + description + 正文（任务清单）。
- 例子：`Writing style.md`（写作风格，避免双破折号、"delve""诚实""真正的游戏改变者"等 AI 腔词）。
- 可引用其他 markdown 文件、可运行 Python 脚本。
- **技能 ≠ 工具**：技能是"做什么 + 何时做"（过程指导），工具是"怎么做"（独立代码）。技能可引用工具。
- 技能 ≠ 记忆：技能是 harness 的"工作手册"。
- **渐进式披露（progressive disclosure）**：
  - 上下文中**只加载技能的 name + description**（像"预告片"）；
  - 只有当 LLM 选中某技能时，才加载完整技能文件正文。
  - → name/description 必须写好，否则技能永远不被发现。

### 4.2 Odysseus 哲学
- Odysseus 核心极小（894 行），靠**技能文件**支撑强大项目。
- Hermes 哲学相反：附带大量预定义技能（约 1000 个技能文件），核心较大。

### 4.3 Anthropic 写技能文件的最佳实践（讲者提炼）
1. **别写 LLM 已懂的常识**（"PDF 是什么""React 框架定义""Rust 优点"等），保持简短。
2. **description 要写两件事**：① 技能做什么；② **何时使用**（LLM 据此决定是否调用）。
3. **name 按活动命名**（如"处理 PDF / 分析表格 / 测试代码"）；**绝不用** util / tools / data / helper 等模糊词。
4. **自由度**：
   - **窄桥（narrow bridge）**：如数据迁移（组织/公司特定内容）→ 写具体，可提供脚本，确保确定性。
   - **开阔领域（open field）**：如代码审查（多种方式达到目标）→ 只设目标，给 Claude 自由，别过度具体（过度具体反而让技能变差）。
5. **长度**：`skill.md` 控制在 **500 行以内**；大了拆成多个 markdown；引用深度最多 **1 层**（两级引用就难搞）。
6. **两种模式**：
   - **清单式（checklist，纵向工作流）**：提供步骤复选框，完成即打勾，防止遗漏。
   - **反馈循环式**：自我检查——"改 → 验证 → 修复报告中指出的问题 → 通过才继续"。每个技能有自己的反馈循环，项目更稳健。
7. **上线前测试**：
   - 用**一个会话写技能，另一个会话（不带偏见）测试**该技能。
   - 类似 **GAN（生成对抗网络）**：第二个会话被指示"严格批评第一个会话"，只有符合标准才通过。
   - 讲者实例：写"写作风格"技能后，用 **AI 检测 API** 验证——生成约 100 篇文章过检测，直到 **AI 检测比例 <5%** 才确认技能有效。
   - 前端技能同理：创建 100 个前端功能检查是否正常，通过才投产。
8. **人类角色**：先写初稿再交智能体；对技能文件的"批准标准"要设得很高。

### 4.4 讲者的产品实例（Vizuara 书籍）
- 写约 **75 个技能文件**，每个上线前都测试（等轴图、图标、与书内容一致性检查等）。
- 希望书像某位作者（如 Roald Dahl）那样让人享受阅读，所以写技能文件把这种风格固定下来。
- 结论：**技能文件能成就或毁掉一个产品的质量**；技能是"个性化产品"的方法，通用技能可复用，但产品核心技能应自己创作（或让 LLM 生成）。

### 4.5 Hermes 的 slash learn（自动生成技能）
- Hermes 能**自主创建技能文件**：发现用户重复操作时，用 `slash learn` 理解用户操作并自动生成技能文件 → 自我优化智能体。
- 连 Claude Code 也未必做到。

### 4.6 技能相关问答
- **工具 vs 工具调用的区别？** 工具 = 工具列表 + 描述；**工具调用** = 选一个特定工具并调用执行。
- **技能文件算长期记忆吗？** 一般不算——记忆是"关于你"的，技能是 harness 的"工作手册"（虽然也可硬把它们称作记忆）。
- **"没有明确描述的技能怎么学到的？"** Hermes 默认就会：`slash learn` 发现用户重复操作，理解并自动生成技能文件（自我优化）。
- **"推荐好的技能库吗？"（桑吉夫问）** 讲者**从不推荐任何技能库**：通用工具（如网页搜索）Hermes 已开箱即用；但产品核心技能（如某种动画设计风格）必须来自你自己的经历，才能与产品建立连接。**技能是"个性化产品"的方法**。
- **技能 vs 工具的本质**：技能是"算法（做什么 + 何时做）"，工具是"实现这些算法的方法（怎么做）"。

## 五、上下文压缩（Compaction）—— 深度层次

> 若面试只答"用另一个 LLM 总结之前的上下文"= 第一层深度，暴露不懂生产级 harness。压缩有多个深度层次。

### 5.1 四个层次的问题
1. **何时开始压缩？**（窗口 20 万，不能等到了才压，要提前）
2. **过去的消息怎么处理？新消息呢？**（新消息保留？旧消息总结？保留多少新消息？）
3. **切割边界在哪？**（不能随便切）
4. **如何展示压缩结果 / 失败怎么办？**

---

### 5.2 Py 的压缩方式
- **阈值**：预留 **16384 tokens**（为压缩后仍要返回结果留空间）。
- **保留最近约 2000 tokens**（向后查找累积到最近 tokens，讲者转写有 2000/20000 出入），对更早内容做总结。
- **切割边界（最关键细节）**：
  - 只能在 **user 消息** 或 **assistant 消息** 处切割；
  - **绝不能在 tool result（工具结果）处切割**——否则新上下文会从孤立的工具结果开始，丢失"为什么调用这个工具"的提问。
  - 若切割落在轮次中间，Py 会做历史总结 + 总结轮次前缀。
- **摘要结构（6 部分）**：目标、约束、进展、关键决策、下一步、重要背景。

### 5.3 Hermes 的压缩方式（比 Py 细致得多）
1. **何时压缩**：有效窗口 = 上下文长度 − 最大输出 token 数；**达到有效窗口 50% 就触发**（Py 是等窗口快满才压）。
2. **在哪里压缩（保留形状）**：
   - 保护**头部**（开头前 3 条用户消息，反映用户初衷——用户可能走神，但开始时投入）；
   - 保护**尾部**（最后 20%）；
   - 只总结**中间部分**。
3. **预压缩旧工具结果**：先优化旧工具结果，改写为简短描述性语句（如 5000 行报错只留最后一行）——**零成本、无 LLM、完全确定性**。因为工具结果常占上下文大头。
4. **微压缩（micro-compaction）**：
   - 每轮结束后就把该轮总结进一个**滚动摘要（rolling summary）**，而非批量压缩。
   - 上下文大小曲线：Py 呈"震荡波动"，Hermes 呈"平稳"。
5. **摘要结构（11 部分）**：历史任务快照、目标约束偏好、已完成行动、当前状态、阻塞、关键决策、已解决问题、相关文件、重要背景、预简化技能。
6. **失败/边缘情况处理（4 种）**：
   - **地板（floor）64000 tokens**：低于它不压缩；
   - 有效窗口 <512K 时，触发阈值从 50% 提到 **75%**；
   - 地板本身超过上下文窗口时，用窗口的 **85%**；
   - **两次尝试后放弃**；
   - 摘要 LLM 遇速率限制 → 冷却 **600 秒**再试；
   - 主 LLM 不可用 → 用**备用模型**；再无 → 用**确定性字符预算**手动总结（不依赖模型）。
   - 若"永不被压缩的固定内容"本身超出窗口 → 无法处理。

### 5.4 Py vs Hermes 压缩对比总结
| 维度 | Py | Hermes |
|---|---|---|
| 何时压缩 | 预留 16384，快满才压 | 有效窗口 50% 触发 |
| 保留形状 | 只保留最近 2000，其余全总结 | 保头（前 3 条）+ 保尾（20%），压缩中间 |
| 摘要结构 | 6 部分 | 11 部分 |
| 微压缩 | 无（震荡式） | 有（滚动摘要，平稳） |
| 失败处理 | 差（没充分考虑边缘情况，出错就重试） | 好（地板/两次打击/冷却/回退 4 部分） |

### 5.5 压缩相关问答
- **系统提示从来没被压缩过吗？（Anil 问）** 对，系统提示**永不压缩**——它们是基本指令。
- **压缩本身有结构吗？（Anil 问）** 有，遵循非常具体的结构。压缩信息总是有结构：Py 有 6 部分结构，Hermes 有 11 部分结构，Claude Code 也有自己独特的结构——**每个 harness 都有自己的压缩信息展示结构**。
- **为什么 Hermes 保留前 3 条消息？** 用户可能在对话中走神，但开始会话时往往很投入，前 3 条消息通常反映用户真正想做什么；中间可能有偏差/干扰。
- **Hermes 是否在上下文中保留滚动总结？（Ud Cash 问）** 会——当会话被突破（阈值触发）时，滚动总结被保留并在突破时使用；上下文容量本身是固定的（由 LLM 决定）。
- **为什么 Hermes 压缩要尝试两次？（乌特卡尔西辛格问）** 因为有时即便系统提示+工具内容小于上下文容量，用户获得的输出仍会超过限制——第一次压缩后仍在上方，第二次压缩后可能还在上方，于是两次尝试后放弃。
- **切割（在哪里压缩）是确定性的吗？（Karen 问）** 是**完全确定性**的——因为能准确定位切割发生的地方，这里没必要用 LLM。
- **为什么预留 16384？** 因为一旦压缩，你必须**返回一些结果**（需要留空间）；压缩过程本身需要空间，模型还要在触发压缩的那一轮给出回复。

## 六、Token 估算（Py 的做法）

- 优先找**最后一条带 usage block 的助手消息**（API 返回使用量），之后的内容做近似估算。
- **尾随 token（trailing tokens）启发式**：
  - 文本 → 字符数 ÷ 4；
  - 工具调用 → name + JSON 参数之和；
  - 图像 → 固定 4800 字符。
- 原因：有时 LM 调用中途终止（出错），没有 usage block，需要估算后续 token。
- 结论：**连估算 token 都不简单**，要处理供应商报错、后续消息等边缘情况。

## 七、缓存控制（Cache Control）

- 无缓存时，每轮重发整个前缀（系统提示、工具、历史步骤）→ 重复付费。
- **缓存控制**：把不变内容（系统提示、工具、历史轮次）设缓存断点，只传增量。
- Py 的做法：系统+工具缓存，用户每轮交互也缓存；每轮旧的尾部设缓存断点跳过，只写新增量到缓存。
- 与 **KV cache** 相关：
  - LLM 无状态，但 Anthropic 服务器端维护缓存（我们看不见）。
  - 预填充（prefill）阶段已算好的键/值向量不再重算 → **省钱 + 降延迟**，大幅降低 **TTFT（首次令牌时间）**。
  - 推理分**预填充（prefill）**和**解码（decode）**两种模式；缓存让预填充更快。
- **TTL（生存时间）**：缓存保持时长（Py 支持 1 小时等，可独立跟踪）。
- 提示：多轮对话 + 缓存控制可降 API 费用（即使直接用 API 也可加）。
- **问答：微压缩会导致 KV 缓存频繁失效吗？** 会带来一些问题，但**前缀缓存（prefix caching）**有帮助；另有缓存控制。KV 缓存管理（保持键/值向量）与 harness 压缩是**两件可并行的事**——可以单独维护 KV 缓存，同时让 harness 做微压缩。

## 八、为什么技能/记忆文件用 Markdown 而非 PDF？

- Markdown 是**最简单、模型最易读**的格式；PDF 需要特定技能读取、较难。
- 语言模型理解 Markdown 最容易，也是最简单的操作方式。
- 这是技能文件用 `.md`（而非 PDF/文档）的原因。

- 简化版设计（保持极简）：
  1. 保留最近 **6 条消息**原样；
  2. 用 **LLM 总结**过去所有内容；
  3. 用简单因子估算 token（**每 token ≈ 4 字符**）；
  4. 压缩摘要要求：把旧消息转化为"原始任务、每条消息中的文本/工具调用、文件创建/编辑及其目的、关键决策、未解决的错误、下一步"。
- 压缩本身也消耗 token（需要 LLM），但这是必要的。
- 提示大意："你正在构建 Odysseus 第三天……去掉内存部分、去掉技能（明天做）……只做 compact……"

## 十、作业与总结

### 10.1 作业
1. 阅读第 3 天材料，重点看 **Codex 如何压缩**（与 Py、Hermes 并排对比）。
2. 理解 Py vs Hermes 的对比（压缩方式、边缘情况）。
3. 不要提前做记忆部分（第 4 天做）。

### 10.2 核心总结
- 光了解"上下文组成部分"不够，要理解 harness **如何管理上下文**。
- **上下文工程 vs harness 工程的区别在于"边缘情况"**（一位旧金山初创 CTO 朋友的观点）：构建上下文时事情可能出错可压缩；构建 harness 发货后**一切必须完美**，边缘情况影响产品质量。
- 压缩要回答：何时压、在哪压、如何展示结果、失败怎么办。
- 技能文件的关键：渐进式披露 + 写好 name/description + 反馈循环 + 上线前测试。

### 10.3 其他课堂问答补充
- **永久上下文（系统提示+工具+技能）多少 token 合适？** 讲者经验：**60~75~80** 是常见合理范围（越大越简单，但不该超过这个上限）。
- **为什么 Odysseus 只有 1000 行？** 因为它是**为特定模型设计的**；而 Hermes/Py 接了 OpenRouter，要写很多**网关机制**（模型集成、运行时切换模型），代码量因此大增。实际人们很少频繁切换模型（多用同系列切换，如 flash 规划 + opus/sonnet 执行，几乎没人从 Claude Opus 切到 Moonshot）。
- **技术上能否做手机 harness？** 可以（可成为第一个做的人）；难点是内存（需永久保存信息），连云端即可解决。
- **ChatGPT 是 harness 吗？** 不是——ChatGPT 是**建立在 LLM 之上的产品**，缺少子智能体管理、内存管理、上下文管理等，所以它不是 harness。
- **讲者画图表的工具**：让模型遵循 **XKCD 规范**（有一个 MCP 可用于 XKCD 绘图）。
