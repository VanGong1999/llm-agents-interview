## 二、内存管理（Memory）

### 2.1 记忆体现在哪？—— 消息数组
- 在循环里，记忆的体现 = **消息数组（messages array）**。
- 存的记忆越多 → 消息数组增长越快 → 可能超出上下文。
- **权衡**：记忆越强 → 越个性化（深刻的人类体验）；但消息数组膨胀、超出上下文。

### 2.2 为什么记忆重要（个性化 = 深刻的人类体验）
- 例子：找辅导员，若第二天老师完全忘了你昨天的困难，就没有互动；老师记住你的长处/短处，两周后说"你在这方面常困难，我们测试下有没有进步"——这是深刻的人类体验。
- 人类都渴望个性化体验（记住优点/弱点/喜好/厌恶）。
- 若有人 6 个月后还记得你，说明更关心你（若 2~3 个月后还记得，更棒）。
- **从进化角度看**，人类习惯与导师有某种经历，都偏爱个性化体验。
- **所有高星标的开源 GitHub 库都有优秀的记忆管理系统**（Hermes、OpenClaw）。

### 2.3 短期记忆 vs 长期记忆
- **短期记忆（short-term）**：用户消息、助手回复、工具调用——一定存回消息数组（默认设置，避免忘记）。会话结束即消失。
  - 三种处理方式：
    1. **限制轮数**（限制保存在短期记忆里的轮次数量）；
    2. **超过轮数提前总结**（如对话轮数增加到 20~25 轮时，选择对整个对话做总结）；
    3. **选择性保留**（基于关键词匹配系统，只保留与用户所说内容相关的重要部分，更具选择性——较少人实施）。
- **长期记忆（long-term）**：**持久化在磁盘**（本地计算机/虚拟机/数据库），会话结束后仍存在。
  - 长期记忆 = 区分"深刻体验 vs 非深刻体验"的关键。
  - 优势：个性化；劣势：消息数组膨胀、超出上下文。

### 2.4 各 harness 的长期记忆对比

#### ① Py —— 最弱（只有 agents.md / claude.md）
- 短期记忆：直接保存对话（超过上下文就压缩）。
- 长期记忆：只管理一个记忆文件——`agents.md`（或 `claude.md`）。**没有其他复杂机制**。
- 用户必须**自己手动**往 claude.md/agents.md 写内容；没有自动写入、没有评分、没有后台清理。
- **缺点**：依赖用户操作，不可扩展（用户忘了加就没有记忆）；不算深刻体验（像辅导员课后让你"把该记的发给我"）。
- 理想：harness 应**自主识别**什么重要。

#### ② Hermes —— 智能体自己写记忆（自我改进）
- 智能体自己写记忆，有两个由智能体维护的文件：
  1. **`memory.md`**：智能体的"个人笔记"——环境、事实、项目、约定、工具特性、它艰难学到的东西。
  2. **`user.md`**：用户偏好（如"别用双破折号/EM dash"等沟通风格）。
- 有**记忆工具**：能添加条目、查找并交换条目、删除条目 → 立即保存到磁盘。
- **学习循环（learning loop）**：每轮结束后创建一个**分支（branch，类似 git fork）**，判断"哪些内容值得保留"→ 添加到 memory.md。
- **`slash learn`**：自我生成技能文件（汇集用户提到的所有资源，创建全新技能）。这是 Hermes 独有的"内置学习循环"，连 Claude Code 也未必做到。
- **策展（curation）**：**7 天后回顾记忆；30 天后标记过时；90 天后归档**。
- 设计理念：**自我提升的 AI 智能体**。

#### ③ OpenClaw —— 更进一步的自我巩固 + 梦境
- 文件：**`SOUL.md`**（灵魂，= 用户偏好，类似 Hermes 的 user.md）+ **每日笔记（daily notes）** + **`memory.md`**（永久长期记忆）+ **dreams（梦境）**。
- 每次会话后记录每日笔记；用户说"这很重要"就永久记录到 memory.md。
- **梦境（dreams）**：**后台巩固过程**——一个后台智能体（像你睡觉时）扫视所有短期记忆，把合格条目**从短期转为长期**。在任何内容提升前应用：评分阈值、召回频率门（一个条目反复出现→该存长期，如"做了五次梦，条目在梦中反复出现"）、查询多样性过滤器。
- **长期记忆如何加载到上下文？** OpenClaw 用一个**非常简单的向量索引（RAG 系统）**：
  - `SOUL.md` 默认加载；
  - 用户提问 → 转成 embedding → 只提取与提问相关的每日笔记/memory.md 片段，加载到上下文（**不加载全部长期记忆**）。
  - 用**混合搜索（hybrid search）**：向量相似性 + 精确关键词匹配。
- 讲者设想：可做**无向量 RAG**（预先索引、相互链接，LLM Wiki 精神），甚至让 harness 在后台"做梦"后反问用户"要存这个吗"（带来魔幻级个性化）。
- 讲者感叹：**为什么没人做一个集各家之长的 harness？** Hermes 不错但没有"梦境"，OpenClaw 很好但没有 `slash learn`。若能把各领域的精华合并成一个记忆系统，会很惊人。

#### ④ Codex —— 仅用户明确要求
- 只有在用户**明确要求记住/忘记/更新**时才操作，**不自动创建**记忆（深藏在 GitHub 仓库说明里）。
- 没有 Hermes 那样的策展（7/30/90 天）。

#### ⑤ Claude Code —— 自动记忆（auto-memory）
- 非常依赖 **CLAUDE.md**（类似 Py 的做法），文档投入大量篇幅讲"如何写 CLAUDE.md"、放哪里（应用级/用户级/项目级/本地 `.claude.local.md` 加 gitignore）。
- 额外功能：**自动记忆（auto-memory）**——在会话间积累知识（保存笔记、命令、调试见解、代码风格偏好、工作流程习惯），无需用户指出。
- 但讲者观察：Claude Code **从不自动生成技能文件**（Hermes 会）；在"个性化"领域不如 Hermes/OpenClaw 受欢迎。
- 社区甚至为此做了 `claw-mem` 仓库（约 10 万 stars，跨会话持久记忆）。

### 2.5 总结对比
| Harness | 长期记忆 | 特点 |
|---|---|---|
| Py | agents.md / claude.md | 用户手动，最弱 |
| Hermes | memory.md + user.md + slash learn | 智能体自写、自我改进、有策展（7/30/90 天） |
| OpenClaw | SOUL.md + daily notes + memory.md + dreams | 背景巩固（梦境）、RAG 混合搜索 |
| Codex | 仅用户要求 | 不自动 |
| Claude Code | CLAUDE.md + 自动记忆 | 自存偏好/风格，但不生成技能 |

### 2.6 企业级记忆系统（开放机会）
- 现有开源 harness 的**记忆管理系统都缺乏安全层**（Hermes 可"做任何梦"）。
- 需加：**角色级/OU 级访问权限**。
- **深度个性化有风险**：若企业产品每月收 200 美元，让智能体"做梦"可能创造随机内容，这是风险——所以深度个性化需谨慎，但这正是企业级机会。
- 企业最关心**安全**（讲者合作的 6 家大公司都如此，是普遍模式）。
- **企业安全四要素**：
  1. **用户访问控制**（不让任何人查询/接触控制器）；
  2. **OU 访问权限**（某 OU 只能访问控制器特定部分，另一 OU 访问另一部分）；
  3. **沙箱隔离**（明确爆炸半径，给客户保证：无文件被删、无信息泄露、任何信息都不离开）；
  4. **速率限制**（陌生人不能发起成千上万并行请求；可按权限分层）+ 防恶意/防蒸馏攻击。
- **数据安全选择**：闭源 harness 数据去向不明；开源 harness + 闭源模型数据仍可能外泄；**最安全 = 开源 harness + 开源模型**。
  - 成本高：如 **Kimi K3 约 2.8 万亿参数，需 8~10 张 B300 显卡**才能托管（讲者团队在 Vizuara 用 8 张 B300 托管了 Kimi K3）。
- **Ranga 问"这些知识对企业有什么帮助？"** 若企业要做原生 AI 产品（希望子智能体独立委派、上下文自管理、记忆自管理），**没有 harness 就无法实现**。当前产品里只有一个 API 调用：不进入循环、不生成子智能体、不能管理上下文/记忆。要持续自主完成任务、委派子智能体，就必须在产品里放 harness。
- **自动化一个部门的方案推演**（Sarab 案例）：某客户想自动化整个部门——
  - 需要一个**控制器**（部门查询可能涉及 100 个并行任务，需指派子智能体）；
  - 闭源控制器（Claude Code）贵 + 隐私问题 → 用**开源 harness（Hermes + 本地托管 GLM 模型）**，全部本地运行；
  - 但若想改功能/压缩方式/内存处理，只有**完全了解开源系统**才能改。
- **Nemo Claw** = 生产级 agent harness 的例子，唯一价值 = **更安全地运行 OpenClaw**。把 PI/Hermes 展示给 CEO/CTO 会害怕（没安全），但 Nemo Claw 考虑了安全，看起来更可信。
- 观点：**安全性应融入产品本身，不能事后附加**（讲者合作的 6 家公司里两种人：懂安全的人 vs "先上产品再加安全"的人）。

## 三、子智能体编排（Subagent Orchestration）

### 3.1 核心机制：子智能体 = 工具
- **所有子智能体都被视作工具**（在基础提示里和工具一样有 name + description，LLM 判断任务可并行时就调用）。
- 子智能体 vs 技能：
  - **技能** = markdown 文件，被调用来执行特定操作；
  - **子智能体** = 有**自己的上下文、记忆、基础提示、工具、模型**的独立智能体（可访问自己的技能文件）。

### 3.2 三种模式（Py 默认）
1. **单（single）**：只生成一个子智能体。
2. **并行（parallel）**：生成多个并行子智能体处理并行任务。
3. **链式（chain）**：生成一串顺序串联的子智能体（任务 1→2→3）。

### 3.3 关键差异：子智能体"住在哪"
| Harness | 子智能体实现 | 并发上限 | 隔离性 |
|---|---|---|---|
| **Py** | 独立 OS 进程（全新上下文/记忆/工具/模型） | 4 | 好——父与子**无内存共享**；子探索成本自担，父只为答案付费 |
| **Hermes** | 同一进程/线程（共享主智能体所有工具） | 3 | 差——信息可能泄露，需上下文变量隔离 |
| **Codex** | 同一进程 | 4/会话 | 差 |
| **Claude Code** | 未公开 | — | —（深度限制 = 3） |

- Py 独立进程的好处：划分边界简单；代价：创建子智能体稍慢。
- Hermes/Codex 同进程：生成快；代价：隔离困难（需明确指出哪些内存不共享）。

### 3.4 Py 的预定义子智能体
- 4 个：**Scout（侦查）、Planner（规划）、Worker（执行）、Reviewer（评审）**。
- 每个子智能体有自己的 name、description、工具、模型、全新上下文窗口。
- `discover agents` 工具：系统提示发现需要子智能体时，检查有哪些子智能体可用。
- Py 已默认连接：scout→planner，worker→reviewer（项目启动自动规划）。

### 3.5 子智能体的优势
- 获得**全新上下文窗口**（上下文增长快/环境迅速发展时，把任务交给子智能体）。
- 多任务可并行分配给并发子智能体。
- 父智能体上下文不受子智能体消耗影响（子消耗 10 万/50 万 token，父上下文不变）。

### 3.6 三层子智能体协调（易混淆点）
1. **子智能体（父子进程）**：系统/模型**自动发起**。
2. **交接（handoff）**：**用户主动发起**（如 `/handoff`）。从当前庞大会话中提炼一个**目标**，交给一个全新上下文的新绘画（只带目标、完全重置）。**不是压缩**（压缩用 LLM 总结成 13 要点格式）。子智能体由模型自主决定何时分配，交接由用户定义。
   - 例子：用户在会话里花了 2 小时、上下文接近极限 → 执行 `/handoff` → 从讨论内容里**提炼一个目标**交接出去。
3. **舰队（Fleet）**：多个实例在多目录/多机器并行（监督者控制 N 个实例）。

- 将军/军队比喻：将军（父智能体）累了（上下文拥挤）→ 派士兵（子智能体）出去侦查，回来报告（子把结果反馈父，父只为答案付费）；总有一刻将军说"是时候彻底放弃"→ **交接**（把学习成果完全传递给士兵，提炼目标交给全新绘画）。
- **三者区别（易混淆）**：压缩 ≠ 交接 ≠ 子智能体。压缩 = 用 LLM 把所有内容压缩成固定格式（如 13 要点）；交接 = 提炼一个目标交给新会话；子智能体 = 生成一个独立实例执行任务。三者常被一起提及，但完全不同。

### 3.7 相关问答
- 子智能体是否继承父记忆？Py 子进程**不继承**任何过去记忆（全新进程，从零开始）；Codex/Hermes 有隔离难题（用上下文变量分离父子上下文）。
- 子智能体 = 一个带自己 LM 模型和任务的智能体（不是单纯带工具的进程）。

## 四、持久性（Durability，最少被讨论的话题）

### 4.1 目标
- 崩溃时能从断点恢复；**执行前先记录状态**。
- 什么会导致崩溃：会话中崩溃、工具调用中出错、笔记本关机后重启、LLM 自己崩溃……都可能发生。
- 确保持久性最简单的办法（学员回答）：**记录状态、创建检查点、持久化上下文快照**——关键是"在执行之前把信息记录在某个地方"。

### 4.2 四个存储（four stores）对比
| Harness | 存储方式 | 写入时机 |
|---|---|---|
| **Py** | 每会话一个 **JSONL 文件** | 每条消息末尾追加 |
| **Hermes** | **SQL 数据库（state.db）** | 每轮写 3 次：API 调用前 / 每批工具后 / 轮末 |
| **Codex** | JSONL + 后台数据库 | 逐项后台追加 |
| **Claude Code** | 每会话 ID 一个 JSONL 转录 | 未公开（推测类似 Codex） |

### 4.3 崩溃处理
- 最后一行中断时：Py 丢弃该行；Codex 补缺失换行；Hermes 每行代表一件事，不会突然结束。
- **写入时机讨论（学员回答）**：Session 说"应在转向（turn）结束时写"；马塔瓦尼说"任何执行开始前写"。实际上 Hermes 最安全——每轮写 3 次（API 调用前 / 每批工具后 / 轮末）。
- **乌特卡什补充**：Hermes 是"写一行（交易完成后）"——其实直到某件事完成之前，它根本不写任何行；所以如果某件事崩溃了，它甚至不会写任何行。
- **为什么持久性重要**：构建 harness 时若没有耐久层，说明没认真考虑边缘情况——虽然耐用性是"小事"，但这是生产级 harness 的必要条件。

### 4.4 文件保留（如何确保文件留在磁盘）
- **Py**：没有影子存储库/快照/备份副本。
- **Hermes**：文件变更前做**影子 git 快照（shadow git snapshot）**。
- **Codex**：曾有基于 git 的机制，后删除。
- **Claude Code**：每次用户提示前创建**检查点（checkpoint）**，保留最近 **100 个**文件快照 + 与对话一起存储；有 **`/rewind`（斜线回放）** 独立恢复代码和对话。

### 4.5 为什么持久性重要
- 构建 harness 时若没有耐久层，说明没认真考虑边缘情况。
- 这是生产级 harness 的必要条件。

### 6.2 核心总结
- 智能体 ≠ harness：智能体 = LLM + 工具（打破玻璃罐）；harness 额外有内存/上下文/子智能体/耐久性管理，能持续自动运行。
- 记忆是上下文的一部分（短期 + 长期都融入上下文）。
- 子智能体 = 工具；三种模式（单/并行/链）；三层协调（子智能体/交接/舰队）。
- 持久性 = 执行前记录状态，崩溃后恢复。

### 6.3 其他课堂问答补充
- **分叉进程会继承父进程内存结构吗？（Yutkash 问）** 不会——Py 的子智能体是全新进程，**不加载任何内存内容**，只获取关于父代理当前操作的基本上下文。
- **伪终端会话启动子智能体？（Ananya）** 若子智能体工作目录与父相同，技术上可访问同样的文件/内存；但子智能体启动时上下文是新的（这正是优势，别让它启动前就上下文过载）。
- **子智能体 = 新智能体（带自己的 LM 和任务），还是单纯带工具的进程？** 是**带自己模型的智能体**（不是单纯带工具的进程）。
- **企业培训顺序（如何教公司用 AI）**：① 先教智能体 → ② 上下文知识 → ③ harness 使用 → ④ 确保每位工程师能操作 harness。核心理念：即便有 Claude Code/Codex 企业许可证，工程师也应**在理解 harness 的基础上使用它**。
- **有没有评估 harness 性能的量化标准？（Ankit 问）** 没有可靠标准。最好的基准是**内部标准**——若能做出漂亮/行业级产品、复杂项目，就说明 harness 有效。讲者见过一个基准（2 个月前发布、5 分支、61 星），实用性存疑。
- **记忆 vs 上下文的区别？** 记忆是**上下文的一个组成部分**；分短期/长期，都融入上下文。长期记忆优势=个性化，劣势=消息数组膨胀超出上下文；短期记忆优势=不增加太多上下文负担，劣势=缺长期记忆就不个性化。
- **怎么创建技能文件？（桑杰问）** 用 Claude Code/Codex 或 **Kimi K3（中等版本）** 写；给示例技能文件做参考，要求后续技能遵循同样的"深度和密度"标准。
- **有现成技能库吗？** 有一个约 20 万星标的技能库可直接取用（通用技能如网页搜索可以复用；但个人项目的核心技能应自己创作）。
- **托管 Kimi K3 更便宜吗？** 托管非常困难（需多张 B300 GPU）；若是为很多人服务的工业应用，长远看自托管可能更好。讲者团队在 Modal 上获得 B300 GPU 托管了 Kimi K3，还托管了量化版本。
