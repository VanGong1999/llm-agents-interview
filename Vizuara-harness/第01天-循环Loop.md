## 二、什么是 Harness

### 2.1 课堂互动：你觉得 harness 是什么？
- 讲者先抛问题"你觉得 harness 是什么？你之前用过 harness 吗？"让学员在聊天里随便说。
- 学员的回答（转写记录）：
  - "与模型相关的代码"
  - "指挥控制 AI，能够有效利用某些工具"
  - "开启一个工具的 LLM"
  - "所有与模型相关的工具，共同助力模型运转"
  - Avanish："理解生态系统和 AI 智能体"
- 讲者再问"你们中有多少人用过 harness？能说出名字吗？"——引出下面的开源/闭源 harness。

### 2.2 大家都已经在用 harness，只是没意识到
- 很多人根本不知道什么是 harness，但实际上都在积极使用。
- 最常用/最广泛使用的 harness：**Claude Code**、**Codex**（全球程序员和开发者最广泛使用的两种，但都是**闭源**）。
- 开源 harness：**Py**（GitHub 约 82k stars，极简但运行良好）、**Hermes**（GitHub 约 200k stars，发布不到 6 个月就接近 200k，增长极快）。
- 构建 harness 所需的要素都已在开源资源中解释过，应该向他们学习。
- 判断是否接近 Claude Code/Codex 无法确定，但**能构建优雅的生产级应用就说明 harness 质量好**。

### 2.3 从 A 点到 B 点（Harness 是什么）
- **A 点**：我们都在用 ChatGPT / 云服务。
- **B 点**：拥有一个接口，能对其查询，且能"真正建立一家公司"。
- 例子（讲者真实做过）：模拟一家公司，自己当**董事会主席**，AI 扮演 **CEO、CTO、CFO**，讲者当 **CMO**；目标是 **3 个月达到 100 万美元年经常性收入（ARR）**。
  - 有网站、营销渠道、进销销售策略、财务监控。
  - 客户在网站留反馈 → 自动发送到 GitHub issue → CTO 智能体自动关闭 issue → 网站更新（一个全自动循环）。
  - 营销循环：每周在 LinkedIn/Twitter 发帖、发新闻通讯，自动追踪点赞/评论，反馈回路强化表现好的帖子类型。
  - 作为人类，每天早上只需看仪表板的最新动态。
- 这是**真实发生**的：讲者成立了一家 8 个人的公司（营销/产品/财务/销售智能体），是完全自动化的销售漏斗。
- 一年前说这种话会被嘲笑，但现在完全可行。GitHub 上甚至有"**单人公司（one-person company）**"仓库，为每个任务配智能体，还有可访问的网站。
- **结论**：这个"问号/黑箱"接收输入、生成神奇的自动化输出、完全自驱——它就是 **harness（支架/线束）**。

### 2.4 为什么只有 LLM 不够
- 讲者先问"假如你只有一个 LLM（如 Gemini 3.5 Pro），它能帮你从 A 点到 B 点吗？"让学员判断——这样才能在课后永远记住 harness 是什么。
- **LLM 的定义**：一种**无状态机器（stateless machine）**，另一种说法是"**罐子里的大脑（brain in a jar）**"。
  - 无状态 = 输入相同内容，LLM 只被训练来预测下一个词；**不保留任何状态、没有过去的记忆**；对环境完全没有概念。
  - LLM 只是一个函数：接收输入、返回"下一个词预测"的输出。
- **LLM 没有工具**，无法与外部环境交互：想看/关闭 GitHub issue，需要能访问 GitHub API；发帖需要 LinkedIn/Twitter API。
- **比喻**：LLM 像汽车**引擎**，力量强大，但**单靠引擎无法把你从一个城市送到另一个城市**。

### 2.5 从 LLM 到 Agent 到 Harness（逐步补全）
1. **LLM + 工具 = Agent（智能体）**：给 LLM 工具（LinkedIn API、Twitter API、GitHub API，通过 MCP 或 Python 代码访问），引擎就能与外部世界交互。但只有 Agent 仍不够。
   - 学员对"只有 agent 够不够"的回答：马塔文"要闭环反馈进行评估"；Vignesh"如果有什么失败的情况呢？"；卡兰"因为它仍然是无状态的"；拉古纳特"内存"——都指向 agent 之外还缺很多东西。
2. 还需要：
   - **编排（orchestration）**：让操作**按时间自动触发**。例如早上 8 点发营销帖、午夜 12 点关 GitHub issue、下午 6 点开董事会、晚上 10 点给人类主席起草每日更新。
   - **任务分配**：面对 100 个相互独立的 GitHub issue，决定是单个智能体顺序做，还是派生 100 个子智能体并行做。
   - **上下文与记忆管理**：当 GitHub issue 有 100 万 token、超出上下文窗口时，需要自动压缩（上下文管理系统）；还要决定什么进短期记忆、什么进长期记忆。
3. **比喻的完整展开**：
   - Agent = **带轮子的引擎**（打破玻璃罐，让 LLM 接触环境）。
   - 上下文 = **燃料**（燃料耗尽需加油/压缩）。
   - 任务分配/导航 = **Google 地图**（知道目的地 A/B/C/D，选最优路线）。
   - 安全 = **安全带**（自动驾驶系统执行 `rm`/删仓库等不可逆操作前必须沙箱化、征得同意）。
4. **Harness = 组装整辆车**。线束工程（Harness Engineering）就是把 LLM、工具、上下文/记忆管理、子智能体任务分配、安全组合起来的过程。
   - 人们造出这个术语，是因为最初体验到 Claude Code 却无定义；"Claude/Opus（模型）"与"Claude Code（产品）"的区别，就是**引擎 vs 整辆车**。

## 三、术语体系澄清（提示/上下文/Harness/循环/图形）

### 3.1 提示工程（Prompt Engineering）
- 创建提示的艺术：详细描述目标、你想要什么、最终目标、希望达到的智能体系统。
- 有系统提示 + 用户提示；多年来已证明"垃圾进垃圾出"，高质量提示产生更好答案。

### 3.2 上下文工程（Context Engineering）
- 比提示工程更进一步：管理**与 LLM 相关的所有内容**。
- 上下文中包含的内容（课堂互动归纳）：
  1. 系统提示
  2. 用户输入
  3. 长期记忆
  4. 短期记忆（对话历史）
  5. LLM 可访问的所有工具
  6. RAG 在运行时提取的相关文档
  7. **技能文件（skills）**
  8. `CLAUDE.md` / `agents.md` 等治理文件（每次都加入提示）
  9. 对话记录（含 AI 的响应）
- **安全不属于上下文**（安全是操作层面的问题，后面课讲）。
- 上下文是**有限资源**（像土地、黄金）：现代 LLM 上下文窗口约 100 万 token，但有限；填满必须**自动压缩**，不能塞随机内容（例如用户重复提问时，可先概括对话再保存）。
- 例：`caveman` 这种 GitHub 仓库（约 10 万 stars）用更省 token 的方式表达同一提示；**输入 token 和输出 token 都要省**（因为输出会追加到后续输入）。
- 上下文工程既是艺术也是科学。

### 3.3 Harness 工程（本课核心）
- 即使做好上下文工程，仍不足以搭建 harness；Harness 工程把它们组合起来。

### 3.4 循环工程（Loop Engineering）
- **循环 = 有时间限制的自动化过程**（如每天 8 点自动发帖、12 点关 issue、18 点检查、22 点写作）。
- 例子：产品循环（识别 GitHub issue→关闭→给用户发邮件→追踪新 issue）、营销循环、CEO 循环（让 CEO 了解最新动态）。
- **循环建立在 harness 之上**；没有 harness，循环没有意义。
- 循环越多 → 自动化越强；循环内可含反馈（获取人类反馈→迭代→完成循环）。
- **线 vs 循环**：线是"决定新内容就结束"；循环可以**无限期运行**，一切自动化。
- "循环工程"一词约一个月前才出现，讲者认为可当作独立领域关注。

### 3.5 图形工程（Graph Engineering）
- **图 = 相互连接的循环**。
- 例子：
  - 循环 1（工单解决循环）：优化"更快解决工单"——但只检查解决时间、不检查解决质量，可能让客户不满随时间加剧。
  - 循环 2（客户留存循环）：分析多平台客户数据，改进产品。
  - 循环 2 监控循环 1 的结果，确保它正常运作。
  - 若十个循环彼此连接（循环1↔循环2、循环1↔循环3、循环4↔循环5↔循环1），就构成了**图**。
- 起源：**Peter Steinberger** 发了一条关于"图形工程"的帖子（仅一句话），立刻催生一个新领域。
- 讲者观点：循环/图形目前偏主观热词，真正挑战是设计 harness 本身。

### 3.6 相关问答
- **循环如何结束/休息？** 由人类定义：如"只运行 4 周就停止"，就像为循环建管道。讲者自己的例子：每周追踪外部动态→收集反馈→生成报告→提改进建议，是每周发生的循环。
- **分布式系统背景者的疑虑**（Sujit）：循环工程是噩梦，通常支持 DAG。讲者回应：自动化工程领域一切都围绕循环（否则每周自动化无法发生）。
- **工作流是不是循环？**（Karen/Ankit）可以这么理解；自动研究循环是很好的例子（见下）。
- **自动研究循环示例**：文献评审智能体 → 创新空白智能体 → 实验智能体 → 写论文智能体，形成自主管道；消融实验 1 的输出作为实验 2 的输入，自动构建实验 3，直到人类满意。
- **与多智能体框架的区别？** 别太纠结术语：智能体是 harness 的一部分，环是 harness 顶部暴露的部分。循环可关乎**时间管理与自动化**（如每周循环），子智能体循环关乎**特定任务执行**。

## 四、Harness 的五个组成部分（金字塔）

讲者正式介绍 **agentic harness 的五个组成部分**（可像金字塔一样组合）：
1. **循环（Loop）** —— 最小基本单元 / 心脏
2. **工具（Tools）**
3. **上下文与记忆（Context & Memory）**
4. **耐久性（Durability）**
5. **整体编排（Orchestration）**

- **原子比喻**：就像金、银、铅等元素都由单个原子构成，**harness 的核心是一个"环（loop）"**，没有它一切都无从谈起。今天就是一起构建这个环。

### 4.1 设计哲学（为什么 harness 要极简）
- 开源 harness（Hermes、Py）代码仍很庞大（它们是为生产级、对接多服务商而建）。
- 讲者哲学：**harness 可以非常简约，仍能构建惊人产品**；押注的是**人类的贡献来自"技能文件（skill files）"**。
- 因此：harness 小巧简约，但**技能文件要非常详细**。
- 目标：千行智能体 harness。
- **代码量对比**：Odysseus 约 **894 行**（公开后仍可充实）；Hermes 约 **70 万行**；Py 约 **12 万行**；Hugging Face 的 **Tao** 约 1 万行（自称"最小编码智能体"）。Odysseus 目标仅 **1000 行**。
- 讲者用 Odysseus 构建的产品：**Ovation**（Sand 网站的完整克隆）等，靠的是详尽的技能文件。
- **渐进式信息披露（progressive disclosure）**：并非由 harness 决定，而是"看具体情况"的灰色地带；讲者选择信任用户自己写详细技能文件，而非把技能嵌入产品内部。
- **可观察性/调试**：几乎每个循环内都设一个"可观察性智能体"（如 GitHub 循环里有可观察性和调试智能体）。
- **自建 harness 的好处**（Abinash 问）：不依赖闭源供应商、拥有独立思考；闭源成本可能上升（AI 领域垄断渐显，Anthropic 前沿但靠补贴，未来可能不可持续）。

## 五、反应循环（REACT / 思考-行动-观察）

### 5.1 基本思想
- LLM 接收输入、产生输出；若给 LLM 工具访问权限，就能与外部环境交互：**交互 → 接收反馈 → 自动修正自己 → 再用另一个工具 → 再接收反馈 → 再修正 → …**，形成自动化链。
- 这就是**反应循环（REACT loop）**。注意：**REACT 不是网络框架**，而是 **Reasoning + Acting**（推理与反应行动），名字源于一篇研究论文。

### 5.2 例子：Claude Code 处理一个 GitHub issue
任务："打开 GitHub 上的第 87 个问题 → 识别问题 → 提供解决方案 → 验证 → 创建 PR"。

Claude Code 内部依次执行的**思维、行动、观察（Thought-Action-Observation）循环**：
| 步骤 | 思考（Thought） | 行动（Action，使用的工具） | 观察（Observation） |
|---|---|---|---|
| 1 | 我要打开这个 GitHub issue | GitHub MCP 服务器 | 看到 issue 内容 |
| 2 | 我得读这个问题 | 读工具（read） | 已经读透了 |
| 3 | 我需要对它分析 | （无需工具，LLM 直接分析） | 已分析 |
| 4 | 这些是我可能要改的地方 | 编辑工具（edit） | 已编辑 |
| 5 | 我要验证 | 指派一个子智能体验证 | 已验证通过 |
| 6 | 我要提交 PR | GitHub MCP 服务器 | PR 已成功创建 |

→ 跳出循环。这就是多次"思考→行动→观察"的循环。
- 你在 Cursor / Claude Code / Codex 中看到的"思维过程"就是这个循环。
- **循环是基本单位**，是 agentic harness 的构建第一步。

### 5.3 幻觉来源
- 如果给模型 1000 个多余工具，模型会困惑、不确定用哪个工具 → 这是智能体产生幻觉的主因。

## 六、消息数组（Messages Array）

### 6.1 消息（messages）是什么
- 一次**轮次（turn）** = 一次完整的思考-行动-观察循环。
- 系统提示（"你是编码助手，拥有这些工具"）→ 用户说"去修复失败的测试"→ 助手思考 → 执行工具 → 打印回应。
- **所有这些回合都存进一个数组，叫"消息（messages）"**；第一回合、第二回合、第三回合…一个接一个附加，消息数组持续增加。

### 6.2 消息数组 = 传给模型的状态
- **LLM 无状态**，所以我们**每次都把整个消息数组传给模型**——这就是模型看到的全部状态，别无其他。
- 消息数组包含：系统提示、工具、技能文件、`CLAUDE.md`/`agents.md`、到目前为止的所有消息（当前+过去）——**涵盖一切**。
- 关键认知：**记忆并不真正存在于模型内部**，而是这个被重新发送的数组。数组的构建靠思考-行动-观察循环。

### 6.3 循环的运行机制
1. 时间 0：消息数组只有系统提示（+技能文件、工具、CLAUDE.md/agents.md）。
2. 把"系统提示 + 用户提问"传给模型。
3. 模型判断**是否需要工具调用**。
   - 需要 → 模型发出工具调用（行动），产生观察结果，**附加到消息数组**（数组增长）→ 进入下一轮，重复。
   - 不需要 → 模型退出循环，给用户答案，停止。
4. 为避免无限循环，通常设**最大轮数（max_turns）**；多数情况模型能自己意识到"已完成"并退出（本例会循环 6~7 次后自动退出）。
- **每次传入都是一种"费用"**：系统提示、用户提示、工具、记忆、技能文件、CLAUDE.md 每次都传 → 所以构建要谨慎，工业项目不该塞 500 个工具。

### 6.4 压缩（Compaction）要点
- **永不压缩**：系统提示、工具、技能、CLAUDE.md。
- **会被压缩**：只有"消息的来回"（用户交互）会被压缩。
- 超出上下文范围时自动压缩（Claude Code 里看到的"压缩对话"就是这个）。

### 6.5 相关问答
- **技能每次迭代都读吗？** 是，每次迭代都读技能，模型决定特定迭代用哪项技能。
- **工具为什么每次都要带全量描述？** 因为不知道第几种情况下会需要哪个工具，每次都带上，模型才知道有哪些工具可用。
- **Odysseus 的工具列表在哪？** 有个文件叫 `tools.py`（转写为"two stop pi"），所有工具放这里，第 2 天专门讲。
- **云端对话上下文会传吗？** 会，也通过消息数组；但云端有**缓存控制（cache control）**机制，可把内容存缓存，不必每次全传（底层机制一样）。
- **能否在发消息前先决定用哪项技能以缩小上下文？** 可以，但会牺牲一些自动化；本质上仍需一个"工具分类器"元素，属于行动类别。
- **Claude Code 的 `/target` 命令怎么结束循环？** 它不结束循环，只有目标自动达成才结束；如果模型没意识到已结束，可能陷入无限循环。
- **前端模板放哪？** 放在**技能文件**里（Ovation 产品有"前端密度""设计系统""视频捕捉"等技能文件，都加到消息数组）。
- **技能文件 vs 工具**：技能文件是**操作列表**（做什么、用哪些工具、怎么做）；工具是**独立 Python 代码**执行特定操作。一个技能可引用工具（如前端技能引用 Figma MCP 工具）。

## 七、构建第一个 Harness（代码实操）

### 7.1 方法与前提
- 不手写代码：把**提示（prompt）交给一个编码助手**（Claude Code / Codex 等），让它生成 harness。
- 需要两件事：① 一个编程工具（Claude Code 或 Codex）；② 给自己的 harness 起名（希腊名是传统，但可用任何神话/文化名字，如 Pegasus、Leonidas、Achilles、Aquarius、Brahma、Apollon 等）。

### 7.2 LLM API 密钥
- 制作 harness 需要一个 LLM。讲者用 **Gemini 3.1 Pro**（转写中也有"gemini 2.5/3.1 pro"）。选 Gemini 的原因：**定价合理 + 性能出色**；也可用 Anthropic API 密钥、任意 API key、甚至本地 LLM。
- API 密钥存放：讲者放在桌面一个文件（如 `odysseus.sh`），在提示里提到即可（不要直接硬编码在提示里，不是好习惯）。
- 后续会整合 **OpenRouter**，自由切换模型。

### 7.3 本日提示的要点
- 提示大意："你正在构建 Odysseus 第一天，一个极简的智能体控制器，用 Python 编写。第一步建立仓库、创建项目文件夹、运行 `git init`，所有代码放进 `Odysseus` 包……"
- 规模目标：简洁的编码智能体；关键点：需要的模型。
- 本日只写两样东西：
  1. **`loop.py`**：核心是 `run_loop` 函数——while True 调用模型（传 messages + tools）；若无工具调用则返回文本退出；否则按顺序执行每个工具调用并追加结果。**工具崩溃时提取错误、不让循环静默失败**，错误显示出来。
  2. **`provider.py`**：模型提供者，定义它如何与 loop 交互。
- 简单演示：写一个"手写掷骰子"工具（掷 3 个骰子，判断总和是否为 10），验证工具是否正常工作。
- 提示要做的小改动：① 名字换成自己的；② API 密钥位置；③ GitHub 仓库设为**公开**；不要用订阅服务（因为要公开仓库，任何人可用）。
- 也可把同一提示交给 Hermes 或 Py（两者 2 分钟即可装好，都连 OpenRouter，可任选模型）。

## 八、课堂问答补充

- **能否追踪消息数量 / token？**（作业里有）会涉及消息追踪、token 追踪。
- **上下文如何传给用户提示？** 上下文通过单独机制传递（缓存控制等），"往上下文放什么"正是上下文工程的核心。
- **在哪提问最合适？** 讲者自建的讨论论坛（技术问题公开，行政/反馈私密）。
- **REACT 论文**：讲者分享了那篇论文（Reasoning + Acting）。
- **作业（Day 1）**：① 探索 Hermes 和 Py（下载、按提示操作、尝试不同模型，如 Kimi K3、GLM5.2 等开源模型）；② 通读材料并完成测验。
- **Harness 能否用于医学/金融/法律等特定领域？** harness 本身是通用的（引擎变汽车，必须宽泛通用）。讲者回答：**使工具具备领域特定性的唯一方法，就是把 LLM 嵌入领域**（模型本身可领域微调，但围绕模型的机制——循环/工具/上下文/耐久性/编排——保持不变）。
- **最大轮数到了还没结束怎么办？** 说明推理出了问题；可改进推理过程、追问智能体"为何花这么久、需要更多信息吗？信息需要在某处公开吗？还是问题不够清晰？"，或提供更清晰的问题。工业上客户关心聊天机器人速度，常把 **max_turns 设为 15**。
- **项目创意**：Kimi K3 已**免费发布权重**——可用自己的 harness 下载权重、检查推理方式等，项目空间很大。
- **技能文件是否"逐步公开（渐进式披露）"由 harness 决定？** 讲者：这是**灰色地带**，看具体情况。Py/Hermes 都有自己的技能文件（占大量代码）；讲者选择信任用户自己写详细技能文件，而非把技能嵌入产品内部。
- **可观察性/调试**：几乎每个循环内都设一个"可观察性智能体"（如 GitHub 循环里有可观察性和调试智能体），循环内部几乎都有观察设置。
- **今天成果**：GitHub 仓库更新 `loop.py` 和 `provider.py`；这是后续四天的基础。
