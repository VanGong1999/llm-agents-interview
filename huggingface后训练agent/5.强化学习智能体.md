## 二、学习全景与权重更新（3:00 - 6:30）

### 三种学习范式的信号对比（核心框架）

| 方法 | 信号类型 | 信号密度 | 学习方式 |
|------|---------|---------|---------|
| **SFT** | 目标token（模仿） | 非常密集（dense） | 离线、监督 |
| **蒸馏（Distillation）** | 教师分布（每个token位置） | 密集 | 离线/在线 |
| **RL（GRPO）** | 奖励信号（轨迹末尾一个数字） | **稀疏（sparse）** | 在线、无教练 |

### SFT的局限：**模仿天花板（ceiling of emulation）**
- 只能训练到数据所代表的水平，数据之外的信息无法学习
- SFT擅长学习**格式**：聊天结构、文档结构、工具使用结构等

### 蒸馏的演进
- 离线蒸馏：每个token位置都有教师分布，信息量大得多
- **在线蒸馏（On-policy distillation）**：教师提供**新鲜rollout**，用来评判和排序学生的rollout
- 相比SFT有**更丰富、更相关的学习景观**，因为真实rollout在循环中

### RL的稀疏性
- 只有一个信号：**轨迹/尝试末尾的奖励数字**
- 可以通过**过程奖励（process reward）**在轨迹中途计算奖励，但GRPO算法本身不具备蒸馏那样的密集信号

### 算法使用顺序（论文中的常见做法）
1. **先SFT**：提供密集表示，为模型"引导"（bootstrap）任务学习到某个天花板
2. **再RL**：从该天花板继续提升

### 国际象棋类比（贯穿全课的核心比喻）
- **SFT/离线蒸馏** = 阅读大师的棋谱：学到大量大师下法，但可能与你实际遇到的策略不相关；且大师棋局可能太复杂，初学者学不会
- **RL** = 只参加锦标赛，一直输，偶尔赢一次就重复那个策略——学习很慢
- **在线蒸馏** = 自己下棋 + 有人实时反馈"这步好，用这个策略"——但受限于教师的知识

### 后训练流水线（Post-training pipeline）设计
- 目标：找到**最短、最有效的策略**
- 典型组合：**离线蒸馏/SFT引导 → RL在自身轨迹上获得稀疏奖励 → 可能迭代循环回不同阶段**

### 三者定位总结
- **RL**：最on-policy，但稀疏
- **SFT**：非常密集，但off-policy
- **在线蒸馏**：居中（第二期重点）

## 三、GRPO单步解剖（15:05 - 17:12）

### 单步流程（训练过程的最核心）
1. **取一个prompt**（如：下棋、给定棋局走下一步）
2. **策略模型生成一组completion**（GRPO中不只生成一个，而是**多个**——示例中为3个）
3. **用奖励函数给每个轨迹打分**——通常是**Python函数**
   - 示例奖励：赢棋、将死、合法走子
   - 可**组合多个奖励函数**，为每个轨迹生成一个总分
4. **得到一组的分数**（示例：0、1、2）
5. **在该组内共享一个相对信号**，据此更新策略
6. **重复**：取下一个prompt，生成、打分、更新，迭代整个数据集

### 关键参数提示
- **生成数量（group size）** 是重要参数，Sergio后续会演示如何调整

## 四、组基线（Group Baseline）与优势（Advantage）计算（17:19 - 19:03）

### "组相对"的含义
- 策略优化是**相对于该prompt的completion组**进行的

### 示例（国际象棋）
- 第1个completion得0分（可能违反规则）
- 中间两个得1分（合法但不好/不赢）
- 最后一个得2分（将死）

### 优势公式（GRPO核心公式）
$$A = \frac{r - \text{mean(group)}}{\text{std(group)}}$$

即：**优势 = （奖励 − 组平均值）/ 组标准差**

- 含义：某轨迹比组内平均水平好多少
- **关键洞察**：
  - **组的构成（what makes up the groups）** 非常重要
  - **组内信息量** 非常重要
  - **如何给组内completion打分** 直接定义给策略的信号

## 五、护栏（Guardrails）：KL散度与裁剪（Clipping）（19:03 - 20:51）

### 两个护栏作用于两个不同时间尺度

#### 1. KL散度限制（KL Divergence）
- **作用**：防止策略偏离基础能力太远
- 示例：不要让它从下棋变成下跳棋，或开始写散文——要保持下棋
- 前提：起始模型必须是会下棋的模型（否则奖励函数无法工作）

#### 2. 批次限制/裁剪（Clipping）
- **作用**：防止批次内任何completion偏离该批次其余部分太远

#### 3. 两个关键参数（TRL和GRPO论文中）
- **ε（epsilon）**：约束**单个重用批次（reused batch）**
- **β（beta）**：约束**整个训练运行（whole run）**
- **重要**：TRL中两者默认均为 **0**，但可调整；Sergio会在实验中演示

## 六、奖励与优势的代码实现（20:51 - 22:33）

### TRL中已实现，无需自己写，但需理解

1. **rewards**：为每个response计算的奖励张量
2. **advantages**：`(rewards - mean) / std`（上述公式的实现）
3. **sequence log probability**：completion mask上的token log概率之和
4. **loss**：`advantages × sequence log probability` 的平均值
5. **两个系数**：
   - 系数1 = `exp(per-token logprob − old per-token logprob)`
   - 系数2 = 系数1的 **clamp（裁剪）**，范围 `[1−ε, 1+ε]`
6. **最终**：`min(系数1 × advantages, 系数2 × advantages)` —— 取两者最小值

## 七、奖励函数即"契约"（Reward Functions as Contracts）（22:33 - 28:24）

### 核心比喻：奖励函数是**契约**
- 契约双方：**你希望模型学什么** ↔ **模型实际在学什么**
- 用Python函数定义"成功"：
  - `is_checkmate`：将死=赢棋
  - `is_legal`：走子是否在允许列表中

### 常见双奖励结构：**格式（Format）+ 准确率（Accuracy）**
- 格式：完成任务所必需的简单信号（如下棋中的合法走子）
- 准确率：答案是否正确（如下棋中的赢棋；agent任务中的任务完成成功）

### 示例表格（数学题，答案为72）

| 行 | 情况 | 格式 | 准确率 | 总分 |
|----|------|------|--------|------|
| 1 | 答案72，格式正确且准确 | ✓ | ✓ | 3 |
| 2 | 格式正确但推理有误（侥幸猜对） | ✓ | ✗ | — |
| 3 | 格式正确但答案为71 | ✓ | ✗ | 1 |
| 4 | 答案72但无标签（推理对、格式错） | ✗ | ✓ | 反映在总分 |
| 5 | 结构化表示正确答案72但后跟更多文本（推理对、格式错） | ✗ | ✓ | 奖励错误 |

### 格式奖励的操纵空间
- 可以定义"只要答案出现在文本中就判对"——这样除中间那行（唯一不含72的）外全部正确
- 但**这可能不是表示任务的有效方式**，通常需要一致的格式

### 观众提问：协调/agent场景的奖励如何设计？
- 下期会深入，但agent harness中可能有工具调用格式（如反引号包裹、特定结构）→ **格式奖励**
- 准确率信号常见做法：**测试套件（test suite）**
  - SWE-bench等软件工程环境论文：拿pull request做RL环境，**PR的测试套件就是奖励信号**
  - 流程："修复这个bug" → 用PR测试套件测试实现 → 确认bug修复 = 奖励信号
- 奖励函数可以**堆叠**（stack）：
  - 代码能否编译（compile reward）
  - 代码正确后再加：**代码行数最少**（训练偏好简洁代码的模型）

### 核心要点
> **花时间真正专注于奖励函数**——这是成功训练运行的关键，相对于任务和输入的prompt而言。

## 八、训练组内变化（Variation）的重要性（28:24 - 32:16）

### 为什么需要变化
- 优势是**相对于组**计算的
- **全对** → 无相对信号
- **全错** → 无相对信号
- **只有一个成功** → 信号很少
- **需要组内有变化（variation）**

### 难度平衡（国际象棋ELO类比）
- 总跟大师下、全输 → 无信号
- 大师跟业余下、全赢 → 学不到东西
- 需要**有输有赢**的对手（合适的ELO）

### 维持变化的"旋钮"（Knobs）
1. **换模型**（更好或更差的模型跑同一任务）
   - 但**最不现实**：模型大小通常由硬件/用例约束决定，或经SFT流水线而来
   - 教育/科研场景可以换模型
2. **调整prompt**（最常用）：给模型更多/更少信息，使任务更难/更易
3. **调整奖励**：给模型更多/更少信息
   - 如格式奖励、编译奖励是**更容易学习的信号**——即使没成功，也能获得有效信号，从而**创造变化**
   - 但最终希望每组都有成功信号可供学习

### DeepSeek论文中的"啊哈时刻（Aha Moment）"
- 学习过程中某个**起飞点**：模型获得足够变化，开始能够学习

## 九、防止奖励黑客（Reward Hacking）（32:16 - 34:56）

### 观众提问：如何防止模型学到"捷径"或对奖励函数的"侥幸猜测"？
- Ben称这是"百万美元问题"

### 核心答案
> **定义一个不允许奖励黑客的函数。**

### 示例
- 格式奖励用了**开放式正则（open-ended regex）** → 模型可能黑掉它
- 国际象棋例子（略荒诞但典型）：模型发现"把对手的国王推倒"就能赢 → 每局都推倒国王
- 奖励黑客通常**很荒诞**，因为模型在找不符合逻辑、我们未在任务设定中定义的东西

### 最佳实践
1. **通过指标解读学习过程**，持续监控
2. **结合数据探查（probing the data）**
   - 警报信号：**熵变得很低**、某些行为反复出现、**奖励却仍在上升**
   - 此时**最好的做法：直接去看数据**
3. 有经验的ML工程师会**一直开着一个查看轨迹的窗口**——不要只"欣赏曲线"看奖励上升，而失去对agent实际行为的把握

## 十、GRPO vs DPO vs PPO 对比（34:56 - 38:36）

### DPO（Direct Preference Optimization，直接偏好优化）
- **离线方法**，比GRPO更早、**更简单易设**
- 数据形式：prompt + **chosen（选中）** + **rejected（拒绝）**
  - 示例：prompt=下棋，chosen=将死，rejected=输棋
- 流程：策略对prompt生成response → 与**冻结的参考模型**比较概率 → 更新策略
- **始终复用同一组chosen/rejected样本**
- 缺点：
  - 离线数据的劣势——可能不代表模型实际在做的事
  - chosen样本可能离模型实际行为太远（如数据集是几年前的，当时agent还不擅长该任务）→ chosen样本信息量不比策略本身多 → **可能让模型变差**
- **Online DPO**：用在线样本做类似的事，也值得尝试

### 为什么推荐GRPO作为起点
- 有**真实的RL循环**，可用Python函数定义
- 学习LLM RL的**最佳方式之一**：一切都在一个循环里
- 但可以比课程展示的循环**更复杂化**

### PPO（Proximal Policy Optimization）
- **第一个用于RLHF的算法**（InstructGPT论文），开启了后训练浪潮
- 比GRPO**更复杂**：多一个模型——**奖励模型（reward model）**给每个生成打分
- 成本更高
- 仍有优势：如果能训练奖励模型捕捉**风格属性**或某些**无法用确定性函数表示**的东西，PPO有优势
- 论文很有价值，PPO的许多特性被LLM RL沿用，值得学习
- 但**不再是首选**

## 十一、TRL中的GRPO参数（38:36 - 40:53）

### 循环与参数的对应关系（GRPO Trainer和Config）

| 阶段 | 参数 |
|------|------|
| 生成一组response | **temperature**（每次生成的温度）、**num_generations**（组大小）、**max_length**（completion最大长度，有些会更短）、是否用**vLLM**（推理引擎，脚本已设好，无需太担心） |
| 给completion打分 | 奖励函数（可**缩放reward**，如格式vs准确率给不同权重，避免过拟合格式） |
| 形成token loss | **epsilon**、**epsilon_high**、**loss_type**（多数情况为**交叉熵 cross-entropy**） |
| 更新策略 | **beta**（与起始模型的距离）、**learning rate**（每步策略改变幅度）、**steps per generation**（定义给定策略有多"在线"）、**number of iterations** |

## 十二、如何解读训练曲线（40:53 - 43:49）

### 正常（健康）运行的曲线特征
- **简单奖励（如格式奖励）**：应**较快上升**（语言模型应能快速做到）
- **准确率/任务完成奖励（绿线）**：起步较慢，但**持续改善**
- **熵（entropy）**：不应骤降或骤升，**接近平坦但缓慢下降**
- **completion长度**：因任务而异；**剧烈上升或下降都可疑**
- **奖励分布（reward spread）**：健康且**有变化**——最佳拟合线平坦但偏差大

### 停滞运行（Stalled Run）
- 两个奖励都**无信号**
- 相应地**无奖励分布**
- 需**深入探查（probes）** 找出任务难在哪
- 建议做**推理测试**：拿一个模型（如通过API调用的强模型）跑该任务+奖励函数，快速探查"这任务到底怎么回事"

### 崩溃运行（Collapsing Run）
- **熵下降**：模型固定到相似/一致的解
- **completion长度上升**：可能在黑客某个东西，或在"胡言乱语（rambling）"
- **某个奖励上升**：可能被黑了，找到了持续黑客的方法
- **KL beta大幅上升**：偏离初始策略很多

### 工具
- 用 **Trackio**（本课使用的工具）看曲线
- 也可直接看Sergio的运行记录，了解实践中曲线应该长什么样

## 十三、实验部分（Sergio主讲）（44:21起）

### TRL简介（44:36 - 45:56）
- TRL是团队开发的**后训练库（post-training library）**
- 包含多种trainer：**GRPO Trainer**、**SFT**等（前几期一直在用）
- 定义trainer**超级简单**：从TRL导入trainer和config → 指定模型、奖励函数（**列表，可传多个**）、训练数据集

### 实验一：最小GRPO训练 + 虚拟奖励（Experiment 1: Minimal GRPO training with dummy rewards）（44:36 - 51:52）

**设置**：
- 最简单的训练方式，使用**dummy（虚拟）奖励函数**
- 目标：奖励模型生成**接近20个字符**的输出（很"dummy"，但用于演示）
- 数据集：Reddit对话的简单数据集
- 脚本：`train_minimal`

**核心信息**：
> 模型会优化你告诉它优化的东西。即使奖励上升，也不代表模型生成了你真正想要的内容——这直接关联到奖励黑客话题（实验三会回来讨论）

**实现方式**：
- 在 **HF Jobs** 上运行——**不需要真实GPU**，用笔记本电脑就能把训练脚本发送到HF Jobs
- HF Jobs会训练、返回资源、生成并保存模型，还有**Trackio**追踪实验进展
- 奖励函数代码**极其简单**（几行）
- **TRL高度抽象了trainer**：几行代码+几个参数就能训练模型

**曲线观察**：
- reward曲线**一路上升** → 模型在学习生成接近目标字符数的内容
- 但明显是dummy目标，不是真实目标

### 实验二：用单元测试训练编码Agent（Experiment 2: Training a coding agent with unit tests）（51:52 - 1:00:33）

**设置**：
- 复杂度提升，场景为**编码agent**
- 数据集：**Python问题集**（每个问题带若干单元测试）
- 示例prompt："写一个函数，从给定的两个列表中找出集合元素"

**奖励设计**：
- **奖励 = 通过的测试比例**（fraction of tests passed）
- 这属于**可验证奖励的强化学习（RL with verifiable rewards）**
- 代码实现比实验一复杂：遍历模型生成 → 运行代码检查是否工作 → 工作则给奖励，不工作则不给
- **可改进点**：用**sandbox**隔离运行代码（当前只是带timeout的进程，示例中简化了）

**如何判断任务是否提供信号（关键方法）**：
- 用一个**超小模型（0.6B参数）** 跑prompt：
  - **所有奖励为0** → 任务**太难**
  - **所有奖励为1** → 任务**太简单**
  - **混合奖励** → 存在**甜点区（sweet spot）** ——这才是想要的信号

**训练前评估**：
- 每个prompt生成**4个**，得到**平均奖励0.22**（偏低）→ 说明模型表现不佳，用该数据集训练可能提升

**实验设计**：
- 同一数据集、两个场景、**三个版本**——只改一个参数：**num_generations（组大小）**
- 每个prompt分别生成 **2 / 8 / 16** 个generation
- 假设：2个太少，无法产生真实信号；8或16可能找到甜点区——开始与"人群"比较，信号既非0也非1，有真实训练信号
- 脚本：`train_grpo.py`（奖励函数略复杂：提取代码、运行代码、检查正确性、给奖励）

**Trackio曲线**：
- 3条曲线对应2/8/16个generation（reward及其他指标各有3条）
- 目标是找到模型在学习、reward攀升的甜点区

## 十四、Q&A与总结（1:05:12 - 1:17:16）

### 课程总结（Ben）
1. 对比了**RL vs SFT**：SFT的**模仿天花板**——数据没有更多信息时，让模型走自己的轨迹并给信号是更好的学习方式（在线蒸馏或在线RL）
2. **GRPO**：从一组rollout中采样 → 优势相对于组 → 必须重视**变化（variation）**，确保组内有足够信息
3. 用**可验证奖励（verifiable reward）** 计算奖励：确定性检查（格式、成功、单元测试）；**数学和代码是绝佳例子**
4. Sergio所有实验都在**Hub上用HF Jobs**运行，所有例子都可用
5. 重要能力：**读曲线、解读运行**——用**Trackio**（免费，本地或云端运行）

### Q1：调整是在运行中还是运行前做？
- **不在运行中做**。发送运行 → 解读 → 改参数 → 再跑
- 建议流程：
  1. **dry run奖励函数本身**：拿一些文本试奖励函数
  2. 训练脚本设好后，做**smoke test**（如5步）——**应看到奖励变化**；如果5步完全无变化，就不该有信心做完整训练
  3. 计算：4个generation × 5步 = 20次 → 至少希望有**1/20的概率**模型能做到该事
  4. 然后跑完整运行，**一次迭代一个数字**开始

### Q2：KL惩罚与奖励黑客的关系？（Ben的长回答）
- **KL惩罚的本质**：起始模型有一张"最可能做什么"的**景观（landscape）**；**beta参数**定义模型能偏离该景观的**陡峭程度/幅度**
- 偏离基础模型初始行为**越远，成本越高** → 策略必须"更值"才能走远
- 与初始策略一致的行为**成本低**
- 国际象棋类比：走SFT中学过的合法棋步 → 成本低、更易生成；做SFT中从未见过的事 → 成本高（但不是不能做）
- **beta从0调到约0.1**（非常低），用来控制允许偏离初始策略的程度
- **在奖励黑客语境下**：奖励黑客通常是模型在SFT中没见过的东西，KL惩罚**会**阻止这类行为
- **但是**：同一参数还用于其他目的，你可能想**放松它**以允许模型走更新颖的轨迹
- **结论**：KL惩罚**不是奖励黑客的完整解决方案**；最好的防御是**设计不允许黑客的奖励函数** + **探查、看曲线**，而非纯靠KL惩罚

### Q3：测试数据集的大小？
- 难有定论
- **学习示例**：从**几千个样本**开始
- **论文中**：常多达**几十万甚至更多**
- 但几千样本就能改变模型能力（很有意思）
- Sergio的实验大约**200步** → 就能获得不错信号

### Q4：如何检查泛化性、防止在测试集上崩溃/组内变化崩溃？（Sergio回答）
- 类似上一个问题：需要**每个prompt更高的generation数量**
- 需要检查**不同的曲线、不同的超参数数值**
- **不是看单一数字或单条曲线**，而是**多个测试用例、多个因素的综合**

### Ben的补充理解（1:16:08 - 1:17:02）
- **组 = 可能性的景观（landscape of possibilities）**
- 建立变化的方式：
  - **增大组** → 更可能有一条轨迹更有变化
  - **提高temperature** → 改变模型行为
  - **改奖励函数/加更多奖励函数** → 给更多信号
- 有了变化量后，再考虑**如何调用、如何防止景观变得过于多变**
- **最佳实践**：**保持极度简单，从默认参数开始，然后逐步迭代实验**

| 主题 | 核心要点 |
|------|---------|
| **GRPO优势公式** | **A = (r − mean) / std** |
| **两大护栏** | **KL散度（β，约束整个运行）** + **裁剪（ε，约束单批次）** |
| **TRL默认** | ε和β**默认为0** |
| **奖励即契约** | 用Python函数定义成功；**格式+准确率**是常见双奖励结构 |
| **信号判断** | 全0=太难；全1=太简单；**混合=甜点区** |
| **奖励黑客防御** | **设计不允许黑客的函数** + **监控指标（低熵+高奖励=警报）** + **看数据**；KL惩罚不是完整方案 |
| **组大小实验** | 2 / 8 / 16 generations对比 |
| **三种运行曲线** | 健康（格式快升、准确率慢升、熵缓降）；停滞（无信号）；崩溃（熵降、长度升、某奖励升、KL beta升） |
| **算法对比** | **GRPO**（起点推荐，简单，真实RL循环）；**DPO**（离线，简单但有过时数据风险）；**PPO**（多一个奖励模型，成本高，适合风格类奖励） |
