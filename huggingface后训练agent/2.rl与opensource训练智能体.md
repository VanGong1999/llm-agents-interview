## 第一场：Louis（Hugging Face）——我们训练的是 Agent，不只是模型

**时间：0:00–32:24**

### 演讲主题与动机
- 标题：**“We're going to be training agents, not just models”**。
- 为什么 agent 重要——两个改变领域的范式：
  1. **ChatGPT**：模型能回答从代码到物理等各种问题；接口是 **chat UI**，是大多数人（包括他们）与模型交互的主流方式。
  2. **Cursor**：强大的 **tab autocomplete** 模型——不是聊天，而是代码自动补全。
  3. **Claude Code（Anthropic）**：**复杂的 multi-agent 系统**，不只是给答案让你自己实现，而是**半自主地去做实现**。
- 对大多数人（至少在 Hugging Face）这是**软件工程最深刻的转变之一**：**过去 6 个月**，很多人从“大量手写开源库代码”转向“**用 agents 生成大量代码**”。
- 结论：**agents 会长期存在，且会越来越强**。

### 关键特征：任务视野（task horizon）快速增长
- 引用 **Meter（非营利组织）** 的著名图表：相对**人类基线**，模型能以一定成功率完成多长的任务；展示**50% 成功率**相对人类；y 轴是**小时数**，x 轴是日期，**基本是指数曲线**。
- 前沿模型（**Opus、GPT-5.4** 等）现在能做**熟练人类约一天（半天或稍长）** 的任务。
- 局限：benchmark **没有覆盖人类能做的所有任务**；但在 Meter 开发的**窄任务集**上趋势明显：**大约每 4–7 个月翻倍**。
- 不清楚能持续多久，但**快速进步是明确的**；也体现在他们自己使用 coding agents 的体验中。
- 不只是 benchmark（公共 benchmark 常被批评**可被 gaming/过拟合**）：
  - **Cursor** 有自主 agents **构建 web 浏览器**；
  - **Anthropic** 让**大量并行 Claude 实例协作构建自己的 C 编译器**；
  - 容易批评（C 在训练数据中代表性高、未必完全自主开箱即用），但**仍然令人印象深刻**——**目标线不断被推移**（“它做不了 X”→ 后来做到了 → 再推移）。

### Hugging Face 自己的实验：用 Claude 自动化 Louis 的工作
- Louis 在 HF 的工作很大部分是**微调开放模型**：理解 Hub 上有什么数据集、构建自己的数据集、用训练框架训练模型。
- 实验：围绕 **Claude** 搭自己的 scaffolding，给它**大量 context engineering + 专用工具**，结果**显著优于 vanilla Claude Code**。
- 信息：**不只是 Anthropic/OpenAI 能做的**——用**公开可用的模型 + API** 已经能做很有趣的事。
- 这些是**长时运行任务**：训练模型可能**花几天**，Claude 能**持续管理**，在**窄领域（微调模型）** 达到**相当强的模型**。

### 开源/开放权重模型的追赶
- 常见抱怨：**专有前沿模型**才真正适用于真实世界任务，**开源/开放权重模型落后**——历史上大致如此。
- 但现在**一些中国实验室全力训练最好的 agentic 模型**：
  - **Kimi K2.6 ICS**（几天前/昨天发布）：有趣例子——让模型**在 Mac 上优化 Qwen 模型的推理**；不用 Rust 等标准工具，而是用**代表性不足的编程/编译语言 Zig**；模型**跑了约 12 小时**想办法加速推理；基线是 **LM Studio**。
- 结论：**已进入新阶段**——不只是少数专有模型能长时运行任务，**开放模型也在快速追赶**。

### 为什么训练自己的模型（三个理由）
- 前提：这些模型**很大、难部署**（Kimi K2.6 是**万亿参数**，“会炸掉你的 Mac Mini”）；出现**本地、快速运行的自有模型**趋势。
- 开源项目爆发式增长（按 **GitHub stars** 衡量）：**Hermes Agent、OpenClaw、Pi**——**很短时间达到 30 万/10 万 stars**，比 **transformers 库**快得多。
- **理由一：隐私/个性化**
  - 不想把所有内容（敏感对话、个人助手内容）都发给 OpenAI/Anthropic；
  - 想要**本地运行**的 agent，有**自己的个性**；
  - 想让 agent **适应自己的任务和需求**。
- **理由二：成本**
  - token 目前**中等便宜**，但价格不一定稳定：如 **Opus 4.7 比 4.6 贵约 1.5 倍**；
  - **Cursor** 的例子：把开放模型**针对特定领域 post-train**（跑在 Cursor 里），得到 **Composer**——**性能与 GPT-5.4/Opus 相当，但运行显著更便宜**；对公司和对用户都好（**同样花费更多 token**）；
  - 其他：**H Company** 发布很好的**计算机使用模型**，小到可本地运行；**Chroma** 构建**搜索 agent**，比大模型便宜得多；
  - **效率很重要**：人们“炫”每天烧多少 token；若每天烧 **10 亿 token**，希望 token **尽量便宜或信息密度尽量高**。
- **理由三：领域专业化**
  - **jagged intelligence frontier（锯齿状智能前沿）**：模型在某些领域（如数学）很强，在另一些领域突然很笨；
  - 若想训练**分布外（OOD）** 或训练集中少见的能力，就该训练**自己的定制 agent**；
  - 例子：**Allen AI 的 Dr. Tulu**——开放权重模型能做**基础 deep research**，但比 OpenAI/Anthropic **差很多**（多步检索与信息综合）；他们证明把标准 RL 从**二元奖励**扩展到**rubrics**，可训练出**很强的 7B/8B 模型 Dr. Tulu**，专注**窄领域 deep research**；
  - 科学领域尤其：**单一模型不太可能完全掌握整个科学广度**，**专业化是关键**。

### 过去一年什么变了：从 RLVR 到 Agentic RL
- **主导范式：RLVR（Reinforcement Learning from Verifiable Rewards）**，由 **DeepSeek R1** 推广——在 base model 上用**二元奖励**即可**引出长 chain-of-thought**；是**第一个能模仿 OpenAI 推理的开放权重模型**。
- **之前 vs 现在**：
  - 之前：**prompt → LM → 答案（可能带 CoT）→ 二元奖励**（数学题对/错，0/1）；**verifier 通常无状态**；rollout **分钟级**；每次 rollout 末尾给奖励。
  - 现在（agents）：**内循环**——给模型任务，它**多步 t 迭代**，**与环境交互**，环境给**观察**（如调 API 拿结果），若干步后**episode 结束**，再**验证该轨迹是否满足任务要求**。
  - 差异：**多步 rollout、可能多轮**；**视野非常长**；rollout 时间**从分钟到小时**（如软件工程要起 **Docker 容器**、管理基础设施；环境慢则端到端很慢）。
- 若想让 agent 做**多小时/多天任务**，必须**把这一点建进训练**——**巨大变化**。
- **信用分配（credit assignment）挑战**：
  - 单 episode 通常 prompt→reasoning→answer→feedback；现在有 **t 个交互轮**、**数百次工具调用**、**成百上千 token**；
  - **不清楚模型在哪一步做了关键洞察或犯错**；
  - 历史做法：**process rewards**（给每一步打标签），但**迄今不可扩展**；
  - 中国实验室在 tech report 中**部分解决**，但**自己训练 agent 时这通常很难**。

### 训练模型通常需要 3–4 样东西
1. **Environments**：让模型与**有状态**的系统动态交互；
2. **Training frameworks**：让这件事容易做；
3. **好的 evals**：告诉我们是否在某个领域有进展；
4. **Scaffolds（问号）**：引出已有模型能力的有趣方式。有人（如 **Noam Brown（OpenAI）**）说 scaffolds 会被 scale 冲走；但**当前范式下**，scaffolds 仍是提升现有 agent 性能的**重要方式**。

### 什么是 Environment（环境）
- 组成：
  - **Tasks**：想让 agent 能做的事；
  - **Execution backend**：sandbox 跑代码、浏览器、bash 终端等；
  - **State 管理**：数据库、监控 agent 能否查询/改文件、coding agent 在 open code 里编辑文件等；
  - **Reward 分配**：简单二元奖励，现在更常见的是 **heuristics + rubrics + 其他 LLM 给 dense feedback** 的混合。
- 这些是**跨所有环境实现相当通用**的组件。

### 去哪里找环境：框架 + Hub
- **框架（构建环境并接入训练框架）**：
  - **Nvidia：NeMo Gym**；
  - **Prime Intellect：Verifiers**（稍后 Will 会讲）；
  - **Meta：OpenEnv**；
  - 列表相当长。
- **环境 Hub**：
  - **Prime Intellect：Environment Hub**；
  - **General Reasoning 的 Open Rewards**（很新）：聚合不同环境，可插到不同训练框架；
  - **Hugging Face**：一套**中立、agnostic 的 Spaces**，覆盖不同类型框架，**Spaces 本身可当环境**，也可用于训练。
- 目前**说谁绝对最好为时过早**；有**设计权衡**；Prime Intellect 视角会多讲。

### 如何做 RL 训练：异步化
- 历史（RLVR）：prompt → rollout → 算奖励 → 反传。
- 现在：**尽可能异步**，两个异步度：
  1. **生成与训练解耦**：**inference 节点/引擎**持续从当前 policy 生成 rollouts；**trainers** 更新 policy。
  2. 历史做法**同步**：等 rollout 全部完成 → 优化 → 更新权重 → 再 rollout——**产生大量气泡（bubbles）**：若一个 rollout 很久才终止，**整个 batch 被阻塞**，其他 GPU **空闲**。
- **现代范式：异步训练**——generators 持续算 rollout，trainers **尽可能高利用率**持续更新权重。
- **Mistral 的 Magestral tech report** 有很好的图（据他所知**最早认识并可视化**这一点）：policy 的更新**在飞行中（in flight）** 发生；buffer **staleness 达到一定程度**就更新权重；generators 可在生成中途**换掉 KV cache**——增加一些 **off-policyness**，但**通常不损害整体性能**。
- **训练框架**也很多（类似环境）：**设计权衡**——小规模/本地训练 vs 超大模型（需引入 **Nvidia Megatron**，有其自身“荆棘”）。
- **没有单一参考框架**——**按用例选最好的**；**多样性对生态有益**，框架互相学习。

### 评估 Agent 为何棘手
- **公共 benchmark 饱和极快**：**EpochAI** 的图显示，尤其现在**6 个月到一年**，大多数 benchmark（尤其传统语言 benchmark）**饱和很快**；参考模型已饱和就**难以获得额外信号**。→ **需要更难的 evals**：
  - **SWE-bench**（Afir/Offair 团队）；
  - **PostTrainBench**：让模型**训练/微调开放模型**，看能否**超过人类基线**；目前仍**远差于人类**。
- **开放模型对公开 benchmark 过拟合**：如 **Kimi** 在新 benchmark 上**SOTA**，但**新 benchmark 出现时**往往**不如专有模型**；普遍认为 **OpenAI/Anthropic 多年建了大量内部 evals/environments** 来校准模型；Louis **乐观**这会在开放权重社区成熟后改变。
- **自己训练模型的关键信息**：**必须有自己内部的、与任务相关的 evals**；**不要只看柱状图**说“指标都涨、这是最好的模型”；**必须自己测**。
- **Agent evals 更复杂**：
  - 传统 benchmark **单轮、易评分**；现在有 **terminal、bash、code sandbox** 等；
  - **易受 reward hacking**：agent 利用 benchmark 设计弱点拿高分；
  - 部分因为社区历史上**只关注能力/性能**，**未设计成对 agent 对抗性稳健**；
  - 这将是**持续挑战**：建**不被 gaming 的 evals**。

### Scaffolds（脚手架）
- **test-time compute scaling** 已知可提升性能：
  - **并行 scaling**：从模型生成 n 个 rollout，聚合/拒绝坏结果——**best-of-n**；
  - **顺序 scaling**：生成 → 修订 → 再生成新序列；
  - 最近有趣：**recursive self-aggregation（递归自聚合）**——在**同一 scaffold** 中**并行 + 混合 scaling** 结合；
  - **ARC-AGI** 上显示：只把它应用到 **Gemini** 就能比**单轮 rollout** 显著提升。
- 不只用于人工任务：**OpenAI** 用 scaffold 在**理论物理**得到有趣新结果；没说 scaffold 是什么，只提到**内部 scaffolded 版 GPT-2** 能泛化出一组**很难的方程**（世界上可能只有少数人能验证）。
- Scaffolds 是**引出更好性能的额外技巧**；迄今多聚焦**静态模型 + scaffold**。
- 但许多论文（含 recursive self-aggregation）显示：**用 scaffold 训练 agent/模型**（scaffold 本身作为**环境**）→ **性能显著更好**；他们评估不同模型用其 harness 训练，**RL + scaffold 有非平凡增益**；社区**仍很早**，**没有很好的配方和理解**。

### 总结：开源社区可聚焦的三件事
1. **开放环境生态**（新兴，很好）——但批评：**大多是玩具**（游戏、简化任务）；前沿实验室用的是 **Excel 完整副本、企业工具完整副本**；若要开放权重 agent **真正解决真实世界任务**，**需要这种环境**。
2. **开放配方（recipes）**：
   - 历史上有预训练开放配方（**ALMO、Small LM、INTELLECT、IMATRON**）和后训练配方；
   - 但 **agentic 时代**信息大多**通过中国 tech report 蒸馏**——极有价值，但**常缺少自己实现时真正重要的细节**；
   - **还没有一套连贯的开放 recipes**：不只是最大化某个 benchmark，而是证明**用这种真实世界环境训练**能得到**高性能且可泛化**的东西。
3. **长时能力（long horizon）**：
   - 开头提到**任务视野每 4–7 个月翻倍**；目前主要由**真正训练大模型的实验室（目前多在中国）** 解决；
   - 对**个人 AI 开发者**，**如何做 long-horizon RL** 仍有很多开放问题；
   - Alex 会讲 **recursive language models** 及**如何在百万 token 上保持连贯性**的技巧。

### 结语
- 已有很多好的开放模型；应想办法让它们**不只在公开 benchmark 上好**，而是**对真实世界有影响的事**上好。

## 第二场：Afir / Offair Press（SWE-bench 团队）——Benchmark 的科学与艺术

**时间：32:53–54:32**

### 开场三个事实
- **想做蜂蜜，需要蜜蜂；想砌墙，需要砖；想做 AI，需要 benchmarks。**
- **benchmarks 是一切之源**：一切都从 benchmark 出发。
- **AI 世界的循环**：
  1. 想出**好的新 benchmark** → **聚光灯照出现有 LM 在某子领域的低性能**；
  2. 例如 **SWE-bench** 显示 LM **不擅长编程**；**GSM8K（5 年前）** 显示 LM **不擅长数学应用题**；
  3. 好 benchmark **暴露缺失能力** → **明确需要什么新的预训练/后训练数据、什么新 RL 环境**；
  4. 然后改进 pipeline 其他部分：**scaffold**，甚至**架构**（“不太推荐但可以试”）；
  5. 获得**新能力** → **再建新 benchmark**。
- 结论：**要让 AI 更好，就需要持续产出好的新 benchmarks**。

### Benchmarks 是易腐资产（perishable asset）
- 建 benchmark 通常**花很长时间**，希望**永存**，但**从来不会**；
- 即便建了**能想到的最难 benchmark**，**通常一两年内饱和**（运气好）；**运气不好两个月**；
- 所以**必须不断建新 benchmark**；
- **激励所有人**：不管你的本职是 mid-training、post-training、pre-training、RL 还是架构，**都应始终想着一个让你兴奋、想为之努力的 benchmark**。

### 过去五年 benchmark 的五个阶段
- Afir 做语言建模研究 **10 年**：前 **6 年**做架构，过去 **3–4 年**转 benchmarking。
- **阶段一：学校考试**——如 **GSM8K**（“Opie 有 5 个苹果，Ben 有 3 个……”）；三四年前**饱和**。
- **阶段二：大学考试**——**MMLU**（大学水平、多主题：数学、科学）；**HumanEval**（大学第一门编程课，如“用 Python 写斐波那契”）；起初超难，**约三年前饱和**。
- **阶段三：人类几天解决的真实任务**——**SWE-bench** 是首批之一；从考试转向**真实世界工作**。
  - SWE-bench 发布时**最高准确率约 1.5%**，以为要很久才饱和；
  - 最近 **Anthropic 的 Mythos** 在 **Verified** 上达到 **93.9**；
  - **SWE-bench Multilingual、SWE-bench Multimodal** 下月发布，**尚未饱和**；
  - 但 **SWE-bench 范式接近饱和**。
- **阶段四：人类团队几年解决的任务**——如 **Commit0**（Cornell Tech，不是他的）：拿完整 Python repo，**保留所有函数签名、清空所有函数内容**，要求**重新实现整个 repo**，有单元测试检查；这类任务**人类团队可能要几年**。
- **阶段五：可验证但从未有人做过的任务**：
  - 例：**Nicholas Carlini 的 C 编译器**——让 **Claude 用 Rust 写 C 编译器**；据他所知，如此规模的 C 编译器**从未用 Rust 写过**；
  - 例：**把 Linux kernel 重写成 Go**——没人做过，但**可验证**；
  - 这是**新时代**，很令人兴奋；会推动模型、agents、语言建模。

### 三个近期 benchmark 例子

#### 1. Crit（CritPoint）
- **极其复杂但易解释**：请**物理学助理教授**想一篇**近期论文**，基于它出一道**给一年级 PhD 学生的题**；
- **关键**：题目要**改得与其已发表研究不匹配**（否则 LM 可能训练过或网上能找到）；要求**从未上线过的变体**；
- 题目**非常复杂**，但答案是**可验证的**——**数字或方程**；用**数学等价（equivalents）** 检查 AI 答案是否等于正确答案；
- **约 4 个月前**发布；现被 **Artificial Analysis** 追踪；很多大实验室在做，**进步很快**；
- 题目**极其难**：让 PhD 学生出题**太简单**（所有现有模型都能答）；于是找**教授**出题，**现在也在快速被解决**。

#### 2. AlgoTune
- 取**约 150 个程序**：**Python 的 gzip、NumPy 的 QR 分解、NetworkX 的 PageRank、AES 加密**等；大量数学/物理/CS 代码；
- 告诉 LM：**你有 1 美元**，要让程序**跑得更快**；它写代码；告诉它“略有提速”→ 再写；“不，你错了，更慢/不编译”→ 继续；**有 1 美元预算**；最后说“准备提交”；
- **两种检查**：**代码正确性**（用**留出输入集**，比较 LM 生成代码与真实参考代码输出是否一致）+ **速度更快**；
- 按在这些程序上产生的**平均加速比**给分；
- **非常难**：拿**人类已优化十多年**的代码（如 Python gzip），要求**更快**；某些算法**没人知道更快的解法**；但**可验证**——你给我更快的解法，我能轻松验证；
- 排行榜：**algotune.io**；
- **创新点**：不只看能力，而是**能力受每任务 1 美元预算约束**；
- 有趣现象：**更便宜的模型有时比前沿模型做得更好**——因为**有更多机会迭代**；前沿模型可能**生成一个候选就耗尽预算**；
- 当前 **GPT-5.2 第一**；**Opus 4.5** 也跑了，但**迭代机会少**，表现不如；
- 可探索**所有轨迹**，看 LM 如何找到加速。

#### 3. Code Clash
- 取 **7 个 arenas**（通过计算机模拟玩的游戏）；展示的是 **Robot Rumble**：
  - 两个玩家（蓝方、粉方），**不是用键盘控制**，而是**各写一个脚本**决定机器人行动；
  - 每方控制一队机器人，在网格移动、攻击对方；每个机器人 **5 HP**；要杀死对方机器人并保住自己；
  - 通常是**本科生竞赛**或**公司面试**用；
- 他们让**两个不同 agents 写代码**控制双方：**GPT 写粉方、Anthropic 写蓝方**，互相对战；把**每轮日志**给 agent（“第一轮发生了什么、第二轮、第三轮、第 100 轮”），说“**请改进你的代码**”；再 clash；**重复 15 次**；**每个模型与每个其他模型对战**；
- 排名用 **ELO**（每对都打过）；
- **极其 long-horizon**：要读**巨大日志**、打 **15 轮**、反复改代码——**反映真实世界**（如 web 应用程序员：上线后用户涌入、数据库崩溃、修一个又崩另一个）；
- **关键价值**：显示出 **SWE-bench 无法区分的模型差异**——当时 **Cohere 3 Coder 与 Sonnet 4.5** 的 SWE-bench 分数相近，但对战显示 **Sonnet 强得多**，因为任务**难得多**；
- 轨迹分析发现（与使用 Claude Code 强弱模型时所见一致）：
  - **最好的模型也难在输掉回合后恢复**：有策略就想坚持，即使你告诉它不奏效；
  - **模型管理的代码库随时间变得极乱**：创建 main1、main2……**大量文件，难以维护**；
  - **agents 难以解读日志、得出有意义的性能洞察**；
  - **最糟**：**模型做改动却不评估其效果**；
- Afir 喜欢**自然、模拟真实世界功能**的 benchmark，但**看似 artificial 的东西也可能很有用**；
- 喜欢找**人与 agent 差距大**的任务：Code Clash 上让**最好的 agent（当时 Claude 4.6/4.5）** 对战**最好的人类写法**，**连输约 1000 回合**——**AI 仍远差于人类**。

### 建新 benchmark 的三条规则（他的博客）
1. **与真实世界有用性相关**：不喜欢 **IQ testy** benchmark；喜欢**模仿/就是真实世界任务**的（Crit、AlgoTune 是真实执行的任务；Code Clash 虽非日常，但**反映非常现实的任务**）。
2. **尽可能难**：
   - AI 进步很快；若发布时**40% 准确率**，说明你在针对**所有大模型厂商已经知道的能力**，**没给新东西**；
   - benchmark 是**地图，指向北方（north star）**——如何到达 AI 下一前沿；
   - **应从 0% 开始**（或 1%）：找**没人尝试训练过**的东西，显示**我们确实需要这个能力且严重缺乏**；
   - 但也**不要难到 20 年才解**；不要**两个月到 75%**，也不要**五年卡在 0**（人们会厌倦、不再想它）；**要在中间**——建 benchmark 很难。
3. **答案简单、可确定性验证**：
   - **不喜欢 LM as a judge**；
   - 建 benchmark 的挑战之一就是**想出极难但极易确定性验证**的问题；
   - LM judge **弱点很多**：有时偏好自己的输出、不够准确/稳健；要**稳健、可重复、准确**；
   - **别偷懒**：多想，直到找到**确定性验证器**；有时看似不可能，但**通常能找到**；
   - **对模型别客气，要严格**。

2. **总有一天阶段四、五也会饱和，会有阶段六**——但**很难想象那是什么样**；**下一阶段 benchmarking 会是什么样？**

## 第三场：Alex Sang（MIT）——Recursive Language Models（RLMs）

**时间：55:08–1:12:21**

### 开场
- 给过很多次 RLM 演讲；本次 workshop 最有趣的是：**为什么这个想法非常适合训练**，以及**未来如何训练模型**（尤其针对 Afir 提到的更有趣、更难的 benchmark）。

### 背景：context management 与长时任务
- **2026 年初至今**，大量注意力在 **context management** 和**让 LM 可靠解决越来越长时任务**。
- 现状：部署 LM 解决**很复杂的事**或**长时间自动化**，**效果不好**；大多数用途是**短时任务**（chat UI 很有用）。
- **编码**是**长时任务中第一个成功应用**——尤其因为**大量 benchmark 和 hill climbing**。
- 有趣问题：如何把**围绕 coding 构建的 scaffold 直觉**应用到**更通用的系统**。

### RLM 是什么（澄清误解）
- **RLM 不是 sub-agents 的提案**（sub-agents 早于 RLM 存在）；
- **也不是把 context offload 到文件/让 LM 用代码管理**的提案（Claude Code/Codex 之前人们就知道这个 trick，避免 LM 处理长 context；最明显版本：**代码库永远不会一次放进 context**）。
- **核心定义**：RLM 是**LM 之上很薄的一层**，**能访问某种 REPL**（Python、Bash、IPython 等）；在这个 REPL 里，LM **能访问 sub-LM 或 recursive-LM 调用**，**作为 REPL 内的函数存在**——**这个区别非常重要**，很多人不清楚为什么重要。
- **同时**：把 **context offload、prompt 存在 REPL 里**同样重要。
- **为什么“函数/程序化工具调用（programmatic tool calling）”设计重要**：
  - 它**强制所有工具调用（包括 sub-agent 调用）成为 coding 环境里的 first-class primitives**，而不是 **JSON tool calling**；
  - 传统：LM 按某种格式做 JSON tool call 调 sub-agent——**很多原因不好**；
  - RLM 的提案可理解为：**LM 唯一应访问的工具是 coding tool，所有其他工具都应嵌入这个 coding 环境**；
  - 这种**极简抽象设计**贯穿所有 RLM 实现。

### Harness/Scaffold 之争：与 Noam Brown 的“scaffold 会被 scale 冲走”
- Alex 的回答：**LM 与 scaffold 的界线非常模糊**。
- 若用**函数式**思维：把 LM 当函数、scaffold 当与 LM 组合的函数——**RLM 看起来就像 LM**；
- 因为**抽象地看，LM 就是“文本 → 语义上有意义的变换”的函数**；
- **RLM 设计的重要主张**：**非常适合 scale**。

### 长 context 视角：为什么扩展长 context 的方式“很傻”
- 领域从 **4K → 16K → 128K → 最近 100 万**；过去一两年停在 **100–200 万**；
- 扩展长 context **非常难**：
  - 不只是 Transformer 系统层限制；
  - **数据问题**：大多数数据**不自然出现在某些 context 长度**；
  - 出现 **context rot**：喂大量 context，模型突然做**很蠢的决定**或输出**毫无意义**；
- **RLM 论文的发现之一**：**length generalization 自然从 RLM 设计中出现**——因为**每次单独 LM 调用永远不必看到超过某个 context 长度**。

### Raymond Whitemp 的框架
- **RLM 是把 tool calls 与现有 reasoning 范式（通过 RL 训练得到）合并成有意义的东西**；
- 可**原生地在模型内 scale 工具使用**。

### 为什么 RLM 适合 RL 训练：QED Nano 与 Long CoT
- **QED Nano**（Louis 参与）：训练小 LM 解**极难数学题**；技巧之一是**让模型迭代精炼推理**；
- 传统推理模型（**o1、DeepSeek R1**）：**单模型采样一条很长的推理轨迹**，受**context window 限制**；
- QED Nano 的技巧：模型**边推理边总结自己的推理轨迹**，从**压缩后的轨迹继续**，产生**更长的推理轨迹**，最终得到**原本单次调用无法解出的答案**；
- 启示：**把多次模型推理调用串起来**，模型**可以超出 context window 很好地推理**。
- 从 RLM 视角：**coding + 内嵌 sub-calls** 让 RLM 能**用代码描述/编写更有趣的方式**，**串联多次 LM/sub 调用**，做**不同推理模式、推理更久**。

### 相关 benchmark：Long CoT（Long Train of Thought）
- 把问题组织成**推理图（reasoning graph）**，模型要解**每个节点**、**遍历图**到最终推理步骤/答案；
- 若训练得当，**RLM 应能做得非常好**。

### 方向：让模型原生具备 test-time compute 策略
- 想要模型**推理更久**、**原生具备** best-of-n、iterative refinement 等策略；
- **不应构建一次性 scaffolds/采样策略**，而应**让模型自己具备实现这些策略的能力**——**RLM 设计使能**这一点。
- 对 agents 同理：**偏离标准 agentic 视角**（人类工程师设计 agent 解任务）；**真正想要的是 LM 设计自己的执行流/所谓 agent** 来解决更复杂任务。

### 未来展望
- 大量 RLM 工作正在进行（他在其中一些，如 **Crime in like work**），很多公司/实验室也在探索；
- 未来几个月/今年：**更稳健的 RLM 实现** + **围绕 RLM 训练的模型**，成为**通用任务求解器**；
- 想象未来：**GPT-6 x-high 之类超高 thinking** 实际上是**薄薄一层 RLM scaffold 套在现有模型上**，做**超长推理**；训练时**仍只训练 base 的 100 万 context 模型**，但**能推理 10 亿 token**；
- 训练策略细节留给 panel；三个方向都有很多开放问题，鼓励大家做。

## 第四场：Will Brown（Prime Intellect）——Evals 与环境是同一件事

**时间：1:12:46–1:40:54**

### 核心主张（略争议）
- 试图连接前面所有主题：**environments、evals、harnesses**——不同人有不同术语，关心起点/终点、什么是 harness/environment/eval/benchmark、什么是 train/test；
- **主张：evals 和 environments 是同一个东西**——不是相似、不是相邻，**就是同一件事**；
- 为什么有用：让事情**更可操作**：
  - 若 environment 只是 RL 的事，人们**直到做 RL 才把它当通用抽象**；但很多人**先建系统**（优化 harness、调 prompt、选模型、评估）；
  - 让它们存在于**同一个循环**，可**并行迭代系统多个部分**，不必为 pipeline 每个部分**维护多个版本**。

### Evals 的定位
- 大家都熟悉模型发布时的 benchmark（**TerminalBench、TAU2** 分数）；用 **TAU2** 举例说明 eval/benchmark 里发生什么；
- 框架不是“去训练这些 benchmark”，而是**用它们作为灵感**，思考你真正关心的任务；
- 若建使用 LM 的系统，要**确信系统在做你想要的**，且**改动系统时**知道是**提升/损害/维持**你关心的轴上的性能；
- **Eval 的目标**：通过例子**描述你的系统（代码 + prompts）在一系列任务上、按你关心的指标应做什么**；
- 与 Afir 的框架一致，**例外**：Afir 把 eval 当**持久 artifact**；Will 把 eval 看得**更 disposable**——不是要展示“最酷新 eval”，而是**你个人希望系统做得很好**的表达方式。

### Environments 的组成
- **Tasks**（扮演 dataset 角色）、**Harnesses**（扮演 agent/系统/工具调用接口角色）、**Metrics**（context reward functions、scoring functions、rules、pass/fail、rubrics——**可互换**）；
- 不只用于 **RL**、**evals**，还用于：
  - **合成数据**；
  - **prompt 优化**；
  - **模型消融**（Opus 换 Sonnet？Haiku？GPT-5.4/5.4 mini/nano？Gemini 是否有用？）；
- 建 LM 系统的人都应**愿意回答这些问题**，才能知道系统**高效工作**；**成本、速度、性能的权衡**要调到最优，尤其大规模运行；
- Environments 让这些部分**活在一个对象里**，**直接比较**。

### Environments Hub（Prime Intellect）
- 平台收集环境、**培育社区**、提供例子；
- 很多人会**开箱即用**做研究/训练；但不是“你们该训练/测试的所有环境”，而是**思考模式、与社区分享**，别人**fork 并构建新版本**；
- 目标：**让建环境和 evals 更流畅、摩擦更小**，因为很多系统**根本没有 evals**；
- 人们常卡在 **vibe check**；
- **Environments 解锁优化**：人们**推迟做 eval**，因为觉得**不可操作**（“评估了然后呢？”）；手动写新 prompt/换模型**不够**让人跨过“我要建 evals”的门槛；
- 既要**给更多建 eval 的理由**，也要**降低摩擦**。

### 库：Verifiers
- 用于创建环境（Hub 上或本地），**封装 tasks、harnesses、datasets**；
- 示例：**harness 很简单**——单轮 chat completion 式回答；模型拿到 dataset 中 **question 列**的 prompt；
- **metric** 是 **correct answer**：**显式检查、非常可验证、确定性**——输出是否与预期完全相等；适合数学题（答案按某种格式解析）；
- 把函数收进 **rubric**（做评分的对象）；**组合起来叫 environment**。

### 新模式：Task set + Harness 显式组合
- 过去一年半探索了很多模式；领域在演化；工具调用、agent harness、skills 的用法**开始稳定**；
- 正在引入**新默认模式**：**显式思考 task set 与 harness，并用自动规则判断是否匹配**；
- **Harbor** 是很流行的封装 task set 格式（现在大多数 benchmark 用它）：**terminal 格式**，agent harness 在 terminal 跑，要 **sandbox**，结束时跑**测试用例**；
- 也有 benchmark 需要**用户模拟器**、**与合成后端（如 MCP servers）交互的工具调用**、或**根本不需要 harness**（trivial harness / 允许插入第三方 agent 库而不必是 CLI agent）；
- 空间很广，但**边界（task set vs harness）** 开始清晰；**仍在进行中**，这是预览。

### Environments Hub 作为整体研究平台
- 希望人们**同时用 environments 做评估和优化**；用 harness/tasks **迭代问题、优化系统**；
- 平台**agent-friendly**：
  - LM **不擅长 one-shot 难 evals**（前沿 eval 本就是模型难做的事，不奇怪）；
  - 但可给**baseline**：**instructions/skills、配置**；某些 skills 指向 environment hub，让 agent **浏览 hub、看模式实例**；
  - 提供 **CLI 工具**：`uv tool install prime`，`prime lab setup` 在新 workspace **为 agent 编排**；agent 有很多工具就绪，**不必处理 infra/setup**；
- **用户流程**：**做一个 environment，让 agent 帮你做**：
  - 已有**非结构化数据**（文档做 QA 检索）；
  - 有**宽泛系统的 traces**，想挖任务；
  - 完全**合成**；
  - 拿 **Hugging Face 上现有数据集**做自己的版本 + 新 harness；
  - 都是**有效起点**；
- 有用的事：**创建环境、跑 evals、看数据、理解性能、做训练**；还有 **prompt tuning**（他们有 **GEPA**）。

### 例子：TAU-bench（telecom split）
- 后端**数据库**（records）模拟世界；**telecom agent** 与用户做技术支持；**用户由 LM 模拟**，有 **user script**；
- 这更接近人们实际在构建的 LM 系统：**面向终端用户的 agent**，与工具交互帮用户解决问题；
- **agentic 接口抽象复杂度**：把复杂度推给 agent（如 AWS/Amazon 信息过载；不用人类菜单潜水，agent 做菜单潜水，人类用语义表达想去哪）；
- 复杂系统有大量数据库、边缘情况；**agent 擅长管理复杂度**，人类容易受挫（尤其想第一次就做对；人类不断 backtrack 会沮丧）；
- **TAU2 是好例子**；但**不想直接训练这些任务**（那是刷榜/作弊）；目标是**跨完全不同的世界做这件事**。

### 合成环境项目
- 保留**通用接口**：**domain policy、user sim、带模拟后端的 tools**；
- **完全重写**所有 tasks、所有 worlds：新世界 **instant response、daily planning、EV charging**；加上 telecom、airline，还有 **gym**；
- **backend 逻辑**仍用底层引擎，但**不用其数据**——**免费得到 harness**，只换数据部分 → **合成环境容易得多**；
- 告诉 agents 如何写 **user sim scripts**、如何想**新合成任务**；docs 有例子；实际是**提示 coding agent 做这些**，告诉它能/不能做什么，然后**看 traces 确保正确、code review**；
- **发现：在合成环境上训练能迁移到真实环境**；
- 训练平台底层用 **PrimeRL**；
- 目标：TAU environment **既是 benchmark**（训练时测进度），**也是可直接训练的其他版本**（看是否跨域泛化）；
- 在 **library、tech support、fitness gym** 上训练，**telecom 上有 uplift**；
- 意义：无论 RL、prompt 优化、模型选择、换 harness，**evals 作为方向信号**；目标是让人**更容易指定关心什么**，并在优化时**直接观察性能**。

### 训练细节
- 一次 **RL 训练**：**Qwen 30B MoE** 上的 **LoRA adapter**；
- 平台用 **hot-swap LoRAs** 于 **PrimeRL** 之上；部署可直接部署 LoRA；
- **PrimeRL**：开源 **Apache 2.0** 框架，用于所有大规模 RL 训练；**容易在自己的 GPU 上用**、可 hack，也有**平台体验**（轻量）；本地运行版可连平台，获得同样的日志/reward 曲线流；
- **Prime CLI**：看可用模型；提供很多模型（很多 fun models），更多模型家族即将到来，尤其**更大规模**；
- 目标：让**优化和 RL 不那么吓人**，给 on-ramp：建系统 → 测量（evals 是好方式）→ 解锁 RL/SFT 等优化。

### Rollout Viewer 与数据
- 基于 **PrimeRL**，用 **orchestrator** 抽象，**按 token 用量**；
- 容易理解模型在做什么、看数据；
- **Rollout viewer** 用于 evals 和 RL rollouts；**不只看分数**，还能**交互查看 tool calls 和 prompts**——对发现**系统 bug、reward hacking 后门、eval 没捕捉到东西**非常有用；
- 精炼系统是**迭代过程**，让测量**忠实于你真正关心的**；
- 希望**指定关心什么的接口越来越高层**、**少要求算法技术深度**（RL 很复杂：资源编排、数值、算法、分布式训练）；抽象掉，想清楚**哪些取决于任务、哪些对所有人都通用**（基线 infra、能力、容错、资源、调度）→ **plug-and-play**；
- **evals 也可在平台跑**，**私密/公开分享**；花了很多时间用**更复杂更难的 evals** 打磨体验。

### 例子：Zapier 的 AutomationBench
- Zapier 本周早些时候在平台发布；Zapier 做跨工作流工具集成（Slack、Linear、Notion 等）；
- benchmark 创建大量**模拟工具**，精神上类似 **TAU-bench**，但**更真实、工具面更广**，更像真实世界 agent 会见的工具；
- 可当 benchmark，也可当**创建自己环境的起点**；可直接训练；
- 与 Zapier 合作，他们做很多训练 run 探查**尖锐边缘**，在早期迭代看到 **reward hacking**，据此**在 benchmark 中解决**。

### 闭环与 sim-to-real
- **建 evals 和训练模型不是一次性**：前沿模型变好很快；
- **缩小 sim-to-real gap**：确保模型**部署环境与训练环境匹配**——**部署的 harness 应是能训练的 harness**，也应是**能评估的 harness**（Claude Code、OpenCode、Pi、OpenClaw、Hermes 等）；
- 若关心**模型优化**，必须**能在 agent harness 上下文里做评估**；
- 让**真实世界任务**更容易、**建 benchmark 不那么 ordeal**（现在很 ordeal）；
- **翻转开关**：不再追求“对所有人最好的模型”，而是**你真正关心用它做什么**（某个部署系统）→ **闭环**。

### 数据从哪来：反转问题
- 难处：eval 数据从哪来？**反转**：不是“数据从哪来”，而是**你的系统在哪运行**；
- 不适用于完全离线场景；但如**个人 agent**：一开始没 eval，但**记录所有 prompts**——每次用 OpenClaw 都有**当前状态快照 + 任务**，**这就是很好的 eval**；
- 在个人系统/公司产品中收集这些，**启动数据飞轮**；
- 目标**不是训练模型的 thinking traces**，而是**收集 prompts + 判断答案对错的标准**；
- **RL 不想直接训练 tokens**；RL 想训练**示例设置（settings）+ 评估标准**；
- 检查对错的不同方式：
  - **code-based merges**（较干净）：个人 coding agent，想按自己的 merge 方式微调本地模型；在 harness 加 tracing，存 prompts 初始快照（记住 commit hash），并**关联 PR 何时 merge、接受了什么 diff**；
  - 与 agent 工作**通常不是 one-shot**（中复杂任务）：迭代、看 diff、告诉它更多，直到满意——**人类实时验证过的快照**；
  - 保存信息：**PR 描述、GitHub comment threads、最终 merge 的 diff**——很好的 target；
  - 重放方式：如**diff 加了新测试用例**→ 保存旧测试、**对初始状态隐藏**、再给 prompt，**新代码应通过测试**；
  - 其他情况：**LM judge** + 全局 specs（system prompt、AGENTS.md）；
  - **LM judge 的可靠性**：问**二元 yes/no**、**几乎所有聪明且懂领域的人都会同意**的问题——通常相当可靠；离线测试后可建立信任；
  - 想**便宜地 judging**（可能本地）、**多标准**、**求和/平均聚合**增强稳健性。

### 持续学习闭环
- 让**从系统取数据并反馈**更容易 → **好的 eval 卫生**；
- 类似**proto-continual learning**：仍**human-in-the-loop**，但**清晰重复**：
  1. 初始 environment + 初始 sample tasks；
  2. 轻量训练；
  3. 部署模型；
  4. 取部署模型的 **agent traces** + specs（**agent skills** 领域：把 traces 变成 environment）；
  5. **反馈循环**：真实性能改进模型；看模型哪里有问题/做得好；再更新模型，**改进之前失败的事**；
  6. 即使不在之前训练集，也能**在线实时、按某种 cadence** 做；
- 随抽象更丰富：**coding agents 更好**、**mix-and-match plug-and-play**；
- 两条曲线相交：**做 eval 所需任务能力变小**（有更多信息可 build on）+ **模型本身变好** → **eval 创建对广泛 AI 工作流和真实任务（如 coding agents）应容易得多、更自动化**；人仍在 loop，但**在更高抽象层**，让更多人受益于闭环。

#### 问题一：什么实践最可能每次都有效？
- **Will**：尤其训练小模型、有大模型和一组问题时——**仍可叫 environment，但不做优化**，更像**数据引擎**：拿任务跑 harness、保存；**甚至不需要 reward functions**；**以“大模型比小模型好”为公理**，信任把 **Kimi 2.6 traces** 训进本地小模型会**在该分布上更好**（可能牺牲 out-of-sample）；**用 teacher model 做 SFT**，traces 因模型好而好。
- **Louis**：**Twitter 看多了会以为 RL 是唯一**；现实中尤其企业**大多做 SFT 蒸馏**——**最简单、最划算**；**被低估但非常强大**。
- **Louis 的反问（辛辣）**：若所有专有公司**关掉 API**（不能蒸馏 Claude 等），且中国实验室（目前做最大模型）也变专有，**世界会怎样**？**RL 是否是前进之路**？
- **Will**：
  - RL 的一大好处是**不需要蒸馏**；它需要 **PR 描述、commit diff**——**这算蒸馏吗？边界模糊**；
  - 即便只有 **Claude Code/Codex 这种产品化 agent**（只给最终 approved diff，没有 thinking traces/中间 tool calls），**仍能在代码库上取得进展**；
  - 高质量 agent 工作流**会渗漏到互联网/生态**（人们用开源代码数据库 seed 生成新环境的 pipeline）；
  - 模型也会**更擅长替你研究**；
  - RL **现在贵且难**，但会**每 token 更便宜**（infra 成熟）+ **更容易**；现在大家觉得 **SFT 容易、实用 RL 难**，这会变；
  - **中等规模模型 RL 后相当好**；很多场景**缩小与前沿模型差距相当可行**，不需太多重活。

#### 问题二：推测前沿闭源实验室有什么我们开源没有的？
- **Alex**（全属推测）：
  - 很多人说**数据**；他猜**不止**——不只是产品使用数据；
  - 不认为有**疯狂的秘密武器**难以想象；更可能是**很多小东西的组合**（数据、算力等），**我们更难获取**，导致更强模型；
  - 值得注意：即便很强的开放模型（中国模型等），应用时（如 RLM 风格）**闭源前沿模型往往更 fit scaffold**；虽然都没在 RLM 上训练过；
  - 你以为重要的能力（coding benchmark、逻辑/数学）**各模型表现其实相似**；但闭源模型在 scaffold 上**泛化更好**；**原因不明**；benchmark 报告里**不常直接看到**，但内部明显有更好的东西。
- **Will**：赌**reward modeling**——labs 内**成熟得多**；开放 infra、benchmark/recipes、架构已很好；lab 内有小 tweak，但**最大差别**可能是：**大量精炼过的 environments/datasets** + **更精细的 reward model 训练**（**verifiable + RLHF 风格并行**）。

#### 问题三：开源环境产业长什么样？谁在建？应用/模型所有者？
- Ben 背景：长期做数据集/标注；痛点：**可及市场小**——只有**规模大到需要自有数据集/训练模型、又有资源、有领域专家**的公司；**数据集的很多问题转移到 environments**。
- **Afir**（自谦不如 Will 懂）：
  - **数据创建**即使**预算很紧**也能有很大影响；
  - 论文 **Swiss Smith**：为 **SWE-bench 自动生成数万 environments**；用**免费 Modal credits** 训练 **32B 模型**，在 **SWE-bench 上有提升**；
  - 此后很多论文**找新方法生成数据**并在小模型上证明，人们再 build on top；这条线很酷；
  - 虽限于 coding，但**学术界极低预算也做出很酷的数据工作**；**鼓励低预算的人做数据工作**，影响很大。
- **Will**：
  - **SWE 风格方法**是很多人想跨域做的：如有一堆邮件（Enron 数据集），**有没有“SWE Smith for 邮件”** 来挖通信类任务；
  - 产业可能样子：**单个 artifact（benchmark、模型、数据集）变得不那么珍贵**，但**做增量步骤容易得多**；
  - **数据公司**大多**卖给 labs**；token 需求持续上升、要更多更快、要的人也在增加——**token 从哪来**？可能来自**更小的专用模型**（每 token 算力更少）——**另一种增加世界 token 供给的方式**；
  - 尤其**合适形状的子领域**：公司内有**领域专家但非 ML 专家**；**让懂会计等的人能交互、看到发生什么**，把专长**编译进数据集**——**可行路径**，让训练模型容易得多。
