## 第一场：Ajit Kosh（Hugging Face）——Agentic AI 时代的评估报告

**时间：2:50–21:59**

### 身份与背景
- **Ajit Kosh**：Hugging Face **技术 AI 政策研究员**；领导 **400+ 研究者的 Eval 社区**；重点做 **eval 文档（eval documentation）**。
- 演讲主题：**Evaluation reporting in the age of agentic AI**——当前 eval 领域**缺什么**、与 agentic eval 的关系、以及他们在做什么来修复。

### 从 LLM 到 Agentic 系统
- 已从“生成文本的 LLM”转向**会规划、决策、行动的 agentic 系统**。
- 例子：**Open Computer Use、Claude Computer Use、Gemini agent mode、Manus、OpenClaw**——“到处都是”。

### 通用 eval 报告的问题：细节藏在“小字”里
- **OpenAI GPT-5.2 系统卡**：报告了很高的 SWE 分数，但**小字里说 237 道题中省略了 40 道**；被 Anthropic 和 eval 社区严厉批评。**快速看表格的人根本注意不到**。
- **Llama 4 发布**：Meta 被曝**用不同版本的 Llama 4 去跑不同 benchmark**，不是最佳 eval 实践；报告也因类似原因被批评——**benchmark maxing（刷榜）**。
- **图表危机 / 数据误导**：例如 OpenAI 的 SWE score 用**69.1 与 30.8 画成几乎一样高的直方图**，没有按现实比例缩放；**很多人不报告 error bars**——eval 严谨性问题。

### 社会影响评估（social impact eval）更糟
- Eval 联盟论文：**“Who evaluates AI social impacts: mapping coverage and gaps in first and third party evaluations”**。
- 社会影响包括：**环境影响、财务影响、偏见**等。
- 考察了 **171 份模型发布文档**，关键发现：
  - **模型开发者随时间变得越来越不透明**：例如**第一方报告中的环境成本报告**透明度下降；**不到 15% 提到劳动与环境影响**；2022 年时大多数组织几乎什么都报告。
  - **Google 和 Meta** 在 2022–2023 年报告很多，**现在不再报告这些社会影响 eval**。
  - **第一方报告总体不透明、质量更低**。
- 对 eval 从业者的访谈（为什么不报告了）：
  - 公司**解散或重新分配了专门做文档/社会影响评估的团队**；
  - 因**政治气候变化或法律责任**，公司被要求**更关注能力报告而非风险测量**。
- **好消息**：**第三方报告（Meter、Apollo、Meror 等）在质量和数量上都随时间上升**——强化了“**高质量独立第三方评估对整体 AI 安全至关重要**”的立场。

### 项目：Every Eval Ever（集中化 eval 信息）
- 问题：第三方评估**格式不统一**（leaderboard、报告、博客文章）。
- **Every Eval Ever**（上个月发布，与多家组织合作）：
  1. **统一的开放数据格式/schema**；
  2. **Hugging Face 上的公开数据集**，收集所有第一方和第三方评估结果。
- Schema 支持：
  - **聚合结果（aggregate results）**：必须报告**来源/出处（provenance）**、模型规格（不只是模型名，还有**量化方式、模型版本**）、**使用的评估库**等。
  - **实例级 schema（instance schema）**：支持**逐条结果**，不只是聚合分数。
- 目标：**Eval Cards**——去 Eval Cards 网站，点某个模型（如 **Qwen 72B**），看到按类别组织的所有第一方/第三方 eval，快速了解模型情况。
- 意义：这种过滤能**把混淆变量固定住**，看模型间的精确分数差异；**不容易被 gaming**。Nathan 稍后会讲其他基础设施问题。

### Agentic Eval 的特殊性
- Agent eval **超越 LLM eval**，因为系统更复杂。
- 例子：**两个 agent 都 pass 同一个 eval，但故事完全不同**——第一个**步数更少、更便宜、更快、零错误/不崩溃**。所以 **agent 的指标不同，评估需要更稳健**。
- **当前 agentic benchmark 互不兼容**：测的东西不同，结果难以泛化。例如 **TauBench** 测用户消息传递，**不能**用来测 web 上的计算机性能，**与 WebArena、TerminalBench 不兼容**。需要更**通用**的性能衡量。
- Agent eval 需要捕捉：
  - **动作序列（sequence of actions）**：测 chain-of-thought 里发生什么？调用了哪些工具？
  - **动作上下文**：用户输入、环境、噪声。
  - **人类交互（human interaction）在 agent eval 中被严重低估**：人类可在 agent 工作流的不同层级交互；**是否测量了人类输入的影响/噪声**？
- 引用论文：**“Agent systems should be general”**（Ajit 是 co-author）——应构建支持**可适配 agent** 的**协议、评估框架、开发实践**；**通用 agent 可能是未来**，评估框架也应如此。

### 具体缺失（concretely missing）
1. **Session-level reporting**：两次 session 可能**分数相同但结果完全不同**；session 级信息对**可复现性**很重要。
2. **Agent identity 是黑洞**：现在大多 agent eval 只标**模型名**，但**模型 ≠ agent**；需要 **sub-agent 列表、MCP servers、memory 配置**等。
3. **Benchmark 特定协议阻碍通用 agent**：需要特定 setup 的 benchmark 对通用 agent 不友好。
4. **稳健性测量未标准化**：**seeds、prompt perturbations、pass@k** 等报告不一致。
5. **成本报告不一致或缺失**：有些 eval 报成本，有些不报。
6. **Benchmark 特征缺失**：尚不能同时做到 **cross-model、cross-environment、cross-agent、cross-protocol、agent-agnostic**。

### 与文档的关系：Every Eval 的 agentic 扩展
- 标准化 eval 报告可为 agent 扩展：
  - **System composition**：系统里有哪些模型、角色、sub-agents、MCP servers。
  - **Session semantics**：明确定义一次 run/session 的字段。
  - **Interaction accounting**：测量交互的额外指标。
  - **Eval conditions**：第三方可干净复现 agent 动作所需条件。

### 仍存技术挑战
- **human–AI / human–agent interaction 测量不足**。
- **涌现的多智能体效应（emergent multi-agent effects）**：OpenClaw 让很多人有了“claws”；Hugging Face 自己注意到**来自别人 Claude 的 pull request 大增**，但**不清楚如何干净地监控**。
- **长时任务（long-horizon tasks）测量**：定义不清；Meter 有 long-horizon benchmark，但**大家对“long horizon”理解不同**。

### 政策影响
- **治理需要 session 数据**：要追责人或 agent，需要清晰的 session 信息，否则**无法干净地审计 agent 行为**；只给分数不够。
- **需要白盒系统记录**：只看模型数据不够，需要看到**哪个 actor 对 harm 负责**。AI 生命周期中已有：数据收集者、模型训练者、系统设计者、决定你与系统交互的人（专业场景中有人负责白名单）、最终用户；**agents 把这个问题放大多个数量级**。
- **共享 schema 有利于独立评估**：一个地方看全部 eval，并按技术参数复现。
- **安全监督被 benchmark gaming 削弱**：社区要持续讨论 eval 报告中的**不当做法（malpractices）**，从刷榜转向**整体 AI 安全报告**。

### 行动号召（Call to actions）
- **公开构建 evals（build evals in the open）**；
- **兼容的开放报告框架**；
- **停止 benchmark chasing**，看整体图景、分数之外的东西；
- **更好的可扩展监督（scalable oversight）**：不能有 100 万个 OpenClaw 却无法被人类监控；
- **eval 政策应超越能力测量**，把**人和社会影响**放在心上。

### Q&A（Ben 主持）
- 问题：**安全担忧多少来自底层 LLM，多少来自 agent？** 以及**如何做 harness 无关（harness-agnostic）的评估**——用一个统一 harness，还是每个主流 harness 都评？
- Ajit 回答：
  - 引用 **IBM 团队的后续论文 “Exgenic”**（“Agent systems should be general” 的后续）——**存在做 harness-agnostic agentic eval 的方法**。
  - 有些错误来自 **LLM**，有些来自**工具本身**；有大量 pre-agentic 的**级联偏差（cascading biases）** 研究。
  - 主张**把 agent 当白盒看**：不仅看底层 LLM 的失败模式，也看**所用工具的失败模式**——某工具是否被正确调用？chain-of-thought 是否不一致？
  - 个人偏好：**报告所有可能信息**以最大化可复现性。

## 第二场：Arvind Narayanan（Princeton）——走向 AI Agent 可靠性科学

**时间：22:06–38:55**

### 团队与主题
- 主题：**Towards a science of AI agent reliability**。
- 团队：**Stefan Robons 是第一作者**（投入巨大），部分 slides 来自他。
- 定位：**可靠性（reliability）是与能力（capability）正交的独立组件**；此前**没有严肃工作去定义可靠性、拆解其组件、测量并看是否随时间改善**。

### 动机：一个悖论
- AI agents **在各类能力 benchmark 上碾压**；若信 hype，公司应大量用 agent 替代人，但**没有可测量的 GDP 影响**。
- 两种解释：
  1. **只是需要时间**（很多公司/人还不知道这些能力）——合理；
  2. **能力 benchmark 只看了“让 agent 有用”的一个组件**；agent **还不够有用到能替代几乎任何人类工作者**——即 **capability–reliability gap（能力-可靠性差距）**。论文探索此假设。

### 消费者产品失败案例
- **Rabbit R1**（约两年前）：无屏幕、可对话、可在线下单——能力惊人（在 LLM 上搭 wrapper 做 agentic 硬件），但用户很快发现**可靠性问题**：**送餐到错误地址**、小费问题。
- 对比 pre-LLM agentic 系统（**Alexa、Siri**）：放错歌 10% 只是烦人；**agentic 产品用你的信用卡下错单 10% 就是“dead on arrival”**。
- 更多部署 agent 的可靠性失败：
  - **OpenAI Operator**：错误购买；
  - **agentic coding 系统删除生产数据库**；
  - **政府**（通常行动慢）也不能免疫。

### 与航空/核能的对比
- 航空：**莱特兄弟**证明能飞之后，达到“**每万亿英里一次错误**”级别花了**近一个世纪**；AI agent 要用于高风险环境，**还有很长的路**。

### 四个可靠性维度（来自传统系统，适配到 AI agents）
1. **Consistency（一致性）**：
   - 70% 准确率可能是“**70% 任务能稳定完成，30% 稳定失败**”，也可能是“**任意任务不可预测地 70% 成功**”。
2. **Robustness（稳健性）**：轻微改变 prompt/环境会怎样。
3. **Predictability（可预测性）**：能否回看 agentic trace 判断任务是否做对。
4. **Safety（安全性）**：失败发生时**严重程度**高低。

### 关键发现
- 考察 **14 个前沿模型**，使用一个 scaffold（论文有 scaffolds/harnesses 细节）。
- **过去 18 个月**：benchmark 准确率** dramatic 提升**，但**四个维度的复合可靠性分数只非常缓慢上升**。
- 如果认为 AI agent 能力**指数级**提升，这是** sobering（令人清醒）的发现**：能力上升 ≠ 有用性；还有另一个维度。
- 使用 **GAIA** 和 **TauBench airline** 两个 benchmark（逐步增加更多）。
- 图表要点：
  - 中间：GAIA 与 TauBench 分开看，**可靠性进展缓慢**；
  - 左：**准确率进展快得多，斜率更高**；
  - 右：**accuracy vs reliability 几乎是直线**——**强线性关系**；可靠性随准确率上升，但**慢得多**；跨大量前沿模型成立。

### 维度细节
- **Consistency 拆成三个指标**：
  - **Outcome consistency**：同一任务每次 pass/fail 是否相同，还是任务内随机；
  - **Trajectory consistency**：是否每次走相同动作序列；**创造性**在某些场景有用，但**客服 agent** 需要**可预测行为**，否则百万客户规模难以质量保证；
  - **Cost/资源稳定性**：跨 run 是否稳定。
- **Robustness**：
  - **Fault robustness**：**向环境注入故障**（API 超时等），看 agent 处理能力；
  - **Prompt robustness**：用 LLM 自动改写 prompt，**保持语义**但改变风格/语气；例：非正式 vs 正式 prompt 可能得到不同答案；
  - **Calibration（校准）**：elicited confidence（“你答对的概率？”）。**未校准 agent 通常过度自信**：说 60% 应真 60%，但**过度自信 agent 给 1.0 却只成功一半**。
    - **好消息**：calibration 在改善（可能因 **Zopency** 等问题，公司因过度自信聊天机器人惹麻烦而小心修复）；
    - **坏消息**：**discrimination（区分度）随时间变差**——agent 总说 50% 左右，无法区分成功与失败。
- **Safety**：测量但**不聚合进总指数**；看失败严重性（格式错误 vs 数据删除）。

### GAIA trace 分析（自动 + 人工）
- **Calibration 问题**：模型在**干净流程 vs 混乱流程**（有工具调用失败）间混淆——以为答案错了，实际与答案正确性无关。
- **GAIA 很多问题有歧义**：从**能力 elicitation** 角度是坏事（低估能力），但从**可靠性**角度很有用——真实部署中**歧义任务一直存在**，模型处理得不好。
- **幻觉**：注入 **false**（让完成任务所需数据不可访问）时，即使默认不常幻觉的模型也可能幻觉。

### 教训
- 部署 agent 的公司必须区分：
  - **Augmentation（增强人类生产力）**：如 coding agent，错误**不那么糟**，程序员仍在 loop 中审代码；
  - **Automation（自动化）**：如客服 agent 自主处理客户，**错误严重得多**；**可靠性在自动化任务中远比增强任务重要**。
- **发布决策**：不只看能力，还要有**可靠性阈值**。
- 对研究者/开发者：**任何 benchmark 都应测这些可靠性指标**（不是专门的可靠性 benchmark）；应成为**常态**。
- 不要假设“模型变聪明，可靠性问题自然解决”；要**专门优化可靠性**。

### 局限与后续
- 发现是**初步的**，正在审查 runs 找 bug；局限：**只有两个 benchmark、scaffold 不多**等。
- 计划推出 **Reliability Index**——追踪社区可靠性变化的**一站式**平台。
- 大图景：
  - **UK AI Safety Institute** 报告列出 **AGI 的六大障碍**；他们**深入可靠性**，识别出 **12 个指标**，**大多数未解决**（约两个基本解决）；若其他研究者也深入其他障碍，会发现**更多需要解决的子维度**。
  - **长时任务**：Meter 说任务套件开始饱和——“也许，但**饱和的可能是指标，不是任务套件**”；不能只看能力，要看**12 个可靠性维度、协作能力、成本、延迟**等。**Agent 评估需要多维度**；只盯能力会**错过 agent 在经济中有用性的许多问题**。

### Q&A
- 问题（Ben）：**ReAct 范式或其他 agent 实现**下，若做**开放式任务**（agent 可用不同方式、不同轮数完成），如何在实际中测可靠性并据此行动？
- Arvind：
  - 代码已公开，欢迎复现/联系；
  - **重要澄清**：很多任务上，他们测的可靠性指标**可能并不可取**。极端例子：**写诗 agent** 若每次同题写同样的诗就很糟——**你要创造性、要随机性**。**取决于任务**是否适合测这些指标。

## 第三场：Pierre（Meta）——GAIA 2

**时间：39:02–54:40**

### 背景
- **Pierre**：Meta 研究工程师；与 **GAIA 原团队**及许多人合作开发 **GAIA 2**（agent 新 benchmark）。
- 不试图做“万能 benchmark”，而是解决**一类挑战**：**agent（尤其 OpenClaw 类）要在不断变化的世界中工作**。
- 旧 LLM eval：给 prompt、看输出、判对错。
- 早期 agent eval：把 agent 放进 sandbox 跑代码文件，检查编译/测试通过，但**没有外部世界输入**。
- **真实消费者 agent**：外部世界会变——新邮件、新闻、互联网变化，必须适应。需要**能做这些的评估框架**。
- 例子任务：**和同事组织品酒会**——agent 要发邮件、等回复、订东西、适应环境；**环境给 agent 的输入不只是用户对 agent 说话**。

### 方案：模拟（simulation）
- GAIA 2 用**模拟**；相关环境：
  - **TauBench**：用户模拟（agent 发消息，用户回复）；
  - **Vending Bench**：环境模拟（改变自动售货机的成本、销量、需求）。
- GAIA 2 聚焦 **multi-app simulation（多应用模拟）**：像手机上一堆 app——有些连外部服务（邮件、通讯），有些纯本地（文件系统），**彼此交互**，并会因 **agent 行为、用户行为、外部环境事件**而改变。
- 构建在 **AR（agent research environment）** 框架上（不专属于 GAIA 2，可贡献其他任务）。

### 四个核心概念
1. **Apps**：像手机 app，保持世界/自身状态，暴露 **tools/API surface**；agent、环境、用户都可通过 **API 调用、Python、MCP、CLI** 交互（适配现代编排框架）。
2. **Universe**：模拟环境 + 初始状态——一堆 apps 及其初始状态：**过往邮件、当前日历事件、与其他 persona 的消息对话**。
3. **Events**：在 universe 上注入事件——来自**用户、agent 或环境**。
4. **Scenarios（任务）**：不是简单 prompt，而是 **prompt + 期望的 agent 事件序列 + 任务期间可能发生的环境事件**。

### 为什么模拟
- **可复现、可观测**（回应 Ajit 的呼吁）；
- 可测**稳健性**；
- **安全**：可让 agent 做**破坏性动作**（删除所有邮件、取消日历），不必在开放网络上做；
- **便宜/可复现**：不依赖外部带宽和 API。

### GAIA 2 规模与生成
- **1000 个 scenarios**，**10 个 universes**，每个 universe 约 **11 个 apps**（所有 apps 出现在所有 10 个 universe 中）。
- 每个 universe 从 **persona 数据库**用 **LLM 分层自动生成**：对话、邮件、日历数据等初始状态；再由**人工标注者**在上面创建任务和事件（scenarios）。

### 五大能力（capabilities）
1. **Execution**：多工具调用改变环境（“取消所有会议”“回复那封邮件”），通常**单轮**内完成多个有风险动作。
2. **Search**：类似 GAIA 1，但**在 apps/universe 内搜索**，跨多个 API surface、不只是关键词搜索。
   - 例：“忘了 Netflix 密码，但记得和父母分享过，能找回吗？”——agent 要**推断父母是谁**，在多个通讯 app 里找含密码的消息并返回。
3. **Adaptability**：多轮；agent 第一轮动作后**环境出岔子**（如订了会但其他参会者取消），agent 要**反应、重新安排/采取新动作**。
4. **Time**：类似 adaptability，但事件**按时间发生**（如“机票低于某价格时订票”），要**等票价下降**并反应。
   - 挑战：scenario 事件跨 **2–3 周**，不想真等 3 周——**模拟时间快进/跳跃**，并让 agent 像在真实世界一样感知。
5. **Ambiguity**：任务**有歧义**，agent 必须**问用户追问**才能解决；会先搜索/行动，然后意识到必须**停下来问用户**再动手。

### 压力测试与稳健性
- **引入噪声**：
  - 所有 apps 上**工具失败**（多种形式）；
  - **改变 apps 的 API**（改所有工具名称和签名），防止 agent **过拟合特定签名**；
  - **环境噪声**：注入与任务无关的外部事件，增加上下文噪声，测试对**真实世界噪声**的稳健性。
- **Agent-to-agent 模式**：agent 不能直接调工具，必须用**自然语言**与 **sub-agent** 对话，sub-agent 是能调工具的专家——测试**无工具、纯对话**完成任务。

### 与 GAIA 1 的区别
- 不再局限于 **web browsing**；在多个 apps 上；**动态、实时事件**；**不再只读**——需要大量**写操作**；可在**动作级验证**。

### 验证方式（重要）
- **放弃 rubric judging**（依赖 LLM 能力、昂贵、难验证）。
- 采用**硬验证器（hard verifier）**：每个 scenario 标注**期望的写动作集合（DAG）**，与 agent 实际动作 DAG 对比，**逐事件检查顺序和参数**（发给正确邮箱？正确时间？）——**纯相等/简单算法**，**比调 LLM 便宜得多、更可复现**。
- **软验证器（soft verifier）**：如发邮件内容，用 LLM 检查内容是否符合预期（不必完全一致）。

### 关键发现（去年发布，表格略旧）
- 很多 agents/models 在 **search 和 execution** 上已相当好；
- **time 极差——约 0%**，所有模型（包括顶级）都如此；
- **adaptability**（动作期间适应环境变化）也不太好；
- **ambiguity** 同样。
- 数字随新模型**变化很快**，需**调整并加难任务**；框架下容易加轮次和期望。
- 还需调整 judge/事件比较方式：**去年期望的输出风格与今年模型输出风格差别很大**。
- 已开源（去年）；**ICLR 今年有论文**；AR 框架可写新 scenario、新任务甚至新 app，可在此基础上建自己的 benchmark；GAIA 2 benchmark 是**人工标注/ curated**。

### Q&A
- 问题（Ben）：**reward hacking / 攻击 GAIA 环境**长什么样？如何预防？
- Pierre：
  - GAIA 2 **checker 很严格**，检查结果时确保没有 hacking 模式；
  - 可**提高噪声**，让 agent 不能**过拟合工具**长相/行为；
  - **提高失败率、改工具签名**，同时保持任务不变。

## 第四场：Mahesh（Bespoke Labs）——环境为何对评估至关重要

**时间：54:47–1:16:22**

### 背景
- **Mahesh**：**Bespoke Labs 联合创始人兼 CEO**——应用 AI 研究实验室，做研究并**交付 RL 环境**；有大量环境构建与用于评估的经验；此前做过 **Open Thoughts**（社区努力，去年最好的开放推理数据集之一）。

### 比喻：Hiccup 与 Toothless
- 《驯龙高手》Hiccup 目标是训练龙 Toothless，**真正转变发生在他开始观察龙、真正理解它**时。
- 隐喻：很多人**训练（SFT/DRL post-training）或直接构建 agents**；与很多企业交流发现他们**没有 eval-first 心态**。
- 主张：**先理解/评估你的 agents，把 setup 做好、指标定义好，再改进 agents**。

### 如何“不要”评估（how not to evaluate）
- 只看输出（偏 web 侧）对简单/小 agent 还行，但很快出问题：**改了东西不知道什么失败了、没及时抓住**。
- 软件工程早有**单元测试、回归测试**等，应纳入。
- **初始关注点错误**：一上来就盯 planner 对不对、函数调用粒度——这些**最终要做，但不是起点**。
- **陷阱**：**部署到生产再评估**（很常见）。

### 为什么 agent 评估难
- **随机性（stochastic）**：两次 run 结果可能很不同（与 Arvind 的 consistency 呼应）；
- **到最终结果步数多**，复杂度高；
- agent **与真实世界/工具交互，底层世界会变**，评估难复现；
- 真实交互**可能很贵**（不想删数据、不想给用户发错消息）。

### 如何搭建评估：分层
- **Level 0：可验证 setup（verifiable setups）**
  - 例：coding agent 是否真修了 bug？**单元测试是否通过**；数学检查值是否正确。
  - **Gotchas**：
    - **单元测试权重**：很多简单测试 + 少数重要测试；大多数测试通过，agent 可能**仍未做真正的工作**；
    - **Reward hacking**：agent **不修 bug 而改单元测试**让它通过。
- **Level 1：输出不可验证**
  - 例：deep search agent 输出一段/几页文字，**没有唯一正确答案**。
  - **Rubrics 来救场**：定义多条 rubric 评估结果是否合理；例：肾结石问题，定义正确性、准确性等 rubric，并给**0/1 分 + 权重**，用 **LLM as judge**，得到总分。
  - 方法论：问题 → 最终答案 → 更新 agent harness/模型 → **测量分数是否上升**。
- **环境概念**：
  - agent 拿任务 → 与环境交互 → 产出输出（有时输出在环境“下面”，如 bug 被修）；
  - **Grader**：单元测试是否通过，或一组 rubric 判断输出是否合理；
  - 两个箭头：agent 与环境交互，也涉及 **harness 行为/规划方式**。
- **隔离/创建环境很有用**：**可重复、可复现、隔离且安全**；环境可以是真实世界，也可**封装成 sandbox**（这里的定义就是 sandbox）。
- **环境格式**：本质是 sandbox，含所需依赖、世界状态、工具、数据；**Harbor** 是流行格式，还有 **OpenEnv** 等；环境伴随**任务定义**和**评分方式**。

### 环境用于评估的关键设计决策
- 可有一个或多个环境（如法律 domain 的不同数据）；每个环境关联任务；
- **环境尽量像生产**；
- **agent 不能访问 grader 或 solution**，否则会 reward hack（Harbor 原生提供）；
- **任务**尽量贴近生产，可定义得很清楚或开放式；
- **Grader**：可验证评分，或用 rubric 把不可验证转成**数字**；
- **确保为正确结果评分**，且**任务要求的所有东西都被评分**——若要求三件事只评两件，agent 会**只做两件**（reward hacking）；例：给单元测试**加指纹**防止 agent 乱改。

### 实际测量什么
- **Success rate**：给定环境/任务，让 agent **rollout n 次**，测成功频率（评分平均）。
- **pass@k**：k 次 rollout 中**至少一次成功**；多任务可求平均 pass@k。
- 示例：比较不同模型/不同 harness 的 pass@k 与 success rate（某特定 domain 示例）。
- **不止成功**：
  - **Efficiency**：多少步到最终结果（成功或失败都可能几百步）；
  - **Token 数**；
  - **Latency**；
  - **Cost**：模型贵、rollout 也贵。
- **Harness 的作用**：同一模型在不同 harness 下 success rate **可能差异巨大**——例：**TerminalBench dashboard** 上同一模型不同 harness 指标不同。
- **Safety**：例（当天文章）确保 agent 没删光数据、没刷爆信用卡；可在环境中封装，也可把安全做成**任务 + grader**（如删数据就**惩罚**）。
- **Reward hacking**：常见，要在评估 setup 中尽量纳入防范。
- **看 traces**：从 success 等指标开始，**读 trace** 了解 agent 行为；可做**自动/深度分析**——如总体好但某类场景成功率下降；对轨迹做**自动失败分析**。

### 总结建议
- **Environment-first**：想好环境、任务、如何正确评分，以及 harness；
- 不只用于评估：nailed down 后可跑 **JEPA 类算法/其他优化**改进 agent，测量改进后再上生产；
- 新挑战：**long horizon**（任务数小时甚至数天，等待久且贵）、**multi-agent / multi-user** 系统；
- 核心：像 Hiccup 一样，**先观察、理解、评估你的 agent，再训练/构建**。

### Q&A
- 问题（Ben）：Hub 上出现更多环境（OpenEnv、Harbor、TerminalBench 等），人们为训练、评估、生产建环境；**如何造“真实世界环境”**（如没有活跃 Slack 频道）？比如想把 **Slack 环境**或**含 Slack + GitHub 的创业公司环境**推到 Hub，怎么做？
- Mahesh：
  - 这是 **sim-to-real gap**；环境要做成隔离 sandbox，但真实世界复杂得多，是挑战；

  - 本质是**让环境尽可能逼真、模拟真实世界**的博弈。

## 第五场：Nathan（Hugging Face）——用 Community Evals 定义“活的 benchmark”

**时间：1:16:28–1:33:07**

### 身份
- **Nathan**：Hugging Face ML 工程师；**LightEval、Open LLM Leaderboard、Community Evals** 的 co-maintainer（Community Evals 是最近的新功能）。

### 2026 年 eval 现状（呼应 Ajit）
- **分数碎片化（score fragmentation）**：不同来源报告结果差异大；新模型发布时评估了一堆模型，但**与之前报告的分数不匹配**，下一次发布**可能也不匹配**。
- **维护负担**：维护 leaderboard 很痛苦（尤其手动更新）；维护评估框架（尤其自定义框架）也痛苦。
- **没有单一真相源**：一些实验室试图评估尽可能多模型、自称唯一无偏评估来源，但**仍不太行**；需要**更多社区参与**。
- **Truth in numbers**：让社区更多人参与评估和建 benchmark；每个人都能说“用我刚 vibe code 的 agent 框架得到这个结果”，多人做就更接近真实评估空间（需带上 Ajit 说的 specificity）。
- **Benchmark 分散在 GitHub repos**，难找；找到后也难在自定义模型上跑。

### Community Evals 是什么
- **Hugging Face 数据集可变成 benchmark**；截图显示 **13 个 benchmark**，包括：
  - **OCRBench、JSMK、MTB、SWE-bench Pro、SWE-bench Verified**；
  - **Math Arena 的 AM 2026**；
  - 对 agentic eval 有 **Harbor 框架的 TerminalBench**。
- 如何解决问题：
  - **去中心化**：Hub 上每个数据集有 **eval YAML 文件**，人人易跑；数据公开（可 gated）；
  - 所有结果/leaderboard 可被社区成员打开；
  - **易访问**：就是 HF leaderboard；
  - **社区优先**：leaderboard 显示在数据集页面。
- 例：**HLE（Humanity's Last Exam）**（Center for AI Safety）——数据集页面有 leaderboard，显示开源模型结果，**每条带注释**说明模型如何跑、用了什么 agent、**5-shot/2-shot/0-shot** 等。

### 如何定义评估（以 HLE 为例）
- **eval YAML**：定义任务名、简短描述、**评估框架**（HLE 用 **Inspect AI**）；每个 task（HLE 只有一个，ID 为 `hle`）有 spec 字段（细节略）。
- 同文件还有：
  - **Solvers**：如何 prompt 模型、如何搭框架/scaffolding；例：简单 system message + generate 调用；用 Inspect AI 可做**很复杂的 agentic eval**；
  - **Scorer**：如何评分；HLE 用 **LLM as judge**，judge 是 **OpenAI o3-mini**。
- 框架可**任意**（不限于 Inspect AI）。
- **为何推荐用现有评估框架**：
  - 很多人**重新发明评估框架**（现在 vibe code 很容易），但**更难维护**（作者自己有体会，有很多奇怪问题）；
  - 用现有框架**大幅降低维护开销**；Inspect AI 定义好后，**模型代码、工具、结果发布都自动处理**——你只需**定义评估**；
  - 让 benchmark **更易访问**（少数框架定义几乎所有 benchmark，便于切换）；
  - **标准化工具**，把 benchmark 与评估逻辑**分离**。

### 如何运行
- 选项：
  - **本地集群**（Open LLM Leaderboard 旧做法）——可维护性差，要管 GPU，多人用集群时麻烦；单个 GPU/小集群对**大模型不够**；
  - **云算力**；
  - **HF Jobs**（希望当初有）：云算力，选硬件，**可复现**，**一行命令**跑评估。
- **反对用推理提供商（inference providers）**：实际在**评估 provider** 而非模型；不知后端如何调用模型、prompt 是否如你所愿；**不可复现**。应**本地推理**或**受控环境如 HF Jobs**。
- 一行命令示例：`uv` / `uvx`；`uv call inspect AI`；指定 benchmark 来自 HF、给 benchmark、给模型（示例：**OpenAI GPT-20B 用 vLLM 跑**）；用 HF Jobs 运行并**发布结果**。
- 发布：可创建 **HF Space**（或网站）——**详细日志**：温度、vLLM server 如何起、尝试次数、**pass@k 指标**、**标准误**等；详细日志对**分享**和**构建改进**都重要。

### 结果如何上 leaderboard
- 评估 run 后，在**模型仓库**开 **PR**——结果自动显示在**数据集 leaderboard**。
- Leaderboard 特点：
  - **自动更新**（Open LLM Leaderboard 以前 pipeline 常坏）；
  - 直接活在**数据集页面**，**无需基础设施**；
  - **实时显示最新结果**；
  - 易分享；
  - 每条结果是 PR，**社区可在 PR 讨论**（觉得分数偏高/偏低）；
  - **模型作者可关闭/隐藏有争议的分数**（先讨论，实在不行可隐藏）。

- Ben 问：若我评估自己用的模型（不完全 exhaustive，跨 provider、量化），结果对**我/我的领域/语言**重要，想推给社区，怎么做？

### 问题：多智能体评估（问 Pierre）
- Ben 提到 OpenEnv 中不少环境是**对闭源环境的重新实现/标准化**——rubrics/rewards 开放，但**seed 数据不开放**，弥合了 open 的差距。
- 问 Pierre：GAIA 2 中**多 agent** 怎么做？是让 sub-agent 以可验证方式行动，还是评估团队？直觉？
- **Pierre**：
  - GAIA 2 有 **agent-to-agent 模式**：一个 sub-agent 负责一个 app/一组工具，可高度专业化；
  - 但 **OpenClaw** 场景：两个 OpenClaw + 一群人同 chat；要模拟**完整独立 agent**（自己的 memory、soul 文件、不同用户/persona、略微不同的工具访问）；
  - 可以做（尚未试），但**评估参数化复杂度爆炸**：已有 judge model、被评模型、agent 编排；**再加更多 agent 的模型、编排**——**简单任务的评估方式爆炸**；要覆盖就得**更多标注**（可能任务、可复现内容）；
  - **目前不知如何管理这种复杂度**，但**必须走到那一步**。

### 问题：Community Evals 的愿景（问 Nathan）
- Ben：Community Evals **乐观、开放**，不强行定标准，只开放数据层；若一切按计划，**6 个月到 1 年**后社区什么样？评估如何在 Hub 上存在？
- **Nathan**：
  - 不试图定义什么，只是**开放可能性**让社区定义自己的方式（“做事方式”可能由更大的实验室/机构定义，但**社区有发言权**——结果如何报告、benchmark 如何创建）；
  - 让**人人易建 benchmark、易报结果**；
  - 希望 6 个月/1 年后，Hub 上像今天**模型**那样——每次新模型出现，很多人 fine-tune 到自己的数据集并开放；
  - **评估数据集和 benchmark 也一样**：每个 benchmark 出现，大家跑自己的模型、做小改动，**互相 build on top of each other**。
