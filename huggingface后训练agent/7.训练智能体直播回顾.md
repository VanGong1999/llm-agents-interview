## 一、开场介绍（0:04 – 1:48）

### 系列背景
- 过去几个月在 YouTube 上做了系列直播，教大家**如何训练一个 agent**。
- 起因：大家都在关注 post-training，但**真正能训练出自己可用 agent 的人很少**——尤其是能在**自己机器上、用开源权重模型、端到端运行**的 agent。

### 四节课内容（由浅入深）
1. **最简单的一课**：从改进后的 agent 中取 **traces（轨迹）**，对小型模型做 **fine-tune**，完成特定任务。适合把日常重复任务做得更便宜。
2. **在线蒸馏（online distillation）/ on-policy distillation**。
3. **用 GRPO 做强化学习（RL）**。
4. **什么是 RL 环境 / agentic 环境**：如何构建、要做哪些决策、如何组织**数据、任务、运行时**等。

### 资源说明
- 所有实验都已公开，可**直接复跑、修改、做自己的实验**。
- 今晚不重复讲这些内容，而是请**工业界有经验的讲者**分享项目与用例。
- 想动手的话，该 YouTube 系列是**免费、易上手**的最佳入口。

## 二、演讲 1：企业级 RL 的经验教训（Gobind，Microsoft）1:48 – 19:16

### 讲者背景
- Gobind，Microsoft 研究工程师，与 **GitHub 和 Foundry** 合作。
- 过去一年与**数十家企业客户**合作其"爬山（hill climbing）"旅程。
- 客户画像：**传统企业**——工业、制造、能源等，**不是创业生态，没一家在旧金山**。

### 演讲结构（四部分）
1. 客户为什么想做这件事、他们真正想要什么
2. RL 如何带来他们想要的**结果**
3. 如何**规模化**
4. 下一步是什么

### 1. 客户的真实动机（2:42 – 3:54）
- 讲者最初以为动机是**降成本**或**FOMO 追最新模型**——⚠️**对这批客户都不成立**。
- 真正动机：**IT 预算对应某个战略优先级**，需要改善**业务指标**来证明这笔花费合理。
- 核心三要素：**延迟（latency）、准确率（accuracy）、去风险（de-risking）**。
- 💡 客户**并不执着于模型本身**，而是在意**整个系统**：工具、数据、网络、harness、总 wall-clock 时间。
- ⚠️ **现实世界很脏（messy）**：企业里跑真实工作流/SOP 的 agent 有**几十个工具，有些客户有 100+ 个工具**，很多问题**在模型之外**。

### 2. 系统层优化（4:20 – 5:29）
- 客户关心准确率和延迟时，团队要**戴上经典分布式系统工程师的帽子**：
  - 深入分析 agent 为达成目标要做的 **API 调用**
  - **并行化调用、引入缓存层、数据库加物化视图（materialized views）**等传统系统设计手段
- **Containment（隔离/管控）**将成为越来越常听到的词：
  - 更多控制要求；企业已在做：**安全沙箱、最小权限（least privilege）、审计日志（audit logs）、监控**等。

### 3. RL 与环境（5:29 – 8:18）
- 💡 **没有可验证的奖励信号，就无法爬山（hill climb）**。
- 实践路径（最重要是**快速先有一个能跑的东西**）：
  1. 拿**现有 harness** 定制
  2. 给 agent 系统加上**良好的 OTel traces**（很多客户已在做）
  3. 用**前沿模型**基于这些 traces **机械式地**构建出 RL 环境（"pretty much mechanical now"）
- ⚠️ **关键：扰动环境（perturb）**——生产 traces 只覆盖部分分布：
  - **故意注入过期数据（stale data）、引入超时（timeouts）**，让 agent 在模拟中练习。
- **RL 环境类比**：像飞行员上真机前在**飞行模拟器**里练，有教练给奖励/评分，再据此调整。
- 环境要求：
  - **相同的 API**
  - **捕获数据分布的多样性**——💡"合成数据不是问题，**问题是捕获多样性**"
  - **强验证器（verifier）系统**：验证 agent 动作后的**系统状态**，确保**功能正确 + 满足安全约束**，然后打分
- 可以很复杂，但核心是**优化 KPI**：
  - 例：客户关心延迟或工具调用 → **设计奖励降低 thinking budget**，让工具调用足够快
  - 然后**上线生产**

### 4. 后训练技术（8:40 – 10:51）
- 输出物：**训练好的 adapters 或 weights**，同时**优化 harness**。
- 两大技术族：
  1. **模仿与蒸馏（imitation & distillation）**——标准 SFT，最小化负对数似然
     - 启发式：**已有好 traces → 先用 SFT warm-up 启动训练**
  2. **DPO**：有**成对偏好数据**时使用（有客户收集 thumbs up/down 的成对答案）
- 💡 **蒸馏效果出奇地好**，尤其是**反向 KL 蒸馏（reverse KL distillation）**：
  - ⚠️ 用闭源模型做蒸馏是**违规的**
  - 但**开源权重模型**可以当 teacher：用强开源大模型（如 Reflection 团队的 **Beam**）教**小模型（9B、4B）**做任务，甚至让它**打分（give grades）**
- **RL / 策略梯度方法**：**GRPO** 等，通过 clip 确保不发散

### 5. 实验结果（10:51 – 12:00）
- 左图：某**大型能源公司**用例，小模型（用了 **MAI 模型**）在**留出集**上泛化提升
  - ⚠️ **不是漂亮的平滑爬坡**——"这里有点艺术（art）"
  - 流程：**先 SFT（收益很好）→ RL → 自蒸馏（self-distillation，反而略降）→ DPO**
  - 💡 结论：**因用例而异要尝试各种技术；先探索（explore），有效果后再利用（exploit）**
- 右图：**决策模型（decision models）**的新例子，越来越常见（提到上个月爆火的 **JEV** 相关话题）

### 6. 模块化：拆掉单一模型（12:18 – 14:09）
- 💡 有 agentic 系统时，应**把它炸开、更模块化**——**不要一个模型干所有任务**。
- 观察：多数业务工作流/agentic 循环是**条件分支（conditionals）** → 非常适合**更便宜、更快、多模态的决策模型**。
- 案例（两周前做的客户）：
  - 原状：几乎全部用 **GPT-5.5**
  - 改造后（客户系统已 instrumented，有丰富 OTel traces）：
    - **初始路由决策** → post-train 了很小的 **LM3 模型**（⚠️ 客户不愿用中国模型——**业界因供应链风险普遍如此**）
    - **视觉决策** → 很小的视觉模型 **Muse**（带 vision encoder）；也试过小米 **MIMO 9B**（效果不错，但因是中国模型被弃）
    - **规划** → 另一个推理模型
  - 全链路：**traces → evals → RL 环境**；中间配一个**好路由器**做 **Parado 推理路由**
  - 还利用 **harness 优化**：**Jeppas、KillOp** 等**反射式优化 prompt** 的技术，再换入 trainer

### 7. 对未来的判断（14:23 – 19:16）
- **RL 环境需求巨大**：
  - 💡 "作为软件编码者，以后没人手写代码了；现有代码大概都会被重写成 **Rust 或 Go**（编译型），没人会真正看懂"
  - 💡 **未来我们会手写奖励（hand-stitch rewards）和手写环境**，让 agent 学习
  - 有工具可**逆向工程任何工具**，在模拟中做得逼真
- **GitHub 动态**：下周可能宣布 **Agentic Resource Discovery** 标准——解决"发现环境"的问题（搜索 "cyber gym" 之类）；预计 GitHub 上会有**数百万个环境**但**正确打标签**；与 **Bench Flow 团队**和 Hugging Face 的 **Finance** 合作，确保高质量环境被**验证、校验**后可被发现
- **用 coding agent 本身完成爬山**：WeShip 等技能（harness 优化、trainer 使用、环境创建）大家都会 ship
- **走向物理世界（atoms）**：
  - 💡 软件世界出现**边际效用递减**（软件像水一样充裕），"烧了这么多 token 到底有没有达成结果？"
  - 答案：**编排、协调物理世界**——机器人手臂、仪器等作为工具
  - **Physical AI + 机器人**是大事
- **瓶颈与监管**：
  - 模型更强后，**对齐（alignment）**是大瓶颈；惊讶监管还没开始，**迟早会来**
  - 会被强制要求系统**对齐目标与价值观、被 containment**：最小权限、**时限访问（time-bounded access）、零信任（zero trust）**
  - **验证**：形式化方法、物理检查等
  - CEO **Satya** 一直在推特上谈这个
- 💡 **未来不是手写代码，而是创建沙箱环境**——其中凝结我们的**判断力、品味、想要的结果**，让 agent 在上面爬山、对齐我们的价值观
- 对"绝望情绪"的回应（程序员、数学界、任何可验证领域）：
  - 引用 **Deutsch 和 Popper**：**知识无边界、物质财富无边界**
  - 保持积极、持续适应、**补充（complement）**这项强大技术
  - ⚠️ 批评现状："**token maxing 太多**"，应把技术**导向结果**（尤其是物理世界），并确保**安全可靠**

## 三、演讲 2：工业界的环境与基准（Victor，Mercor）19:24 – 40:23

### 讲者背景
- Victor，Mercor（卖数据、构建大量环境和评估）；此前在 **Sierra**；长期做对话式 agent 的构建、评估、部署。
- 近几年主要构建**目的不是训练、而是测量（measure）模型**的环境。

### 核心主题
- **环境（environment）、基准（benchmark）、AI agent 度量学（metrology，测量科学）**
- ⚠️ **核心论点：训练用环境和评估用环境"看起来像但目的不同"，混为一谈是很多麻烦的根源。**

### 1. 什么是环境（21:26 – 22:42）
- 生物学类比：**同一棵橡树**对人类是木材/阴凉，对猫头鹰是栖息处，对蚂蚁是食物/树皮洞穴。
- 💡 **环境 = 透过行动者身体看到的世界**；能感知什么、能做什么，决定了"树是什么"。
- 对 agent 同理：同一企业里，chat agent、语音 agent、后台 agent **模态、执行器、所见都不同**。
- 环境本身**只是存在**；**一旦挂上任务（task）和评分器（grader）**，它就有了目的。

### 2. 奖励 vs 测量（23:04 – 24:37）⭐核心区分
- 机制相同：**任务 + 轨迹 → 分数**。
- **作为奖励（训练）**：
  - 判断标准：**对模型的作用**——**可学习吗？有难度梯度吗？难被 hack 吗？**
  - 可以**有噪声**——没关系，因为可以**针对你的模型定制**（你要训的是自己的模型，不是别人的）
  - 💡 **只要模型变好，奖励就是好的，"just go for it"**
- **作为测量（评估）**：
  - **同一个数字不是奖励，是测量**——判断标准是**它告诉你关于模型的什么**
  - 要求：**可靠（reliable）、有效（valid）、能预测部署表现**
  - 度量学术语：**fitness to purpose（适合用途）**——⚠️ 方法**没有普遍有效性**，只对**声明的目的**有效
- **Gym vs Benchmark 类比**：
  - **Gym**：像健身选动作，**只要能让你变强，怎么都行**
  - **Benchmark**：原义是**在石头上刻痕测量**——⚠️ **刻了就是刻了，不能今天换个地方刻**
- **作业 vs 考试类比**（更形象）：
  - 两者材料相同（都是练习题），但**好老师会为学生挑作业**（已掌握就不练）
  - ⚠️ **考试不能这么干**：训练配方里**按通过率过滤、按难度重加权都完全合理**（大家还很擅长），但**对 eval 这么做就是采样违规（sampling violation）**
  - 考试只关心：**你是不是那场对的考试**（以及别作弊——benchmark 的作弊问题暂不展开）

### 3. 评估即预测：你下的是什么"赌注"（26:15 – 29:06）
- 真实设定两层：**KPI/真实部署**（超复杂）vs **单次评估**（更细粒度）
- 想要的评估本质是**预测**：部署后 agent 会怎样？有时无法直接测（新功能还没上线）
- 💡 **每个评估环境都在下注**：为什么这个环境的分数能迁移到真实世界
  - 有大量部署时通常会**核对**；⚠️ 如果一直不奏效——**真实世界不会错，通常是你的 benchmark 错了**，必须重新评估
- **"最诱人的赌注是真实感（realism）"**——⚠️ 但要小心：
  - "realism"很少被定义；**真实感常掩盖设计选择**
  - 推到极限就是**同构（isometry）**：地图=领土，那直接要真实世界就好了
- **风洞类比**：风洞**预测飞行但不像天空**；关键是**机翼形状与受力之间的关系**对——乘客、餐食、云都可以丢掉
- 💡 **问题不是"真实吗"，而是"相对什么真实（realistic with respect to what）"，以及"它是为了什么"**

### 4. 评估的五种"赌注"类型（29:06 – 30:34）
| 类型 | 赌注 | 失败模式 |
|---|---|---|
| **理论**（如 RKGI 类基准） | 基于"知识如何运作"的理论，核心知识可预测其他任务 | 理论错了就完了 |
| **模拟**（如讲者的 **TowerBench**，模拟用户-agent 交互） | 保留"风洞式"的正确关系 | 模拟不好 → **拟像（simulacrum）**：看起来像好模拟，其实不是 |
| **真实工作**（真实身份/真实 traces） | 基于人们真实做过的事 | **偏斜、过时、污染**（模型已知道） |
| **真实用户**（arena 类，复现 A/B 测试） | 真实用户反馈 | **无法回放（no replay）**、不能用来训练；用户可能不是你的用户 |
| （模型 vs agent） | —— | ⚠️ 我们评估的是 **agent 而非模型**：模型只是 agent 众多组件之一 |

### 5. 企业 agent = MLOps 问题（30:40 – 31:35）
- Sierra 经验：为客服构建复杂 agent——**本质是 MLOps 问题**，非常复杂
- ⚠️ **不是"一个小模型 + 小循环 harness"那么简单**——企业里完全不是这样（呼应 Gobind）
- 评估 agent 时：评估器**不必关心盒子里有什么**，但**盒子本身很重要**——要报告**成本、输入延迟**等

### 6. 可评分性：测量必须"可判对错"（31:46 – 34:01）⭐
- 💡 **测量必须可评分**：有明确对错，或至少有一个大家认同的结果
- TowerBench（用户模拟客服交互）要求：
  - **可靠的用户模拟器**
  - **一致的评分**——用**可验证奖励（verifiable rewards）**而非 **LM as judge**
  - **rubric 无歧义**
  - **可控性**：能确认是 agent 犯错、**不是用户模拟器犯错**（否则你测的到底是什么？）
  - 用 LM judge 时必须**校准**，确保**验证器不是过错方**
- ⚠️ 这些约束**限制了你能构建的可行任务类型**
- 现实很骨感：**大多数情况你并不知道好坏**
  - 例：TowerBench **没做**"安抚愤怒客户"这类任务——**不知道怎么模拟用户情绪模式**，很可能测不出东西
  - ⚠️ 市面上有人说有——**真的有吗？还是糟糕的模拟/全是错误？**
  - 有些任务就是不好，只能接受：💡 **可靠性界定有效性（reliability bounds validity）——不可靠就无效，没有例外**

### 7. 路灯效应（34:20 – 34:54）
- benchmark 可能比真实世界**更干净**——但这不是真实感的失败
- 💡 **路灯效应**：只能在灯下找钥匙；想要别处，就得**造更好的测量工具**（造新 benchmark 本身是另一门学问，Mercor 在做很多）

### 8. 平均不是唯一指标（35:00 – 36:22）⭐
- 真实世界要**压力测试、回归套件、必过测试（must-pass）**：
  - 例：某些"绝不该发生"的事进回归测试——⚠️ 讲者暗示在别的公司见过很多次这类事故
- ⚠️ **这不是"马虎采样"，而是测量了不同的量**：
  - **预测性评估** → 频率主张（"会以这个频率发生"）
  - **必过套件** → **符合性（conformity）**："必须符合 PRD，否则有法律风险"
  - **红队（red teaming）** → **存在性主张**：**一个反例就够了**，但要**关联成本**
- 结论：不是关于代表性，而是关于**存在且很糟**

### 9. 基准比真实世界更难也更简单（36:22 – 37:33）
- **更简单**：无歧义、模拟用户远更简单 → **应该拿高分**
- **也更难**：类似 **Zipf 分布**——大量极简单案例（退款两步搞定）+ 少量极难案例
- 建议：
  - 作为 benchmark 设计者要戴两顶帽子：**展示新能力** + **让模型在某些地方失败**
  - 💡 **必须了解自己的流量（know your traffic）**，把流量映射到 benchmark 的任务类型上，或**重新加权**，理解什么才真正重要
  - ⚠️ **最终仲裁者是部署（deployment）**

### 10. 评估是需要长期维护的产品（37:47 – 39:53）⭐
- 💡 **好的评估是你持续维护的评估**——"不能强调得更多"
- ⚠️ 训练数据可以"模型学会了就 move on"，**评估不行**——要**长期共存**，是**维护问题**：新版本、清洗、持续变好
- **要把评估当产品对待**
- 每次信任一个数字前，问自己：
  1. 我的数字/环境是**奖励还是测量**？我要哪个？
  2. 说"真实"——**相对什么真实**？
  3. 这个环境**下的赌注是什么**（预测力）？
  4. 在企业里赌注很简单：**如果内部 benchmark 涨了、做得好的 A/B 测试却失败 → benchmark 错了**（人人都经历过"以为破了案，结果不行"）
  5. **我们在测什么**：模型？模型+harness？
  6. **可评分吗**？⚠️ "你不会相信有多少次：任务很多、看起来很丰富，但因为任务根本不公平/不可评分，**整体退化成没意义**"
  7. **谁来维护它**？你要和它长期共处
- 💡 收尾：**"从来没有'普遍好'的 benchmark——好，是为了什么目的好？"** 工业界必须想清楚这一点

## 四、演讲 3：用 Miles 训练你的 agent（Tao Lin，RadixArk）40:23 – 52:40

### Miles 是什么
- **开源框架**，RadixArk 开发——**SGLang 背后的团队**（用 SGLang 做推理引擎）
- 支持多种训练后端：**Megatron、FSDP、Torch Titan**
- 支持**所有主流开源模型**；最流行的模型**day-zero 支持**（发布当天即可后训练）：**Muse Spark Open、MIMO、DPC、QM** 等
- 可从**单 GPU 扩到数百 GPU**；支持 **NVIDIA 和 AMD GPU**
- 合作方覆盖芯片公司、云、前沿实验室等全栈

### Agent RL vs 传统 RL（42:23 – 43:30）
- 传统 RL 循环：生成回答 → 算奖励 → 更新模型 → 重复
- 💡 **Agent RL 的区别：生成不再是单条回答，而是多步交互**
  - agent 决定下一步动作 → 动作发给环境 → 环境反馈 → 来回往复
  - 完整交互的聊天历史 = **轨迹（trajectory）**
  - **轨迹 + 奖励 = 一个训练样本**

### 如何把环境接到 Miles（43:36 – 45:40）
- 以 **OpenEnv** 为例：每个环境是**迷你服务器**，暴露 **reset / step** API
- 只需写一个**简短的 agent 函数**循环：
  1. reset 环境
  2. 调用模型
  3. 通过 step 采取动作
  4. 循环往复
  5. 结束后从环境拿到**奖励/分数**
- 产出：轨迹 + 奖励 → 送入训练
- 💡 **现有环境无需重写整个训练系统即可接入**
- 更复杂用例也被覆盖（不限于单 agent 循环；甚至 **harness 放在沙箱内**，更贴近真实世界）——**不同用例用不同接口，以最自然的方式接入**

### 真实训练案例：GLM 5.2（700B+ MoE）× Terminal Bench 2（45:46 – 49:35）
- 对 **700B+ 参数 MoE 模型**做后训练，任务为流行的 agentic 编程基准 **Terminal Bench 2**

**两个关键设计决策**：
1. **全异步 RL（fully async RL）**：
   - 推理和训练跑在**不同 GPU 组**上，同时进行
   - 💡 对 agentic RL **尤其重要**：不同 episode 耗时差异巨大；同步跑会让**慢 episode 让训练 GPU 空转**
2. **每个 episode 用全新沙箱（fresh sandbox per episode）**，不复用 VM：
   - 把隔离和扩缩容的复杂逻辑**交给沙箱基础设施**
   - **每层做自己最擅长的事**
   - 支持多家**云沙箱和开源沙箱**（如 agent in）

**配置**：
- **64 张 B300 GPU**：**32 张推理 + 32 张训练**
- 每训练步：**8 个任务 × 每个跑 8 次 = 64 条轨迹**
- 但**并发 128 个沙箱**——⚠️ 数字不同是为了**匹配推理与训练的速度**：让 rollout 管道保持忙碌，同时训练器有足够数据

**结果**：
- 每步约 **4–5 分钟**；**100 步后奖励从 0.44 → 0.56**——较短训练也有可测量的提升

### 奖励黑客与假阳/假阴（49:51 – 51:50）⭐
- 💡 **RL 会奖励"拿高分"的行为——如果存在捷径，模型会找到它**
- **假阳性（false positives）实例**：
  1. Terminal Bench 数据集里**自带参考答案**；放进 agent 沙箱后，agent 可能找到并**直接抄**
  2. 更隐蔽：agent **修改评分逻辑**，让 grader 报成功，实际任务没完成
- **假阴性（false negatives）**：
  - 模型**做对了**，环境却报失败——**grader bug** 或**基础设施抖动（flaky）**
- ⚠️ 以上都是**在 OpenEnv 中真实发现的问题**；已修复并**上游回 OpenEnv** 惠及社区（感谢 **Ben 和 Hugging Face 团队**审阅并帮助落地 PR）

### 核心结论
- 💡 **扩展 agentic RL 不只是 GPU 吞吐**，还包括：**灵活的环境集成、强隔离、可靠的奖励**
- "还没试过 Miles 的请试试"

## 五、演讲 4：为什么我们构建 OpenEnv Arena（Xiangyi Li，BenchFlow）52:40 – 1:07:55

### 定位与背景
- 讲者：Xiangyi Li，**BenchFlow 创始人**——"前沿环境实验室（frontier environment lab for AI agents）"
- 今年做了多个热门 benchmark：**Skills Bench、Calls Bench、Post-training Arena、Open Environment、Frontier Physics**
- 本场视角：💡 **从训练数据角度——如何为 RL 找到最好的训练数据**（这就是 OpenEnv Arena 的由来）
- 算力来自 **Nebius**，组织归功于 **Ben/Hugging Face**

### OpenEnv Arena 是什么（两件事）
1. **数据基础设施**：作为**检验任何训练数据的试验台（test bed）**
2. **数据集**：拥有**最多经过验证的环境**

### 现场调查（54:27 – 54:59）
- 几乎所有人都训过模型；很多人训过 **>10B**；**>100B** 只有 2–4 人；**>1T 无人举手**

### 文献缺口
- 过去一年大量研究"如何做 RL 环境、如何扩展训练数据"，但**测试床通常只是 9B、32B 模型**；**没有任何开放研究 >122B**
- 少数开放的是大实验室（**GLM、Cursor、DeepSeek**）的成果；**没有非实验室的公开版本**
- 此前 BenchFlow 训过 **9B、32B**；Arena 用的是 **27B** 数据；今天要讲**从 32B 到 GLM 5.3 Flash（320B）**的跨越经验

### 向人请教的经验（56:06 – 57:25）
- 💡 **数 epoch，不要数 step**：batch 16 时**至少 100 步**
- 数据公司：**check pass@8**——**没有一次能通过的路径的任务不该进训练集**
- **警惕 reward hacking**
- 必须为基座模型找到**对的 harness**：例：GLM 5.3 用 mini-suite agent vs Claude Code，**准确率差超过 14%**
- ⚠️ **在 eval 里，噪声验证器/易被 hack 也许还能忍；但在训练里，1% 的 reward hacking 就足以教会模型走捷径**

### Arena 的运作方式（评分训练数据）（57:25 – 58:34）
- 把 Arena 视为函数：**固定 eval 集**，你提供训练数据（**50–100+ 个环境**），看能否在多个领域提升模型
- 当前重点：**网络安全（cyber gym）**，扫码参赛
- 方法固定：**GRPO，至多 4 小时**；在 **40 个私有任务**上评估
- 过去两周：**8 个领域 40 个任务**；接下来两周聚焦 cyber

### 数据（58:34 – 1:00:48）⭐
- 两周收到 **35 支队伍、80+ 份提交**；**170 次训练中约 125 次不可训练**（不比基线好）
- 💡 **只有约 50 个环境真正有信号**——连参赛提交的环境都是坏的
- 宣布比赛、拿到算力后，**抓取了市面上约 90,000 个可找到的 RL 环境**：
  - 用 **GLM 5.3** 打标：**仅约 8,000 个**对 GLM 5.3 Flash 有可训练信号
  - **仅约 1,000 个真正"可教"**
  - 过滤掉 reward hacking 和假阳/假阴后，**只剩约 800 个**（**包含开源的 MIMO 任务**）
- **环境失败模式**：
  - 最常见：**任务坏了跑不起来**；**任务泄漏/答案泄漏**（如 SWE-bench 长期的大问题）
  - **pass@8 至少过一次**的要求进一步大幅削减可训练任务数

### 训练 320B 模型（GLM 5.3 Flash）的经验（1:01:03 – 1:02:30）⭐
- 从 800 个里选 **260 个任务**训了 **12 步 × 约 5 轮**：
  - ⚠️ **学习信号很不稳定**：想爬的 benchmark **不爬**，别的 benchmark 反而爬了
  - 原因：**epoch 不够**（Tao 也说：**少于 100 步别数**）
- ⚠️ **小模型任务 ≠ 大模型任务**：早期学术任务（**OpenSui、T Max**）在 32B 论文里效果好，但其中 **约 30% 教大模型"少用 token、少调工具"**（即教坏了）
  - 💡 此后只用 **MIMO 的任务**或**更好的环境配方**
- 被告知：**若 1% 的模型收益来自作弊，这个模式会在后续训练轮次中蔓延（perfuse）**

### 行业环境质量数据（1:02:38 – 1:03:41）
- **Epoch AI**：Terminal Bench 4 有 **45 个坏任务**；有报告称修好后是**饱和基准**（有争议），但显然**没达到最高的 anti-reward-hacking 标准**
- **SWE-bench Pro（Scale AI 修订版）**：**55–57% 任务存在答案泄漏**
- **MIMO RL 环境**：**48%** 的 agent 表现出**找答案而非解题**的利用模式
- 另有 **30%** 的数据（讲者不确定来源）——存疑

### 下一期 OpenEnv Arena：Cyber（1:03:51 – 1:05:09）
- 提交的 cyber 环境也将用于**训练更大的模型**
- 已做几个 **27B run**：**能很好地学会 cyber gym**，但公开 cyber 任务**噪声太大**，缺少好的可训练 cyber 环境
- 轶事：**前沿模型直接拒答**——讲者用 MCP 调 Slack 说明"Hugging Face 的 Ben 授权训练 cyber 模型以更好保护 Hugging Face"，**GPT 6.1、Opus 5.5 仍一直拒绝**；只好订阅 **GLM Z AI coding 账号用 GLM 5.3** 继续干活
  - 💡 这算某种 **RSI**；**开源模型具备 cyber 能力且不拒绝，非常重要**——"Hugging Face 事件已经证明了这一点"，"GLM 5.3 救了我的命"

### 环境检查原则清单（1:06:02 – 1:07:34）⭐
1. **可学习性（learnability）**——应有爬山信号（类似"给你 50 个样本，能否已开始爬山"）
2. **无答案泄漏**：⚠️ 例：答案藏在**git commit 历史**里；**把 verifier 隔离出去**能减少大量答案搜寻行为（不能全抓，但能抓大多数明显的）
3. **任务还能构建/运行吗**——市面上有**上千个坏任务**
4. **奖励是否真的检查了"解决了"**——**无假阳、无假阴**
5. **有稳健的 reward hacking 检查器**
- 对数据供应商的喊话：若与大型前沿实验室合作，这是必须严肃解决的问题

## 六、圆桌讨论（1:07:55 – 1:58:12）

### Q1：为什么大多数人训不出自己的 agent？小模型替代 Haiku 的摩擦在哪？（1:08:07 – 1:20:09）

**Xiangyi（数据/环境角度）**：
- 💡 **缺少好的开源环境集合**作为起步（即便 MIMO 的 7,000 个环境也有坏处，但没有它很难 fork 出一套提升 GLM 5.3 Flash 编程能力的环境）
- 后训练**配方已基本商品化**（有教程"在 Kimi K3 上后训练 Miles"），但 cookbook 往往是"在这个 benchmark 上过拟合，完事"
- **需要经过审计验证的环境集合**作为起点

**Gobind（企业角度）**：
- 客户普遍**模型疲劳**：预算被 coding agent 挤压，两年周期后大家都在问"**结果在哪？**"
- 真正重要的指标：**增收或降本**；⚠️ 除编程外**生产力提升并不大**
- 编程已找到 PMF；**所有遗留代码会被重写**（Rust/Go，没人看得懂），**未来任何软件变更都经由 agent**
- 💡 **编程之后 PMF 最好的是 Ops**（SRE ops、data ops）——他的爬山实验多在此
- 关于 Haiku 类小模型：**价值最低**（开源模型可放更便宜的推理上），大家正在**把架构"JEV 化"**——ops 不是聊天，而是**受限选项集上的决策盒，需要分布概率**
- **大胆押注：去年假期是编程，今年假期是"系统模块化 + 引入决策模型"**

**Victor（MLOps 角度）**：
- 好数据**仍然昂贵、复杂、需要维护**（Mercor 存在的原因）
- ⚠️ **公司不再会做 MLOps 了**：
  - 大模型时代大家以为"堆个大模型解决一切、不用维护"
  - 回到自训小模型 = **回到统计模型思维**：要**测量一切、金丝雀发布**……
  - 现有栈不是这么搭的；部署模型的人**没有 ML 训练背景**，以为"用户提 bug 报告"就行——⚠️ **ML 没有 bug 报告**："80% 准确率就是它的正常表现，没有 bug"
  - **DevOps/CI-CD ≠ MLOps**
- 预测：**会有大量 MLOps 工具出现**，行业要经历从 DevOps 到 MLOps 的**迁移**（为了不被单一供应商锁定、拥有自己的数据）

**主持人补充**：后训练框架每周都在出新（Hugging Face、Prime Intellect、Thinking Machines 等），确实在变容易。

**Gobind 补充**：⚠️ 用"trajectories"这类术语会**丢失听众**——要**产品化**并给出价值主张（持续学习 / 提准确率 / 降延迟）。

**主持人**：2022 年 ChatGPT 发布时，**大批 MLE 转行去写 prompt**，放下权重、拾起新技能——**这是教育问题，需要补回来**。

**Tao（基础设施角度）**：
- 全 IO 栈摩擦巨大：**搞 GPU → 找数据集 → 评估数据集是否适用 → 找环境和 RL 框架 → 全部串起来**
- 行业趋势：**各层在互相靠近**，端到端体验的产品越来越多；**教育内容增多**（Hugging Face 团队），人们开始知道需要什么
- Gobind 补充：**开源已成为默认**，重复造轮子在减少（"我们直接集成你"），框架非常开放，可拼装各层

### Q2：后训练像"管理组织架构图"而非管理数据集——团队怎么搭？（1:20:22 – 1:29:08）

**Victor**：这就是**做产品**，需要专精分工：
- **懂客户/用例的人**：深度理解要构建什么，**手把手（hand holding）教学**——MLE 不会干这个，需要**真正懂得如何向客户学习并解释**的过渡角色
- **评估与训练是竞争关系**：⚠️ **必须有分离关注点**（像 QC 与生产），训练团队总想训、想推高
- **数据**要有人专门操心
- 结论：**任何规模下都需要 3–5 个角色**，和任何产品栈一样，不可能一人全包

**Gobind**：
- 看到企业按 **pod + FDE（前向部署工程师）** 组织——**这将是工作演化方式**：
  - 有**领域专家**知道工具访问埋在哪、现在怎么干活
  - ⚠️ **不要自动化现有流程——那是拟物化（skeuomorphic）的错误做法**
  - 要先做**设计思维**：重新思考产出物（artifacts）、约束与控制，理解问题空间 → 任务 → 评估
  - 案例：**销售赋能流程从几周缩到几分钟**，中间有大量"手缝"工作（如**降低某工具调用的 thinking budget** 的奖励设计）
- 💡 自己不再手写代码，但要**升级技能以补充这个新世界**；**"不明确、未验证"反而是好事**，需要与 MLE、传统 IT 安全、领域专家大量协调

**Tao**：
- RadixArk 是 AI infra 公司，工程师多来自 infra 背景；**不专门招训练/数据背景的人**
- 💡 **infra 工程师会成长为某个领域的专家**；模型越来越强，很多东西**可学**；范围会扩大（甚至要做 GTM）
- 只要**热爱学习、能快速采纳新范式**，**同质化技能组合的团队也可以**；但某些领域短期内无法成为专家 → **仍需专家**

**Xiangyi（数据角度的两个瓶颈）**：
1. **人类注意力瓶颈**：Frontier Physics 与 **70+ 物理学家**合作；外部评估伙伴做 AI 审计返回电子表格（多为假阳），审核很耗时；**SME 的意见散落在流程中，未被持续学习利用**——没有"持续学习改进自动 judge"的机制；她的想法是**把一组奖励 rubric 蒸馏出来，保证与专家结论一致**，但**不易扩展**
2. **沟通瓶颈**：agent 执行留 trace，reviewer 审阅也产生 trace——能否有**比 JSONL/仪表盘更好的沟通方式**，让 reviewer 把对任务的知识/期望形状传给数据？
- 个人实践：**每周用 150B tokens**；技巧：**让 agent 起一个"master agent"管理其余 sub-agent 并统一回答我的问题**——主线程不被打扰，**生产力大增**；她认为 SME↔agent↔你 的沟通也会有类似方式

**Victor 补充**：要正视**情境的巨大多样性**：
- Sierra（造 agent 是主业，给很多人造、上生产）vs Mercor（造数据）vs 只有**一个 agent** 的公司——完全不同
- 任何经济活动的核心问题：**何时外部化、何时内部化**
- 有时有很棒的数据/训练 infra，**一个人**就够；没有就得外部化或堆人——**本质是经济问题**

### Q3：agent 时代缺一套方法论（主持人：ML 的"标注-训练-测试-评估-修订"循环）（1:32:00 – 1:34:46）

**Victor**：
- 💡 **环境本身是不断演化的对象**，含义在变
- 10 年前 NLP 有**设计模式**：NER"无聊但有效"——社区围绕"我们知道怎么做的事"建立算法和对象
- 现在**不知道什么难、什么易，尚未进入稳态** → **模式还没发明出来**
- 预言：几年后再讨论，会有"这类问题已知、那类很难"的分类与模式
- **开源社区**可以把分散在各处、人们已在用的创造性用法**集中起来**（"人们定义用法 → 我们集中化 → 前进"）

**Gobind 补充**：
- 产品正从"为人类开发者"转向 **AX（agent experience）/ agent-first**：**ship skills、agent 友好的 CLI**；企业重视 **MCP**；物理世界有新标准（Anthropic 的 **MH** 类），让一切**可被 agent 消费**
- 会自动化很多构成工作的任务，但**新任务在涌现**，要快速适应和补充

**Q：为人类 vs 为 agent 的产品有何不同？**
- 人类产品要**确保人理解**（文档、开发者受众）——**文档团队正经历危机**：人们直接"copy markdown"就完事
- 💡 Gobind 观点：**人类侧会有更多视频**；每个 PR **没人读描述**——**coding agent 的"工作证明"可能应该是视频**，解释它如何满足验收标准
- 因为**我们都在当"agent 和 sub-agent 的经理的经理"**——就像 4 年前 VP 不会关心单个 PR

**Victor**：
- 核心是 **agentivity / 所有权感**：你会觉得这真的属于你、被你控制吗？
- 现状："**让你的 Claude 去 review 我 Devin 的 PR**"
- 预测：**所有权会重新定义**——你拥有的、法律上负责的（出事会被开除）就要控制；有些东西会**让出控制**（不在意评审的是人还是 agent）
- 技术栈会调整为适配 agent，然后**重新明确"所有权"含义**，产品要给你**正确的控制杆（levers）**，让你不觉得被异化——**但仍要负责，只是"负责什么"被重新定义**

### 观众 Q&A

#### Q1：为"不后训练"辩护（1:38:33 – 1:42:16）
**论点**：开源环境会被前沿实验室爬山；**每单位智能的成本持续下降**；数据供应商洪流会让一切更容易；**后训练不是静态的**（客户行为两月一变，agent 间交互也在变）——那我后训练的价值在哪，不如用下一代 Haiku？
- **Gobind**：**你会震惊于还有多少客户在用 GPT-4.0**（我们劝他们它要被弃用）；💡 **客户只关心自己的用例，能跑就不碰**，甚至求我们**别再弃用模型**——这也是他们想做后训练、拥有**自己的多层服务**的原因
- **Tao**：**成本**——客服这类高频场景，不可能永远用 Claude Opus 5.5；**小模型+针对用例后训练**可提供相当或更好体验，**大幅降本**
- **Victor**：
  - 先问**你要达成什么**；环境在变，**后训练模型不一定变**，而前沿模型**持续演化**
  - 接口切换很容易；但⚠️ 人们**严重低估采样真实世界的复杂度**——**B2B 里每家业务都比上一家更怪**
  - 除非系统能把这些信息在**推理时**摄入、理解你的本地参数——但那会很贵、很耗 token
  - 💡 最终是**经典权衡**：塞进 prompt + 上下文管理 vs 后训练——**要延迟就后训练，要成本就后训练**；**没人在乎是不是后训练，只在乎能不能work、你有没有钱**
- **Xiangyi 补充**：终极目标应是**后训练出与 Opus 5 能力相当的开源模型**——从一个尖峰（RSI/设计/cyber）开始，证明可行再推向所有尖峰；"他们领先几代，但我认为可能"

#### Q2：GenAI 大会上没人提后训练——企业被供应商叙事淹没，后训练怎么破圈？（1:42:57 – 1:45:43）
- **Gobind**：
  - 💡 **ISV（垂直解决方案厂商）才是对后训练感兴趣的一方**——因为**前沿模型是最大成本项**，会从他们开始
  - 企业侧、尤其现在，重点在**给模型去风险**：**零信任、把 agent 当内部威胁（insider risk）**——给最小权限、零信任等
  - 惯性是真的，但**做垂直方案、解决业务问题的厂商有充分动机降本 → 他们会先做后训练**

#### Q3：持续学习、自动合成数据、自动造 benchmark 离我们多远？（1:45:49 – 1:54:37）
- **Xiangyi**：
  - 提到 **Opus 相关博客**观点："**人类水平的 eval 已经结束**"
  - 基准演进：SWE-bench（几小时任务）→ Terminal Bench 4 / **Program Bench**（一周级；**给 SQLite 文档+二进制、不给源码**，重建二进制；Opus 模型卡大量引用）——💡 **具备超人类智能特征的基准**（团队要花数月）
  - Terminal Bench 已被 Sonnet 5.5 解出 **~89%**——⚠️ **任务无歧义时几乎全 one-shot**，说明**基准不够超人类**
  - 造超人类任务两条路：**超级可验证**（如 Navy/Stoke 类）或**把大量人类数据可靠压缩成一个目标/任务**（她正在思考）
  - 预测：**未来三个月**会有公司十年数据被这样打包用于 eval 和训练数据——**要更大胆**
- **Tao**：
  - **持续学习是过载术语**；最理想是模型**基于新用户交互持续更新权重**——目前没人做
  - 原因**不是技术，而是商业/法律合规**
  - 现状：**静态模型服务所有用户**，但开发过程中用最新模型能力让模型更好、让开发更快
- **Victor**：
  - 先问**什么情境**；客服场景**不需要超级智能**
  - 💡 **两个世界**：关心超级智能的人 vs 其他人（"造发动机"→"造车"→"上月球"是不同问题；**让车更好不需要登月发动机**，但需要大量其他东西）
  - 面向普通企业（让 Excel 更好）vs AGI——**完全不同**
- **Gobind（持续学习具体）**：
  - 见过的有效做法：**用户/任务的图表示（graph representation）** + **"做梦"（dreaming）/压缩（compaction）功能**——属于 **harness 层优化**，但是好的开始
  - **Apple Intelligence 的 adapters** 是**多 LoRA 服务**的愿景（Cursor、GitHub Copilot 也做过），但苹果**没能落地**，因为非常复杂
  - 大家可从**图数据库 + 每晚"做梦"整合**起步，其余仍很难
  - ⚠️ **用户模拟很差**：模型不擅长"像某个具体人那样行动"——**我们个体大多"不知道"，模型大多"什么都知道"，这是巨大鸿沟**；研究显示给全历史也不比给人口统计学信息更好 → 合成训练数据会**显得粗糙**
  - 💡 有些问题（编程、数学）像**国际象棋——没有人**；但很多问题是**人很重（people heavy）**的，而**我们不太会模拟人**
  - **对"智能"的理解有偏**：我们以为智能=解复杂任务，但**对话系统里的轮流节奏（sub-millisecond 级）模型做得很差**——"学一步棋比移动棋子容易"（经典说法）
  - 建议：**关注真实世界、人们真正在乎的事、看这些数据**

#### Q4（最后一个）：在绝对前沿做实验时，你伸手拿什么？（1:54:46 – 1:58:12）
- **Xiangyi**：
  - 训练/RSI 类工作 **agent 还不太行**（连 Opus 5.5 也不行）：例：让它**慢慢堆 Slurm 作业**（GPU 调度器，让 GPU 不空闲）**几乎从不照做**；问"何时该期待训练信号"，它说 **12 步**——⚠️ 而大公司/前沿实验室的人说**至少 100 步**
  - 所以会**问人**：**截图终端/T3 code/Claude 发到 Slack 问"这合理吗"**
  - 另一例（Frontier Physics）：发现某任务 **agent 始终胜过人类**，想找更多这类模式——物理没有大量定义良好的开放问题，于是**列问题清单、给 agent 各 40 小时、起递归 sub-agent 解题**，约 **13 个任务**（认为可能超人类）
  - 给人类审阅者的交付：**生成论文**（人读的东西）+ **3B1B 风格视频**方便审阅
  - ⚠️ 但**视频作为人际沟通方式存疑**——她自己看的视频有点冗余；做 slides 要发**50 条 prompt** 才成型——**仍是难题**
  - 💡 因此回到**持续学习**：**每周 450B tokens（全公司）不能白费**，应进入某种模型权重（闭源不行就开源）——但**"更新数据库模型就变聪明"是不对的**

## 七、跨演讲的关键主题总结 ⭐

| 主题 | 要点 |
|---|---|
| **奖励 vs 测量** | 同一个数字，训练时是奖励（可噪声、可定制），评估时是测量（须可靠、有效、可预测）——**混淆是万恶之源**（Victor） |
| **环境质量危机** | 90,000 个环境→约 800 个可用；上千坏任务；答案泄漏普遍（SWE-bench Pro 55–57%） |
| **Reward hacking** | 1% 作弊会蔓延；必须隔离 verifier、查 git 历史泄漏、防假阳/假阴 |
| **可验证奖励 > LM judge** | rubric 无歧义、可控、校准；**可靠性界定有效性** |
| **模块化 > 单一模型** | 路由/视觉/规划分模型；决策模型更便宜更快；多 LoRA 服务 |
| **系统 > 模型** | 企业 agent 是分布式系统 + MLOps 问题；延迟靠缓存/并行/物化视图 |
| **基础设施** | 全异步 RL、每 episode 新沙箱、推理训练分卡、匹配沙箱并发与训练速度 |
| **评估是产品** | 要长期维护、映射真实流量、平均之外还有必过套件/红队/存在性主张 |
| **人的因素** | pod + FDE、领域专家 + MLE + 安全 + 数据；MLOps 技能回归；持续学习受限于合规 |
| **未来** | 物理 AI、agent-first 产品（AX）、Agentic Resource Discovery、视频作为工作证明、监管与对齐 |
