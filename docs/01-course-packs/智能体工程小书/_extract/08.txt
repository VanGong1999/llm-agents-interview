The catch is independence. Samples from
one model share its blind spots: a mis-
leading passage tends to mislead every
sample, and perfectly correlated voters
gain nothing. Voting helps with idiosyn-
cratic errors (slips) and not systematic
ones (misunderstanding the task). Di-
verse voters (different prompts, evidence
or models) are usually worth more than
extra samples. Voting also needs compa-
rable answers.
Diversity must be arranged; it does not
arise by itself. Asked for a joke about cof-
fee, several current models return the
same joke, and asked for a metaphor in-
volving time, most say a river [86]. The
same conformity appears among agents.
A group of agents each asked to build
something impressive mostly chose ray
tracers or compilers, and agents shar-
ing a repository chose the same branch
name [79]. Assigning distinct perspec-
tives, evidence or models buys more

8.4 Subagents are tools
Now let agents delegate. The simplest
and most useful form needs no new
machinery: a subagent is a tool whose
implementation runs another agent loop.
def subagent_tool(model, tools, max_steps=15):
readonly = [t for t in tools
if t.effect == "read"]
def investigate(question: str) -> str:
res = run(question, model, readonly,
max_steps=max_steps,
system="Investigate; report "
"findings with file:line. "
"Do not modify anything.")
return (res.answer or
f"(helper stopped: {res.status})")
return Tool(
"investigate",
"Delegate a self-contained question to a "
"read-only helper with a fresh context. "
"Returns a short report.",
{"question": {"type": "string"}},
investigate)
Calling investigate starts a fresh loop
with only the question and the read-only
tools; its short report becomes the par-
ent’s observation (Figure 8.2).

8.5 When multiple agents help,
and when they hurt
Multi-agent designs differ along three
axes: orchestration, how the agents are
run; communication, how they exchange
information; and coordination, how they
123


===== PAGE 132 =====

divide work and avoid treading on each
other [79]. Four orchestration patterns
cover most systems (Figure 8.3). Inde-
pendent agents attempt the task sepa-
rately and an aggregator picks or merges;
it is parallelization with agents as the
units. Centralized orchestration has one
agent decompose, delegate and inte-
grate, which is orchestrator–workers
with a persistent manager. A decentral-
ized swarm has no manager: agents claim
work from shared state (a to-do list, a
ledger of tasks, a set of failing tests) and
talk to one another. Hybrid systems keep
a manager and let workers communicate
directly. Cost and coordination overhead
rise in that order.

8.6 Contracts between agents
The task description is the child’s en-
tire world: state the objective, output
format, boundaries and budget, and ask
for evidence (file and line, source ids).
Treat the report as an observation, to be
verified before it drives an irreversible
action. Protocols such as Agent2Agent
(A2A) standardize cross-organization
delegation [1]; contracts and verification
remain the designer’s job.
Two forms of delegation are worth distin-
guishing (Table 8.1). The subagent above

Summary
• Workflows fix the structure (chaining,
routing, parallelization, orchestrator–
workers, evaluator–optimizer); agents
decide it at run time. They compose.
• Majority voting helps when errors are
independent; correlated errors erode
the gain, so diversify voters.
• A subagent is a tool that runs another
loop: it isolates context, allows spe-
cialization, and can be restricted by
131


===== PAGE 140 =====

construction.
• Multi-agent systems differ in orches-
tration (independent, centralized,
decentralized, hybrid), communica-
tion and coordination, and trade many
more tokens for parallel breadth. A
strong single agent is the baseline
to beat. Parallelize reading; serialize
writing.
• Delegate with an explicit contract
and verify what comes back. Choose
agent-as-tool for bounded subtasks
and handoff when a specialist should
own the interaction; coordinate
through a task ledger and isolated
worktrees.
