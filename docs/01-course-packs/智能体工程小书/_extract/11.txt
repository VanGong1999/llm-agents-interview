11.2 A design review checklist
The checklist below follows the agent
map. It is meant for reviewing a design
before building it and for diagnosing a
system that underperforms.
Architecture (Ch. 1).
Is an agent neces-
sary, or would a workflow do? Is success
verifiable? What does an error cost, and
can it be undone?
Model (Ch. 2).
Which model, at which
effort level, and how was it chosen? Is
the provider behind an adapter? Are
stop reasons other than “done” handled?
Loop (Ch. 3).
What are the budgets
(steps, tokens, time, money)? Do all
tool failures become observations? Is
“answered” distinguished from “suc-
ceeded”?

===== PAGE 180 =====

Tools (Ch. 4).
Is each tool necessary
and distinct? Do outputs serve the next
decision, and are they bounded? Are
errors instructive? Is each tool’s effect
class declared?
Context (Ch. 5).
What does the model
see at step 1 and at step 50? Is the pre-
fix stable for caching? How is growth
controlled, and is information removal
recoverable?
Retrieval and memory (Ch. 6).
How
does the agent find what it needs? Is
retrieval quality measured separately?
What is written to memory, with what
provenance, and how is it corrected?
Control (Ch. 7).
What verifies
progress? Is “done” checkable? Can
work survive a context reset or crash?
Are external effects idempotent or
reconciled?

Composition (Ch. 8).
If several agents
are used, what does each see, and could
one agent with better context do as well
at lower cost?
Safety (Ch. 9).
Which legs of the lethal
trifecta are present? What does the gate
allow without asking? What bounds the
effects of executed code? Are approvals
specific to the exact action?
Evaluation (Ch. 10).
Is there a suite,
built from real tasks and failures, with
outcome-based graders? Does it include
adversarial cases? Are results reported
with uncertainty, cost and the metric that
matches use?
11.3 Operating an agent over time
Its most important component is sup-
plied by someone else, on their schedule.
173


===== PAGE 182 =====

Version the whole configuration:
model and settings, prompt, tools,
context and gate policies, harness code.
Change one element at a time, evaluate
every change, and tag traces with the
version.
Roll out gradually,
watching cost, la-
tency, steps and tool errors, which often
move before success rates.
Learn from incidents:
keep the trace,
find the component that allowed the
failure, fix it, add the case to the suite.
Reverting changes future behavior, not
effects already caused.
Revisit the harness when models
change.
Scaffolding for a weaker
model can hold back a stronger one;
each upgrade is a chance to remove
structure and let the suite judge [14].
Harnesses should get simpler over time,

not only larger. The relation runs both
ways. The strongest models do best with
the simplest harness, while a cheaper or
open-weight model (one whose weights
are published) may need the structure a
strong one no longer does, and a cheaper
model in a better harness can be the
economical choice [79]. Which pairing
wins is a measurement, not a slogan.
11.4 Where to go next
In practice you may use an off-the-shelf
harness: provider agent SDKs with built-
in tools, context management, permis-
sions and subagents; graph-based work-
flow frameworks with checkpointing;
managed services that run the loop and
sandbox. The agent map applies to all:
ask what each does for every component,
and where it lets you plug in. Table 11.2
shows how differently three open-source
coding harnesses answer those questions,
with the same model inside [79].
