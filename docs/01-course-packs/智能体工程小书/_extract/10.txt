A task is thus a package of three parts:

A fourth part, a reference solution, is not

10.3 Graders
Code graders
check outcomes pro-
grammatically (hidden tests, database
rows, tolerances, unmodified files):
cheap, fast, objective. Their weakness
is coverage, so include checks against
known shortcuts (Exercise 1). A verifier
is a classifier of outcomes and has both
155


===== PAGE 164 =====

error types. False negatives, a correct so-
lution the checks reject, are as damaging
as false positives, and both change as
models change: newer models find new
shortcuts and also new valid solutions
that an old verifier never anticipated.
Model graders
apply a rubric to what
code cannot judge, such as faithfulness
or completeness [87]. They favor longer
answers, first-listed options and out-
puts like their own, and drift with their
model. Calibrate them against hand-
graded samples; specific criteria (“cites
a source for every number”) agree with
humans far better than holistic scores. A
model grader is itself a system to evaluate:
build a small benchmark of hand-graded
cases for it and track its agreement over
time.
Human graders
are the reference and
the source of calibration data; use them

"""P(some of k trials pass); c of n passed."""

10.5 Building a suite, and reading
benchmarks
Start with twenty to fifty real tasks, es-
pecially observed failures, each with an
unambiguous criterion [13]. Keep capa-
bility tasks (progress) and regression tasks
(protection); include adversarial cases
scored for success and safety; hold some
tasks out to avoid overfitting.
Accuracy is one dimension of quality.
Consistency asks whether repeated runs
reach the same outcome, which pass𝑘
measures; robustness asks how a small, ir-
relevant perturbation of the task changes
the outcome; predictability asks whether
failures are legible and recoverable. A
leaderboard that scored agents on all of
these found no relation between accu-
racy rank and reliability rank [35]. The
most capable agent is not the most de-
pendable one, so a suite should include
perturbed variants of its tasks and report
160


===== PAGE 169 =====

consistency beside accuracy.
Tasks are software and have bugs. Before
a suite is trusted, run every task through
quality checks (Figure 10.5) [79]: static
checks for misconfiguration; a model
judge that maps each requirement in the
instruction to a check in the verifier; the
oracle solution, which must pass; frontier
agents (the most capable current mod-
els), whose traces show whether the task
is hard for the intended reason or be-
cause a package is broken; and an agent
told to cheat, which finds the shortcuts
the grader missed. Then version tasks. A
fix to the verifier means regrading stored
trials without rerunning agents; a fix to
the reference solution needs no rerun
at all; any change the agent can see, to
the instruction, environment or tools,
invalidates past trials. Keep every trial’s
trace, not only its score: most of what a
suite teaches is in the traces, and a pub-
lished number without its trials cannot

10.6 Observability
After deployment, the instrument is the
trace: a tree of spans for the run, each
model call (tokens, latency, stop reason)
and each tool call (arguments, result,
duration). OpenTelemetry’s generative-
AI conventions let one toolchain collect
traces from any framework [54]. Traces
yield the operating metrics: success prox-
ies, cost, latency and steps per task, tool
errors, approvals.
Dashboards summarize; transcripts ex-
plain. Read failures and a sample of
successes regularly: no aggregate will
tell you the agent has started deleting
failing tests. Every surprising transcript
is a candidate for the suite.
Summary
• Evaluations are the agent’s test suite:
run them on every change to tools,
context, policy, prompt or model.
