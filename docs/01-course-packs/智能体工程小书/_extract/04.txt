Where we are. We design 𝒜, the set of actions the model
may propose, and the observations those actions return.
Tools are the agent’s only way to affect the world and its
main way to learn about it.
4.1 Why tools
Models are strong at text, code and math-
ematics and weak in three recurring situ-
ations (Table 4.1). The first is exact, long
or verifiable computation: accuracy on
multi-digit multiplication falls steadily

each case the remedy is the same. The
model writes a request as text, and an

4.2 Tools as an interface for a
model
A tool has five parts, all visible in the
Tool type of miniagent:

# implementation

# read|write|execute|
# external
@property
def schema(self) -> dict:
return {"type": "object",
"properties": self.params,

===== PAGE 61 =====

"required": list(self.params),
"additionalProperties": False}
The name, description and schema are read
by the model; they are a user interface
whose user is a language model. The
implementation is ordinary code. The ef-
fect class is read by the harness: it says
whether the tool only reads, writes local
state, executes code, or reaches outside
the system, and the gate of Chapter 9 uses
it to decide what needs permission.
The SWE-agent authors called this layer
the agent–computer interface and showed
that, with the model fixed, its design
changes success rates substantially [80]:
a viewer showing a bounded window of
numbered lines beat raw cat; summa-
rized search beat dumped matches; an
editor that rejects syntax-breaking edits
beat one that does not. None made the
model smarter; all made observations
more informative and errors easier to
detect.

Return what the model needs for its
next decision.

Keep the toolset small and distinct.
Every definition occupies context on
every call, and overlapping tools force
the model to guess. Minimal harnesses
whose default tools are read, write, edit
and a shell hold their own on terminal
benchmarks against far richer ones [79].

4.5 Code as the action language
An alternative to many small tools is
to let the model write a program: the
action space becomes a programming
59


===== PAGE 68 =====

language, and the harness runs the script
in a sandbox, an execution environment
that confines what the program can touch
(Chapter 9). Executable Python actions
have been shown to beat JSON tool calls
on multi-tool tasks [70], because they
compose: a loop over twenty files is one
action, not twenty round trips through
the context.
Tools from MCP servers (next section)
can likewise be presented as a code li-
brary, keeping intermediate results out
of the context [6]. The price: model-
written code needs real isolation (Chap-
ter 9) and is harder to permission call by
call.

4.8 Skills: procedures loaded on
demand
Some knowledge is neither a tool nor a
fact but a procedure: how this team for-
mats release notes, how to fill a partic-
ular form, which checks to run before
merging. An agent skill packages such
a procedure as a folder containing a
SKILL.md file (a short name and de-
scription, then instructions) and optional
scripts or reference files [10, 2]. Only the
name and description sit in the context
permanently. When a task matches, the
65


===== PAGE 74 =====

agent reads the full instructions, and from
there any referenced files or scripts. This
progressive disclosure keeps the standing
cost of a large library of skills to a few
dozen tokens each. Skills thus sit at the
boundary between this chapter and the
next: they extend what the agent can do,
and they do so by managing what it sees.
Summary
• Tools cover what the weights cannot:
exact computation, knowledge out-
side training, and interfaces that are
not language.
• A tool is a name, description and
schema (read by the model), an
implementation, and an effect class
(read by the harness).
• Good tools return what the next de-
cision needs, make errors instructive,
bound their output, are few and dis-
tinct, and leave room to call nothing.
