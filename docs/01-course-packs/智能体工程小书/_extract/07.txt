7.3 Planning
Capable models plan implicitly, which
suﬀices for short tasks. For longer ones
an explicit plan, an artifact the agent main-
tains, decomposes the task into verifiable
milestones, keeps the objective visible
at the end of the context, and can be
reviewed by a human before an hour is
spent.
A to-do tool (steps with statuses, up-
dated as work proceeds and shown to
the user) is simple and effective. Plans
must be revisable; a fixed plan is a work-
flow. Plan-then-execute, fixing the plan
before any tool output, is less adaptive
107

but has a security benefit (Chapter 9).
A plan can also be compiled. ReWOO has
the model write the whole sequence of
tool calls before any is executed, with
placeholders (“the result of step 2”)
connecting outputs to inputs; a worker
runs the steps with no further model
calls, and one final call composes the an-
swer from the evidence [77]. LLMCom-
piler goes further: the plan is a graph of
steps and their dependencies (a directed
acyclic graph), independent steps run
in parallel, and a failed check triggers
replanning [40] (Figure 7.2). Both used
fewer tokens than ReAct at equal or bet-
ter accuracy, because the model does not
re-read the growing history at every step.
Code as the action language (Chapter 4)
subsumes the idea, since a program is
a plan with variables, and current mod-
els issue several independent tool calls
in one reply for the same reason. What
survives is the principle: when steps are

7.4 Stopping
The agent should stop on the checkable
definition of done, or stop and report
when blocked; saying that “I could not
complete this because…” is acceptable
reduces fabricated workarounds.

An initializing session sets up the environment and a
structured list of goals. Each later session starts with a
fresh context, reads the progress notes, the goal list and
the version-control log, makes one increment of verified

The ingredients transfer. A goal list, items
marked passing only after verification,
prevents premature victory. Progress notes
are a deliberate compaction by the outgo-
ing agent. Version control logs changes and
allows reverts. A startup routine verifies
the inherited state. One goal per session
keeps contexts focused. All are memory
written by the agent for its successor.

7.6 Durable state and side effects
Machinery fails too: processes crash,
calls time out. Production harnesses per-
sist an append-only event log of every
reply, call and observation, from which
a run can be inspected and resumed
(the companion’s jsonl_logger is the
simplest version).
Resumption is easy for reads and subtle
for writes: if a request was sent but the
response never recorded, did the effect
happen (Figure 7.4)?

Summary
• Fight compounding error with ver-
ification (raise 𝑑), decomposition
(shorten the effective horizon) and
durable state (keep progress).
• Prefer strong verifiers: deterministic
checks and tests over model judges,
and model judges over unaided self-
critique. Make “done” checkable.
• Explicit plans help on long tasks:
they decompose, keep the goal visi-
ble, and can be reviewed; they must
be revisable. Independent steps can
be planned together and run concur-
rently.
• Stop on a checkable criterion or when
blocked; set budgets from data.
• Multi-session work needs a goal list,
progress notes, version control and a
startup check. Side effects need pend-
ing records and idempotency or rec-
