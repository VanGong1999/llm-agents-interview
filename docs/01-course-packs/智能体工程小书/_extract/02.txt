Because each request begins with the previous request as
an exact prefix, providers can cache that prefix and bill it
at a small fraction of the normal rate; only the new suﬀix
(dark) is processed at full price. Any change early in the
context invalidates the cache from that point on.
Prompt caching reduces this cost substan-
tially (Figure 2.1). If the request at step
𝑡begins with exactly the bytes of the
request at step 𝑡−1, the provider can
reuse its internal computation for that
prefix and charge a fraction of the input

price for it. Caching rewards a discipline
we will meet again in Chapter 5: keep
the beginning of the context stable and
make the history append-only. Inserting
a timestamp into the system prompt, or
reordering tool definitions between calls,
silently forfeits the cache [48].
The mechanism explains the rule. A
model processes a request in two phases:
prefill, which reads the whole input in
one parallel pass, and decode, which gen-
erates one token at a time. During prefill
the model computes, for every input to-
ken, internal vectors (the keys and values
of its attention layers) that every later to-
ken consults; the serving system keeps
them as the KV cache so that decoding
need not recompute them. Each vector
depends on the token’s position and on
everything before it. A request that re-
peats an earlier request’s prefix byte for
byte can reuse the stored vectors; a single
token inserted near the front changes

the positions of everything after it and
forces recomputation from that point [79].
Latency follows the same split: the time
to first token is dominated by prefill and
grows with the context, while the time
per output token is roughly constant. An
agent pays both on every step, which is a
second reason, besides price, to keep the
context small.
2.3 Tool calling: a typed contract
A model that can only emit prose cannot
reliably operate a computer: the harness
would have to guess, from a sentence
like “let me look at the stats file,” which
function to call with which argument.
Current models are trained to emit tool
calls: structured requests that name a tool
from a list supplied in the request and
give arguments matching that tool’s JSON
Schema [62]. The harness executes the
call and returns the result, tagged with
the same identifier, in the next request.

A ToolCall carries an identifier, a tool
name and an argument dictionary. A
Reply is what one model call returns:
text for the user, zero or more tool calls,
the provider’s raw content (needed
later), and a stop reason. The Model
protocol says that anything with a
method next(system, tools,
messages) returning a Reply can serve
as the policy. Everything else in the
harness depends only on these types.

Syntax, schema, meaning
A tool call can be malformed (invalid
JSON), violate the schema (a missing ar-
gument, a wrong type), or be well-formed
and still wrong (editing the wrong line).
Providers can often constrain decoding
to the schema, removing the first two lev-
els; the harness should validate anyway,
since not every mode guarantees it. The
third level is caught only by the environ-
ment and the evaluator.
2.4 Reasoning before acting
Writing out intermediate steps before
the answer (chain-of-thought reasoning)
27


===== PAGE 36 =====

improves accuracy on multi-step prob-
lems [72], and majority voting over sev-
eral sampled chains improves it fur-
ther [68]. Current reasoning models build
this in, generating hidden or summa-
rized thinking before each output, in-
cluding between tool calls. An effort set-
ting trades tokens and latency for ac-
curacy; the right level is an empirical
question.
Two consequences for the harness. Think-
ing content must usually be passed
back unchanged in later requests (some
providers sign it and reject edited histo-
ries), which is why Reply keeps the raw
content. And stated reasoning is not a
reliable audit log: judge an agent by its
recorded actions and their effects, not its
narration.

The adapter does three things worth
copying into any implementation. It
sends tool definitions as name, descrip-
tion and JSON Schema, which is the com-
mon denominator across providers. It re-
turns the assistant’s content verbatim on
the next request, which preserves think-
ing blocks and any provider-specific
structure. And it groups consecutive tool
results into a single user turn, which is
how this API expects the results of paral-
lel tool calls to be returned.

2.6 Choosing a model
Model choice trades capability, cost and
latency, and benchmarks only roughly
predict your task. Three rules of thumb:
• Measure cost per completed task,
not per token. A cheaper model that
needs twice as many steps, or fails a
third of the time, is not cheaper.
• Start with the most capable model
that is affordable, then move down.
It establishes what is achievable; only
then is it clear whether a smaller
model’s failures are the model’s or the
harness’s.
31

• Different roles can use different
models. A helper agent that skims
files on the main agent’s behalf (a
subagent, Chapter 8) or a model that
checks formatting (a grader, Chap-
ter 10) can often use a smaller, faster
model than the main loop.
• The harness is part of the measure-
ment. The same model scores differ-
ently under different harnesses on
the same benchmark, and the gap
is often as large as the gap between
models [79, 67]. A number quoted for
a model is a number for that model
inside someone’s harness.
Record the exact model identifier and
effort level with every experiment; an
alias that silently moves to a new version
is a change to 𝜋.

Summary
• A model call samples tokens from a
learned conditional distribution. Out-
puts are random; the model knows
only its weights and its context.
• APIs are stateless, so each step
resends the history and total input
grows quadratically in the number of
steps. Prompt caching makes a stable,
append-only prefix cheap.
• Tool calling is a typed contract:
the model proposes (id, name,
args); the harness validates, exe-
cutes and returns the result under the
same id.
• An adapter isolates provider details.
A scripted model tests the harness; it
does not measure the model.
