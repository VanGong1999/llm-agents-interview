6.5 From passages to grounded
answers
Take a second example: “Does our API
support batch requests, and with what
limits?” over a documentation folder.
Keep provenance with every retrieved
item (stable identifier, version, loca-
tion); have the model cite identifiers
and the harness check each was actually
retrieved; and check support claim by
claim, which needs a human or model
grader (Chapter 10). The check is not op-
tional. When generative search engines
were audited, users rated their answers
fluent and useful, yet only about three
citations in four supported the sentence
they were attached to [46]. A model gen-
erates the citation the way it generates
everything else.
When sources disagree, say so with dates
and scope. “I could not find” is more
honest than “there is no.”

6.6 The write path: memory
Memory is what the agent writes for
its future self: preferences (“prefers
pytest”), project facts (“integration
tests need DB_URL”), lessons (“CI uses
Python 3.10”). Three questions decide
whether it helps.
What and when.
Write what would oth-
erwise be rediscovered or asked again,
when it is learned. Do not duplicate what
the store already records. The future
value of a memory is unknown when
it is written (a user’s joke that meetings
before ten are not binding “unless there
are pastries” may or may not be a prefer-
ence), which is why the raw episodic log
is kept beside the curated memories: a
poor curation decision can be revisited.
Who writes.
Three mechanisms are
common. The agent writes through a
memory tool when it judges something
97


===== PAGE 106 =====

worth keeping, as in MemGPT, where
the model also manages which facts
stay pinned in its context [55]. A back-
ground process reads the conversation
and adds, updates or deletes memories
on its own schedule, keeping bookkeep-
ing out of the agent’s context [79]. Or
an event triggers the write: the context
nearing its limit, a session ending. The
model-driven form is more flexible; the
workflow form is more predictable and
easier to audit.
How to read it back.
Small memories
load into every context; larger ones are
searched like any corpus or exposed
through a memory tool [55]. Similar-
ity alone is a weak signal for memories.
Generative Agents scored each memory
as a weighted sum of recency, importance
(a model’s rating when the memory was
written) and relevance to the query, and
found reflection, writing higher-level sum-

How to keep it true.
Store source and

can run while the agent is idle: sleep-time
compute reasons over stored memories
between sessions, merging five separate
statements about a user’s color prefer-

trieval later finds the conclusion already
drawn [44]. Treat memory as untrusted
input: a memory written while reading a
malicious document can carry its instruc-
tions into every later session (memory
poisoning, Chapter 9).
The weights are a memory too.
The
model’s weights hold facts and proce-
dures of their own. For facts that are
few and change, the context wins: fine-

Summary
• The store 𝑀holds what does not fit
in the window. Retrieval is the read
path; memory is the write path.
• Working, episodic, semantic and pro-
cedural memory differ in contents,
update policy and staleness.
• Retrieval can be a fixed pipeline
(RAG) or a tool in the loop (agentic
retrieval). Use the pipeline for simple
lookups and the tool when the agent
must follow leads.
• Lexical search finds exact terms,

• Evaluate retrieval separately with
