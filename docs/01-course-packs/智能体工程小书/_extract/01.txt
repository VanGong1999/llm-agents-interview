An agent is a program in which a
model repeatedly chooses actions, the
program executes them in an envi-
ronment, and the observations inform
subsequent choices, until the model
declares the task done or a limit is
reached.
The definition excludes a single model
call (no loop) and a fixed pipeline of
calls (the model does not choose the next
step). It specializes the classical notion
of an agent as something that perceives
and acts upon its environment [60] to a
language model acting through text and
structured data [73, 71].

1.5 When an agent is worth it
Each model decision costs tokens and
seconds and introduces a chance of error.
10


===== PAGE 19 =====

Four questions decide whether moving
right on the spectrum is worth it [4, 52]:
1. Is the path unpredictable? If you can
write the sequence of steps down in
advance, write it as code or as a work-
flow.
2. Can the outcome be verified? Agents
improve dramatically when the en-
vironment says whether an action
worked: tests pass, a query returns
rows, a page loads.
3. Are errors cheap and recoverable?
An agent that edits a scratch copy of a
repository can be wrong many times
on the way to being right. An agent
that sends email cannot.
4. Is the value worth the cost and la-
tency? An agent may use tens or hun-
dreds of model calls where a work-
flow uses three.
11


===== PAGE 20 =====

Software engineering scores well on all
four, which is a large part of why coding
agents were the first agents to become
broadly useful [32, 80]. The boundary
between workflow and agent moves with
the models. Agentless fixes GitHub is-
sues with a fixed three-stage pipeline
(localize the file, draft candidate patches,
run tests) and for a time matched agents
that chose their own steps, at a fraction
of the cost [75]; SWE-agent, which opens
files and runs commands as it sees fit,
is the agent form of the same task [80].
When the path is predictable enough,
the workflow wins on cost and debugga-
bility; when it is not, the agent wins on
coverage. Our running example inherits
these properties: the path is unknown,
the test suite verifies, edits in a working
copy are reversible, and a correct fix is
worth a few cents.

Summary
• An agent is a loop: build context, let
the model choose an action, check it,
execute it, observe, repeat.
• The model is a fixed stochastic policy
𝜋; agent engineering designs the har-
ness around it: actions 𝒜, context 𝜙,
store 𝑀, gate 𝑔, loop structure, and
evaluation 𝑅.
• Choose the least autonomous architec-
ture that solves the task. Agents pay
off when the path is unpredictable,
outcomes are verifiable, errors are re-
coverable, and the value justifies the
cost.
